# Agent 笔记：远程开发——传输链与远端工作区服务

状态：提议中

## 先说结论

Lithe 要支持“完整的远程开发”：项目放在 SSH 主机、Docker 容器（包括 Dev Container）或远程 Mac 上，本地只负责界面，文件读写、终端、构建、运行、调试、LSP、Git 和 Agent 都在远端执行。做法是把远端能力全部放进一个独立的远端服务 `lithe-remote-server`。SSH、`docker exec` 这些连接方式只叫传输链（transport chain，从本机到工作区所在位置的一串跳转），它们只负责“把服务启动起来、接通标准输入输出”，不实现任何功能。Linux 和 macOS 远端的差异放在服务内部的平台适配器里，并且以能力描述（capabilities，服务在握手时报告的主机事实）的形式告诉客户端。客户端只看能力，不写“如果远端是 Mac 就怎样”的分支。

这不是插件能完成的事情，它是宿主的核心能力。插件以后只需要声明“我的后端跑在本地界面侧，还是跑在远端工作区侧”。目前已经落地的是 Rust 后端：协议、远端服务（文件、目录遍历、文件监听、进程、终端、登录环境、隧道和端口）、断线后不中断的常驻会话、传输链、远端安装和客户端 API。产品界面暂不接入，Windows 暂不考虑。

## 问题

现在所有能力都默认“项目就在本机”：

- macOS 应用里有一百多处直接用 `FileManager.default`，Rust Core 里也有大量 `std::fs` 和 `Command::new`。它们读写的都是本机路径，没有一层能替换成“远端实现”的接口。
- 唯一的远端能力是数据库的 SSH 隧道（`rust/lithe-db-sidecar` 里的 `open_ssh_tunnel`），它只服务数据库，不能复用来打开远程项目。
- Windows 端的 WSL 工作区是另一套独立实现，没有和“远程”共用抽象。

如果不先定下边界，后面每个功能都会各自加一个“远程分支”：文件树用一种 SSH 命令，终端用另一种，构建再拼一条 `ssh host 'mvn …'`。这样做的结果是 Docker 和远程 Mac 都要各写一遍，路径和引号的处理散落在各处，连接断开、进程清理、凭据这些问题也没有一个统一的负责者。

## 提案

### 整体分层

```text
本地 Lithe（界面、设置、钥匙串、本地历史）
        │  工作区后端接口（文件 / 进程 / 终端 / 监听 / 搜索 / 端口 / 插件后端）
        ├── 本地实现（现在的代码，迁移到接口之后）
        └── 远程实现 ── lithe-remote-protocol ── 传输链 ── lithe-remote-server
                                                   ├─ 本机子进程（测试用）
                                                   ├─ ssh 主机
                                                   ├─ docker/podman exec 容器
                                                   └─ ssh 主机 → 主机上的容器
```

三个 Rust crate，职责分开：

| crate | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `rust/lithe-remote-protocol` | 帧格式、消息信封、方法名、参数类型、错误码 | 不做任何 I/O 决策 |
| `rust/lithe-remote-server` | 远端的全部能力和 Linux/macOS 适配器 | 不知道自己是被 SSH 还是 Docker 启动的 |
| `rust/lithe-remote-client` | 传输链拼命令、远端安装校验、会话收发 | 不实现文件或进程语义 |

### 传输链只做“执行一条命令”

每一跳只需要做到“在下一跳上执行命令，并接通标准输入输出”。

- SSH 跳转使用系统的 OpenSSH（`ssh -T -e none -- <目标> <命令>`）。用户的 `~/.ssh/config`、ProxyJump、硬件密钥、1Password 这类 agent 都自然生效，Lithe 不解析也不复制这些配置。
- 容器跳转使用 `docker exec -i` 或 `podman exec -i`。OrbStack、Colima 等兼容 Docker 的工具只需要换可执行文件路径。
- 链可以叠加：`[ssh devbox, docker api]` 就是“先 SSH 到 devbox，再进入它上面的 api 容器”，不需要在 devbox 上额外装任何东西。
- 空链就是本机子进程。CI 用它跑完整个远程栈，不需要 SSH 环境。

SSH 会把远端命令交给远端用户的登录 shell 当作一个字符串解析，而 sh、bash、zsh、fish、csh 的转义规则互不相同（例如 fish 在单引号里也会处理 `\`）。所以穿过 SSH 的参数一律用单引号包起来，并且**直接拒绝**任何 shell 在单引号里还会特殊处理的字符：`'`、`\`、`!` 和控制字符。这些参数都由 Lithe 自己生成（安装路径、容器名），拒绝比转义更可靠。

唯一的例外是内层 SSH 跳转生成的命令行。链里有两个 SSH 跳转时（例如 `[ssh 跳板机, ssh 开发机]`），内层生成的命令本身带单引号，外层还要再引用一次。这时把单引号写成 `'"'"'`：先结束单引号，在双引号里放一个单引号，再重新开始单引号。上面五种 shell 读回来都是原样的。因为内层命令只由通过了校验的参数拼成，不含 `\`、`!` 和控制字符，这个例外不会放宽对原始参数的限制。

链的身份字符串（例如 `ssh:devbox/docker:api`）用作最近项目、按主机存储的键，它不包含保活参数这类不改变目标的设置。

### 远端服务的启动和安装

1. **探测**：通过链执行 `sh -c`，在标记行之间输出 `uname -s`、`uname -m` 和 `$HOME`。远端 shell 启动文件打印的欢迎信息会被忽略。
2. **选择构建产物**：架构以远端报告为准。Apple 芯片的 Mac 上跑 amd64 镜像时，需要的是 x86_64 的服务。Linux 产物使用 musl 静态链接，所以同一个二进制能跑在各种发行版和精简镜像上。
3. **校验已安装版本**：执行 `<路径> --identity`，服务对自己的可执行文件计算 SHA-256 并输出。只有哈希和本地产物完全一致时才复用。这样不依赖远端有没有 `sha256sum` 或 `shasum`。
4. **上传**：总是由本地通过同一条链上传，不让远端自己下载，因为很多服务器和容器不能访问外网。上传先写到临时文件名，再改名为正式文件，配合 `umask 077`，同一台机器上的其他用户无法替换它。
5. **安装位置**：默认是 `$HOME/.lithe-server/bin/<版本>-<哈希前 16 位>/lithe-remote-server`，不同版本并存，互不覆盖。

本地这一侧，服务产物属于应用的打包资源，运行时只读取，不写入 app bundle。实现打包时还要遵守已发布程序包的运行时只读规则，并登记到 worktree 资源清单。

### 远端服务必须保持轻量

远端服务会在第一次连接时上传到每一台主机、每一个容器，很多时候链路很慢，容器里的资源也有限。所以它必须是一个 Rust 编译的原生二进制：不依赖远端的 glibc、Node.js、Python 或任何运行时，复制过去就能运行。作为对比，基于 Node.js 的远程服务通常有几十 MB，还要在远端解压一整套运行时。

实测（stripped release，opt-level `s` + LTO）：

| 目标 | 只有文件和进程时 | 全部后端能力 | 链接方式 |
| --- | --- | --- | --- |
| `x86_64-unknown-linux-musl` | 约 760 KiB | 约 1.15 MiB | 静态（static-pie） |
| `aarch64-unknown-linux-musl` | 约 680 KiB | 约 1.0 MiB | 静态 |
| `aarch64-apple-darwin` | 约 610 KiB | — | 只依赖系统库和系统框架 |

空闲时常驻内存约 2 MB。依赖仍然只有 `libc`、`serde`、`serde_json`、`base64`、`sha2`。inotify 和 FSEvents 都直接调用系统接口，没有引入 `notify` 这类封装 crate。

用 `panic = "abort"` 构建还能再省约 9%（约 110 KiB），但没有采用。原因是会话里任何一个线程 panic 都会让整个常驻进程退出，连带用户所有的终端和构建一起结束。现在的 unwind 模式下，出问题的只是那一个线程，锁中毒（poisoned lock，持锁线程 panic 后锁被标记）也会被恢复。

Linux 静态版用 Rust 自带的 `rust-lld` 链接，在 macOS 和 Linux 上都能直接构建，不需要 Docker、zig 或额外的交叉工具链。M1 打包时直接沿用这个做法。

开发者需要遵守的动作：

- `scripts/verify-remote-workspace.sh --static` 会构建两个 Linux 静态版，超过 1.5 MiB 就失败。要提高上限，必须先在本 Note 里写明实测原因。
- 给服务加依赖前先量体积。异步运行时（如 tokio）、HTTP 库、正则库这类大依赖，只有在实测证明标准库线程做不到时才考虑。
- 功能留在客户端能做的，就不要放进服务，例如解析项目结构、计算 diff、渲染。服务只提供主机必须提供的能力：文件、进程、终端、监听、端口。
- 不要在服务里内嵌语言服务器、JDK 这类大资源。它们按插件单独上传，按需安装。

### 协议的几条硬规则

- **流前标记（preamble）**：服务先写一行 `LITHE-REMOTE-PROTOCOL/1`，客户端丢弃它之前的所有字节，最多 64 KiB。这样登录横幅不会破坏协议流；如果远端根本没有服务，被丢弃的输出（例如 `not found`）会作为诊断信息返回给用户。
- **帧格式**：4 字节大端长度加 UTF-8 JSON，单帧不超过 16 MiB。单次文件传输不超过 8 MiB，更大的文件分段读取。
- **路径**：协议里的路径是远端主机上的绝对路径。这一层是文件系统和进程的适配器，工具链、终端和调试器都需要真实的主机路径；以工作区为根的相对标识在这一层之上构造。
- **错误**：错误码稳定（例如 `NOT_FOUND`、`CONFLICT`、`DIRECTORY_NOT_EMPTY`），客户端按错误码分支。`message` 只给人看，OS 错误号放在 `details` 里。
- **兼容**：不兼容的修改才提升协议版本号。新增方法通过 `features` 列表声明，客户端先查列表再调用。
- **只走标准输入输出**：服务不监听任何 TCP 端口，所以共享主机上的其他用户连不进来。端口转发以后也走这条流。

### 文件和进程的语义

- **保存是原子的**：内容先写到同一目录下的临时文件，再改名覆盖目标，读者和崩溃都不会看到写了一半的文件。写入会穿过符号链接，链接本身保留。代价是文件换了 inode，硬链接会断开，这和其他编辑器的安全写入（safe write）模式一样。
- **防止覆盖别人的修改**：写入时可以带上上次读到的大小和修改时间。不一致就返回 `CONFLICT`，不带版本时默认不覆盖已存在的文件。只是“创建”的写入（不带版本、也不允许覆盖）用不覆盖的改名提交，所以两个请求同时创建同一个文件时只有一个成功，另一个返回 `ALREADY_EXISTS`；提交前的存在性检查挡不住这种并发。
- **临时文件不泄露内容**：覆盖已有文件时，临时文件创建时的权限不超过原文件（umask 只会再去掉权限），写完再恢复原文件的权限。否则保存一个只有自己能读（`0600`）的文件时，其他用户可以趁临时文件还是 `0644` 打开它，之后再收紧权限也收不回已经打开的文件描述符。
- **不覆盖的重命名**：Linux 用 `renameat2(RENAME_NOREPLACE)`，macOS 用 `renamex_np(RENAME_EXCL)`，文件系统不支持时才退回“先检查再改名”。
- **按会话结束进程**：每个子进程都通过 `setsid` 成为新会话的首进程。结束进程时，信号发给这个会话里的所有进程，包括 shell 作业控制（job control）另外建出来的进程组。这样 Maven、Gradle 这类构建工具的 worker 不会残留；dash 不会像 bash 那样把挂断信号转发给后台作业，所以这一步必须由服务来做。`process.exit`、`terminal.exit` 只表示首进程退出；会话里还有成员（例如后台启动的守护进程）时，服务继续持有这个会话，`process.kill`、关闭终端和会话结束时的清理仍然能结束它们，`server.state` 用 `leaderExited` 标出这种进程。会话里没有任何成员后才删除记录，这时再 kill 返回 `UNKNOWN_RESOURCE`。POSIX 不会在进程组或会话还存在时复用这个编号，所以向保留的编号发信号不会误伤其他进程。
- **输出顺序**：输出分块作为事件发送，退出事件一定排在该进程的所有输出之后。孙进程如果继承了管道、一直不关，最多再等 500 毫秒，之后的输出会被丢弃。
- **背压**：发送队列有上限，客户端读得慢时，服务就停止读取子进程的输出，内存不会无限增长。
- **会话结束时的清理**：`--stdio` 会话在连接断开时结束；常驻会话在客户端调用 `server.shutdown`、或空闲超时后结束。结束时，服务先向所有进程和终端发送 `SIGTERM` 或 `SIGHUP`，2 秒后对仍有成员的发送 `SIGKILL`；判断是否结束看的是会话里是否还有进程，而不是首进程是否退出。之后服务最多再等 5 秒，让进行中的请求完成再退出，否则被中断的写入会在用户文件旁边留下临时文件。
- **客户端请求超时**：客户端由一个单独的写线程负责发送，请求只是把帧放进有上限的队列。对端停止读取时只会卡住写线程，每个请求仍然在自己的超时时间结束，也不会挡住后面的请求；超时时还没发出的帧直接丢弃。

### 平台适配器（Linux / macOS）

所有平台差异都放在 `rust/lithe-remote-server/src/platform/` 里，并通过能力描述告诉客户端：

| 差异 | Linux | macOS | 客户端看到的能力 |
| --- | --- | --- | --- |
| 服务被强杀后的子进程 | `PR_SET_PDEATHSIG`，内核负责杀掉进程组长 | 没有对应机制，只能在服务正常退出时清理 | `process.orphanProtection` |
| 文件名是否区分大小写 | 用“换大小写再查同一个 inode”来探测 | `pathconf(_PC_CASE_SENSITIVE)`，失败时用同样的探测 | `fs.volumeInfo.caseSensitive`（按卷） |
| 不覆盖的重命名 | `renameat2` | `renamex_np` | 行为一致，不暴露 |
| 账户信息 | 先读环境变量，再查 passwd | 同左 | `userName`、`homeDirectory`、`defaultShell` |
| 文件监听 | inotify，逐个目录注册 | FSEvents，一个流监听整棵树 | `watch.backend`、`watch.directoryLimit` |
| 会话里的进程 | 读 `/proc/<pid>/stat` | `proc_listallpids` 加 `getsid` | 行为一致，不暴露 |
| 正在监听的端口 | 读 `/proc/net/tcp{,6}`（容器里就是容器自己的网络） | 系统自带的 `lsof` | `ports.listening` |
| Unix socket 对端的用户 | `SO_PEERCRED` | `getpeereid` | 行为一致，不暴露 |

`PR_SET_PDEATHSIG` 有一个容易踩的坑：它跟随**创建子进程的那个线程**，而不是整个进程。线程一退出，子进程就会被杀。连接线程和工作线程都会来来去去，所以服务里所有子进程都交给一个专门的、和会话同生命周期的创建线程（`spawner.rs`）来创建。

FSEvents 的另一个坑：同一个文件的标志位是累积的。一个在监听期间新建的文件，之后每次保存都还会带着“已创建”标志。macOS 适配器会记住已经报告过“新建”的路径，之后的事件按“修改”报告。

inotify 的坑：目录是逐个注册的，新建目录要在收到创建事件后再注册，而注册之前已经写进去的文件不会产生事件。所以新目录注册时，会把里面已有的内容补报为“新建”。到达 `fs.inotify.max_user_watches` 上限时，发送 `watch.error`（`LIMIT_REACHED`），已注册的部分继续工作。

现在就要为远程 Mac 预留、但第一步还没实现的部分：

- 通过 SSH 访问 `~/Documents`、`~/Desktop` 受 TCC（macOS 的隐私权限系统）限制。需要识别出这类错误，并提示用户在“远程登录”里开启完全磁盘访问。
- SSH 会话里钥匙串通常是锁着的，`git` 的 `osxkeychain` 会失败。后续由凭据回传解决。
- 服务被 `SIGKILL` 时的孤儿进程，需要一个基于 kqueue 的守护者。

### 会话和连接分开：断线不丢终端和构建

进程、终端、文件监听这些状态都挂在会话（`session.rs`）上，不挂在连接上。

- 传输链实际执行的是 `lithe-remote-server --connect <key>`。它只是一个代理：连上 `<key>` 对应的常驻进程（daemon），常驻进程不存在就先启动一个，然后在标准输入输出和 Unix socket 之间转发字节。
- SSH 断开时，被结束的只有这个代理。常驻进程通过 `setsid` 脱离了 SSH 会话，收不到挂断信号，终端和构建会继续运行。
- **事件按序号确认，不按“写进 socket”算送达**：每个事件带递增的 `seq`。服务端保留客户端还没确认（`server.ack`，客户端每收到 256 个事件确认一次）的事件，最多 8 MiB。只算“写进 socket”是不够的：连接断开时，事件可能还在发送队列里或内核缓冲区里，这些都会丢。第一版就是这样丢事件的，代码审查时发现。
- **先订阅、再续传**：握手之后服务端不会马上发事件，要等客户端调用 `server.resume`。重连的客户端先用 `server.state` 找回仍在运行的终端和进程，订阅好，再用上一次连接最后收到的 `seq` 调用 `resume`。这之后的事件按顺序各到达一次，而且进入对应的订阅，不会落进通用通道。第一版在握手响应之后立即重放，重连后接上的终端就收不到断开期间的输出。保留的事件超出上限时，`resume` 返回 `truncated`，客户端据此重新读取状态。
- 一个会话同一时间只有一个客户端，新连接会顶替旧连接。网络切换后，旧连接常常半死不活、还没被发现，顶替能让重连立刻生效。
- 连接结束时，常驻进程必须关掉这个连接 socket 的**所有**描述符，包括为“顶替”保留的那一份。只调用 `shutdown` 不够：在 BSD/macOS 上，对端半关闭之后 `shutdown` 会返回 `ENOTCONN`，什么都不做。开发时就出过这个问题：代理一直收不到结束信号，每次断开都会在远端留下一个卡住的代理进程。现在由 `the_proxy_exits_by_itself_when_its_client_disconnects` 测试防止回归。
- 隧道和目录遍历属于打开它们的连接，连接断开就结束。本地的 socket 已经不在了，它们留着没有意义。
- **关闭期间不可达**：常驻进程收到 `server.shutdown` 后，先删除 socket 再回复，之后才去结束进程（最长约 13 秒）。紧接着重连的客户端会启动一个新的常驻进程，它会等旧进程释放锁，而不是直接退出。第一版会连到正在关闭的旧会话，或者新常驻进程拿不到锁就静默退出，用户看到的都是连接失败。
- 没有客户端的会话会在空闲超时（客户端在握手时指定，默认 10 分钟，最多 24 小时）后结束，避免被遗忘的会话一直占着共享主机。
- 安全：socket、锁文件和日志都放在只有用户自己能访问的目录里，常驻进程还会校验对端的用户 id。socket 路径有约 104 字节的长度限制，macOS 的临时目录本身就很长，所以超长时退回到 `/tmp/lithe-server-<uid>/`，同样要求是私有目录。
- 并发启动：两个代理同时发现没有常驻进程时，会各启动一个。锁文件（`flock`）决定由谁负责，另一个直接退出。
- socket 名字里带服务版本号。客户端升级后会启动新的常驻进程，不会连到旧版本；旧的那个空闲超时后自己结束。

### 资源 id 由客户端分配

进程、终端、监听、隧道、遍历的 id 都由客户端指定，在会话内唯一。这样做有两个原因：

1. 客户端可以在发请求之前先订阅这个 id 的事件（`RemoteSession::subscribe`），最早的几条输出不会因为请求结果还没返回而被漏掉。
2. 重连后 id 继续有效。握手结果里的 `nextResourceId` 让重启后的客户端接着编号，不会和仍在运行的资源冲突。

所有事件都叫 `<family>.<name>`，并带 `<family>Id`。客户端的读线程据此把事件分发给对应的订阅；没有订阅的事件进入通用通道。

### 终端、登录环境和端口

- **终端**：用伪终端（PTY）运行，被启动的程序成为新会话的首进程，并把这个终端设为控制终端，和 SSH 登录时完全一样。所以作业控制、`Ctrl-C`、窗口大小变化（内核会发 `SIGWINCH`）都符合用户习惯。默认程序是用户的登录 shell，按 POSIX 惯例在 `argv[0]` 前加 `-`，sh、bash、zsh、fish、csh 都认。关闭终端相当于关掉终端窗口：向它的整个会话发 `SIGHUP`，2 秒后还在的发 `SIGKILL`。
- **登录环境**：经 SSH 或 `docker exec` 执行的命令，拿到的环境往往很少，nvm、SDKMAN、Homebrew 加进 `PATH` 的路径都不在里面。服务会用用户自己的 shell 以交互式登录 shell 启动一次，让它运行 `lithe-remote-server --print-environment`，读取它最终得到的环境，并在会话内缓存。用服务自己的二进制输出环境，可以避开 GNU 和 BSD `env` 的参数差异；每次尝试最多等 10 秒，profile 卡住（例如启动 tmux）也不会挂住服务；交互式失败就退回非交互登录 shell，再失败就用服务自己的环境，并在 `diagnostics` 里说明原因。`process.spawn` 指定 `environment: login` 就会用这个环境作为基础。
- **复制**：`fs.copy` 拒绝把文件复制到它自己身上（同一路径、经过符号链接的任一方向、或者是硬链接），也拒绝在解析链接之后把目录复制进它自己。覆盖写入会在读取源文件之前先截断目标，第一版因此会把源文件清空。socket、FIFO 和设备文件从不复制：作为复制对象本身时返回 `UNSUPPORTED`，在目录树里时跳过并计数，因为打开 FIFO 读取可能永远阻塞。
- **端口**：隧道把远端的 TCP 端口或 Unix socket（Docker、数据库的 socket）接到协议流里。客户端的 `PortForward` 在本地监听，每个连接开一条隧道，所以浏览器访问 `127.0.0.1:<本地端口>` 就能到达只监听在远端回环地址上的服务。本地客户端发完请求后半关闭时（HTTP/1.0、`nc -N`），转发用 `tunnel.shutdownWrite`：先把排队的数据写完，再只关闭写入端，远端的响应照常返回；`tunnel.close` 只用于中止。`ports.listening` 列出远端正在监听的端口，为以后的自动转发做准备。

### SSH 连接配置界面（M2 参考）

M2 接入“打开远程文件夹”时，SSH 连接的配置界面参考用户提供的一个现成 SSH 客户端的连接表单：名称、颜色、主机、端口、用户名、认证方式（密码、私钥、SSH Agent、无认证、自动按顺序尝试）、私钥路径或私钥内容、私钥口令、sudo 凭据、2FA 自动应答，以及收在“显示高级选项”后面的只读、SSH 超时、SSH 保活、环境变量、远程命令等。字段落到核心时按下面的原则处理，具体界面另写 Note：

- **能直接映射到现有跳转的**：主机、用户名对应 `SshHop.destination`，端口对应 `port`，私钥路径、超时、保活对应 `-o IdentityFile=`、`ConnectTimeout`、`ServerAliveInterval` 这类 `options`。只填了一个 `~/.ssh/config` 里的别名时，其余字段留空，交给系统 OpenSSH。
- **需要把交互回传到界面的**：密码、私钥口令、2FA 验证码都是 OpenSSH 在连接时提出的问题，应通过 `SSH_ASKPASS` 回传到 Lithe 弹窗（和 M3 Git 凭据共用一个 askpass 入口），不要把密码拼进命令行或环境变量。是否以及怎样保存到钥匙串，另行决定。
- **私钥内容**：粘贴的私钥不能写进 app bundle 或工作区。保存位置、生命周期和权限要在界面 Note 里单独说明，并优先只支持私钥路径和 SSH Agent。
- **与远程工作区无关的**：sudo 白名单、终端远程命令、自动应答脚本属于终端类产品的功能，不进第一版远程开发；名称、颜色只属于界面。只读开关是客户端策略，由工作区后端拒绝写操作，不需要服务配合。
- 表单的说明文字按设置界面的现有约定收进 ⓘ，不平铺在每个字段下面。

### 正确做法

- 远端需要一个新能力（例如文件监听）时，在协议里加方法，在服务里实现，在 `features` 里声明；Linux 和 macOS 的差异写在 `platform/`。
- 客户端需要区分平台行为时，读能力描述。例如比较路径时看 `caseSensitive`，不看 `os`。
- 新增一种连接方式（例如 Kubernetes `kubectl exec`）时，只加一种跳转，不碰服务。

### 不要这样做

- 不要在功能代码里拼 `ssh host 'mvn package'`。所有远端执行都走 `process.spawn`。
- 不要为了“远程 Mac”在客户端写 `if os == macos`。缺少的事实应该补进能力描述。
- 不要让服务监听 TCP 端口，也不要把服务装到其他用户可写的目录。
- 不要在 SSH 跳转后面传入用户提供的任意字符串（例如带 `'` 的路径）。把它放进协议请求里，不要放在命令行里。

## 考虑过的备选方案

### 把远程文件系统挂载到本地（SSHFS / SFTP）

最吸引人的地方是现有代码几乎不用改，把远程目录当成本地目录用就行。不采用的原因是：LSP 索引、全文搜索、Maven/Gradle 构建都要大量读小文件，走网络会慢到不可用；而且构建和运行会发生在本地，而不是项目所在的机器上，在 Docker 和异构架构下结果甚至是错的。

### 远端跑整个 IDE，本地只显示画面（JetBrains Gateway 模式）

最吸引人的地方是远端和本地行为天然一致。不采用的原因是：Lithe 的界面是原生 SwiftUI/AppKit，没法拆成远端渲染、本地显示；远端也不一定有图形环境。

### 内置 SSH 库（如 russh），不依赖系统 ssh

最吸引人的地方是可以完全控制连接复用和认证流程，Windows 上也不受 OpenSSH 版本限制。不采用的原因是：用户的 SSH 配置、ProxyJump、硬件密钥、各种 agent 和公司的 Kerberos/证书方案都要重新实现，“无缝兼容”反而做不到；系统 OpenSSH 是成熟的上游工具，按仓库规则应该优先复用。将来确实需要时，可以把它作为另一种跳转加入，不影响服务和协议。

### 让远端自己下载服务

最吸引人的地方是本地不用上传几 MB 的文件。不采用的原因是：大量开发机和容器不能访问外网，而且远端下载需要 `curl` 或 `wget`、证书链和代理配置，失败面更大。本地上传对所有链都成立。

### 每个功能各自发 SSH 命令，不做远端服务

最吸引人的地方是不用维护远端二进制。不采用的原因是：每次操作都要新建 SSH 会话，延迟很高；进程清理、输出顺序、原子写入都没法保证；Docker 和 Mac 也要各写一份。

### 服务用 tokio 异步运行时

最吸引人的地方是 PTY、隧道这类大量并发 I/O 写起来更顺。没有采用的原因是：加上终端和隧道之后，标准库线程加有界通道依然够用，每个终端或隧道只多两三个线程；musl 静态产物更小，背压和顺序也更好推理。只有在实测出线程数成为瓶颈（例如同时转发成百上千个连接）时才重新评估，协议本身不受影响。

### 资源 id 由服务分配

最吸引人的地方是客户端不用管 id 冲突。没有采用的原因是：客户端只有在请求返回之后才知道 id，而这时进程的第一批输出可能已经到了，只能先缓存所有“未认领”的事件；重连后，重启过的客户端也没法和仍在运行的资源对上号。由客户端分配 id，再配合 `nextResourceId` 和 `RESOURCE_ID_IN_USE`，这两个问题都没有了。

### 用 `notify` crate 做文件监听

最吸引人的地方是成熟、跨平台。没有采用的原因是：它会带来一串依赖（FSEvents 绑定、crossbeam 等），而服务需要的只是“递归监听 + 排除目录 + 合并批次”这一小部分；更关键的是，FSEvents 的累积标志和 inotify 新目录补报这两个语义问题，无论用不用它都要自己处理。直接调用系统接口，代码量相近，体积更小，行为完全可控。

### 断线后靠客户端重新执行，而不是常驻会话

最吸引人的地方是服务可以保持无状态。没有采用的原因是：构建、测试、长时间运行的服务、终端里的交互程序都无法“重新执行”而不丢状态；Wi-Fi 切换或笔记本合盖是远程开发里最常见的情况，用户期望回来时一切还在。

## 验收标准

- `cargo test -p lithe-remote-protocol -p lithe-remote-client -p lithe-remote-server` 在 macOS 和 Linux 上通过。端到端测试经本机传输启动真实的服务二进制，按功能分成几个测试文件：
  - 代码审查发现的问题都配了回归测试，并通过“临时撤掉修复、确认测试失败”验证过：复制到自身、半关闭请求的响应、断线后不丢不重的续传、空会话及时清理。常驻进程关闭期间重连的那个测试，在修复之前就失败过。
  - `tests/server.rs`：握手和能力描述、未握手前的请求和协议版本不匹配、原子写入和冲突检测、并发创建同一文件只有一个成功、断开时正在进行的写入完成且不留临时文件、对端停止读取时请求按时超时、分段读取大文件、穿过符号链接写入、目录操作的错误码、复制时保留链接和权限并拒绝复制到自身内部、复制文件到它自己（含链接和硬链接）被拒绝且文件完好、复制时跳过特殊文件、登录横幅被忽略、服务缺失时返回诊断信息、上传一次之后复用已校验的二进制。
  - `tests/processes.rs`：输出先于退出事件、标准输入转发、整个会话的进程一起结束、首进程退出后 kill 和断线清理仍能结束会话成员、正在使用的 id 不能复用、`--stdio` 会话断开后子进程被清理、登录环境包含 profile 导出的变量。
  - `tests/terminals.rs`：命令运行在控制终端上、调整窗口大小后程序看到的尺寸跟着变、关闭终端会挂断 shell 和它的后台作业。
  - `tests/watch_and_walk.rs`：新建、修改、删除都能报告；一次建出的整棵目录树完整报告，新目录也会被继续监听；排除的目录不报告；监听的根目录被删除时监听结束；遍历按名字顺序、不跟随链接、排除目录、限制条数。
  - `tests/tunnels.rs`：通过隧道访问 TCP 端口和 Unix socket、连接已关闭的端口返回稳定的错误码、本地端口转发的完整链路、半关闭的请求仍能收到响应、能列出本地监听的端口。
  - 单元测试：覆盖受限文件时临时文件不放宽权限（`fs.rs`），多个 SSH 跳转嵌套时参数原样到达 sh、bash、zsh、csh、fish（`transport.rs`，本机装了的都会测）。
  - `tests/persistence.rs`：断线期间进程继续运行且输出被重放、断线后续传时每个事件恰好到达一次、重连后先订阅再续传能接上终端并收到断开期间的输出、旧常驻进程关闭期间重连会得到新会话、空会话不需要额外请求就会被清理、空闲会话超时结束、两个代理并发启动时只有一个常驻进程、已订阅的事件不会进入通用通道。
- 服务能检查通过所有远端目标（Linux musl 两种架构、macOS 两种架构）；两个 Linux 静态 release 版用 `rust-lld` 构建成功，并且都不超过 1.5 MiB 的体积上限。
- Linux CI lane（`.github/workflows/ci-remote.yml`）只在远程相关路径变化时运行，不占用 macOS 和 Windows runner。
- 后续阶段的验收标准在各自的 PR 和 Note 中补充，例如 M1 要在真实的 SSH 主机、Docker 容器和远程 Mac 上各验证一次完整流程。

## 风险

- **macOS 远端的孤儿进程**：服务被 `SIGKILL` 时，macOS 上的子进程会继续运行。能力描述里如实报告了这一点（`serverShutdown`），实现会话保持时再补 kqueue 守护者。
- **非 UTF-8 文件名**：这一版协议无法表达非 UTF-8 文件名，列目录时会计数并跳过，不会静默丢弃。如果用户确实遇到，再加一种字节编码的名字字段。
- **环境变量**：登录环境靠运行用户自己的 shell 得到。profile 写得很特别时（比如要求输入、或者每次都会执行 `exec tmux`），会退回非交互登录 shell 或服务自己的环境，并在 `diagnostics` 里说明。界面接入时需要把这个说明展示给用户。
- **只有 `sh` 的假设**：探测和上传依赖远端有 POSIX `sh`。distroless 这类精简镜像需要 M5 的 `docker cp` 路径。
- **一个会话只有一个客户端**：新连接会顶替旧连接。如果以后同一个工作区要同时开两个窗口，客户端需要用不同的 key，或者在协议里加入多客户端。
- **保留的事件有上限**：断开期间输出很多的构建，超过 8 MiB 未确认的部分会丢失，`server.resume` 会返回 `truncated`。如果用户需要完整日志，应该让构建写日志文件，而不是依赖事件流。
- **确认的是“交给客户端库”**：客户端库把事件分发到订阅通道时就算收到，`last_event_seq()` 也按这个计数。应用丢弃了还没读完的句柄，那部分事件不会再补发；需要更精细控制时，按每个事件自带的 `seq` 决定从哪里续传。
- **按会话结束进程时的 pid 复用**：信号按会话 id（等于首进程的 pid）发送。会话还有成员时，这个编号不会被复用；会话一空就必须尽快忘掉它。服务每 500 毫秒检查一次只为剩余成员保留的会话，`kill` 和关闭终端在发信号前也会再检查一次。剩下的风险只在“会话刚空、检查还没跑”的这几百毫秒里，而且还需要恰好在这段时间里分配到同一个 pid。检查一次扫描整张进程表，判断所有待查的会话。
- **测试会碰到用户自己的配置**：交互式 shell 会读写用户真实的 `~/.bash_history`。开发时就发生过一次：终端测试把测试命令写进了开发者的历史记录，之后已经清理。现在所有测试终端都设置 `HISTFILE=/dev/null`；登录环境测试使用临时的 `HOME` 和固定的 `/bin/sh`。以后新增的测试也必须这样隔离。
- **回退方式**：三个 crate 目前没有被产品代码引用。如果方向需要调整，可以整体删除，不影响现有功能。
