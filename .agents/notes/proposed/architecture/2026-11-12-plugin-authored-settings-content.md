# Agent 笔记：插件在设置的两块区域里自己做界面

状态：提议中

## 先说结论

设置窗口里有两块区域交给插件自由创作：插件详情「设置」标签的正文，以及插件用 `page` 声明的侧栏页的正文。侧栏入口本身（名称、所属分组、位置）仍然只能声明。区域里的内容由插件二选一：**描述模式**（插件返回一棵与界面框架无关的 JSON 界面树，宿主用 Viva 控件画）或**自绘模式**（插件包里的网页，放进系统网页引擎，只占这块矩形）。不管用哪种模式，框外的一切都归宿主管，写入设置必须经过 Core 校验，而且只能写本插件声明过的设置。

## 问题

现在这两块区域只能显示 Core 按清单生成的声明式设置行（`settings[]`）。插件作者做不了字段联动、「测试连接」按钮、可视化预览这类界面，例如数据库连接向导或配色预览。

现有的原生声明 `native-ui.schema.json` 引用了 macOS 共享控件名（如 `LitheSettingsSelect`），切换到 Viva 后已经不适用，而且它只用于工具窗口。

如果不先划边界，插件会想改别的设置页、弹自己的对话框、改窗口底部按钮。那样宿主就没法统一管理设置窗口，也无法保证 `${setting:}`（把设置值代入启动参数的模板）的安全。

## 提案

### 两块区域

| 区域 | 入口由谁决定 | 内容由谁画 |
| --- | --- | --- |
| 插件详情「设置」标签 | 宿主固定 | 插件，两种模式任选；没有自定义内容时显示声明式设置行 |
| 侧栏插件页（「语言与框架 › <语言>」「构建、执行、部署 › <构建系统>」） | 插件在清单里声明 `page`，分组和位置由宿主按[设置页分类](../../implemented/feature/2026-10-15-macos-settings-hierarchy.md)决定 | 插件，两种模式任选；同一页有多个插件声明时，用已有的贡献者切换，每个插件只画自己那一块 |

### 两种模式

**描述模式**：插件后端（用现有的 Node 或 Rust SDK）返回一棵 JSON 界面树。宿主用 Viva 控件把它画出来，再把点击、提交等事件发回后端，后端返回新的树。

- 词汇与界面框架无关：布局（列、行、网格、分组、分隔线）、内容（文本、标题、宿主图标、徽标、链接）、控件（按钮、开关、文本框、数字框、单选、多选、文件或目录选择、列表、树、表格）。
- 样式只开放主题 token（宿主主题里命名好的颜色、字号、间距档位）：语气色（普通、弱化、强调、警告、危险、成功）、字号档、粗细、间距档、宽度（填满或按字符数）。不开放任意颜色、字体和绝对坐标，这样深浅色、缩放、无障碍和输入法由宿主统一保证。
- 这套 schema 替换 `native-ui.schema.json`。工具窗口的 Tree/List/Form 也改用同一套词汇，桌面端在 `plugin_native.go` 现有的渲染代码上改造。
- 输入框不会每按一次键都调用后端，只在失焦或提交时发事件。

**自绘模式**：插件提供包内的 HTML 页面，用 Canvas、WebGL、SVG 等随意绘制。

- Viva 用 `canvas.NativeView(id, rect)` 在指定矩形里挖一个洞，放进系统网页引擎（macOS 是 WKWebView，Windows 是 WebView2，Linux 是 WebKitGTK）。页面天然只占框这一块；宿主的标题、标签页和按钮画在洞外，下拉弹层画在更高一层。
- 页面的加载规则、内容安全策略（CSP，限制页面能加载什么）和 bridge（页面调用宿主的通道）沿用[插件自带网页界面](../../implemented/architecture/2026-10-18-plugin-web-content-in-host-windows.md)的实现：Rust Core 的 `plugins.web.*` 决定规则，桌面端 `pluginweb` 只做 I/O。不另起一套。
- 宿主把主题 token 以 CSS 变量提供给页面，用不用由插件决定。
- 这仍然是可选方式，和「插件界面原生优先，网页只作可选」的方向一致。

### 宿主强制的边界（两种模式相同）

- **只画在框里。** 裁剪和滚动归宿主。弹出层只能由宿主控件打开（下拉、文件选择），并且锚在框内。插件不能弹对话框、发通知，也不能改标题、标签页、底部按钮、别的设置页或别的插件。
- **只写自己的东西。** 写入走 Core：Core 按清单校验 id、类型、范围和作用域（API-19 `settings.update`）。插件没法写宿主偏好或别的插件的设置。修改工具的真实配置（例如 Maven 的 `settings.xml`）走本插件自己的函数，并遵守[设置反映工具真实配置](../../implemented/architecture/2026-10-25-settings-native-configuration-editing.md)：显式 Apply、冲突保护、写后重读。
- **保存归宿主。** 描述模式里控件绑定到设置 id，草稿由宿主保存；自绘模式里页面通过 bridge 把改动暂存给宿主。两种模式都是点宿主的保存按钮时才由 Core 提交，提交结果的生效方式（restart、immediate、reload、nextRun）也照旧由宿主分发。
- **生命周期跟着区域走。** 区域显示时才调用后端或加载页面，切走、关闭窗口、停用或卸载插件时取消请求并释放页面。每次调用都有超时。
- **失败只影响这一块。** 后端出错、超时或页面加载失败时，框里显示错误，并回退到声明式设置行，窗口其他部分照常可用。
- **文案分两种。** 宿主自己的文案（保存、错误、回退提示）走 `shared/i18n`；插件画出来的文字属于插件内容，由插件自己做本地化。

### 正确做法

- 数据库插件在「设置」标签用描述模式画一个连接表单，「测试连接」按钮调用本插件函数，用户点宿主的保存按钮后，Core 校验并写入插件声明的 `host`、`port`。
- 主题插件在自己声明的侧栏页用自绘模式，在 Canvas 上画配色预览；用户选好的主题 id 通过 bridge 暂存，点保存后写入声明的设置。

### 不要这样做

- 不要让插件在框外画任何东西，或者在宿主里按插件名加专用页面分支。插件需要新页面时只能用 `page` 声明。
- 不要绕过 Core 直接写偏好目录或 `.lithe/plugin-settings.json`。那样会跳过校验，`${setting:}` 就可能把未校验的值带进启动命令。
- 不要为了描述模式开放任意颜色或像素坐标。需要像素级控制的插件请用自绘模式。

### 已确认（2026-11-12）

1. API 编号：界面树渲染归入 API-13，自绘页面归入 API-14，读写设置归入 API-19，都算现有编号的扩展，不新增编号。
2. 契约版本：在 v0 里直接删掉 `native-ui`，换成新 schema，不升版本号（版本已于 2026-11-11 全部归 0）。
3. 时间：现在做，包括一个 Core 契约加 SDK 的 PR，以及 #1799 的桌面端渲染。

## 考虑过的备选方案

### 只保留描述模式

吸引力在于宿主最好管：样式统一、没有网页引擎、无障碍有保证。用户在 2026-11-12 否定了这一点：有些插件确实需要自己绘制（图形预览、可视化编辑），只给 JSON 会把它们挡在外面。所以两种模式并存。

### 远程画布（暂不考虑）

插件后端发出绘图指令（矩形、路径、文字、图片），宿主用 Viva 的 `gfx` 画出来，再把鼠标和键盘事件转发回去。吸引力在于完全不依赖网页引擎，三端画出来一模一样。

2026-11-12 用户决定暂不考虑，原因有三：

- 每次交互都要跨进程往返，拖动和动画会卡顿。
- 文字输入和输入法要宿主重新实现一遍。
- 插件作者还得学一套新的绘图接口。

以后如果需要在不允许网页引擎的环境里自绘，再重新评估。

### 把插件进程的原生窗口嵌进框里

插件自己开一个原生视图，由宿主重新挂到设置窗口里。看起来最自由，但各平台嵌入方式完全不同，插件进程也能借此操作宿主窗口，安全边界守不住。不采用。

### 在宿主进程里运行 WASM 绘制

插件提供 WASM 模块，在宿主进程里调用 Viva 的绘图接口。省掉了跨进程往返，但插件代码会跑进宿主进程，资源和崩溃都难隔离，还要再维护一套 WASM 运行时和接口版本。不采用。

## 验收标准

- 同一个插件分别以描述模式和自绘模式在「设置」标签和侧栏页里显示内容，并能通过宿主的保存按钮写入它声明的设置；Core 拒绝未声明 id、越界值和错误作用域。
- 自绘页面的内容不会画出框外。滚动设置页、打开下拉弹层、切换标签页时，页面位置和遮挡关系都正确。
- 后端超时、后端崩溃、页面加载失败时，框里显示错误并回退到声明式行，窗口其他区域可以继续操作。
- 停用、更新、卸载插件或关闭设置窗口后，没有残留的后端调用和网页进程。
- 运行 `scripts/macos/verify/verify-runtime-bundle-immutability.sh`，确认插件包和应用包在整个流程中没有被写入。
- `native-ui.schema.json` 不再出现在 Core 契约里，工具窗口改用新 schema 后行为不变。

## 风险

- 系统网页引擎在三端的行为不完全一致，Linux 上的 WebKitGTK 版本差异最大。回退方式：自绘模式按平台声明是否可用，不可用时显示声明式行。
- 原生视图挖洞以后，宿主弹层必须画在更高一层，否则会被网页盖住。需要先在 Viva 里验证设置窗口的弹层顺序。
- 替换 `native-ui.schema.json` 会让现有声明原生工具窗口的插件失效。需要在契约更新记录里写清楚，并同步更新官方插件。
