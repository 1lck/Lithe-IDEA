# Agent 笔记：由插件定义工具的工具链发现与选择

状态：提议中

## 先说结论

从 Dock 启动时找不到版本管理器安装的运行时、项目要求的版本未生效，不能靠宿主逐个补目录和版本文件解析器解决。本方案把工具定义、安装事实提供方和使用方分开：插件说明工具是什么，版本管理器回答当前事实，宿主只提供统一选择、查询和环境展示框架；Java、Maven 等定义全部由插件贡献，不保留宿主内置定义表或兼容别名。当前已实现 Core 基础切片及 macOS 只读设置页，尚未接入两端的查询进程、文件监听、保存和运行时消费者。完整方案仍在本提案中跟踪，不能把页面出现解释成产品已能使用 mise 或已经完成工具迁移。

## 问题

[PR #1581](https://github.com/1lck/Lithe-IDEA/pull/1581) 最初用 `toolchainSources` 声明安装目录、版本文件格式和选择规则。它能发现 mise 的安装，但 Core 仍需要理解 `miseToml`、`toolVersions`、`lts`、`prefix:` 等私有语义；接入 nvm 或 SDKMAN 又要修改 Core。这既复制上游规则，也无法保证新工具只改插件就能接入。

原方案还通过文件名把候选插入不同的运行时选择链。版本管理器贡献“发现结果”，却可能改变任意同名命令的启动目标；要求的版本未安装时静默回落，用户仍看不见选错版本的原因。

设计依据以 [2026-10-31 的改写计划](https://github.com/1lck/Lithe-IDEA/pull/1581#issuecomment-6541366112) 和 [交互原型](https://gist.github.com/xiaoyumuxi/2ae889a6592599b13998bc811c647942) 为准；原型中的工具名称和演示数据不是宿主预置表。通用边界遵循[独立插件能力与领域契约](../../implemented/architecture/2026-10-31-plugin-capability-and-domain-boundaries.md)，候选解析复用 [#1420](https://github.com/1lck/Lithe-IDEA/pull/1420) 已落地的[可执行文件候选规则](../../implemented/architecture/2026-10-21-plugin-settings-surfaces.md)，不另写第二套顺序算法。

## 提案

### 1. 三类贡献，各自保留真实来源

这里的工具链是“某个工具的一份可用安装及其选择来源”，不是 Java 的别名。提供方（Provider）是回答已安装版本、项目要求和全局默认的插件；使用方是确实需要该工具的语言服务器、构建任务或运行配置。

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 工具定义插件 | 工具 ID、名称和图标、可执行布局、版本探测、发现位置、包装脚本、环境导出及启动模板 | 在宿主里注册私有解析器，或借显示名称覆盖别人的工具 |
| 提供方插件 | 调用上游或读取自己支持的配置，返回安装、带来源的要求、监听对象 | 修改宿主选择顺序、执行下载或自动信任项目配置 |
| 使用方插件 | 显式引用工具 ID，声明最低版本、工作目录和切换后的生效策略 | 按文件名猜工具，或在宿主选定后私自再找另一份安装 |
| Rust Core | 校验声明和结果、确定性候选排序、四层选择、带原因的解析轨迹 | 解释管理器私有版本表达式，启动进程或直接拥有平台文件系统能力 |
| 平台宿主 | 安装身份验证、只读文件探测、进程与查询生命周期、存储、文件观察、通用界面 | 内置工具定义、硬编码 SDKMAN 等位置、解析 `mise.toml` 或 `.sdkmanrc` |

“系统扫描”是宿主内置的通用提供方，但扫描位置和布局全部来自已启用定义的 `discovery` 等声明。它没有自己的工具表；没有定义时不扫描、不导出变量、不生成工具行。

工具链是独立领域，Core 代码放在 `rust/lithe-core/src/toolchain/`，不能因为事实由插件贡献就把解析、固定和选择模型放进 `plugins/`。插件清单模块只负责贡献准入，调用工具链领域校验；公开契约仍在插件契约目录中描述贡献接口，不改变工具链本身的含义。

正确做法：Java 支持插件贡献工具定义，mise 插件调用 mise 自己的机器可读接口回答选中了哪份安装，宿主展示来源并执行通用校验。不要这样做：把 `miseToml` 改名成 `tomlTools` 后继续在 Core 解释它，或用 `if tool == "java"` 把返回目录当作特殊的 JDK home。

### 2. ID 和执行权限不能靠声明自证

工具 ID 是显式关联，不靠命令名关联。社区插件定义自己的工具时使用 `<pluginID>:<tool>`；不带前缀的短名只允许经宿主验证的官方签名插件定义。这里的“官方”来自安装验证后的发布者身份，不能来自清单中的自称字段、插件 ID 前缀或显示名称。重复 ID 拒绝后来的注册者，不允许覆盖已有定义。

社区提供方可以回答 `java` 等短名，但结果只对它已声明、请求已授权、且存在已启用定义的工具生效。提供方不能通过返回 `git` 的同名文件取得宿主命令替换权。安装审查须列出被影响的工具、运行的后端和探测参数；`toolchains.provide` 的说明必须表达“影响工具选择”，不能只说读取目录。

定义中的环境导出与路径模板由 Core 做通用限制：不能覆盖 `PATH` 或动态加载器变量；路径追加只能落在确认过的 home 内；版本探测只接受受限参数，启动按参数数组展开，不经 shell 拼接。正则只负责从探测输出提取可比较版本，不能把管理器的 `lts`、厂商别名或配置优先级重新交给宿主解释。

插件未启用时，提供方仍可能观察到项目要求该工具。该要求可以生成仅用于展示的“定义插件未启用”诊断，但不能进入候选、导出环境或启动程序。提示中的插件身份与“在插件页启用”操作来自可信的已安装注册表；没有可确认的定义插件时只报告缺失定义，不根据提供方任意字符串构造安装或启用目标。

### 3. 四层选择，共用一个结果

解析器（resolver，按候选顺序寻找可用程序的机制）扩展现有 `executables` 数组及 `skip`、`resolved`、`terminalFailure` 三种结果。工具可执行布局与候选来源分别表达，不能让同一个字段有时表示 `bin/java`，有时表示解析规则。Core 产出的同一快照用于环境页、使用方和实际进程启动，不能让各入口再选择一次。

| 层 | 通用规则 | 不可用时 |
| --- | --- | --- |
| 固定 | 从当前目录向上找最近的祖先 `pins`，只接受用户明确固定的安装 | 非空固定值无效返回终止失败（`terminalFailure`），不回落 |
| 项目文件 | 最近目录优先；同目录内包装脚本（Wrapper）优先于项目环境，项目环境优先于版本声明；同文件原生读取优先于兼容读取 | 未安装的要求返回跳过（`skip`）并携带结构化原因，继续下一层且保留“未满足”状态 |
| 全局 | Lithe 全局默认优先，其次是提供方全局设置，最后是登录 Shell 的环境 | 提供方全局要求冲突时让用户选择；选择前使用登录 Shell，不按插件 ID 猜测 |
| 自动 | 在已通过校验且满足最低版本的安装中选择最新版本 | 没有候选时显示真实缺失原因，不制造默认安装 |

候选的稳定排序和同集合插入约束沿用 #1420；不能让使用方跨集合改变别的工具的优先级。不同原生提供方对同一项目位置给出无法比较的要求时，应保留冲突并按契约处理，不把稳定展示排序误当成业务优先级。

管理器的 `request` 是不透明的来源信息，例如 `lts` 由管理器解释；Core 只比较已探测出的规范版本。手动添加只提供可固定的安装，不参与自动层。语言服务器、构建模型和运行配置分别声明 `restart`、`resync` 或 `nextRun`，界面据此提示；不能一看到文件变化就强制重启所有运行中的用户任务。

Core 基础切片先独立验证固定值，因此低层提供方超时不能撤销一个有效固定值。没有固定值时，提供方超时或不可用保留诊断并允许下一层继续；身份、代次、安全校验和主动取消失败不能伪装成“未安装”。最近的项目要求即使未满足也屏蔽父目录要求，不能以“找到了能运行的版本”为由改变来源优先级。

### 4. 目录固定与手动添加的写入边界

环境页按目录展示结果，子目录继承最近祖先的固定值。固定写到 `.lithe/toolchains/local.json` 的 `pins`；现有 `toolchains` 字段保留，草案不授权提前迁移旧数据。目录标识使用规范的工作区相对路径，根为 `.`，不能用绝对路径或 `..` 把固定作用域扩展到工作区外。

`local.json` 保存本机安装路径，因此首次明确保存时，平台存储适配器还要确保 `.lithe/.gitignore` 包含 `/toolchains/local.json`，保留已有内容。打开项目或设置页只读，不创建这两个文件；未修改、取消、失焦和切页不写入。保存必须检查读取基线，受保护地原子替换并回读；任一步失败都报告真实结果、保留草稿和既有数据，不能把部分写入报告成全部成功。

“添加…”由用户选择目录，再按该工具的布局和版本探测校验。手动安装记录仅存在平台应用存储；选择固定后才把对应安装引用写进本地项目固定文件。它不是自动发现结果，也不写安装包或项目的便携配置。

### 5. 查询由宿主管，版本语义由插件管

宿主使用已有进程、能力协商和 JSON-RPC（带请求 ID 的进程间消息）机制请求 `toolchains/query`，不另建每个工具一套通信框架。每次查询捕获 `operationID`、工作区、已启用定义与提供方快照及代次；关闭或切换工作区、停用插件、输入变化时先使旧代次失效，再取消请求和回收本次拥有的资源。超时和停止都有本地期限，晚到结果不能发布到新工作区或新插件集合。

`watchFiles` 声明文件名或有界 glob（有限目录匹配规则），返回结果也可以列出实际读取的输入。必须观察尚不存在的匹配项及其父目录，否则新建版本文件不会触发刷新。任何一个相关文件创建、删除、改名或修改，都撤销整份查询快照并重新查询全部已启用提供方，不把一部分旧安装和一部分新要求拼在一起；短时间事件可以合并，但不能丢掉失效。

缓存身份包含工作区、定义和提供方的规范清单、启用状态、运行环境及输入指纹。只比较已存在文件的修改时间不足以覆盖新建、删除和目录替换。无变化可复用，检查失败则显示失败或重新查询，不能把读取错误当作“没有变化”。本机提供方不能服务远程工作区；远程接入须在远端适配器完成前保持不可用。

### 6. 项目代码与外部安装分开授权

提供方返回的安装须有数量上限，路径必须是绝对路径，并通过平台文件事实和 Core 通用规则校验：真实目标存在、可执行、规范化后不在工作区内。符号链接也按最终目标判断；不能只检查文本前缀。校验结论和选中目标绑定，在实际启动边界重新确认，不能把一次旧 `stat` 当作永久授权。

项目包装脚本和项目环境本来就在工作区内，不能套用上述规则后全部禁用，也不能因此放宽外部提供方安装校验。它们必须是单独标识的项目代码来源，沿现有“执行仓库代码”的明确用户操作和逐操作确认规则启动；当前没有持久的工作区信任状态，不能假设曾经打开项目就是永久授权。后台探测不能借版本校验执行仓库携带的任意程序。

提供方后端不能依赖它正在发现的工具，否则会出现“先找到 Node 才能问插件 Node 在哪里”的循环。第一阶段使用自带运行时或单文件原生程序，构建时固定并验证资源；不在启动时下载运行时、自动安装版本或执行 `mise trust`。带后端插件仍按现行[热激活边界](../../implemented/architecture/2026-10-26-plugin-live-activation.md)要求重启，本提案不提前放宽。

当前 Core 切片尚无原生链接链身份验证：项目程序和环境 home 的规范身份与声明路径不同时先拒绝，不能把仅有布尔授权当作符号链接安全证明。因此常见 venv 解释器链接及规范化后不再匹配观察声明的配置链接仍有保守限制，后续平台接入必须单独验证再放开。Wrapper 没有安装 home 时返回 `null`，不导出基于 home 的变量或 PATH，避免把仓库根误作工具安装。

### 7. 统一界面不等于统一业务表单

环境页由宿主提供目录树、工具行和使用方列表。工具名称、图标、探测、导出的变量及使用关系都来自已启用插件；一行展开后按“固定、项目要求、全局默认、自动检测”的顺序列出四个来源：首个有值的来源加框并标“首个命中”，没有值的来源变淡但不隐藏，让解析顺序一眼可读；解释放进信息提示。来源页展示登录 Shell 的读取结果和插件声明的版本管理器，手动安装接入后也放在这里；提供方自己的可执行文件位置、离线选项等仍由插件在自己的设置页注入。

设置遵循[真实配置编辑规则](../../implemented/architecture/2026-10-25-settings-native-configuration-editing.md)和[侧栏分类](../../implemented/feature/2026-10-15-macos-settings-hierarchy.md)：默认只读发现真实来源并回显，编辑草稿经明确确认后写回、检查冲突、重新读取；非敏感配置不能保存成上游不使用的影子配置，秘密不能明文回显。环境固定和手动安装是 Lithe 自己的偏好，必须标明作用域，不冒充管理器原生配置。

插件停用或卸载后，撤销其工具行、使用方、导出变量和设置页，取消它拥有的查询及监听；写下的固定值保留，重新启用再校验并恢复。存在固定值不代表定义仍然有效，不能靠残留固定继续导出环境或启动程序。所有用户文案实现时进入 `shared/i18n/`，不把原型里的字符串直接写进视图或服务。

当前 macOS 页面先交付通用只读框架：构建分组新增“运行环境”和“环境来源”，保留旧项目页，直到真实使用方迁移后再删除旧链路。加载器只读取已注册且已启用插件的声明与本机 `local.json`；固定继承仍调用 Core，不在 Swift 维护第二份规则。页面只显示读到的事实：存在的版本文件只说明“版本未查询”，固定值显示“已保存，未验证”，自动检测只给出按声明顺序找到的第一个可执行文件并标“版本未验证”，全局默认在提供方查询接入前显示“未查询”；实际版本、使用方与变量没有事实就不显示。添加、切换、保存和查询还没有真实实现，所以界面上直接不放这些控件，也不放禁用的占位按钮。目录树只列项目根目录、自己有版本文件或固定值的目录及其上级，扫描与行数有上限，超出时用诊断说明覆盖了多少目录。隔离预览（`--toolchain-settings-demo`，仅 Debug）只用样例插件清单代替已安装插件：工作区是真实文件（临时生成或 `--toolchain-demo-workspace` 指定），固定、版本文件、自动检测和登录 Shell 都走生产加载器、Core 和启动时的同一读取流程；它不进入生产插件表或运行流程，退出时删除临时目录。远程工作区在读本机文件前拒绝。

来源页只展示两类已有事实。第一类是登录 Shell 读取：使用的 Shell、读取状态、变量数量、耗时与时间，以及 `PATH` 各目录来自登录 Shell 还是 Lithe 的启动环境。其他变量可能含有密钥，只计数不显示值。“重新读取”只刷新子进程缺少的变量和下次启动用的 `PATH` 缓存，不改本进程的 `PATH`（线程启动后 `setenv` 不安全）；发现 `PATH` 变了就提示重启。第二类是插件声明的版本管理器：它监视的文件、本项目里实际找到的文件，以及来自哪个插件。提供方的运行状态、查询命令、耗时和全局默认，在原生查询客户端接入前一律不显示，不保留占位徽标。

设置页复用既有布局框架，而不是把 HTML 的像素宽度写成整页不可压缩尺寸。嵌套 `LitheSplitPaneView` 声明理想页尺寸，目录和详情接受父容器分配的双轴边界；标签组用共享 `LitheChipFlowLayout` 换行；工具行和提供方行用 `ToolchainEdgeLayout`，主体放不下时把右侧徽标移到下一行；四个来源卡片用 `ToolchainStepGridLayout` 等宽分列，列数只取 4、2、1，避免出现半空的一行，同一行卡片取最高的高度。卡片里的路径保持单行，从前面截断以保留文件名，悬停显示完整路径。宽度不足时改变行列数并重新计算真实高度，不能只裁掉控件、让 `ViewThatFits` 测量与显示走不同高度分支，或用最大卡片高度压住增长的内容。原生缩放回归同时检查反复缩小/放大、分隔条拖动、卡片边界及后续行顺序；隔离预览也使用生产 `SettingsWindowChrome` 和外观容器，避免演示窗口与产品的内容尺寸含义不同。

### 8. 资源归属和分阶段迁移

| 资源 | 所有者与生命周期 | 可写位置及校验 |
| --- | --- | --- |
| 工具定义与插件固定资源 | 插件版本，构建时生成并签名；运行时只读 | 已安装包内仅可读，不影响代码签名或 Sparkle 增量更新基线 |
| 查询快照与文件指纹 | 工作区和插件代次，失效、关闭或停用即撤销 | 内存；若以后落盘缓存，单独补资源注册、身份与清理规则 |
| 固定值 | 用户的本机项目偏好，停用后仍保留 | 工作区 `.lithe/toolchains/local.json`，明确保存并回读 |
| 手动安装与全局默认 | 用户应用偏好，用户删除或修改前保留 | 平台应用存储，不复制运行时，不写 app bundle |
| 查询后端临时物和日志 | 插件、工作区和操作拥有，结束时有界清理 | 平台缓存或临时适配器，禁止从发行目录推导写入目标 |

本轮没有下载、运行时缓存或生成资源入口，不更新资源复用清单。后续新增时同步 `scripts/resources/worktree-resources.json`、校验路由和测试、`docs/ci-builds.md`；查询状态和语言服务器工作区状态不能跨工作树共享。

## 考虑过的备选方案

- **继续补 `toolchainSources` 的目录与文件格式。** 最快复用旧 PR，但每个新管理器仍迫使 Core 发版；别名、全局覆盖和信任语义会持续偏离上游，因此不采用。
- **把工具定义移成宿主 `shared/` 下的数据文件。** 少写几个代码分支，却仍由宿主决定有哪些工具；插件停用后工具行和环境导出无法自然消失，违背全部由插件注入的目标，因此不采用。
- **让版本管理器直接改 PATH 或注入任意命令。** 能解决 Dock 的环境缺失，却把发现权限扩大成替换宿主程序的权限，也丢掉工具 ID、来源和使用方关系，因此不采用。
- **提供方主动推送并为每个项目常驻。** 可减少部分查询，但增加生命周期与一致性成本；当前请求式方案已有取消、期限和输入失效边界，先不新增常驻推送协议。
- **每个运行时一条选择链或一个设置表单。** 局部实现直接，但 JDK、Maven 和其他命令继续出现不同优先级；选择、显示与执行会再次漂移，因此采用同一候选机制和通用展示骨架。

阶段 3 清理 `ProjectRuntimeService` 的专属选择链和 `project-jdk`、`project-maven` 等被替代引用前，须按 [Java/Maven 迁移清单](2026-10-26-maven-java-domain-plugin-migration.md)核对真实消费者和数据迁移。Node、Go、Python 等在其插件声明定义之前保持当前实现，不新增特判；不能在本次提案删除仍在生产使用的代码，或用永久兼容别名伪装迁移完成。

契约草案位于 `shared/contracts/plugins/v1/proposals/toolchains/`，其中尚未实现的消费者启动、查询客户端和界面行为继续保留未支持标记。Core 已实现的清单贡献和命令由本次正式契约单独说明，不把草案全集直接当作能力承诺；旧 `local-v1` schema 与 Run 配置读写路径保持不变，新 Core 固定解析入口只处理调用方传入的 JSON，不打开文件或保存忽略规则。合并后在插件文档仓库按合并的 `preview` 提交执行 `node scripts/contract.mjs sync --revision <commit>`；实际插件后端协议接入时同步 Node/Java SDK，并在合并前执行 SDK 端到端验证。每阶段的功能矩阵只记录实际实现和目标平台运行证据，不把本提案或 Core 单元测试当作 Windows 已完成。

## 风险

- **声明会影响启动目标。** 清单 schema 只能检查形状，不能证明官方身份、文件存在或可执行；实现必须同时具备安装验证、平台文件证据、Core 通用限制和启动边界复核。
- **版本比较再次泄漏工具语义。** 已安装版本需要统一的可比较结果，未知版本不能靠工具名修补；Java 8 的特殊输出应由定义的探测规则处理，无法规范的版本不能静默参与“最新”选择。
- **文件监听遗漏或查询失败。** 新建文件、符号链接替换和丢失事件可能留下旧快照，必须覆盖目录身份变化和失败状态；不能把失败翻译成“已更新”。
- **源优先级仍可能冲突。** 原生与兼容声明之间、多个原生项目要求之间不能仅靠稳定排序得到业务答案；需要明确冲突结果与用户可行动入口。
- **多文件保存不是天然事务。** 忽略规则和固定文件的保存需定义失败与重试结果；任何部分成功都不得丢掉用户源数据或误报全部成功。
- **迁移跨度大。** Java/Maven 仍有真实生产消费者；按阶段替换并删除对应旧路径，否则会长期保留两套真源。未验证的平台保持待验证，不能以契约共用推断产品一致。

## 验证

当前验证覆盖文档、契约和 Core 纯数据边界，不运行应用，也不声称运行时流程已验收：

- `./scripts/agent-notes/verify-agent-notes.sh`：中文笔记格式、生命周期、链接与路径。
- `./scripts/architecture/verify-shared-contracts.sh`：现行共享契约及 JSON 有效性；不能替代草案 schema 的专门校验或未来 Core 语义测试。
- `./scripts/platform-feature-matrix/verify-platform-feature-matrix.sh`：矩阵记录实际 Core 切片与平台待接入状态，不把纯数据测试标成产品运行时已验证。
- `cargo test --manifest-path rust/Cargo.toml -p lithe-core --lib toolchain_pins -- --test-threads=1`：目录按组件继承、失效数据、跨平台路径语法、数量边界和 legacy 数据保留。
- `cargo test --manifest-path rust/Cargo.toml -p lithe-core --lib toolchain_resolution -- --test-threads=1`：通过正式命令验证四层选择、真实回复解码、冲突和版本规则；文件事实与探测结果由隔离快照注入，不访问本机工具。

后续实现必须按对应平台执行稳定性测试、Core/边界验证和 `./scripts/macos/verify/verify-runtime-bundle-immutability.sh`，并留下真实视口、完整启动流程和进程清理证据。安全与生命周期测试使用隔离文件系统、可控制的时钟/事件和明确本地期限，不依赖开发者安装的 mise、SDKMAN 或个人配置。
