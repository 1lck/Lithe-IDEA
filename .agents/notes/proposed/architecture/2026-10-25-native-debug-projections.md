# Agent 笔记：原生指令与内存调试的后续投影边界

状态：提议中

## 先说结论

原生程序的无源码栈帧、反汇编和内存展示是独立的 Debug UI 扩展，不是 [#1210 Registry 与第三方 DAP 接入](2026-10-25-debug-adapter-provider-and-declarative-registration.md)的关闭条件。基础接入先复用现有源码调试；本提案只保留未来如何表达指令位置和后端差异的边界，不修改旧字段或新增权限。

## 问题

LLDB/GDB 可以同时服务 C、C++、Rust 和汇编，但二进制不一定有源码或行号。当前会话模型以源码调试为主；若用假文件或零行号塞进现有模型，UI 会跳到错误位置，旧消费者也可能误解缺失值。

## 提案

后续从真实 DAP 结果出发，为会话内源码引用、指令位置、内存引用、指令断点和指令单步增加版本化投影。地址及引用保持字符串，避免 JavaScript 数值精度损失；它们是不透明后端引用，不是工作区文件路径。没有源码时明确表达缺失，不直接把旧必填数字改成 null 交给旧消费者。

寄存器优先展示后端给出的变量分组（scope），不假定所有 CPU 有统一寄存器表。反汇编、内存读取、写入和指令断点分别受后端协商、宿主实现与操作授权约束；写入权限需要单独设计，不从已有 launch 或读取能力推导。

源码身份仍为工作区相对路径，外部源码通过已授权映射或会话引用读取。栈帧、变量及内存引用绑定会话和暂停代次，继续执行或重启后重新获取。Rust、Swift、TypeScript 及 fixtures 一起演进，再接平台展示。

正确做法：没有源码的暂停展示指令地址，支持源码的帧仍跳转真实文件。反例：为让编辑器能跳转，给未知帧伪造一个工作区文件和第一行。

## 考虑过的备选方案

- 放回 #1210 的 P5：容易把基础 Registry 与新 UI、架构和权限绑定，已拆出，另行验收。
- 复用现有必填文件位置并填默认值：字段少，但无法区别未知位置与真实第一行，不采用。
- 自研统一原生调试器：重复 LLDB/GDB 的能力及平台权限处理；仍采用标准 DAP 和成熟上游。

## 验收标准

- 有符号源码调试、无源码指令调试分别验收；旧 Registry 与源码流程不要求启用新投影。
- 覆盖未知位置、超出整数精度的地址、继续后引用失效和不支持能力；不得发生假跳转或旧解码器回归。
- 两端分别验证反汇编、只读内存、寄存器分组及指令断点；写入只有在新权限与独立用例通过后开放。

## 风险

GDB 是否支持 DAP 取决于版本和构建，操作系统调试授权及指令集也各不相同。统一模型不意味着全部平台或后端都能实现这些功能，未验证的组合保持不可用。
