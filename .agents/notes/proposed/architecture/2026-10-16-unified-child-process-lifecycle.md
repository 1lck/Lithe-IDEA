# Agent 笔记：统一的子进程生命周期与退出清理

状态：提议中

> Viva 迁移状态：桌面端已有进程账本 `desktop/internal/processledger`，构建、调试、测试、项目生成、本地 shell 和插件服务等启动点登记其中，下次启动时清扫上次遗留的进程。退出时的逐项确认、进程分类和监护进程仍未落地，Windows 的 Job Object 只用于经 `buildprocess` 启动的构建、运行、测试、调试和插件工具进程（`desktop/internal/buildprocess/process_windows.go`），终端 shell 不在其中；Windows 上账本通过进程句柄读取创建时间和程序路径，不启动外部程序（原因见 [Lithe 退出时结束它启动的全部子进程](../../implemented/bug-fix/2026-10-14-child-processes-end-with-the-ide.md)）。下文提案按 Viva 重新核对，实施前以代码为准。

## 先说结论

用户反馈：退出 Lithe 后，终端里启动的 Spring 服务、运行配置、LSP 和插件进程有时仍在后台运行，继续占用端口和内存。原因是各类进程各管各的停止逻辑，而且只覆盖“正常退出”，应用崩溃、被强制退出或更新超时后没有任何兜底。

提案的核心是进程账本（记录“谁启动了什么、退出时该怎么处理”的登记表）。每条记录在启动时就带上退出策略：普通进程退出时自动结束；守护进程、容器这类结束后会影响用户的资源，退出时弹出确认，让用户逐项选择“结束”或“保留”。只有能证明由当前 Lithe 实例启动的资源才进入账本，Lithe 之外启动的进程一律不关心。

对开发者的影响：长期进程必须通过进程账本登记，不能直接启动后不管；插件声明的进程和外部资源必须带退出策略。

## 问题

### 用户能观察到的现象

- 在内置终端里执行 `mvn spring-boot:run` 后退出 Lithe，8080 端口仍被占用，下次运行时提示端口冲突。
- 强制退出或崩溃后，`jdtls`、调试适配器、数据库 sidecar 继续运行。
- 更新安装时清理超过时限，应用直接退出，没来得及停止的进程变成孤儿进程（父进程已退出、被系统接管的进程）。
- 另一方面，Gradle Daemon、Docker 容器这类资源不能一刀切地结束：用户可能希望它们在 IDE 关闭后继续服务，但现在既不会结束它们，也不会告诉用户它们还在运行。

### 现有实现的缺口

- 账本只覆盖启动登记和下次启动的残留清扫。正常退出时的分类、逐项确认，以及“终端里还有程序在运行”这一层，本提案尚未在桌面端对齐验证。
- 进程组不是隔离边界：调用 `setsid`、`nohup`、双重 fork 的子孙进程会离开进程组。终端只结束 shell 主进程时，作业中脱离会话的程序会留下。
- Windows 上父子 PID 链一断，`taskkill /T` 就找不到子孙进程，服务进程也无法被结束。
- 没有 Job Object 时，应用崩溃后所有子进程都会存活。

### 不处理的后果

端口冲突、内存持续占用，用户只能去活动监视器或任务管理器手动结束进程。随着插件和 LSP 变多，残留进程会越来越多，也会违反 `AGENTS.md` 中“测试结束后确认没有 Lithe 进程残留”的要求，自动化测试也无法稳定断言。

## 提案

### 第一层：进程账本

#### 账本记录什么

账本登记的是“受管资源”，分两种：

- **进程**：由 Lithe 启动的子进程，以及后来被发现属于它的子孙进程。
- **外部资源**：不是 Lithe 的子进程、但由 Lithe 创建的东西，例如 Docker 容器、Compose 项目。它们没有可以直接发信号的 PID，只能调用所有者提供的停止动作（例如 `docker stop <id>`）。

每条记录至少包含：

- 所有者：窗口、项目会话、模块 ID 或插件 ID；
- 类型：`run`、`terminal`、`languageServer`、`debugAdapter`、`pluginTool`、`sidecar`、`daemon`、`container`、`oneShot` 等；
- 退出策略（见下一节）和停止方式、宽限时间；
- 进程身份：PID 加启动时间和命令名，避免 PID 被系统复用后误杀无关进程（`processledger` 已按这三项核对）；
- 展示信息：名称、命令行摘要、监听端口、内存，供退出确认使用。

账本位于资源所有者（构建、调试、测试、插件服务等）与操作系统进程之间，不另起一套模块生命周期。确定性规则（记录结构、分类、停止阶段）若放进 Core 仓库的共享规则，两端应共用同一组 fixture；发信号、Job Object、监护进程等平台能力留在各平台的适配层，即 `desktop/internal/processledger` 及其平台文件。

#### 四种退出策略

| 策略 | 含义 | 典型例子 | 退出时 |
| --- | --- | --- | --- |
| `terminate` | 生命周期从属于 IDE | 运行配置、测试、LSP、调试适配器、空闲终端的 shell、数据库 sidecar | 自动结束，不打扰用户 |
| `confirmEach` | 误关代价高，必须逐个确认 | 仍有程序在运行的终端标签 | 逐个弹出确认，没有“全部结束”，可在设置中改为不询问 |
| `askOnExit` | 结束会影响用户，需要用户决定 | Gradle/Kotlin Daemon、`mvnd`、终端中脱离会话的后台进程、Docker 容器、插件声明的常驻服务 | 列入退出确认，可逐项或批量选择 |
| `external` | 不能证明由本实例启动（见下文“只管 Lithe 自己启动的东西”） | 用户在 Lithe 之外启动的 Docker 守护进程、容器、Gradle Daemon | 不登记、不处理、不展示 |

默认值是 `terminate`。没有被明确判定为其他类别的记录一律自动结束，这样漏判的结果最多是“多结束了一个进程”，而不是“又留下一个进程”。

#### 怎么区分：分类在启动时决定，不在退出时猜

退出时再按进程名、命令行去猜类别不可靠，所以每条记录的策略来自以下四个来源，优先级从高到低：

1. **用户设置**：“进程终止策略”页面中的默认值，以及在退出确认中勾选“以后对这类资源都这样做”后记住的选择（按识别规则 ID 保存，同样在该页面列出）。
2. **启动方声明**：宿主功能在启动进程时显式传入策略；插件进程的策略来自插件清单。启动时就确定，不需要推断。
3. **识别规则（Recognizer）**：用于“插件或运行配置启动的进程，又自己派生出守护进程”的情况。例如 Gradle 插件声明：命令行主类为 `org.gradle.launcher.daemon.bootstrap.GradleDaemon` 的进程属于 `daemon`、策略 `askOnExit`。识别规则只能由插件清单或宿主内置功能的清单提供，宿主通用代码里不按工具名写分支。
4. **脱离检测**：带有本实例标记、但已经离开原来的进程组或会话的进程，说明它有意变成后台常驻，且没有被任何识别规则认领，就归为 `askOnExit`，名称显示为“未识别的后台进程”。

外部资源（容器）没有进程标记可追踪，由对应插件作为资源提供者在创建时登记，并附加 `lithe.instance=<实例 UUID>` 标签，以后可以精确找回。

#### 只管 Lithe 自己启动的东西

账本和退出确认只处理能证明由当前 Lithe 实例启动的资源。证明方式只有三种：经过账本启动、带有本实例的进程作用域环境标记、带有本实例的 `lithe.instance` 标签。不满足的一律视为外部资源，不登记、不展示、不结束，也不作为“建议项”出现。

例如：

- 用户在 Lithe 之外启动的 Docker 守护进程、容器、Gradle Daemon，即使正在被 Lithe 使用，也不出现在退出确认中。
- 用户在 Lithe 终端里执行 `docker run`：`docker` 命令行进程本身按终端规则处理；但容器由 Docker 守护进程创建，不继承这个标记，目前无法证明归属，因此不列出。以后如需覆盖，必须先找到可靠的归属证据（例如通过 Docker 插件的动作创建并打上标签），不能按“本次会话期间创建”这类时间窗口去猜。

#### 终端：退出前逐个确认

终端里运行的程序通常是用户手动启动的服务或命令，结束它们之前必须让用户逐个看过。退出 Lithe 时，在任何进程被停止之前：

- 账本按终端标签统计其 shell 会话下的进程。只剩空闲 shell、没有其他进程的标签视为空闲，直接关闭，不弹确认。
- 仍有程序在运行的标签逐个确认。每次只显示一个标签：标签名、所属项目、工作目录、正在运行的命令及其子进程、监听端口、运行时长。
- 每个标签只有三个按钮：“结束此终端”“跳到此终端”“取消退出”。没有“全部结束”，也没有“记住选择”。选择“跳到此终端”或“取消退出”都会终止整个退出流程，已经确认过的标签也不会被结束。
- 终端无法在 Lithe 退出后保留：PTY 随应用关闭，所以终端只有“结束”和“不退出”两种结果。
- 关闭单个终端标签时，如果标签里还有程序在运行，也弹出同样的确认。

#### 设置：进程终止策略

上面描述的是默认行为：终端默认逐个确认。用户可以在设置中新增的“进程终止策略”页面改变默认值。

页面分组和选项：

| 分组 | 选项 | 默认值 |
| --- | --- | --- |
| 终端 | 退出 Lithe 时，运行中的终端：逐个确认 / 直接结束 | 逐个确认 |
| 终端 | 关闭单个终端标签时，有程序在运行就确认：开 / 关 | 开 |
| 守护进程与容器 | 退出 Lithe 时：询问 / 总是结束 / 总是保留 | 询问 |
| 守护进程与容器 | 已记住的选择：按识别规则列出，可单独修改或清除 | 空 |
| 普通进程 | 优雅停止的等待时间（运行配置、LSP、调试器等总是随 Lithe 结束，只能调整等待多久） | 5 秒 |
| 启动时清扫 | 上次遗留的进程：询问 / 自动结束 | 询问 |

几条固定规则不开放配置，页面上用说明图标讲清原因：

- 终端和守护进程之外的确认窗口里没有“全部结束”，终端确认里也没有“记住选择”。想减少确认，只能来这个页面明确修改，避免用户在退出时随手点错。
- Lithe 之外启动的进程和容器不出现在这个页面，也不受任何选项影响。

设置保存在用户设置存储中，不写入安装目录。页面搜索关键词应包含“进程”“终止”“终端”“守护进程”，搜索这些词都能找到该页面。

#### 说明图标：用 ⓘ 讲清楚每个选项

很多用户不熟悉“守护进程”“进程组”这些概念，所以每个分组标题和每个不直观的选项旁边都放一个说明图标（圆圈里一个 i）：

- 鼠标悬停约 0.3 秒，在图标旁弹出说明气泡，移开后关闭。不使用原生 `.help` 提示：它要停留约一秒才出现，而且只适合一行字。
- 点击图标或用键盘聚焦后按空格，也能打开同一个气泡，方便触控板用户和使用读屏软件的用户。
- 说明文字放在共享 i18n 词条中（`shared/i18n/`），不写死在界面代码里。
- 做成共享组件（设置窗口相关的共享控件，见 `desktop/internal/settingswindow/`），设置页其他需要解释的选项也复用它，不各写一套气泡。

说明文字的写法：先说“这是什么”，再说“选了会怎样”，最后给一个例子；不出现未解释的术语。草稿如下，实现时可以润色，但要保留这三层意思：

- **终端**：终端标签里你手动运行的程序，例如 `npm run dev`、`mvn spring-boot:run`。选“逐个确认”时，退出 Lithe 前会一个一个问你是否结束；选“直接结束”时不再询问，退出时全部关掉。没有程序在运行的终端总是直接关闭。
- **守护进程与容器**：一些工具为了加快速度，会在后台常驻一个进程，例如 Gradle Daemon；容器指 Docker 容器。它们由 Lithe 启动，但关掉 Lithe 后你可能还想继续用。这里只包含在 Lithe 里启动的，你在 Lithe 外面启动的不会被列出，也不会被结束。
- **普通进程**：运行配置、测试、语言服务器、调试器等，它们只为 Lithe 服务，退出时总是结束。等待时间是先请它们自行收尾的时长，到时还没结束就强制关闭。
- **启动时清扫**：如果 Lithe 上次意外退出，可能有进程没来得及关掉。选“询问”会在下次启动时列出来让你决定。

#### 退出流程总顺序

1. 未保存文件确认（沿用现有流程）。
2. 终端逐个确认（设置为“直接结束”时跳过）。
3. `askOnExit` 资源确认（见下一节）。
4. 统一停止顺序（见后文）。

任何一步选择取消，整个退出都取消，此前的确认全部作废，不停止任何进程。更新安装触发的退出也走这个顺序，清理时限只从第 4 步开始计算。

#### `askOnExit` 资源确认

收集所有 `askOnExit` 记录：

- 没有这类记录，直接进入停止阶段，不弹窗。
- 有这类记录，按所有者分组展示：名称、类型、PID 或容器 ID、端口、内存、启动来源。每一行可以单独选择“结束”或“保留”。
- 底部提供“全部结束并退出”“按选择退出”“取消退出”三个按钮，以及“记住对这类资源的选择”复选框。
- 只有能证明由本实例启动的资源，默认勾选“结束”。

用户选择“保留”的记录标记为 `retained`，写入应用数据目录的实例记录。兜底层和启动清扫都会跳过它们，下次启动时显示为“上次保留的资源”，用户可以在那里继续结束它们。

#### 统一停止顺序

用户确认后，按以下阶段执行，总时限可配置（建议默认 5 秒）：

1. **冻结**：账本拒绝新的启动请求，防止清理过程中又冒出新进程。
2. **协议级优雅停止**（并行）：LSP 发送 `shutdown`/`exit`，DAP 发送 `disconnect`，插件按清单声明的方式停止，容器调用提供者的停止动作。
3. **信号级优雅停止**（并行）：运行会话和终端发 `SIGTERM`/`SIGHUP`（Windows 发 `CTRL_BREAK_EVENT`）。Spring Boot 收到后会执行自己的优雅关闭。
4. **强制结束**：宽限到期后，Unix 对整个进程组发 `SIGKILL`，Windows 通过 Job Object 结束进程树。
5. **核对**：确认除 `retained` 之外的记录都已结束。超过时限时，界面显示“仍在停止 N 个进程”，并提供“强制退出”按钮，不允许静默退出。

单个会话停止（关闭终端标签、停止运行配置、禁用插件）复用同一套阶段，只是范围缩小到一个所有者，且不弹 `askOnExit` 确认窗口；但其中的 `confirmEach` 记录（运行中的终端）仍然逐个确认。

### 如何保证以后新增的插件也会登记

靠“宿主启动进程必须经过账本”的结构保证，而不是靠开发者记得调用某个 API：

1. **宿主启动一切受管进程都经过账本**。语言服务器、插件服务、构建和调试等启动点已接入 `processledger`（见 `desktop/internal/pluginlsp/`、`desktop/internal/pluginservice/` 等），新增启动点时必须同样登记。
2. **清单必须声明生命周期**。Core 仓库 `shared/plugins/contract/v1/` 的契约为每个语言服务器、常驻服务和资源提供者增加 `lifecycle` 字段（[契约](https://github.com/Lithe-IDEA/Lithe-core-rust/blob/main/shared/plugins/contract/v1/README.md)）；对缺少或非法字段的插件返回稳定错误码，插件直接无法安装。
3. **识别规则也只能来自清单**。插件要让自己派生的守护进程进入 `askOnExit`，必须声明 `processRecognizers`；没有声明的派生进程会被脱离检测捕获，或者按默认 `terminate` 结束，不会静默残留。
4. **未登记进程有诊断**。发现带本实例标记、却不在账本里的进程时，记录一条“未登记进程”诊断（包含所属插件），方便在开发阶段发现漏声明的情况。
5. **静态检查**（待实现）。禁止在进程适配层之外用 `os/exec` 启动长期进程。

清单示例：

```json
"languageServers": [{
  "id": "gradle-ls",
  "lifecycle": { "exitPolicy": "terminate", "stop": "lspShutdown", "gracePeriodMs": 2000 }
}],
"processRecognizers": [{
  "id": "gradle-daemon",
  "kind": "daemon",
  "match": { "mainClass": "org.gradle.launcher.daemon.bootstrap.GradleDaemon" },
  "exitPolicy": "askOnExit",
  "displayName": "Gradle Daemon"
}],
"resourceProviders": [{
  "id": "docker-containers",
  "kind": "container",
  "exitPolicy": "askOnExit"
}]
```

字段名称在实现阶段以 Core 仓库 `shared/plugins/contract/v1/` 的 schema 为准，这里只说明需要表达的信息。

### 第二层：操作系统级兜底

第一层只在应用还活着时有效，崩溃或被 `kill -9` 时需要第二层。

**Windows：Job Object。** 应用启动时创建一个顶层 Job，并设置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`。每个会话再创建一个嵌套子 Job。子进程在创建时直接加入 Job（而不是先启动再加入），避免竞态。应用进程因任何原因结束、Job 句柄被内核关闭时，其中所有进程都会被结束。停止单个会话用 `TerminateJobObject` 代替 `taskkill /T`。

进程加入 Job 后不能再移出，所以“保留”这样实现：

- 启动时就确定要保留的进程，用 `CREATE_BREAKAWAY_FROM_JOB` 启动在 Job 之外（顶层 Job 需要允许 breakaway）。
- 正常退出时，先结束所有未保留的进程，再清除顶层 Job 的 `KILL_ON_JOB_CLOSE`，最后退出。
- 崩溃时来不及清除这个限制，会连同保留项一起结束。崩溃时用户没有做过选择，这是可以接受的结果。

**macOS 与 Linux：监护进程。** 没有 Job Object，进程组和会话都能被 `setsid` 逃逸，所以由一个监护进程负责兜底：

- 监护进程使用同一个已签名的 Lithe 可执行文件，以专用参数启动，不新增二进制，也不向应用包内写入任何文件。
- 它监听主应用的退出（macOS 用 kqueue 的 `EVFILT_PROC`/`NOTE_EXIT`）；主应用通过管道把账本变更（进程组、会话 ID、进程身份、退出策略、`retained` 标记）同步给它。
- 每个子进程的环境变量中注入进程作用域标记（实例 UUID）。环境变量会被子孙进程继承，即使进程已经脱离会话，也能通过读取同用户进程环境变量的系统接口找回来（macOS 为 `sysctl(KERN_PROCARGS2)`）。
- 主应用异常结束后，监护进程跳过 `retained` 记录，对其余已登记的会话、进程组和带有本实例标记的进程执行 `SIGTERM`、等待、`SIGKILL`，然后退出。`askOnExit` 记录和终端在没有用户选择时按“结束”处理。
- 主应用正常退出时，先完成第一层，再通知监护进程“已清理”，然后监护进程退出。

终端单独处理：停止终端时不只结束 shell 主进程，而是枚举同一会话下的所有进程，对这些进程组逐一执行停止阶段。这样 shell 里每个作业所在的进程组都会被覆盖。

### 第三层：启动时清扫残留

两个兜底都失效时（例如主应用和监护进程同时被 `kill -9`、断电），下一次启动时按实例标记和进程身份扫描残留：

- 实例记录写在应用数据目录（用户可写位置），不得写入安装目录或发行包资源目录。
- 上次标记为 `retained` 的资源不算残留，显示为“上次保留的资源”。
- 其余残留在界面中提示“发现上次遗留的 N 个进程”，列表默认全部勾选“结束”。

### 正确做法

```go
// 启动受管进程：启动后立即登记，返回的函数在进程结束后移除登记
cmd := exec.Command(path, args...)
if err := cmd.Start(); err != nil {
    return err
}
stop := processledger.Track("run", cmd.Process.Pid)
go func() {
    _ = cmd.Wait()
    stop()
}()
```

```text
Windows：创建时直接加入会话 Job，而不是先启动再加入（实现时在平台适配层完成）。
```

### 不要这样做

- 不要在宿主功能或插件的代码里直接启动长期进程而不登记。账本不知道它的存在，退出和崩溃时都不会被清理。
- 不要在宿主通用代码里写 `if name == "gradle"` 来判断守护进程。识别规则要放进对应插件或内置功能的清单，否则每加一个工具都要改宿主。
- 不要给终端的确认窗口加“全部结束”或“记住选择”。逐个确认就是为了防止误关，批量按钮会让它失去意义；想少确认，只能去设置页明确修改。
- 不要在退出时才按进程名推断类别，也不要按进程名 `pkill java` 收尾。前者不可靠，后者会误杀用户在 Lithe 之外启动的进程。
- 不要用 `taskkill /T` 或按 PPID 递归重建进程树作为唯一手段。中间进程退出后进程树就断了。
- 不要把实例标记、账本快照、用户记住的选择写进应用安装目录或发行包资源目录。这会破坏 Sparkle 增量更新基线，也违反运行时只读边界。

## 考虑过的备选方案

### 只补齐各模块的 `stop()` 逻辑

改动最小，可以逐个修复终端和运行会话的停止实现。但这只覆盖正常退出，崩溃和强制退出仍然会残留；而且每新增一类进程都要重新写一遍，下一个插件很可能再漏掉。所以只作为第一层的一部分，不能单独采用。

### 退出时按进程特征统一判断类别

不需要改插件清单，退出时扫描进程，按命令行、端口等特征判断哪些是守护进程。实现快，但特征表会集中在宿主里不断增长，违反“插件专属逻辑由插件声明”的原则；判断错误时用户也无从得知原因。改为启动时声明、识别规则由清单提供，脱离检测只作为兜底。

### 所有后台资源一律保留，只结束前台进程

对用户最“安全”，不会误结束容器或守护进程。但这正是现在残留问题的来源，用户无法得知哪些资源仍在运行。改为列出来让用户决定。

### macOS 上使用 launchd 托管每个子进程

让 `launchd` 以临时 job 的形式托管子进程，可以借助系统来回收进程。但它需要为每个进程生成 plist 或调用私有 API，标准输入输出和 PTY 难以接入，用户在终端里启动的进程也无法纳入，复杂度和收益不成比例。

### macOS 上使用 `NOTE_TRACK` 跟踪 fork

kqueue 曾支持 `NOTE_TRACK`，可以自动跟踪子孙进程的 fork，但现代 macOS 已经不再支持，不能依赖。

### 只依赖 PTY 关闭时的 `SIGHUP`

关闭 PTY 主端时，内核会向前台进程组发送 `SIGHUP`，实现最简单。但后台作业、`nohup` 和主动忽略 `SIGHUP` 的进程都不受影响，无法满足“全部结束”。

### 监护进程使用单独的辅助二进制

职责更清晰，但要新增签名、公证、打包和平台对应物。复用主可执行文件加启动参数，同样能隔离职责，而且发行包结构不变。

## 风险

- **误杀用户进程**：环境变量标记可能被继承到用户有意脱离的进程。缓解：以进程身份（PID 加启动时间）核对；脱离会话的进程归为 `askOnExit`，交给用户确认，而不是直接结束。
- **退出窗口打扰用户**：每次退出都弹窗会让人厌烦。缓解：空闲终端不弹确认；`askOnExit` 支持“记住选择”；嫌麻烦的用户可以在“进程终止策略”页面关闭某类确认。确认窗口本身不提供批量和记住选择，是有意保留的摩擦。
- **用户看不懂选项而误配置**：每个选项都有 ⓘ 说明，危险选项常驻警告，崩溃兜底不受该设置影响。
- **终端里创建的容器会留下**：用户在 Lithe 终端里手动 `docker run` 的容器无法证明归属，按“只管 Lithe 自己启动的东西”不会被列出或结束。这是有意的取舍，需要在用户文档中说明；需要随 IDE 管理的容器应通过 Docker 插件创建。
- **读取其他进程环境变量的权限**：`KERN_PROCARGS2` 只能读取同用户进程，被提权的进程无法读取；受系统保护的可执行文件可能只返回参数、隐藏环境变量。不能把空环境当作“实例内没有遗留进程”的证明。这类进程只能依靠第一层和进程组处理，需要在文档中说明。
- **Job Object 限制**：第三方程序如果自己创建了不允许嵌套的 Job，加入时会失败，此时退回到 `taskkill /T` 并记录诊断。
- **退出变慢**：优雅停止会延长退出时间。缓解：各阶段并行执行，总时限可配置，超时后由用户选择“强制退出”。
- **回退方式**：账本、退出确认、兜底、启动清扫分别加开关，独立落地。监护进程出现问题时可以关闭第二层，退回到只有第一层的状态，不影响正常退出路径。

## 验收标准

- 跨平台进程生命周期测试夹具：启动一个包含普通子进程、`setsid` 逃逸进程、`nohup` 后台作业、双重 fork 守护进程和监听端口的进程树，分别覆盖以下四种退出方式，结束后断言除 `retained` 之外没有带本实例标记的进程存活、端口已释放：
  1. 正常退出；
  2. 更新安装退出（超过清理时限）；
  3. 对主应用执行 `kill -9`（Windows 用 `TerminateProcess`）；
  4. 主应用和监护进程同时被强制结束后再次启动（验证第三层清扫）。
- 分类 fixture 覆盖：宿主声明、插件清单声明、识别规则命中、脱离检测、用户记住的选择五种来源的优先级；未被任何来源判定的记录得到 `terminate`。
- 退出确认：没有 `askOnExit` 记录时不弹出；选择“保留”的进程在退出后仍存活，且下次启动显示为“上次保留的资源”；选择“取消退出”后不停止任何进程。
- 终端确认：只有空闲 shell 的标签不弹确认；有程序运行的标签逐个确认，任一标签选择“跳到此终端”或“取消退出”后，所有终端和进程都保持运行。
- 进程终止策略设置：每个选项的默认值与上表一致；修改后退出流程按设置跳过或执行对应确认；“已记住的选择”可查看、修改和清除；崩溃兜底在任何设置下都不结束保留项。
- 说明图标：每个分组和不直观的选项都有 ⓘ；悬停约 0.3 秒出现说明，点击或键盘聚焦也能打开；中英文文案通过 `shared/i18n/` 生成；设置搜索能找到该页面。
- 归属边界：测试前在 Lithe 之外启动的守护进程和容器，以及另一个 Lithe 实例启动的进程，在退出确认、兜底和启动清扫中都不出现，且退出后仍存活。
- 缺少 `lifecycle` 字段的插件清单被契约校验拒绝，并返回稳定错误码。
- 关闭单个终端标签时，该 shell 会话中所有作业都被结束，其他终端和运行会话不受影响。
- 测试遵守 `write-stable-tests` 的有界等待、资源清理规则，单测试有计时上限。
- `scripts/desktop/verify/verify-runtime-bundle-immutability.sh` 在启动、运行、退出的完整流程后仍然通过。
- `shared/platform-feature-matrix/features/` 增加“退出时结束或确认全部子进程”能力行，两个平台分别记录实现和验证状态。
