# Agent 笔记：桌面端更新渠道、可配置更新源与更新对话框

状态：提议中

## 先说结论

Viva 桌面端已经能检查、下载和安装签名更新，但没有任何发行构建带上更新源，设置页永远显示“此构建未配置更新源”。本方案把更新分成两个渠道：正式版（Stable，经过发布流程的版本）和 AutoBuild（每天从 `main` 自动构建）。两个渠道各有一份签名更新源，默认指向官方仓库 `1lck/Lithe-IDEA`，用户可以改成镜像地址。

更新的交互照 Motty：
- 有新版本时，标题栏右上角出现绿色下载箭头。
- 点开后先显示这次更新了什么（更新日志），再由用户选择“下载并安装 / 跳过此版本 / 稍后”。
- 检查到新版本后不在后台自动下载。

不再保留单独的 Dev 应用身份，两个渠道共用一份设置。旧版本读到不认识的配置时会忽略，但不会把它从文件里删掉，并提示用户。

## 问题

1. **更新不可用。** 发行构建没有注入 `UpdateFeedURL`、`UpdatePublicKeys` 和 `UpdateChannel`（见 `desktop/internal/buildinfo/update.go`）。所以 `newUpdateClient` 返回 nil，设置页只显示“未配置”。用户每次都要去发布页手动下载完整安装包，增量更新的客户端代码也一直用不上（[#1913](https://github.com/1lck/Lithe-IDEA/issues/1913)）。
2. **只有一个渠道。** `UpdateChannel` 只是一个字符串。用户不能在“稳定”和“每天最新”之间选择，AutoBuild 用户也无法回到正式版。
3. **跨渠道比较版本号会装错版本。** AutoBuild 版本号沿用 `viva.toml` 的 `0.7.0`。按语义化版本（SemVer），`0.7.0-autobuild.<时间>` 小于正式版 `0.7.0`。如果直接比较，AutoBuild 用户会被“更新”回更旧的正式版代码。
4. **更新提示没有内容。**
   - Viva 的签名更新源（feed）只有 `notes_url` 链接，没有日志正文。用户看不到更新了什么就要决定下载。
   - 后台检查发现新版本时，只弹一条“有新版本”的通知，没有统一的入口。
5. **旧版本会抹掉新版本的设置。** `desktop/internal/store/store.go` 保存时把 Go 结构体整个序列化写回文件。旧版本不认识的字段读的时候被丢掉，下一次保存时就从文件里消失了。
   - 两个渠道共用设置以后，在 AutoBuild 和正式版之间切换，很容易触发这个问题。
   - 这是现有缺陷，与渠道无关也应修复。

## 提案

### 1. 两个渠道：“安装渠道”与“更新渠道”分开

- **安装渠道**由打包时写入，用户不能修改，表示“现在装的是什么”。
  - `buildinfo` 增加渠道、构建时间（UTC）和 commit，由打包脚本通过 `-X` 注入。
  - 带 `lithe_stable` 标签的构建是正式版，AutoBuild 工作流打出来的是 AutoBuild。
  - 本地 `go build` 和带 `dev` 标签的构建是“本地构建”：不检查更新，渠道选项置灰。
- **更新渠道**由用户在设置里选择，表示“以后从哪个渠道更新”。默认跟随安装渠道。存进 `settings.json` 的 `updateChannel`，空值表示跟随安装渠道。
- **AutoBuild 版本号**改为 `<viva.toml 版本>-autobuild.<UTC YYYYMMDDHHMMSS>`，例如 `0.7.0-autobuild.20261115100000`。
  - 同一渠道内照常按 SemVer 比较，时间越新越大。
- **跨渠道从不比较完整版本号**，切换规则如下：

| 情况 | 行为 |
| --- | --- |
| 更新渠道等于安装渠道 | 正常更新，可用增量补丁 |
| 正式版 → AutoBuild | 先确认风险，再显示 AutoBuild 的更新日志对话框；确认后完整下载并替换 |
| AutoBuild → 正式版 | 默认等下一个基础版本更高的正式版（`0.7.1` 高于 `0.7.0-autobuild.*` 的基础 `0.7.0`）；同时提供“现在回到正式版”，完整安装最新正式版，并提示它可能比当前代码旧 |
| 下载或安装进行中 | 不允许切换渠道 |
| 切换完成 | 丢弃另一渠道已下载的包，立即检查新渠道 |

- 跨渠道检查不需要改 Viva。`update.Config.Current` 是“和谁比较”，不必是正在运行的版本：
  - 立即切换（正式版 → AutoBuild、“现在回到正式版”）时传 `0.0.0`，`Client.Check` 照常验签、校验模式、应用和渠道，返回目标渠道的最新版本。
  - AutoBuild 等下一个正式版时传基础版本（去掉预发布后缀，如 `0.7.0`），只有更高的正式版才算更新。
  - 跨渠道一律不用增量补丁：补丁只对同一渠道上一版的精确字节有效。

### 2. 更新源可配置，默认指向官方仓库

- 默认地址写在代码里，不再只依赖 `-X` 注入，这样任何构建都有默认源：
  - `https://github.com/1lck/Lithe-IDEA/releases/download/desktop-update-feed/stable.json`
  - `https://github.com/1lck/Lithe-IDEA/releases/download/desktop-update-feed/autobuild.json`
  - fork 仓库可以在构建时用 `-X` 覆盖这个默认值。
- 设置页每个渠道一行更新源。
  - 默认显示为“默认（github.com/1lck/Lithe-IDEA）”，可改成自定义 HTTPS 地址，也可以恢复默认。
  - 只有用户修改过的渠道才写入 `settings.json` 的 `updateSources`。
- **自定义源只换下载地址，不换信任对象**：仍用内置公钥验签。镜像必须原样提供官方签名过的文件，不能自己生成更新源；需要自己密钥的 fork 必须自己编译。
- 签名公钥保持逗号分隔的多把，用于轮换密钥：新旧两把公钥同时内置一段时间，再停用旧钥。

### 3. 更新流程：先看日志，再决定

1. 检查时机沿用现有的启动后 5 秒、之后每小时。发现更新的版本时：
   - 标题栏最右侧（可排列按钮区之后、系统窗口按钮之前）出现绿色圆环加实心下箭头的按钮。
     - 图形和颜色沿用 Motty 的 `updateIcon`，颜色 `RGB(22, 163, 74)`，明暗主题相同。
     - 悬停提示写出版本号和点击后会发生什么。
   - 同一版本只弹一次通知，带“查看更新内容”按钮。
   - 不弹对话框，免得打断正在输入的人；也不自动下载。
2. 点绿箭头、通知按钮或设置页“查看更新内容”，都打开**更新对话框**：
   - 标题是版本号。
   - 副标题依次是当前版本、渠道、下载大小（有增量补丁时同时显示增量和完整大小）。
   - 正文是 Markdown 更新日志，限高可滚动，链接在浏览器打开；底部有“在 GitHub 查看完整说明”。
   - 按钮是“跳过此版本 / 稍后 / 下载并安装”。
   - 不能自更新时（deb/rpm 管理的安装返回 `ErrManagedExternally`，安装目录不可写返回 `ErrNotWritable`），主按钮换成“打开下载页面”，正文下方说明原因。
3. **三个选择：**
   - **跳过此版本**：按渠道记入 `updateSkipped`。绿箭头和通知不再为这个版本出现；更新的版本照常提示。用户主动“检查更新”时仍显示它。
   - **稍后**：关闭对话框，绿箭头保留。
   - **下载并安装**：开始下载。对话框可以关闭，此时绿箭头外圈变为进度环，再点可以查看进度或取消。
     - 应用补丁的阶段不能取消，沿用现有 `Applying` 语义。
4. 下载并校验完成后，绿箭头变为“已就绪”样式，对话框主按钮变为“重启并更新”。补丁失败时改下完整包，沿用现有逻辑。
5. 用户主动点“检查更新”且有新版本时，直接打开对话框，不受“跳过此版本”影响。没有新版本时，只在设置页显示“已是最新”。

### 4. 更新日志的来源（照 Motty）

Motty 0.4.10 的做法：签名的 Viva 更新源只带版本、安装包和补丁；`Client.Check` 发现新版本后，再单独请求这个版本的说明，取不到就在对话框里显示“没有更新说明”。日志只是展示内容，信任仍然来自签名更新源里的安装包摘要，所以不需要把日志签进更新源，也不用改 Viva。

Lithe 照这个顺序做，只换日志的位置：

- 日志放在更新源旁边：`stable.json` 旁是 `stable.notes.md`，`autobuild.json` 旁是 `autobuild.notes.md`，和更新源一起发布到 `desktop-update-feed`。镜像整目录复制即可，自定义更新源也能拿到日志。
- 第一行是 `<!-- lithe-update-notes version=<版本> -->`。客户端只在版本与已验签的更新源一致时显示正文，避免更新源和日志先后上传时显示错版本的日志。
- 客户端最多读 16 KB，按 UTF-8 字符边界截断，和 Motty 一样。
- **正式版**：使用 `desktop-vX.Y.Z` 发布说明的正文。
- **AutoBuild**：工作流根据上一次 AutoBuild commit 到本次 commit 之间的 first-parent 提交（PR 标题和编号）生成。超长时截断，并附完整的 compare 链接。

### 5. 不保留 Dev 身份，共用设置

- 两个渠道使用同一个应用 ID `app.lithe.viva`、同一个设置目录和同一个安装位置；切换渠道就是原地替换安装包。
- **保留不认识的配置**，在 `desktop/internal/store/` 统一实现，所有经 `store.Save` 保存的文件都受益：
  - 读取时，按目标类型的 JSON 字段（包括嵌套对象）找出当前版本不认识的键。同名字段但格式变了、解码失败的，也按不认识处理：当前版本用默认值，原值保留。
  - 保存时，先写当前结构体，再把这些键原样合并回去。
  - 当前版本认识、但被用户清空的字段正常删除，不能被旧值“复活”。
- **提示**：读取到不认识的配置时，每组键只通知一次：“有 N 项设置来自更新版本的 Lithe，当前版本不支持，已忽略但没有删除。”通知可展开查看键名。
- **切换渠道时可以选择恢复设置：**
  - 跨渠道安装前，把 `settings.json` 的原始字节存一份快照到用户数据目录的 `update-snapshots/<渠道>-<版本>-<时间>.json`，只保留最近 5 份。
  - 以后切回某个渠道时，确认对话框提供“保留当前设置（推荐）”和“恢复上次使用该渠道时的设置”。
  - 恢复时直接复制原始字节，不经过结构体，避免再次丢字段。
  - 快照只写用户数据目录，不写安装目录（见 [运行时只读边界](../../implemented/bug-fix/2026-09-25-runtime-bundle-immutability-and-update-delta.md)）。

### 6. 发布端（#1913）

- 用 `viva update-keygen` 生成 Ed25519 密钥。私钥存为 Actions secret `VIVA_UPDATE_KEY`，公钥编译进程序。私钥不进仓库。
- 固定的滚动 tag `desktop-update-feed` 下放 `stable.json`、`autobuild.json` 和各自的 `.sig`。正式版和 AutoBuild 工作流只更新自己那一份。
  - 不能用 `releases/latest`，因为 `desktop-v*` 都以 prerelease 发布。
- 安装包仍放在各自的版本 release 里，更新源里的地址指向它们。
- **增量补丁照 Motty 的 `tools/mirror-release.sh`**：
  - 发布前下载上一版的归档，逐个平台传给 `viva feed -patch-from <os>/<arch>=<上一版版本>=<旧归档>`。只为上一版生成补丁，更早的版本下载完整包。
  - 正式版的上一版是上一个 `desktop-v*`；AutoBuild 的上一版是 `desktop-AutoBuild` 当前持有的归档，必须在滚动 release 被覆盖前下载。
  - Windows 的补丁挂在 zip 上，NSIS 安装版复用同一个补丁（Motty 的 `patchesFor`）。macOS 只给 zip 生成补丁，dmg 不进更新源。
  - 取不到上一版时只发布完整包，不让发布失败。
- `viva` 命令从 `desktop/go.mod` 的 `replace` 目录编译，不用 `go run …/cmd/viva@<版本>`（Motty 这样做，但会绕过 Lithe 的 fork 固定）。

### 7. 落地顺序

维护者要求一次做完，下面几部分放在同一个 PR 里；不需要改 Viva fork。

1. **`desktop/internal/store`**：保留不认识的配置，加上提示。按缺陷修复流程，先写在修复前失败的回归测试。
2. **桌面端更新：**
   - 渠道与更新源设置。
   - 标题栏绿箭头、更新对话框、跳过和稍后、进度、重启更新。
   - 设置快照与恢复。
   - 中英文词条、Core 日志目录事件、功能矩阵和无头截图。
3. **发布流水线（#1913）**：两份更新源和旁边的日志、增量补丁、构建注入。密钥由维护者生成后写入 secret；没有密钥时跳过更新源发布。

更新器继续留在 `desktop/` 的 Go 代码里。Viva 是 macOS、Windows 和 Linux 的唯一客户端；签名、比较和安装复用上游 Viva `update` 包，不在 Rust Core 另写一套。

### 正确做法

- AutoBuild 用户把更新渠道改成正式版、最新正式版是 `0.7.0` 时，提示“将在高于 0.7.0 的正式版发布时更新”，并提供“现在回到正式版”。
- 后台检查发现 `0.7.1`：出现绿箭头和一次通知，用户点开后先看到日志，再决定下载。
- 旧版本读到新版本写的 `editorPreferences.foo`：用默认行为运行，保存时把 `foo` 原样写回，并通知一次。

### 不要这样做

- 不要直接比较 `0.7.0` 和 `0.7.0-autobuild.20261115100000` 来决定跨渠道更新，SemVer 会认为正式版更新。
- 不要让没人请求的检查弹出对话框，或者在后台自动下载。被跳过的版本白白消耗流量，用户也失去了先看内容的机会。
- 不要让 `store.Save` 只写结构体里的字段，那样旧版本保存一次，新版本的设置就没了。
- 不要先下载再给日志，也不要因为日志取不到就不提示更新：日志失败只影响正文，对话框照常显示版本、大小和按钮。
- 不要从 GitHub Releases API 读日志：未登录每小时只有 60 次请求，镜像也没有这个 API，滚动的 AutoBuild release 正文是下载说明模板。
- 不要把设置快照写进 app bundle 或 Windows 安装目录。

## 考虑过的备选方案

### AutoBuild 使用单独的 Lithe-Dev 应用身份

已退役的 Swift 客户端曾让 AutoBuild 用独立的应用 ID。它最有吸引力的地方是两个版本的设置天然隔离，还能同时安装。

不采用的原因：用户要维护两个应用和两份设置，切换渠道时设置不跟着走。维护者已明确不保留 Dev 版本。设置冲突改由“保留不认识的配置”和快照恢复解决。

### 发现新版本就在后台下载，下载完再显示日志

这是 Sparkle 等更新器的常见做法，用户点“重启”就能立刻更新。

不采用的原因：用户还没看到更新内容就已经花掉了流量；被跳过的版本也会被下载。维护者明确要求先显示更新内容，再选择下载或跳过。

### 把日志签进更新源（给 Viva fork 加 `Release.Notes`）

日志和安装包一起验签，客户端只需一次请求。

不采用的原因：要给 fork 加格式字段并向上游提 PR，桌面端 PR 要等 fork 合入才能固定版本。Motty 已经证明不签名的日志足够：日志只是展示内容，能不能安装由签名更新源里的摘要决定。

### 日志直接读 GitHub Release 正文（Motty 的来源）

不需要额外发布文件，正式版的发布说明也已经存在。

不采用的原因：未登录时每小时只有 60 次请求；自定义镜像拿不到；滚动的 AutoBuild release 正文是固定的下载说明，不是这次构建改了什么。Lithe 只沿用 Motty 的顺序（验签后再取日志、取不到就显示没有说明），日志改放在更新源旁边。

### 每个渠道一份独立的设置文件

彻底避免新旧版本互相改写设置。

不采用的原因：用户在一个渠道里调好的设置，切到另一个渠道就没有了。维护者要求共用设置。

### 一份更新源同时包含两个渠道

只维护一个文件。

不采用的原因：Viva 的 `Feed` 一个文件只表示一个渠道，并校验 `Channel` 字段；而且正式版和 AutoBuild 由不同工作流、在不同时间发布，同时改写一个文件容易冲突。

## 验收标准

- 正式版构建和 AutoBuild 构建打开设置 → 更新，都能显示安装渠道、构建时间和 commit，并能检查更新，不再显示“未配置”。本地构建显示本地构建，不检查更新。
- 后台检查发现新版本后，标题栏出现绿箭头，同一版本只通知一次，不弹对话框，不自动下载。
- 对话框先显示更新源旁边、版本一致的 Markdown 日志；日志取不到或版本不一致时显示“没有更新说明”，其余照常。“跳过此版本”之后，这个版本不再出现绿箭头和通知；更新的版本出现时照常提示。
- 下载中绿箭头显示进度，可以取消；下载完成后可以重启更新。deb/rpm 和不可写的安装只提供下载页面，并说明原因。
- 从正式版切到 AutoBuild，以及从 AutoBuild 回到正式版，都走完整安装，且不会因为版本比较装错版本。下载中不能切换渠道。
- 自定义更新源能正常检查和下载；签名不匹配时拒绝并显示原因。恢复默认后回到官方源。
- 旧版本读写含新字段的 `settings.json` 后，新字段原样保留，并提示一次；被清空的已知字段不会复活。
- 切回某个渠道时可以选择恢复快照，恢复后的文件与快照字节一致。
- 发布流水线为两个渠道生成签名的更新源，并经过真实签名产物演练：完整更新、增量更新、补丁不可用时回退完整包；`scripts/desktop/verify/verify-runtime-bundle-immutability.sh` 通过。

## 风险

- **macOS 版本字符串**：Viva 的 macOS 安装器只要求包内 `CFBundleShortVersionString` 与更新源版本字符串完全相同（`update/install_darwin.go`），打包时也把版本原样写进这个字段和 `CFBundleVersion`，所以 `0.7.0-autobuild.<时间>` 不需要改 Viva。仍要在发布演练中确认签名、公证和 Finder 都接受这个字符串。
- **私钥丢失或泄露**：所有已安装的客户端都会停在旧版本。私钥必须备份；客户端支持多把公钥，可以轮换。
- **合并设置的边界情况**：嵌套对象、数组和类型变化的字段容易出错，需要用回归测试覆盖“未知键保留”“已知键清空”“类型冲突”三种情况。出问题时可以回退到只保留顶层未知键。
- **日志事件依赖 Core**：渠道切换、跳过版本、更新源失败、保留未知配置等新事件，要先在固定 Core 修订的日志目录里声明。Core PR 没合入之前，桌面端 PR 不能标记 ready。
- **AutoBuild 增量补丁**：滚动 release 被覆盖后就拿不到上一版的精确字节。发布流程必须在覆盖前取得旧包；取不到时只发布完整包。
