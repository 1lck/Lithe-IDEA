# Agent 笔记：构建、执行、部署设置页在大量插件注入时的结构

状态：提议中

## 先说结论

「构建、执行、部署」这一页同时装着作用域与保存、每个插件声明的工具卡片、调试器单步三件事。页面高度随插件数量线性增长。改成下面的结构：

- 分组页本身改成**目录**：只列子页和状态摘要，最上面汇总需要处理的问题，点一下直达对应工具。
- 宿主自带两个固定子页：**工具链**（所有插件注入的工具，一行一个，按需渲染）和**调试器**（支持单步过滤的调试器）。
- 插件声明的页面按种类排在后面，多了就折叠，折叠里最多显示 6 项，其余进「全部 N 个」目录页。

插件只声明自己提供什么、属于谁，位置由宿主决定，宿主不按插件名写任何分支。插件页里的内容用[插件在设置的两块区域里自己做界面](../architecture/2026-11-12-plugin-authored-settings-content.md)的描述模式，需要时可以放画布节点。

可以操作的原型：[`docs/design/build-execution-settings.html`](../../../../docs/design/build-execution-settings.html)。演示栏可以把插件数量切到 5,000，看列表渲染计数和侧栏折叠。

## 问题

现状截图里的问题：

- 一页装了三件事。按现在的卡片高度，每个插件约增加 150 像素，几千个插件时页面高达几十万像素。
- 同一条路径在一张卡片里出现三次：生效行、下拉框、候选行。
- 插件 ID 原样显示，原因码 `versionUnsatisfied` 没有翻译。
- 每张卡片自带「保存」和「使用自动」按钮，和窗口底部的「应用 / 好」是两套提交方式。
- 作用域（全局默认，或只对当前项目生效）的两段说明常驻在页面顶部；有草稿时禁止切换作用域。
- 调试器单步过滤挤在工具链下面，以后其他调试设置没有地方放。

## 提案

### 页面结构

| 位置 | 内容 | 谁决定 |
| --- | --- | --- |
| 「构建、执行、部署」分组页 | 目录：子页列表、每页的状态摘要、最上面的问题汇总 | 宿主 |
| 「工具链」固定子页 | 所有插件注入的工具 | 宿主固定页面，行来自插件声明 |
| 「调试器」固定子页 | 支持单步过滤的调试器，以后其他调试设置按标签页加 | 宿主固定页面，行来自插件声明 |
| 插件页 | 构建工具、编译器等插件用 `page` 声明的页面 | 插件声明，种类和位置由宿主按[设置页分类](../../implemented/feature/2026-10-15-macos-settings-hierarchy.md)决定 |

插件页的折叠规则：同一种类不到 3 个页面时直接列在侧栏；3 个以上才二级折叠（沿用设置页分类笔记的规则）。折叠里最多显示 6 项，其余进「全部 N 个…」目录页。目录页可以搜索、按需渲染，每行写明提供插件。分组折叠时，问题数显示在分组标题上。

**按需渲染**是指只创建窗口里看得见的那几十行，滚动时复用；列表有 5,000 行时，界面上始终只有二十几行。

### 插件怎么注入

| 插件声明 | 编号 | 出现在哪里 |
| --- | --- | --- |
| `toolDefinitions`（工具定义） | API-23 | 「工具链」页的一行，按类别分组 |
| `requiresTools`（插件需要的工具） | API-23 | 插件页里的工具引用：链接到「工具链」页对应的行，不自己放选择框 |
| `commandInstallers`（缺命令时用哪个工具安装） | API-23 | 工具行出问题时就地给出「用 Homebrew 安装…」这类按钮 |
| `debugAdapters[].features`（调试器支持的功能） | API-30 | 「调试器」页左侧的一项，右侧只显示它声明支持的开关 |
| `settings[]` 和 `settingActions[]` 的 `page`（设置页） | API-19 | 侧栏插件页，按种类放 |
| 页面里的界面树和画布节点 | API-13 | 插件页正文，见上面链接的笔记 |

同一个 JDK 只在「工具链」一处选。插件页需要 JDK、Maven 这类工具时，按工具 ID 引用，点击跳到工具链并选中那一行。

### 工具链页

- **作用域**放进工具栏，常驻的两段说明收进 ⓘ。两个作用域的草稿分开保存，有修改的作用域带蓝点，可以随时切换。
- **列表**一行一个工具，行高 46 像素，按需渲染。筛选、分组、排序和计数由 Core 算好（Core 投影，即 Core 按当前筛选条件给出结果列表和计数），平台只取可见的那一段。
- **筛选**：文字筛选（名称、版本、路径、插件），加上「需要处理 / 已手动指定 / 未应用」。「需要处理」汇总未找到、版本不满足、检测失败、需要信任和冲突；组内也按问题优先排序。
- **分组**默认按类别，也可以按插件。插件自用运行时（语言服务器用的 JDK、gopls、clangd 等）默认折叠；出了问题照样计入「需要处理」和组标题的角标。
- **候选安装**用单选列表代替「下拉框加下方重复几行」。版本、路径、来源（PATH、JAVA_HOME、SDKMAN 等，由插件给出）各占一列。不满足要求的候选灰显并写明原因，原因码全部翻译。第一项写成「自动（实际生效值）」或「继承（全局默认 · 版本）」。
- **当前生效**只显示工具实际在用的值；草稿另起一行「应用后」，不把草稿当成生效值。
- **「为什么是这个？」**把 Core 已有的决策链（`tool.Trace`）按层展示：项目指定 → 项目环境 → 全局默认 → 自动发现。
- **问题就地处理**：未找到时，如果插件声明了安装器，直接给安装按钮；冲突时引导到插件页。
- **项目信任**只在「当前项目」作用域、确实有工具来自项目内环境时才出现；信任后在工具栏显示状态和「撤销」。

### 调试器页

左侧列出声明了单步过滤的调试器，右侧编辑。「不进入的类」改成逐条列表，添加、删除不用手改多行文本；标题改成通用的「不进入的代码」，写法示例由插件给出，宿主不写 Java 专用的“类”。

### 提交和搜索

- 提交统一走窗口底部的「应用 / 好」，并写明写入目标和作用域。去掉卡片里的「保存」和「使用自动」；单个工具用「恢复自动 / 恢复继承」。
- 侧栏搜索同时命中设置页、工具、调试器和插件页声明的关键词，点结果直接跳到对应工具并选中。

### 契约缺口

下面的字段现在的契约里没有，需要在 Core 契约 PR 里补。字段名都是示意。

| 缺口 | 编号 | 用途 |
| --- | --- | --- |
| 工具定义加可选的 `category` | API-23 | 宿主固定的类别表，只用来分组显示；不声明时归“其他” |
| 工具定义加可选的 `audience` | API-23 | 区分用户工具和插件自用运行时 |
| `settingPage` 加 `debugAdapterID` | API-19、API-30 | 插件把调试设置挂到「调试器」页的对应调试器下；现有字段只有 `languageID`、`buildSystemID`、`compilerID` |
| 界面树加工具引用节点 | API-13，沿用 API-33 的 `type:"tool"` | 插件页按工具 ID 引用工具链 |
| 页面加 `keywords` | API-19，文字按 API-37 本地化 | 侧栏搜索命中插件页 |
| 注册表上限按 5,000 个插件定 | —（Core 内部上限，不是插件 API） | 现在 Core 的上限是 128 个插件、512 个工具定义、256 个提供者，单个插件的 `toolDefinitions` 最多 32 个 |

「按插件」分组不需要改契约。

### 正确做法

- Gradle 插件声明 `toolDefinitions`（Gradle，`category` 为构建工具）和 `requiresTools`（JDK）。宿主在「工具链」的“构建工具”组里放一行 Gradle；Gradle 插件页里的 JDK 显示为工具引用，点一下跳到工具链里的 JDK 行。
- lldb 插件声明 `debugAdapters[].features` 支持单步过滤，宿主在「调试器」页列出 lldb-dap；插件不需要写任何页面。

### 不要这样做

- 不要在宿主里按插件名或构建工具名加专用页面或专用分组。
- 不要让插件页自己放 JDK 选择框，让同一个工具在几个页面各选各的。
- 不要在卡片或插件页里放自己的保存按钮。
- 不要把草稿值显示成当前生效值。

## 考虑过的备选方案

### 保留一页长列表，卡片改成可折叠

改动最小。但页面高度仍然随插件数量增长，几千个插件时滚动条失去意义；问题工具也只能靠用户自己往下找。不采用。

### 每个插件一个页面，工具放在各自插件页里

插件作者最自由。但 JDK 这类工具会被几个插件各自选一次，用户不知道哪个生效；侧栏也会有几千个入口。不采用，工具统一放「工具链」，插件页只做引用。

### 宿主为常见构建工具写专用页面

Maven、Gradle 的页面可以做得很细。但这违反“宿主不为具体语言或构建工具写专用页面”的规则，新构建工具也得等宿主发版。不采用。

## 验收标准

- 插件数量从 10 增加到 5,000 时，「构建、执行、部署」分组页和「工具链」页的高度只跟子页数量有关，列表同时存在的行数不超过可见行数加少量缓冲。
- 「需要处理」筛选能找出未找到、版本不满足、检测失败、需要信任和冲突的工具，计数和组标题角标一致。
- 同一个工具的路径在一行和它的详情里只出现一次；原因码全部有中英文案。
- 草稿只显示在「应用后」；点「应用」后重新读取，「当前生效」才变化。
- 两个作用域的草稿分开保存，切换作用域不丢草稿。
- 插件页引用的工具能跳到「工具链」并选中对应行。
- 侧栏搜索能命中工具、调试器和插件页关键词。
- 宿主代码里没有按插件 ID 或工具 ID 写的分支。
- 运行 `node scripts/i18n/verify-app-language-localization.mjs` 和 `node scripts/i18n/generate-i18n.mjs --check`。

## 风险

- Core 的注册表上限要大幅提高，插件加载、工具发现和投影计算的耗时要先测。工具发现应按需、按可见行做，不在打开页面时探测全部工具。
- 类别表由宿主固定，新出现的工具种类只能先归“其他”，类别表需要随版本补充。
- 实现时需要同步更新[设置页分类](../../implemented/feature/2026-10-15-macos-settings-hierarchy.md)的二级折叠规则（折叠最多 6 项、「全部 N 个」目录页），并更新跨平台功能矩阵。
