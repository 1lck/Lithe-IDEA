# Agent 笔记：Viva 编辑器的性能基线与预算

状态：已实现

## 先说结论

编辑器随 #1794 / #1799 迁入 Viva（Go 写的桌面端），旧 macOS 和 Windows 的性能基线脚本随旧客户端一起删除，编辑器因此没有任何性能数据。现在有一套无头 Go 基准（benchmark，用固定输入反复执行一个操作，并记录耗时和内存分配的 Go 测试），覆盖文本存储、语法染色和编辑器视图三层；每一项都对照 `desktop/benchmarks/editor-budgets.json` 里带理由的预算判定，预算取最高标准。基线只在本地运行，结果是报告而不是门禁：改动编辑器模块的人在同一台机器上改动前后各跑一次，把对比写进 PR，新引入的超预算结果要逐项解释。第一次测量就发现了六处缺陷，它们靠读代码都没有被发现。

## 问题

编辑器最贵的一类问题是“与文档大小成正比的工作”：每次按键、每次撤销或每次打开文件，都去处理整篇文本。它在 100 KiB 的文件上察觉不到，在 10 MiB 的文件上就变成按键卡顿。绘制和输入又是热路径（每一帧、每一次按键都会执行的代码），一次多余的内存分配会被放大成每秒几百次。迁移到 Viva 之后，这些既没有基线，也没有预算，没有人能回答“编辑器到底快不快”。

第一次测量暴露了六处缺陷：

1. 每次按键都把整篇文档和已保存的版本各复制成字节切片再比较，按键成本与文档大小成正比。
2. 撤销和重做把放回的旧版本当成一篇新文本：重新扫描每一行的宽度，高亮器丢掉全部状态从头分词，折行布局整个丢掉等下一帧重算，同样与文档大小成正比。
3. 打开和重新加载在窗口线程（处理输入和绘制的线程，被占用时界面就卡住）上建 rope（用树存放文本的数据结构，在中间插入不必搬动整篇）并扫描每一行的宽度。对用制表符缩进的 Go 文本，行宽扫描还对每一行在树里查了两次，并复制了大量行。
4. 每次重绘都在分配内存，每帧 113 到 152 次（随文本形态变化）：复制行、拼标签字符串、格式化行号。
5. 在超长的单行（例如压缩过的 JSON）上，一帧会把整行复制一遍。
6. TextMate 分词器（把源码切成带语法类别的片段，用于染色）的整篇吞吐远低于 20 MB/s 的预算。

修复第 3 处时读代码还发现：视图通过配置一直持有打开时的原始字节，真实打开路径上多占约一份文件大小的内存。常驻内存基准自己也持有输入字节，所以测不出这一处；它说明基准只能抓到它覆盖的东西，读代码仍然必要。

修完之后复核剩下的超预算结果，又发现基准自己测错了两处，一共造成 15 项超出：

- 绘制和滚动基准把准备视图的几帧画在另一块画布上，计时循环从一块新画布开始，首帧为画布扩容的几十 KB 被平摊进每一帧，在 0 字节的预算上显示为每帧 1 到 40 字节。证据是迭代次数从 2000 增加到 8 万时，每帧字节数从 198 降到 4，总量保持在约 350 KB。
- 输入染色基准在两种规模下各自编辑文档的中间行，100 KiB 那行是注释，10 MiB 那行是代码，规模比因此在 0.42 到 5.93 之间跳动，比较的是两行内容，而不是文档大小。

两处都按场景本来的定义修正，预算、场景和文档都没有改。超出预算的结果要先查清原因再接受：它可能来自编辑器，也可能来自基准。

这六处在没有数据时都没有被当成问题。方法上还有一个要求：不同的人、不同的机器和以后的提交，必须拿到同样的输入和同样的判据，结果才能比较。

## 决策

开发者怎么做：改动 Viva 编辑器模块前先读[编辑器性能基线](../../../skills/develop-lithe/references/editor-performance.md)，它是规则、数值、命令和读报告方法的真源；在同一台空闲机器上改动前后各运行一次基线；把对比写进 PR 说明，并逐项解释新引入的超预算结果。本 Note 只解释这套机制为什么这样设计。

### 基准文档由生成器合成

基准用的文档由 `desktop/internal/editor/editorperf` 按固定种子生成，不读磁盘、不下载，也不把几十兆的夹具文件提交进仓库。伪随机数用 splitmix64（一个几行就能写完的随机数算法）手写实现，不用标准库的 `math/rand`，因为 `math/rand` 对同一个种子产生的数列允许在 Go 版本之间改变，那样同一个“10 MiB Go 文档”在不同的 Go 版本下就不是同一份文本了。

文档有六种形态：Go、Java、JSON（整篇只有一行）、Markdown（含中文）、日志，以及混合文本（CRLF、制表符、中文、emoji、超长行）。小文档是 100 KiB，大文档默认 10 MiB，可用环境变量 `LITHE_EDITOR_PERF_LARGE_BYTES` 或脚本参数 `--large-bytes` 调整，例如 50MiB。小文档是大文档的前缀，所以同一个场景在两种规模下处理的是同一份文本，两者的比值才能说明“耗时是否随文档增长”。

### 三层基准

基准名按 `BenchmarkEditor<层><场景>/<变体>/<规模>` 命名，一共 110 项结果：

- `desktop/internal/editor/rope`：建树、成对插入删除、按行号找行首、按偏移找行号、取视口内的行、取全文字节。
- `desktop/internal/editor/syntax`：视口染色的冷读和暖读、输入后的染色、输入后的补染、整篇分词、首次使用。
- `desktop/internal/editorview`：绘制（纯文本、Go、Java、折行、小地图、超长行、中文、混合、选区、标记等变体）、按键、回车、撤销重做、光标移动、翻页、滚动、粘贴 1 MiB、打开、重新加载、重新折行、常驻内存。

分层的目的是定位：如果视图层变慢而文本存储层没变，问题在视图里；反过来则在文本存储里。

### 预算取最高标准，并且每条都写理由

产品决策是编辑器必须高性能，所以预算按“最高标准”设，而不是按“当前能做到”设：绘制和滚动 0 次分配、0 字节、不到 1 ms（120 Hz 屏幕一帧只有 8.3 ms，编辑器只是其中一部分）；一次按键连同下一帧不到 1 ms；打开文件时窗口线程上的部分不到 2 ms；后台整篇分词不低于 20 MB/s；一个文档的常驻内存不超过 2 MiB 加 1.5 倍文本字节。

预算文件里每个基准家族一条，每条都带 `why`，说明这个数字为什么合理。上限有三种写法：绝对值（纳秒、分配次数、分配字节）、随文本字节线性增长（一个常数加每字节若干纳秒），以及规模比（大文档结果除以小文档结果，用来抓出“与文档大小成正比”的工作）。

耗时上限只在参考机（Apple M4，标签 `m4-mbp`，类别 `physical`）上判定，因为耗时取决于机器，在别的机器上判定会制造误报。分配次数、分配字节和规模比与机器速度无关，在任何机器上都判定。所以在没有参考机的开发机上，一个“每次按键复制整篇文档”的缺陷仍然会被规模比和分配字节抓出来。

### 结果是报告，不是门禁

超出预算的结果只写进报告，不会让脚本失败；只有基准编译不过、运行 panic 或输出读不出来时脚本才失败。报告把每一项标成 within、over、not judged（有预算但当前机器上没有任何一项能判定）或 no budget（没有匹配的预算）。基线也不是 CI 必跑项：CI 的 Linux 任务只检查脚本语法、ShellCheck 和报告生成器的 `node --test`，从不运行基准。

“只报告”不等于“可以放松”：不得为了让报告好看而上调预算、删除场景、缩小文档规模或改动生成方式。已有的超预算结果不要求在同一个 PR 修复，但新引入的必须解释。

### 运行、记录和对比

`scripts/desktop/perf/editor-bench.sh` 有四个子命令：

- `run` 运行基准，把原始输出和 Markdown 报告写到 `.artifacts/editor-perf/`。
- `record` 用更多样本运行，并通过 Viva 的 `tools/perfhistory` 追加到随仓库提交的 `desktop/benchmarks/history/<机器>.jsonl`。1 分钟平均负载超过 CPU 核数的四分之一时它拒绝运行，因为 Viva 实测过同一个基准在负载约 10 时从 35 微秒变成 134 微秒，在忙碌的机器上记录的历史会掩盖或凭空制造回归。
- `compare` 调用 `perfhistory compare`，阈值 15%，忽略 20 ns 以下的结果。
- `report` 对已有的输出文件重新生成报告。

### 范围

基线不测补全、诊断、diff 和搜索，因为这些功能还没有做完；它们落地时补场景，触发条件见“后果”。

基线也不包含真实窗口、GPU、进程常驻内存，以及与 VS Code、Zed 的对比。这几项都要启动真实应用、打开同一份文件并等它显示出来：Lithe 桌面端目前不能从命令行打开文件，判断“已经显示”需要界面自动化，而界面自动化需要辅助功能权限。无头基准不能代替这些测量。

### 正确做法

- 绘制路径交给画布的字符串，取自已经存在、不会再变的内存。rope 的叶子是不可变字符串，落在一个叶子里的行和行里的一段直接是它的子串；跨叶子的行拼接一次后按文本版本缓存；行号取自一段预先格式化好的行号窗口。稳定的帧因此 0 次分配：

  ```text
  line  = rope.Line(n)              // 落在一个叶子里时是叶子的子串，不复制
  label = line[from:to]             // 标签是行的子串，制表符和控制字符处断开
  canvas.DrawText(label, pos)
  canvas.DrawText(numbers.Of(n), gutterPos)   // 行号窗口里的子串
  ```

- 一次按键后判断“文档是否已修改”时，让文本存储自己比较树，或增量维护一个修改标记，代价只取决于这次改动：

  ```text
  doc.Edit(change)
  dirty = doc.DiffersFromSaved()   // 在树上比较，不复制整篇文本
  ```

- 撤销和重做放回的是同一篇文本的另一个版本，两者共享没被编辑过的节点。先找出改动的区间，再像一次普通编辑那样让高亮器、折行布局和长行缓存只更新这一段：

  ```text
  start, oldEnd, newEnd = rope.Diff(current, restored)   // 跳过共享节点，只读改动附近的叶子
  view.text = restored
  highlighter.Edit(restored, start, oldEnd, newEnd)      // 不是 SetText，保留其余各行的状态
  layout.Splice(lineOf(start), ...)                      // 不是丢掉整个布局
  ```

- 打开大文件时，建 rope、扫描行宽和检测缩进都放到后台，窗口线程只接收准备好的结果。

### 不要这样做

- 不要用 `unsafe` 把复用的缓冲直接当成字符串交给画布。Viva 画布会跨帧保留标签并按内容比较；缓冲在下一帧被改写后，画布保留的旧标签和新标签指向同一块内存，比较永远相等，变化发现不了，画面可能停在旧内容上：

  ```text
  buf = view.numberBuf[:0]
  buf = appendInt(buf, n)
  label = unsafe.String(&buf[0], len(buf))   // 下一帧 buf 被覆盖，旧标签跟着变
  canvas.DrawText(label, pos)
  ```

- 不要在每次按键里把整篇文档和保存版本复制成字节切片再比较。这样每次按键都是 O(文档大小)，在 10 MiB 的文件上就是一次明显的卡顿：

  ```text
  cur = doc.Bytes()                 // 复制整篇
  saved = savedDoc.Bytes()          // 再复制整篇
  dirty = !bytes.Equal(cur, saved)
  ```

- 不要用耗时的“感觉”或没有同一台机器、同一规模对照的数字写“更快”或“更省内存”。

## 考虑过的备选方案

### 把基线作为 CI 必过的门禁

门禁能让超预算的改动无法合入，最有吸引力。没有采用：共享 runner 的性能抖动大，绝对预算在上面无法可靠判定；macOS 分钟数昂贵；仓库还曾因 GitHub Actions 用量过高被判定为滥用。所以基线只在本地运行，由 PR 说明里的前后对比和评审来把关，CI 只保证脚本和报告生成器本身没有损坏。

### 提交夹具文件

直接把测试用的大文件提交进仓库最直观，也不需要生成器。没有采用：10 MiB 以上的文件会让仓库膨胀，而且大小要能配置（例如换成 50 MiB），夹具文件做不到。确定性的生成器在任何机器上给出同样的字节，规模随时可调。

### 只和上一次结果相对比较，不设绝对预算

相对比较不需要决定“多快才够快”，实现也简单。没有采用：编辑器如果每次慢一点点，每一次相对上一次都能通过，累积起来却越来越差。绝对预算说明了“快”的标准，相对比较（`compare`）只作为补充，用来抓单次改动引入的回归。

### 用 `math/rand` 生成文档

标准库现成，不用手写随机数。没有采用：`math/rand` 对同一个种子给出的数列可能随 Go 版本变化，那样基准文档在升级 Go 之后悄悄变了，历史数据就不可比了。手写 splitmix64 的输出完全由代码自己决定。

### 只通过真实窗口测量

真实窗口最接近用户看到的结果。没有采用为基线：无头 Go 基准可复现、成本低，能在每次改动前后快速运行；窗口、GPU 和进程常驻内存的测量受显示器、驱动和系统状态影响，很难稳定。真实窗口、GPU 以及与 VS Code、Zed 的对比是另一类测量，无头基线不替代它们。

## 后果

- 收益：编辑器第一次有了可重复的数据。第一次测量发现的六处缺陷里，输入、撤销、打开、绘制和超长行五处已经修复，分词器提速但仍超预算。在 10 MiB 文档上，一次按键从 678 µs 降到 46 µs，撤销一次从 225 ms 降到 46 µs，打开 Go 文件时窗口线程上的部分从 224 ms 降到 1.04 ms，粘贴 1 MiB 从 250 ms 降到 3.6 ms；稳定的一帧从 113 到 152 次分配降到 0 次。“与文档大小成正比”的缺陷能被规模比和分配字节在任何机器上抓住，不依赖参考机。每条预算都有理由，评审可以直接争论数字，而不是争论感觉。
- 代价：耗时上限只在 Apple M4 参考机上判定，其他机器上只能看到分配和规模比，耗时项显示为 not judged。基线靠开发者自觉在本地运行，没有自动拦截，需要评审检查 PR 说明里是否附了对比。
- 代价：记录历史必须在空闲机器上做，运行期间不能编译或运行其他程序；`desktop/benchmarks/history/<机器>.jsonl` 会随记录次数增长并提交进 Git。基准文档的生成方式一旦改动，历史数据就不再可比，所以生成方式和预算都不得随意修改。
- 已知状态：TextMate 分词器的整篇吞吐目前是 Go 约 1.9 MB/s、Java 约 2.5 MB/s、Markdown 约 6.9 MB/s，远低于 20 MB/s 的预算。正则引擎跳过不可能匹配的起点之后，整篇分词快了 7% 到 21%；剩下的时间主要花在回溯匹配本身，要达到预算需要换掉回溯执行方式（例如不回溯的引擎或记忆化）。报告里会持续显示这三项超出，直到分词器本身被改进；预算不因此调低。
- 重新评估的触发条件：补全、诊断、diff 或搜索功能完成时增加场景；与 VS Code、Zed 的对比或真实窗口测量开始时，确认两者的边界；有稳定、独占的测量机器（例如自托管 runner）时，重新评估是否把部分检查放进 CI；参考机更换时，重新建立历史记录。

## 验证

- `scripts/desktop/perf/editor-bench.sh run`：运行全部基准并生成报告；报告里每一项都能给出判定状态，超预算项只报告。
- `node --test scripts/desktop/perf/editor-perf-report.test.mjs`：校验报告生成器和 `editor-budgets.json`（格式、模式不互相遮蔽、判定逻辑）。
- `go -C desktop test ./internal/editor/editorperf`：校验文档生成器的确定性和小文档是大文档前缀。
- `node --test --test-name-pattern='editor performance reports' scripts/resources/test-reuse-worktree-resources.mjs`：校验 `.artifacts/editor-perf/` 下的输出登记为不可复用，复制入口拒绝它。

- 第一次记录的完整结果在 `desktop/benchmarks/history/m4-mbp.jsonl`；六处缺陷各自修复前后的数字在对应的提交和 #1799 的 PR 描述中。
