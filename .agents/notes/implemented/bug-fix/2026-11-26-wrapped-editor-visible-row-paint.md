# Agent 笔记：自动换行编辑器只遍历可见折行

状态：已实现

## 先说结论

一行压缩 JSON 可以换成数万显示行。编辑器绘制时直接从首个可见显示行开始，避免每帧遍历视口上方的所有折行。以后修改折行绘制时，保留按逻辑行计算的坐标和提示位置，只限制遍历起点，不重建整行布局。

## 问题

逻辑行是一段以换行符结束的文本；显示行是自动换行后屏幕上的一行。`View.Paint` 已经通过行索引得到首个可见显示行，却仍从逻辑行的第一个折行开始循环，逐个计算纵坐标并跳过不可见部分。滚动到超长行底部后，每次输入和重绘都为同一段不可见前缀付出线性成本。

## 决策

- 复用现有行映射给出的首个可见折行序号，只有视口中的第一个逻辑行从该序号开始；后续逻辑行仍从第一个折行开始。
- 保留逻辑行起点、原折行序号和整行折行切片。字节边界、提示、组合输入、选区、行号与末行注释继续使用原坐标。
- 保留上下边界检查，使部分可见行和恰好处于边缘的行仍遵守原裁剪规则。
- 新增长行深滚动重绘基准，和既有输入基准共同防止不可见前缀重新进入热路径。

正确做法是复用已经算出的可见起点；不要先遍历或复制全部折行，再对结果做裁剪。

## 考虑过的备选方案

- 保留从零遍历，继续依靠 `continue` 跳过：只减少实际绘制，仍保留与前缀长度成正比的循环。
- 切掉折行切片前缀后将序号重新从零计数：会改变下一折行字节边界、组合输入和内联提示使用的整行序号。
- 绘制时重建一份可见行列表：已有映射可以直接定位，新增列表会增加分配或缓存失效边界。

## 后果

热循环只访问可见折行及下边界，深滚动后重绘不再为不可见前缀逐行计算坐标。没有新增缓存、每帧分配、Core 命令或持久状态；首次折行和编辑后的布局计算仍由原实现负责，这次不改变它们的复杂度。

## 验证

- `TestDeepWrappedViewportMatchesShortSuffix` 对比深滚动与相同短后缀的实际文本、裁剪及选区矩形，覆盖整行和部分可见行、跨逻辑行底部。
- `scripts/desktop/desktop-go.sh test ./internal/editorview` 覆盖折行、折叠、内联提示、组合输入、行号及绘制语义。
- `scripts/desktop/perf/editor-bench.sh run --bench '^BenchmarkEditorView(Paint|Type|Scroll)' --count 6` 在同机前后比较；文档规模和预算不变，绘制和滚动保持零分配。
