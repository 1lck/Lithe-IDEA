# Agent 笔记：Viva 调试会话的进程退出与取消清理

状态：已实现

## 先说结论

调试适配器可能直接退出，不能只等调试协议的结束事件才清理。宿主必须同时观察原生进程退出，并在停止时解除管道写入、等待正在创建的 Core 会话返回后销毁它。旧会话迟到的结果不得修改新会话。

## 问题

调试适配协议（DAP）负责调试语义，但进程崩溃时不保证发送 `terminated`。把 Go 内存管道作为子进程标准输入，会让 `exec.Cmd` 创建输入复制任务；输入源没有关闭时，进程已经退出也可能卡住 `Wait`。

停止与创建并发时，先销毁再收到创建成功会留下 Core 会话。后台复用局部结果变量，再让界面回调读取它，也会产生数据竞态。

## 决策

- 使用原生文件管道作为适配器标准输入，宿主拥有并关闭父进程端；取消和有界写入超时都关闭管道。
- 同时观察进程退出与协议结束。清理幂等，立即停止进程和写入，再等待启动任务结束后销毁 Core 记录；等待退出观察器回收。
- 会话 ID 跨项目唯一，界面结果按项目、会话身份和代次核对。投递给界面的结果使用独立值快照。
- 正确示例：用户点击停止，创建调用迟到成功，清理任务随后销毁该 ID。不要先销毁尚不存在的 ID 就认为完成。

## 考虑过的备选方案

只等待 DAP 结束事件无法覆盖崩溃；把无界 `Wait` 放进后台任务也不能解除输入复制任务。继续使用内存管道会增加一个需要额外管理的复制任务，因此这里使用原生管道。取消后只丢弃界面结果也不够，仍须回收 Core 会话和进程。

## 后果

异常退出和停止可以释放本次会话，旧错误不会污染重启后的界面。代价是宿主需要维护启动完成和退出观察器的同步信号；写入超时会关闭会话管道，不能继续复用。此约束只解决传输与生命周期，不代表真实程序的启动配置、运行时适配或完整调试能力已经接线。

## 验证

`desktop/internal/workbench/debug_test.go` 覆盖无结束事件的退出、旧错误迟到、创建返回前停止、取消阻塞写入，以及正常断点/暂停/继续流程。前两项在修复前失败，修复后通过。

```bash
scripts/desktop/desktop-go.sh test -race ./internal/workbench -run TestDebug -count=1 -timeout=90s
```

## 适用范围

`desktop/internal/workbench/debug.go` 与 `desktop/internal/buildprocess/process.go` 的原生 stdio 调试路径。DAP 帧解析与状态规则仍由固定版本的 Rust Core 负责。
