# Agent 笔记：悬停打开“打开于”时也要查询应用

状态：已实现

## 先说结论

项目树右键“打开于 › 打开方式”有时一直显示“正在查找应用…”，永远不列出应用。原因是查询用 `ui.C.After`（Viva 的“绘制结束后再执行”）推迟启动，而鼠标停留打开子菜单的那一帧不是点击，Viva 会丢掉推迟的回调，查询从未开始。现在查询在声明子菜单的那一帧里直接启动；凡是“子菜单或面板一打开就要做的事”，都不要交给 `ui.C.After`。

## 问题

用户把鼠标移到“打开于”上停一下，子菜单就会展开，这是最常见的打开方式。Viva 的子菜单在指针停留 100 ms（`submenuDelay`）后，通过一次普通的重绘展开；这次重绘没有送达任何点击或指针事件。

`ui.C.After` 的约定是：只在送达点击或指针事件的那次绘制之后运行回调（`gfx.Canvas.AfterPaint` 只在 `eventPass || hasPointer` 时登记），其他绘制里直接丢弃。旧代码 `askTreeApps` 在子菜单刚出现时调用 `c.After(func() { a.findTreeApps(file) })`：

1. 悬停展开的那一帧里，回调被丢弃，查询没有开始。
2. 这一帧结束时，`treeApps.endFrame` 已把“子菜单正在显示”记为真。
3. 之后的每一帧都认为“已经问过了”，不再发起查询。
4. “打开方式”看到还没有这个文件的结果，就一直显示“正在查找应用…”。

只有点击“打开于”时，子菜单在点击的事件处理阶段展开，回调才会运行，所以点击打开时一切正常。原有测试全部用点击打开菜单，没有覆盖悬停这条路径。系统查询本身很快（实测约 20 ms），与卡住无关。

## 决策

`askTreeApps` 在子菜单刚出现（或换了文件）的那一帧里直接调用 `findTreeApps`。`findTreeApps` 只登记状态，再用 `a.background` 在后台线程查询，结果经 `a.post` 回到窗口线程；它不会阻塞绘制，所以可以在绘制中调用。工作台已有同样的做法：状态栏内存详情在绘制中直接发起后台读取（`debug_memory.go`）。

正确做法：子菜单、弹窗或面板一出现就要开始的后台工作，在声明它的那一帧里直接启动，并用状态（例如 `loading`）防止重复启动。

```go
if !m.shown || m.file != file {
	a.findTreeApps(file) // 只登记状态并启动后台任务
}
```

不要这样做：用 `c.After` 推迟这类工作。`c.After` 只适合点击、选择变化这类事件处理里的后续动作；放在“打开即执行”的位置，悬停、键盘或程序触发的展开都会悄悄丢掉它，界面停在加载状态。

## 考虑过的备选方案

- 改用 `a.post` 推迟到下一次唤醒：同样能避开丢弃，但多绕一次唤醒，而 `findTreeApps` 本来就不阻塞绘制，没有必要。
- 改写成 Viva 的副作用钩子（`ui.Effect`，按声明的键启动后台工作，键变化时取消旧的；工作台的 `keyedEffect` 封装了它）：同样不经过 `c.After`。但它对同一个键只运行一次，而“打开方式”每次重新打开菜单都要重新询问系统，以便反映用户刚修改的关联；改用它还要另写菜单关闭时的复位和失败日志，改动面比修复本身大，这次不做。
- 在 Viva 里让 `ui.C.After` 在普通绘制中也运行：Viva 的文档写明它只服务于点击和指针事件的后续处理，这是有意的约定，不是缺陷，不应改动。

## 后果

- 悬停和点击打开“打开于”都会立即查询，列表在几十毫秒内出现。
- 每次子菜单出现仍只查询一次；同一文件查询进行中时不重复发起。
- 回归测试 `TestProjectTreeOpenWithListsTheApplicationsWhenOpenedByHover` 用指针停留打开两级子菜单，修复前失败（系统未被询问），修复后通过。
- 如果以后 Viva 修改子菜单的展开方式（例如在指针事件中直接展开），这条规则仍然成立，不需要重新评估。

## 验证

- `../scripts/desktop/desktop-go.sh test ./internal/workbench -run 'TestProjectTreeOpen' -count=1 -v`（在 `desktop/` 下运行）：包含悬停打开的回归测试和原有的点击用例。
- 手工验证：在项目树里右键一个文件，把鼠标移到“打开于”上停住，再移到“打开方式”，应列出系统应用，而不是一直显示“正在查找应用…”。
