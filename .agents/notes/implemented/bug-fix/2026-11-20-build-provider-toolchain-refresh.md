# Agent 笔记：保存工具链后刷新构建提供者

状态：已实现

## 先说结论

独立构建提供者（在后台常驻、执行插件构建或测试请求的进程）在启动时绑定工作环境。
通过宿主工具链启动的提供者会在项目 pin 或全局默认值保存后重新启动，独立窗口进程也能读取新值。
已提交的请求由旧进程处理完。初始化期间发现配置已变更会在原请求期限内重新启动。

## 问题

原来进程复用只比较插件设置，不比较宿主保存的工具链。即使设置页已显示新程序，
仍可能由旧进程执行下一次测试任务。

## 决策

启动器先执行 Core 的启动计划。在实际解析宿主工具前，工作台才读取来源文件的身份和内容，并把
这份版本记入会话复用键。项目 pin 只影响读取该项目来源的实例，
全局目录里的工具链配置影响共用该目录的实例。复用前和初始化完成后均核对文件版本。
无变化的保存不改文件。原子替换即使恢复相同的内容，也会因文件身份变化被识别。
直接运行打包程序或打包运行时的提供者沿用插件设置复用键，工具链文件读取失败时仍可运行。
与语言服务器共享的提供者继续走语言服务器的启动与复用机制。

旧进程在后台排空。退役进程和项目关闭时仍在清理的进程继续登记在工作台，直至完成原生销毁。
例如卸载插件时先阻止新启动，等登记中的相关进程退出，再删除包及状态目录。切换项目时
记录所属项目，避免关闭旧项目的任务影响新工作台的会话。

## 考虑过的备选方案

保存时主动停止所有会话会取消正在执行的任务。只递增进程内计数又无法覆盖使用相同配置目录
的独立窗口。测试、模型和依赖查询共用提供者，所以在宿主复用入口检查来源。

## 后果

依赖工具链的会话按请求读取既有的有界配置文件。读取版本本身只访问这两个文件。
来源更新时会重新解析并启动，即使改动的是同一个来源中的另一个工具。连续三次读取或启动
均被来源变动打断时，返回工具链冲突供用户重试。

## 验证

在 `desktop/internal/workbench/build_provider_restart_test.go` 使用 Core 的运行时启动计划验证项目 pin
保存和重复保存、另一个客户端写入、初始化期间保存、已有请求排空，以及卸载前等待退役进程销毁。
初始化重试用例检查两次启动的可执行文件路径。打包提供者用例覆盖项目和全局配置文件无法读取时的
复用和重启。共享提供者选用语言服务器的行为见 `desktop/internal/pluginbackend/pluginbackend_test.go`。
原生窗口的验证动作是先用旧工具执行，再保存新工具并重跑，核对两次实际启动的路径。

## 适用范围

Viva 两端共用的宿主进程管理。Core 的选择规则、插件契约和界面文案不变。
