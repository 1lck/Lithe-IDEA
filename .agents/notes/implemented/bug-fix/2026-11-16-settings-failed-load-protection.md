# Agent 笔记：设置文件读取失败后不得被默认值覆盖

状态：已实现

## 先说结论

桌面端使用默认值继续启动，不意味着磁盘中的设置文件可以被默认值替换。存储层读取或解码 JSON 文件失败后，禁止覆盖该文件以保留原始内容。只有成功重新读取、确认原文件不存在或明确删除后才恢复保存。

## 问题

#1943 中，损坏的 settings.json 会使 workbench.New 使用默认设置；之后修改主题等偏好触发 saveSettings，用新的默认值原子替换文件。原子写入只防止写入中断，不能阻止使用无效读取结果覆盖原始设置。

## 决策

### 正确做法

- desktop/internal/store/store.go 按文件名记录最近一次 Load 的致命读取/JSON 解码错误，Save 遇到该状态时返回错误，不调用 WriteFile。保存失败沿用已有日志与通知。
- Load 成功、文件不存在或 Remove 确实成功（包括本来不存在）时清除保护；删除失败不得清除保护。
- 未知键或当前版本不兼容的字段类型仍交由现有 kept/Unread 保存原值；这种可恢复读取不阻止保存。
- 不同设置文件相互独立，某个文件损坏不应阻止其他文件保存。

### 不要这样做

- 不要在加载失败后直接用默认值保存损坏文件；这会删除未损坏的旧设置。
- 不要把可恢复的字段类型不兼容误判为致命失败；否则跨版本保留失效。

## 考虑过的备选方案

### 自动备份后覆盖

可以继续保存，但要解决备份命名、并发写入和回滚等问题；目前优先保护原文件且不制造额外写入。

### 只在工作台层跳过保存

改动范围小，但其他 Store 使用者仍可能在类似失败后覆盖原始文件；因此保护由存储层统一实现。

## 后果

- 原始内容保留，用户可以修复 JSON 后重新加载，或明确删除后重建。
- 在文件恢复之前，保存会返回错误，由现有调用边界通知用户。
- 不增加后台任务、下载或运行时文件，只增加按文件名保存的临时错误状态。
