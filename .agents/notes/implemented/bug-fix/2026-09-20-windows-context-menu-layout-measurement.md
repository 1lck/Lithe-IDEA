# Agent 笔记：Windows 右键菜单定位不受开场动画影响

状态：已实现

## 先说结论

弹出菜单的位置必须按完成布局后的尺寸计算，不能把动画缩小后的视觉尺寸当作实际尺寸。
文件树只传入鼠标相对窗口的坐标，统一由 `Dropdown` 根据真实菜单大小避开窗口边缘。
菜单获得焦点或父组件重新渲染时，仍须保持同一套定位结果，保证按下和松开鼠标命中同一个选项。

## 问题

#558 中，靠近窗口底部的文件菜单在点击选项时突然向上跳，第一次点击没有执行操作。
原菜单在开场动画中缩放到正常大小的 98%，同时用 `getBoundingClientRect()` 测量宽高；
该接口返回包含缩放变换的视觉尺寸。菜单获得焦点触发父组件重新渲染后，定位逻辑又测量了
动画结束后的尺寸，原本判断为能放在下方的菜单会突然改为向上弹出。

文件树还按写死的 250 × 400 尺寸提前限制坐标，使菜单定位组件收到的坐标已经偏离鼠标。
菜单项数量、字体或窗口尺寸变化时，这两层边界判断容易相互干扰。

## 决策

- 菜单本身使用 `offsetWidth`、`offsetHeight`，即不包含缩放动画的布局尺寸，
  统一计算锁定宽度、上下左右边界和最终位置。按钮锚点仍使用屏幕上的实际矩形。
- 文件树传入 `clientX`、`clientY`，让固定在窗口上的弹层使用同一坐标空间。
  调用方不得再按猜测的菜单宽高预先移动坐标。
- 保留现有动画、窗口边界监听和尺寸变化监听。内容变高、窗口调整或锚点移动时仍需重新定位；
  仅仅从开场动画进入正常状态，不应改变边界判断。

正确做法：菜单实际高 398 像素时，首次定位和点击时都按 398 像素处理。
不要把缩放后的约 390 像素用于首次定位，再在点击时改用完整高度。

## 考虑过的备选方案

- 关闭动画能绕开当前触发条件，但会取消既有交互效果，不能明确区分布局和视觉测量的职责。
- 阻止菜单项获取焦点会破坏键盘与无障碍操作，而且其他重新渲染仍会触发错误定位。
- 本次不整体迁移到基础菜单库：文件树复用的 `Dropdown` 同时服务坐标弹出、按钮锚定和可搜索菜单，
  整体替换会扩大行为变更范围。修复留在现有公共定位入口。

## 后果

边缘菜单在鼠标按下和松开之间保持稳定，普通锚定菜单也不会锁定缩放后的宽度。
布局尺寸按整数 CSS 像素返回，与最终整数坐标定位一致；如以后引入父级整体缩放，需要重新审视
锚点和菜单是否仍处于同一坐标空间。
