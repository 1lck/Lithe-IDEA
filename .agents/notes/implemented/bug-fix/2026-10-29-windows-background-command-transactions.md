# Agent 笔记：Windows 后台命令的事务与关闭边界

状态：已实现

## 先说结论

把磁盘和进程操作移到后台线程，只解决界面被阻塞的问题，还必须保护多个任务之间的顺序。运行配置保存、文件粘贴和终端创建不能继续依赖 UI 线程的串行执行。

## 问题

两个后台配置保存会共用同一临时文件，失败回滚还可能覆盖另一个任务的新值。剪切粘贴期间用户可以复制新的内容，旧任务结束后不能无条件清空剪贴板。窗口销毁后，迟到的终端创建也不能继续登记成有效会话。

## 决策

- 运行配置、生成配置和 Maven 配置共用进程内事务锁。读取回滚快照、写入、失败恢复都处于同一次持锁区间；Maven 成对配置读取也使用此锁。不要只锁单次 rename，否则多文件回滚仍会互相覆盖。生产入口持锁，底层写函数不重复取锁。
- 文件粘贴使用独立的后台互斥，从选择目标名称一直保护到复制或移动完成，避免两个粘贴选择同一目标。读取剪贴板只短暂持有状态锁，复制/剪切新内容不等待磁盘操作。
- 剪贴板每次写入都有新的内存身份。旧剪切完成时只清理它读取的那一份；即使新内容相同，也不能清除新的复制动作。身份不进入 JSON，前端契约保持不变。
- 终端窗口销毁时，在会话表内留下关闭标记并取出已有连接，后台回收连接；迟到的登记失败后复用已有 close_terminal 路径关闭刚创建的终端。标记按进程内唯一窗口 label 保存，其他窗口不受影响；未来若重用 label，需要窗口实例身份。

正确做法：A 保存失败时先在事务内恢复旧值，B 随后读取已恢复的文件。不要让 A 在 B 已成功保存后再执行旧快照回滚。

## 考虑过的备选方案

只给每次保存换临时文件名不能解决跨文件回滚交错，因此采用完整事务锁。让复制、剪切与磁盘粘贴共用同一把锁会重新卡住 UI，因此分离状态锁和后台粘贴锁。比较剪贴板内容无法区分重复复制同一内容，因此比较内存身份。

## 后果

配置保存和粘贴分别串行，不同文件的同类操作也会等待；这些低频操作的等待发生在后台。锁只协调当前 Lithe 进程，不承诺外部编辑器冲突检测。临时文件仍在用户工作区，窗口关闭标记只在内存，均不写安装目录，不影响代码签名或 Sparkle delta。终端整机进程回收仍需 Windows 验证。
