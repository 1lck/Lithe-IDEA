# Agent 笔记：Viva 插件动作注册、首次调试与运行进程回收

状态：已实现

## 先说结论

插件声明本身符合契约，也可能因为宿主接线不完整而无法显示 Run 或首次调试失败。Viva 现在把动作声明与工作区路由分开交给 Core 校验，注册变化后异步刷新文档，首次调试按需加载适配器。Run 启动的进程还会随附加调试会话在后台有界回收；Java 规则仍由独立插件和上游工具负责。

## 问题

这些路径来自 `0faecba491` 的 Viva 迁移：注册请求中的 context 被一并交给严格声明解码器，真实 Core 因额外字段拒绝；轻量假宿主没有解码器，原测试未覆盖。注册完成后也没有刷新已打开文档，动作可能要等用户再编辑才出现。

Run 发起调试时直接要求适配器目录已加载，但目录之前只会在 Debug 面板打开时加载。调试工具栏停止又只断开调试适配器协议（DAP）连接，没有回收 Run 自己启动的进程，真实 Java 调试中会留下仍暂停的 JVM（Java 虚拟机）。

## 决策

声明校验仍由 Core 严格执行；Go 只移除已经检查过的路由 context，不放宽未知字段规则。注册和撤回通知窗口排队刷新，锁内不调用插件，避免注册应答和动作查询相互等待。语言服务器就绪后也重新收集动作。

模型刷新未必修改文本，不能只凭文档文本版本接受动作查询的异步结果。窗口为每份文档持有动作呈现代际，清空或重新查询时推进它；晚到的旧结果不能覆盖新动作，也不能替换当前失败提示。Java 插件另行监听渐进导入的项目/classpath 事件并校验服务器代际，不将第一次 ServiceReady 等同于所有模块导入完毕。

Run 的首次调试复用既有适配器加载入口，完成后检查原调用是否取消。Run 原生进程所有者给附加会话一个有界停止回调，调试连接关闭后在后台调用；手动附加到外部进程没有回调，不接管外部进程所有权。

关闭项目可能同时从调试会话和工作区请求停止同一个 Run。自动清理重复到达时只保留第一次停止及退出宽限；只有用户或插件再次明确请求停止，才立即强制结束。调试清理先销毁 Core 会话，再等待 Run 的退出宽限，避免进程的较长收尾耗尽 Core 销毁的截止时间。例如，工作区和调试会话都关闭属于一次自动回收，不能等同于用户连续点击两次停止。

真实插件测试在创建工作台后就登记无交互清理，不依赖成功路径的关闭动作。即使断言在断点暂停或文档未保存时中止，也直接关闭测试拥有的项目，等待后台任务、停止剩余运行，并验证 Core 调试会话已移除；不能把需要用户确认的关闭弹窗当作失败清理。

## 项目 JDK 与语言服务器的编译目标

普通源码目录没有 Maven 的目标版本约束时，Viva 曾只把项目选择的 JDK 交给 Run，没有在后端解析语言服务器启动时传入契约已有的可选 `tools`。JDT 因而按随包 Java 21 编译，Run 却使用用户选择的 Java 8，生成的 major 65 class 会被 Java 8 拒绝。只检查 Maven 构建的 class 无法发现这个问题，必须也检查 JDT 的运行前构建。

宿主现在复用 Build/Run 的工具选择，将清单声明工具的 executable、home、version 作为原生安装事实交给后端。可选安装不存在时不覆盖服务器已有配置；读取失败继续返回失败，项目脚本不作为安装事实，环境与凭据不跨这个边界。Java 插件根据这些事实配置 JDT，宿主不解释 Java 版本或 POM。

例如选择 Java 8 的普通源码项目，应在 JDT 编译后仍生成 major 52，并实际用 Java 8 运行、暂停和停止；不能仅让 Maven 的 source/target 掩盖默认 JDK 接线缺失。回归同时覆盖普通目录、外部 JAR、Ant 源码布局和 Eclipse 多源码根；Ant 布局的通过不等于支持执行 Ant target。

冷启动还受到共享握手期限约束。Windows 虚拟机中的真实 JDT 握手实测约 15.4 秒，超过原 Core 默认的 10 秒。Core 的通用默认期限改为 60 秒，显式期限仍优先，取消、超时终止和进程树回收保持原行为；不按 Java 名称分支，也不增加 Core 启动重试。Core 已将声明中的 runtime 归一为工具计划，入口路径也已经展开为绝对路径。Viva 旧桥接只处理旧 runtime 的入口，导致工具计划丢掉 JAR 文件。原生适配器现在把 Core 的入口转换回包内相对路径后逐段验证，拒绝越界和符号链接；再通过 Core 已有的 toolchains.instantiateLaunch 使用定义方的模板。Java 工具的 `-jar` 和入口位置由 Java 插件声明，宿主没有 Java 分支。Gradle 集成同时核验真实设置函数与中转没有超时；不通过延长设置调用期限掩盖进程退出。注入时间的回归验证 15 秒时仍可初始化、61 秒时失败并终止，不让测试真实等待一分钟。目标平台完整工作流必须另行运行，单项 Core 回归不代表 Windows 已验收。

## 冷索引期间的动作恢复

JDT 的 ServiceReady 和项目导入事件并不保证索引任务已经结束。Windows 冷导入中，动作查询在索引结束前用完 6 秒期限，插件返回空动作；索引稍后结束却没有新的模型变化，动作一直为空。将测试等待从 15 秒延长至 120 秒仍失败，证明不能只延长测试等待来解决。

Java 插件现在记录每个活动工作区的一份延迟查询状态，启用 JDT 公开的 `progressReportProvider` 扩展，并监听既有 `language/progressReport` complete 边界；只有发生过瞬态查询失败才在该边界重新注册动作。每个工作区最多跟踪 128 个活动任务标识，等活动任务全部完成才重查，避免零散完成事件在索引结束前耗尽预算。完成计数同时覆盖“工作完成先到、查询超时后到”的竞态。一个失败周期最多自动刷新三次，成功重置预算，工作区和服务器代际变化会隔离旧状态；关闭工作区时删除记录。不新增轮询、计时线程或项目语义模型。

Core 保留标准 LSP 进度的所有权；插件不申请转发宿主保留的方法。JDT 自己选择扩展通道，进度通知会跨现有插件通道转发，但普通进度报告只做常量级检查，不会逐条触发动作查询。延迟、恢复和预算耗尽分别进入 SDK 结构化诊断；这不修改宿主 API。Windows 长 classpath 另由插件复用 manifest JAR 规划，JAR 字节交给宿主临时文件接口，运行结束由宿主删除，不写安装目录。长 module-path 仍不属于已完成范围。

## 考虑过的备选方案

- 放宽 Core 声明解码：掩盖宿主把路由信息当成声明的错误，也允许其他无效字段通过。
- 固定增大等待或对所有进度报告重查：前者已在真实冷导入中证明不能恢复丢失的动作，后者会在正常索引时反复触发昂贵查询。只在失败后的工作完成边界重查。
- 要求用户编辑文件或先打开 Debug 面板：把接线时序变成操作前提，不能修复首次使用。
- 在 Java 插件里按 PID 杀进程：插件不拥有宿主进程树，会重复实现原生清理并误伤外部附加目标。

## 后果

首次打开 Java 文档即可出现动作，首次 Debug 不依赖面板预热，停止会清理所拥有的运行。代价是窗口多一个内部刷新通知和调试会话多一个进程清理回调；不增加公共插件 API。

旧源码兼容性另行判断：当前随包 ECJ 编译器拒绝 Java 5/7 源码级别，安全拒绝测试不能当成这些工程完整可运行。正常关闭的既有销毁重试噪声独立记录为 [#1860](https://github.com/1lck/Lithe-IDEA/issues/1860)，本修复不改变该策略。

## 验证

- 真实 Core 解码回归：动作/Provider 注册在修复前报 `plugin.host.invalidParams`，修复后接受并刷新；拒绝重复注册不触发刷新。
- 同文本版本下倒序送达两次收集结果：修复前旧空结果覆盖新动作，修复后保留新动作；测试直接控制送达顺序，无时间竞争。
- 未打开 Debug 面板的 attach/launch 回归：修复前返回适配器仍在加载，修复后按需加载并进入既有调试流程。
- `TestJavaPluginMavenWorkflow` 与旧布局矩阵：真实 ZIP、Maven、JDT 和调试器，验证断点变量、继续退出、再次调试后停止，以及安装目录哈希不变；停止回收回归在修复前超时，修复后退出。
- 自动停止重复到达和销毁顺序用事件控制：修复前分别提前强制终止、先等待进程再销毁 Core；修复后保留宽限，且进程等待开始前已销毁 Core。用户再次停止的强制结束行为仍保留。
- `TestJavaPluginCleanupWhilePaused` 在真实 Java 断点暂停后直接返回，跳过成功路径关闭，由始终执行的清理收回运行并确认 Core 返回会话不存在。
- `scripts/desktop/desktop-go.sh test ./...` 与受影响包的 `-race`；本机证据来自 macOS arm64 无头工作台，原生窗口与其他平台未据此标记已验收。
