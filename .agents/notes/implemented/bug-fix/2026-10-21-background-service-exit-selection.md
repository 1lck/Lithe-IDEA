# Agent 笔记：后台服务退出确认使用可滚动的多选列表

状态：已实现

## 先说结论

退出 Lithe 时的后台服务列表不能把完整命令当作单行复选框标题，否则用户无法判断将结束哪个服务。列表固定宽度和可见高度，使用原生文本视口只绘制可见文字、只挂载附近的复选框；长命令仍完整换行且可选择复制。全选、全不选和已选数量帮助用户批量操作，确认之前只改变本次弹窗的选择。

## 问题

Issue #1344 的截图中，Java 的长启动参数被原生复选框裁剪。原来的纵向列表没有高度上限，服务较多时还可能把底部退出按钮挤出屏幕。

Issue #1627 又报告该列表滚动卡顿。原实现虽然限制了视口高度，却预先创建了全部复选框和多行文本框；每条长命令仍由普通文本框绘制。限制高度不等于虚拟化，也不能只按服务数量估算成本：一条命令就可能跨越多个屏幕。隔离诊断显示长文本会放大绘制开销，但没有复现报告中的持续低帧率，不能据此宣称已找到唯一根因。

## 决策

原生弹窗仍由 `MacProcessExitConfirmationPresenter` 管理，服务列表由同层的 `BackgroundResourceSelectionView`（AppKit 原生视图）呈现。完整名称、详情、端口与进程数放进一个只读 `NSTextView`（原生文本视口）；TextKit（系统文本排版引擎）缓存固定宽度的排版并按视口绘制字形。文本允许选择和复制，也支持不含空格的长参数换行。列表视口最多 260 点，内容不足时按实际高度收缩。

排版只在构造这次确认快照时准备，滚动不重建全文、不重算命令高度。复选框位置来自名称首行的排版位置，局部视口观察只挂载可见范围及少量预取范围内的按钮；离屏按钮移除。勾选状态按资源 ID 保存在确认视图中，不从按钮数组反推，因此滚动回收不会丢失选择，全选也包含未挂载项。观察只绑定自己的 clip view（滚动裁剪视口），卸载和销毁时解除，不向业务模型转发滚动像素。

键盘在复选框上通过 Tab/Shift-Tab 或上下方向键移动到相邻资源，先滚入视口再聚焦，不能因为按钮尚未挂载就跳过资源。辅助功能查询提供所有资源的轻量复选框元素，读屏操作可滚到离屏资源并勾选，不要求把全部原生按钮挂在界面树里。

辅助功能元素按资源 ID 在本次确认内保持身份，勾选值每次读取当前选择集合，不保存创建时的状态副本。单项、全选和全不选只对实际改变且已提供给辅助技术的元素发送值变化通知；滚动不发送选择通知，也不为通知创建离屏控件。否则读屏端持有旧元素时，会把已取消的服务继续读作勾选。

全选和全不选只修改此弹窗内的选择，并更新数量；返回的仍是原来的资源 ID 集合。名称相同的服务不合并。只有已识别服务才显示“记住选择”，且默认不勾选。按选择结束、全部结束、取消，以及启动残留清扫的映射沿用原逻辑，不改进程终止和所有权判断。

正确做法：先在列表中勾选目标，用户确认后由已有协调器决定结束哪些资源。不要在复选框变化或全选时立即停止进程，也不要因为本次界面改进而给终端和 Agent 任务增加批量结束。

## 考虑过的备选方案

- 继续保留单行标题，仅增加悬停提示：仍难以比较多条长命令，也不能解决多服务时的整体高度问题。
- 重写整个退出流程或改用另一个模态窗口：本次仅需修复后台服务的多选内容，原生弹窗已有可靠的确认和取消映射，保留它可以缩小回归面。
- 每条命令独占一个弹窗：无法一起检查和批量选择后台服务，反而增加退出步骤。
- 只把整条服务变成惰性行：服务数量少但单条命令很长时，仍会留下一个跨多屏的普通文本框。原生文本视口同时保留字形缓存、可见绘制和连续选择，无需自研文本绘制器。
- 仅打开图层缓存或替换滚动条：隔离对照没有证明稳定收益，也没有消除全量控件与长文本重绘的边界问题。

## 后果

用户能完整查看和复制命令，并在服务较多时滚动选择；控件数量随视口而不是服务总量增长。代价是原生适配层维护文本排版锚点和局部按钮生命周期，首次准备仍需排版完整快照以确定滚动范围；窗口仍使用系统弹窗外观，不新增产品菜单或主题系统。此视图不创建进程、不读写发行目录，也不产生运行时文件。
