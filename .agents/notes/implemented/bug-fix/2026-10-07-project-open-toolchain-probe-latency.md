# Agent 笔记：打开项目时的工具链版本探测与复用

状态：已实现

## 先说结论

打开带有已保存运行配置的项目时，Java 和 Maven 版本查询必须在后台执行，界面可以继续接收输入。相同工具的成功查询结果在本次应用进程内共用，并发查询只启动一个版本命令。手动刷新或工具文件变化后重新查询；项目切换与取消打开必须丢弃旧结果。

## 问题

运行配置恢复原先在主线程同步调用工具链解析。枚举 Java 后，解析器还会再次查询已选中的 Java；恢复配置的第二轮解析可能重复同一批工作。真实调用链的计时记录显示一次打开执行了 22 次 `java -version`、一次 `java_home -V` 和一次 `mvn -version`，主队列最长等待约 1.9 秒。仅保留一个已保存运行配置的最小目录也能复现，因此不是文件树或项目体积引起的问题。

## 决策

运行模块通过异步端口 `RunRuntimePort.loadRunConfigurationToolchainCandidates` 恢复项目配置。`ProjectRuntimeService` 在普通后台工作队列执行阻塞的平台查询，等待结束后才应用候选。原有同步编辑和启动入口保持兼容，并通过平台缓存复用成功版本结果。

平台适配器 `MacRuntimeProbeCache` 负责进程内存缓存和并发合并。缓存键使用解析符号链接后的工具路径以及文件身份，Java 额外检查 `release` 文件，Maven 检查核心库与 wrapper 元数据，`java_home` 检查安装目录及其条目。缓存输出不包含调用者路径，返回候选时保留当前请求的路径，避免符号链接别名串用。失败和无法解析的版本不缓存。

自动发现复用缓存。用户主动刷新时清空缓存并改变查询代次，刷新前仍在执行的查询不能重新填入缓存。运行服务在等待后核对项目会话、设置和取消状态；运行模块同时核对自己的加载身份。

正确做法：恢复配置时 `await` 异步端口，在平台工作队列查询工具版本，然后校验结果仍属于当前项目。不要这样做：在主线程换成一个同步缓存调用后，仍让首次缓存未命中的版本查询阻塞界面；也不要把阻塞进程调用塞入 Swift 的协作式执行器。

## 考虑过的备选方案

- 只把查询移到后台：界面能够响应，但同一工具仍重复启动版本进程，因此同时增加缓存和并发合并。
- 在应用层固定选择某个 JDK：会改变共享的最低版本选择规则，不能解决所有项目，保留现有 Core 选择策略。
- 把版本结果写入工具目录或安装包：会修改发行基线；此次缓存只存在内存，不创建目录、不写 bundle，也不跨工作树共享。

## 后果

首次遇到一个新的工具仍需查询版本；已有成功结果在同一进程内复用。原生进程继续使用现有五秒截止时间，取消会阻止后续查询并丢弃当前结果，已经启动的单个进程按已有截止时间结束。合并请求的原生等待最多八秒，并且发生在后台工作队列。刷新或升级工具会付出一次重新探测的成本。

此次没有新增可复用磁盘资源，不需要在工作树资源清单注册内存缓存。平台文件身份检测只读，不影响代码签名或 Sparkle 增量更新。

## 验证

- `MacRuntimeProbeCacheTests` 验证成功复用、失败重试、并发请求、刷新期间结果失效，以及真实临时工具的符号链接与文件变化。
- `ProjectRuntimeLoadingTests` 验证生产运行服务在查询期间释放主线程、切换项目和取消后丢弃旧结果，以及自动发现与手动刷新不同的缓存行为。
- `ExecutionModuleTests` 验证恢复配置等待异步端口，并在重置、项目切换和取消时保持加载身份边界。
- `MavenRuntimeTests` 和 `MacRuntimeDiscoveryTests` 验证原有自动 JDK 选择与工具发现规则。
- 用真实 `AppModel` 与平台组合根打开最小配置目录和实际项目，在五秒观察窗口内每十毫秒提交主队列工作，检查最大延迟低于两百毫秒。机器相关探针留在本地诊断产物，不进入确定性的单元测试。
- 运行 `scripts/verify-runtime-bundle-immutability.sh`、`scripts/verify-agent-notes.sh`、测试稳定性检查和平台功能矩阵检查。

## 适用范围

macOS 已保存运行配置的项目恢复与原生 Java/Maven 版本查询。没有改变 Rust 工具链选择策略、持久化配置格式或 Windows 的版本探测实现。
