# Agent 笔记：外部文件同步与保存前冲突保护

状态：已实现

## 先说结论

已打开的本地文档由原生目录监听及时刷新，但保存前必须独立核对磁盘实际字节；外部变更未解决时保留编辑内容并阻止写入。监听负责及时刷新，保存校验负责在通知遗漏时保护文件，两者不能互相替代。

## 问题

[Issue #569](https://github.com/1lck/Lithe-IDEA/issues/569) 报告：外部修改嵌套文件后编辑器不刷新，并可能随后覆盖外部修改。原来的项目根目录非递归监听不覆盖嵌套源码；保存后短暂忽略事件也可能漏掉外部写入。保存前也缺少独立的磁盘校验。

## 决策

### 文档拥有监听，项目索引保持独立

Viva 为打开文档的父目录共享一个原生目录监听，注册后再次检查文档，覆盖首次读取与监听建立之间的变化。变更按文件名筛选；通知洪峰或系统报告事件丢失时，重新检查该目录的打开文档。每个窗口最多并行检查四份，保存中的文档延后检查。监听失败会提示并记录日志，保存前仍独立核对。

关闭文档、关闭项目或晚到的监听注册都会释放监听。关闭标签和项目前，后台主动复核磁盘，不假定监听事件已经送达。

### 每次保存核对真实字节

应用层保留最后确认的原始 UTF-8 内容作为磁盘基线，而不是修改时间或文件长度。比较使用字节，不用规范等价的字符串比较代替。

原生适配器串行化写入：比较基线、准备同目录暂存文件、再次比较身份和字节，然后替换。符号链接和不支持的对象直接拒绝；本地文本限制为 32 MB。文件不存在时只有明确认可的缺失状态才能重建，创建不能覆盖并发出现的新文件。

文件系统没有跨进程的通用“比较并替换”操作，最终校验与替换之间仍有短暂竞态。

### 冲突选择只认可一个已观察版本

干净文档自动重载；有本地修改时显示冲突。用户选择保留编辑器版本，只认可冲突提示当前观察到的磁盘内容，之后磁盘再次变化，保存再次冲突。加载磁盘版本的结果若迟到，直接拒绝；替换前的正文进入撤销历史，保证可以恢复。读取失败不能当作文件未变化。

例如磁盘原为 A，外部变为 B，编辑器写成 C。即使通知丢失，保存的基线 A 与磁盘 B 不符，B 和 C 都保留。认可 B 后外部又写入 D，仍必须重新提示。不要把“保留编辑器版本”实现成永久强制写入。

### 文件被删除时保留内容

文件被删除后，即使编辑器原本干净，也不得因关闭标签或项目丢弃仅存内容。磁盘恢复到原基线后解除冲突。用户明确允许重建已删除文件后，保存使用同目录暂存文件和原生的不覆盖提交；如果新目录项先出现，保留双方内容并重新提示冲突。

[Issue #2405](https://github.com/1lck/Lithe-IDEA/issues/2405) 中，整个父目录被移走后，创建暂存文件会因父目录不存在而失败。明确允许重建时，原生写入适配器先补齐缺失的父目录；普通保存和自动保存不能因此获得重建权限。目录属于用户文档路径，随文档保留，不是应用缓存，也不从发行安装目录推导写入位置，不改变代码签名或 Sparkle 增量更新基线。

重建失败时保留编辑内容，并恢复删除提示。用户可选择“丢弃并关闭”；只有明确点击该动作才关闭标签，并清除恢复草稿，避免下次启动重新出现已丢弃的内容。重建失败与丢弃操作都不能覆盖后来出现的文件。

在项目树内剪切粘贴目录时，已打开的标签必须与重命名、拖动一样更新路径和监听。每次后台磁盘检查捕获发起时的路径；检查返回时路径已变化，就重新检查当前路径，不能把旧路径缺失的结果套到新路径上。例如把 `test/controller` 移到 `test1/controller` 后，旧检查晚到不得显示删除提示。

### 保存与输入的顺序

浏览器或原生编辑器可能还有输入尚未交给文档。保存、运行及调试前，必须先等待编辑器的输入同步，再捕获要写入的正文；同步失败或等待期间取消时，不得开始写盘。随后仍通过磁盘字节核对，不能恢复成无条件写入。

延迟的自动保存等待中的写入失败或冲突时，不能把那次失败重试成自动写盘；只有该写入成功、且正文仍属于它时，才继续保存更新的正文。

### 硬链接

Viva 当前对硬链接采取保守拒绝，尚未接入单次确认：保存时对链接数大于 1 的文件，不能静默拆链，也不能静默原地写。读取不应因此被拒绝。这一项仍待实现，不能声称已与旧 macOS 客户端等价。

### 构建输出先筛选，再判断事件洪峰

洪峰阈值统计筛选后的有效变化。普通工作区事件由 Core 的默认目录策略排除构建输出。重命名先分解两端再筛选，从 `target` 移入 `src` 的文件仍能出现。系统报告事件丢失时，始终恢复重扫，不因路径在 `target` 下就忽略。

## 考虑过的备选方案

- 无界的全项目递归监听：资源和事件量随项目增长，也无法解决漏通知后的覆盖。打开文档不能依赖项目 watcher。
- 单文件句柄监听：替换式保存后可能继续关联旧对象。父目录观察加激活时核对更可靠。
- 时间戳、长度或保存后短暂忽略：都不能判断真实内容。跨程序强制加锁会破坏协作，各平台语义也不同。
- 拒绝读取所有硬链接：会把正常的 XML 误判为非文本。
- 只在保存失败时重试创建暂存文件：父目录一直缺失时不会成功，用户仍无法关闭。父目录恢复必须属于明确认可的重建操作，同时提供丢弃出口。

## 后果

已观察到的冲突会阻止保存，通知遗漏不再直接导致无条件覆盖。保存校验依赖完整内容基线，增加读取和内存成本，因此由后台执行并限制文档大小。文件系统调用没有硬超时，取消只能拒绝迟到的界面结果，不能撤回已提交的系统写入。远程、WSL 和虚拟文档不套用本地文件保证。
