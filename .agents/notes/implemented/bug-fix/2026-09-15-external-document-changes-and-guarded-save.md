# Agent 笔记：外部文件同步与保存前冲突保护

状态：已实现

## 先说结论

Windows 为已打开本地文档监听父目录，子项目源码不再依赖项目根目录的通知。
两端保存前都核对磁盘实际内容；外部变更未解决时保留编辑内容并阻止写入。
监听负责及时刷新，保存校验负责在通知遗漏时保护文件，两者不能互相替代。

## 问题

[Issue #569](https://github.com/1lck/Lithe-IDEA/issues/569) 报告 Windows 外部
修改嵌套文件后编辑器不刷新，并可能随后覆盖外部修改。调查时 `main` 为
`34b2a09b`、`preview` 为 `99b2fa00`，相关代码一致：项目根目录非递归监听
不覆盖嵌套源码，Maven POM 有独立监听。保存后 800ms 忽略事件也可能漏掉外部写入。
macOS 原有 FSEvents 覆盖子目录，但两端原来均缺少保存前独立磁盘校验。

## 决策

### 文档拥有监听，项目索引保持独立

Windows 前端为所有工作区的已打开本地文本维护完整注册快照。原生端按窗口、
文档 ID 和注册代次路由通知，同父目录复用系统监听。关闭一个窗口不取消其他
窗口的文档。窗口激活时重建注册并重新读取，恢复被删除、重建的父目录。
监听父目录而不是旧文件句柄，因此原文件被临时文件替换后仍能收到通知。

前端每个窗口最多并行核对四个文档，每轮最多核对四次。连续编辑打断核对后，
控制器在下一次事件循环继续处理剩余项，关闭时取消这次调度；不能等用户再次
输入或聚焦才重试。重复事件合并，保存期间的通知等待保存完成后核对，不根据
固定时间屏蔽保存后的外部事件。

macOS 文档观察端口覆盖项目文档和独立文件，普通事件只核对路径匹配的文档，
父目录删除或替换只影响其下的文档。事件丢失、监听根变化或应用激活时才核对
全部打开文档，避免构建产物变化反复读取所有正文。Maven、文件树和 Git 继续
使用各自监听。

搜索结果中的临时预览文档也纳入同一个文档观察集合，重新打开预览时可等待
异步核对；预览晋升为标签页后继续保留同一正文与磁盘基线。关闭预览取消其
读取任务和监听，迟到结果不得更新已经移除的预览。预览未成为标签页前，不向
语言服务发送普通标签页的变更回调。

### 每次保存核对真实字节

应用层保留最后确认的原始 UTF-8 内容作为磁盘基线，而不是修改时间或文件长度。
这里采用完整内容，避免摘要令牌管理和额外的原生缓存生命周期；代价是内存和
跨边界传输更多。Swift 比较 UTF-8 字节，不能用规范等价的字符串比较代替。

原生适配器串行化写入，比较基线、准备同目录暂存文件、再次比较，然后替换。
Windows 使用 `ReplaceFileW` 保留原目标访问控制；macOS 复制元数据后替换。
文件不存在时只有明确认可缺失状态才能重建，创建不能覆盖并发出现的新文件。
符号链接、硬链接及不支持的对象直接拒绝；本地 UTF-8 文本限制为 32 MB。

手动、自动、关闭、运行和调试前保存通过同一个受保护入口。macOS 调用链等待
异步保存结果，文件访问在后台队列执行。保存期间的新输入保留为未保存状态，
依赖保存完成的运行或关闭操作不能继续使用旧快照。关闭窗口或退出应用时，
全部工作区保存完成后还必须重新检查当前关闭范围：先保存的工作区可能又被
编辑，也可能新开了未保存的工作区；逐个保存成功不代表现在可以安全关闭。
Windows 未命名文档另存为也读取独立目标基线后调用受保护写入。

macOS 关闭确认在按钮回调内同步领取用户选择，再开始异步保存。对话框的显示
标识与关闭事务分开：自动收起只能取消仍在等待选择的同一个确认，不能撤销
已接受的保存，也不能取消队列中的下一个确认。保存失败或显式取消保留文档；
保存失败还要释放工作区协调器的关闭请求，允许用户解决问题后重试。
项目关闭队列处理完后再次检查保存期间新增的未保存文档。

延迟自动保存由每个任务自己的标识管理，旧保存完成只清理自己的取消句柄。
新输入、文档关闭和会话重置必须能取消当前延迟任务；到期时再次检查自动保存
开关。手动保存也检查会话代次，旧会话返回不能清除新会话的任务或显示过期提示。

### 冲突选择只认可一个已观察版本

干净文档自动刷新；有本地修改时显示冲突。缺失文件通过共享 `diskConflict`
事件保留正文，普通保存不能悄悄重建。用户选择保留编辑器版本，只认可冲突
面板当前观察到的磁盘内容；随后磁盘再次变化，保存再次冲突。

加载磁盘版本拒绝迟到读取。macOS 沿用丢弃前本地历史回调；Windows 将替换前
文本写入现有撤销历史，保留当前会话内的恢复能力，不声称新增了持久化历史。
读取失败不当作文件未变化：提示检查访问权限并重试，保存校验失败则拒绝写入。
监听注册失败记录日志，窗口激活重试；没有新增独立监听状态面板。

例如磁盘原为 A，外部变为 B，编辑器写成 C。即使通知丢失，保存的基线 A 与
磁盘 B 不符，B 和 C 都保留。认可 B 后外部又写入 D，仍必须重新提示。
不要把“保留编辑器版本”实现成永久 `force=true`。

## 考虑过的备选方案

- 全项目递归监听能改善未打开文件的索引，但资源和事件量随整个项目增长，
  也无法解决漏通知后的覆盖。本次只保证打开的文档，不扩大索引改造。
- 单文件句柄监听在替换式保存后可能继续关联旧对象；只在激活时核对又不够及时。
  因此采用父目录观察加激活恢复。
- 时间戳、长度或保存后短暂忽略都不能判断真实内容；跨程序强制加锁则破坏协作，
  而且各平台语义不同。保留内容基线并在原生提交前复查。

## 后果

已观察到的冲突会阻止保存，通知遗漏不再直接导致无条件覆盖。共享 Rust 状态机
只决定状态，不承担原生文件访问；应用层不得绕过原生受保护端口直接写编辑文档。

文件系统并不提供对任意外部程序通用的“比较并替换”事务，最后检查与替换之间
仍有短竞态，不能承诺绝对杜绝并发覆盖。替换成功只表示该次系统调用成功，随后
继续通过通知核对。操作系统本地文件调用没有硬超时；任务取消可拒绝迟到 UI
结果，不能撤回已提交的系统写入。远程、WSL 和虚拟文档不套用本地文件保证。

完整内容基线增加读取、内存和传输成本。后台执行、有界文档大小和合并通知
限制开销；不在每次输入时访问磁盘。Windows 撤销记录不是跨会话持久化备份。

## 验证

共享 fixture 位于 `shared/fixtures/documents/lifecycle-v1.json`。
运行 `./scripts/verify-shared-contracts.sh`、`./scripts/verify-rust-core.sh`、
`./scripts/verify-core.sh` 和 `./scripts/verify-rust-core-comments.sh`。

macOS 使用 `./scripts/test-macos.sh` 及
`./.agents/skills/write-stable-tests/scripts/test-stability-macos.sh`，验证等长同时间
修改、缺失重建、过期基线、Unicode 字节差异、异步保存期间输入及关闭流程。
`DocumentSaveBatchTests` 验证跨工作区保存后的新输入和新增会话；
`MacDocumentObservationTests` 验证普通事件路径筛选、目录替换和丢失事件恢复。
Windows 使用 `./scripts/build-windows.ps1 -Configuration Release`，以及
`./.agents/skills/write-stable-tests/scripts/test-stability-windows.ps1`；原生测试覆盖
替换通知、多窗口释放、提交前变化与暂存清理，前端测试覆盖注册代次、保存延后
核对和冲突选择。连续打断后的调度、保存等待和关闭取消使用手动调度器验证，
不依赖真实计时器。POM 监听测试设定固定初始修改时间，不依赖主机时钟推进。
原生监听测试有五秒截止时间，不使用睡眠来猜事件顺序。
关闭确认自动收起、旧确认迟到、保存中取消、项目关闭时新增输入和自动保存任务
交替使用有界测试门控制顺序。Windows CI 显式运行文档监听控制器测试，并在
WindowsRust 范围单独运行 `lithe-project`；只运行宿主不会执行依赖包内的测试。

边界和笔记分别使用 `./scripts/verify-service-boundaries.sh`、
`./scripts/verify-windows-boundaries.sh`、`./scripts/verify-agent-notes.sh`。
实际运行结果和未通过的既有测试写入交付说明；单元测试不冒充完整产品界面验收。
