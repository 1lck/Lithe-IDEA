# Agent 笔记：未打开文件的诊断必须可见

状态：已实现

## 先说结论

语言服务报给未打开文件的诊断，只要落在某个已打开工作区（用户打开的项目根目录）内就必须保留，工作区之外的（JDK 源码、依赖 jar、反编译的 class）才丢弃。不能再以“文件有没有打开”作为诊断的过滤条件，否则用户会看到构建失败提示，却看不到错误在哪里。

## 问题

Java 项目因为编译错误无法启动时，Lithe 提示“请修复报告的错误”，但错误位于用户没有打开的模块里。语言服务已经把错误推送过来，客户端却因为文件没有打开而丢弃了它，只写一行调试日志。用户在界面上根本看不到错误。

这个过滤是有意写的，但它把“打开的文件”当成了诊断的范围，是需要被推翻的旧决策。

## 决策

诊断文件的解析顺序：

1. 能匹配到已知缓冲区或已跟踪文档的，返回那个文件原本的路径拼写，使同一文件来自不同来源（语言服务和 linter）的诊断合并在同一条记录下。
2. 否则，路径落在任一工作区根目录内的，返回归一化后的发布路径。
3. 否则丢弃。

语言服务用空诊断数组撤回某个文件的错误，因此未打开文件的处理分为三种结果：有诊断则保留；之前有记录、现在为空则清除记录；本来就没有记录、现在也为空则忽略。已打开的文件永远保留，不受上限约束。

工作区关闭时，清掉该工作区下所有未打开文件的诊断，否则项目关掉后错误仍留在面板上。

正确做法：判断依据是“在不在工作区内”。
不要这样做：`if (!isDocumentOpen(published)) return;` 这类以“有没有打开”做过滤的代码。

## 考虑过的备选方案

- 只在启动失败时抓一次快照：改动最小，但问题面板只显示打开的文件，且会形成第二份诊断真源。
- 完全不限制，收下全部发布的诊断：JDK 源码、依赖 jar 和反编译产物会压过真正要看的错误。
- 只把被丢弃的诊断写入日志：用户界面上依然看不到错误。
- 在共享的诊断存储里统一加上限：会把已打开文件的诊断也一起限制掉。

## 后果

构建失败阻止启动时，用户能在诊断面板里直接看到是哪个模块、哪个文件、哪一行。代价是大型项目的诊断状态会比以前大；超过上限后新文件的错误会被丢弃，这是刻意的取舍。构建报编译错误时仍然拒绝启动，是否允许“仍然运行”是另一项独立决策。
