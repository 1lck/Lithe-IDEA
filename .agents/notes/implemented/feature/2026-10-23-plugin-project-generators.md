# Agent 笔记：插件注入的新建项目向导

状态：已实现

## 先说结论

“新建项目”是一个向导：左栏列出“新建项目”和“生成器”两组，右侧是所选条目的表单。窗口外框、名称、位置、Git 初始化和空项目由宿主负责；其余条目由插件声明的项目生成器（Project Generator）注入。生态知识（脚手架命令、模板、下载地址）留在插件声明里，宿主和 Core 不按生成器 ID 分支。

## 问题

新建项目原来只是选一个文件夹再打开。Cargo、Spring Initializr、Maven Archetype 等各自有脚手架，把它们写进宿主会违反“宿主不按插件名分支”的原则，写进 Core 又会把生态表写死在 Core 里。建完项目后还要重新选择基础环境，也是重复配置。

## 决策

### 责任划分

| 部分 | 负责方 |
| --- | --- |
| 声明的校验、表单求值（默认值、显示条件、错误码）、生成计划、压缩包解压 | Rust Core（`project.*` 命令） |
| 窗口、名称、位置、Git 初始化、空项目 | 桌面宿主（`desktop/internal/workbench/new_project.go`） |
| 执行计划：临时目录、写文件、运行命令、下载、移动到位 | 桌面宿主（`desktop/internal/projectgen/`） |
| 字段、模板与步骤 | 插件 |

### 清单

每个生成器声明展示信息（名称、分组、图标、顺序）、字段、所需的语言或构建系统、步骤和创建后打开的文件。字段只能引用它之前声明的字段，因此默认值一次求完，显示条件不会成环。

步骤有三种，按顺序在临时目录中执行：

- `files`：复制包内的模板目录；
- `command`：调用脚手架，可以用 `collect` 把生成的子目录内容上移到项目根；
- `archive`：拼出 HTTPS 地址下载 ZIP 并解压。

运行命令的步骤是安装确认中的一条程序，任何改动都会要求用户重新确认。

### 模板语法

清单字符串使用 `${…}`。模板文件使用 `{{ … }}`，因为 POM、Gradle 脚本等本身含有 `${project.version}` 这类文本，必须原样保留。带变量的路径写在步骤的 `target` 中，不要写进模板文件名，因为文件名中的 `|` 在 Windows 上非法。

### 生成过程

1. Core 校验表单并展开所有文件、参数与地址；
2. 宿主在目标父目录下建立临时目录，按步骤执行。压缩包由 Core 解压，拒绝目录外路径、符号链接和覆盖已有文件，并限制写出的字节数；
3. 全部成功后才移动到最终位置，目标已存在则拒绝。失败或取消时删除临时目录；
4. 所选的运行环境写入新项目的工具设置，需要时用 `git` 初始化仓库，`openFiles` 写入新项目的工作区会话。

压缩包下载边收边计数，超过 512 MiB 立即取消。插件包与应用包只读，写入只发生在用户选择的目录和临时文件中。

### 工具字段

生成器可以声明一个工具字段，引用工具定义的 ID 和最低版本，宿主用已有的工具发现列出安装，用户的选择写进新项目的工具设置。宿主不判断语言名称或版本是否够新，这些规则由 Core 给出。

## 考虑过的备选方案

- **独立的内置模板插件。** 未采用。用户把模板看作语言支持的一部分，多一个只有模板的插件反而难以理解。
- **宿主解压压缩包。** 未采用。压缩包来自用户可修改的服务器，路径穿越、符号链接和大小上限的检查应只写一次，放在 Core 中。
- **生成器自带发现命令。** 未采用。会让新建项目看到的安装与设置页不一致，选择也无法写成项目的工具设置。
- **用插件网页绘制表单。** 未采用。插件界面原生优先，名称、位置、校验和提交需要宿主统一控制。

## 后果

- 社区插件只靠声明就能增加新建项目条目，表单规则和计划在 Core 中，两个平台得到相同结果。
- 生成器中的版本与依赖列表会随时间过时，需要通过插件发版更新。
- 停用提供生成器的插件时，条目照常列出但不可创建，并提示启用。
- 暂不支持 Windows 宿主的生成器界面，相关插件需要在 Windows 市场中隐藏。

## 验证

- `scripts/desktop/desktop-go.sh test ./internal/projectgen/ ./internal/workbench/ -count=1`：覆盖生成计划、文件执行与新建项目窗口。
- 在真实环境中验收：模板生成、脚手架命令、压缩包下载、取消后无残留临时目录。
