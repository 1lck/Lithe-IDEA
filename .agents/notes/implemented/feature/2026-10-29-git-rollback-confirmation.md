# Agent 笔记：Git 批量回滚的确认范围

状态：已实现

## 先说结论

提交面板的回滚按钮先打开可重新勾选文件的“回滚更改”窗口，最后确认才改文件。提交面板的勾选仍表示真实 Git 暂存区；回滚窗口里的勾选只是这次操作的草稿，关闭窗口不写入。回滚包含已暂存和未暂存内容；新增文件默认只取消暂存，只有明确勾选删除本地副本才删除磁盘文件。

## 问题

- 旧按钮使用行高亮作为范围，而不是提交复选框中的文件集合，勾选多个文件后不能直接批量回滚。
- 旧的普通丢弃操作只把暂存区内容恢复到磁盘，已经暂存的更改不会恢复到上次提交。
- 直接把确认文案改成“回滚”会让用户误以为已经恢复全部内容，因此范围和实际 Git 操作必须一起修改。

## 决策

- 参考 IntelliJ Community revision `0698a5fe297dfa08069f015cc423a6a85ed7fc60` 的 `platform/vcs-impl/src/com/intellij/openapi/vcs/changes/ui/RollbackChangesDialog.kt`。上游使用带复选框的文件浏览器，纳入集合与高亮分开；空集合不能确认，新增文件的本地删除选项默认关闭。本次只参考公开交互和源码，不复制上游窗口实现。
- 回滚入口的范围：有已暂存文件时默认纳入这些文件，否则使用行多选，再否则纳入当前列表全部文件。窗口中可以增减纳入文件。
- 草稿（候选文件与纳入标识）和请求的所有权属于 Git 功能模型；点击确认先捕获草稿再关闭窗口，异步执行只使用捕获的值，不读取已经清空的窗口绑定。
- 确认时检查工作区、请求身份及最新已知文件状态，拒绝被替换或失效的草稿。执行期间阻止同一仓库的暂存和提交交错；取消、重置或仓库切换后不派发后续写入。
- 后台全量 Git 读取不占有索引或工作区写权限，因此不能单凭“正在刷新”禁用回滚。确认时继续检查最新已知状态，执行写入会使较早的状态读取失效，防止迟到的读请求把已回滚的行加回来。
- 普通文件通过共享 Core 的既有丢弃操作一次恢复上次提交的暂存区和磁盘内容。只有新增文件先取消暂存，再按删除选项保留或删除。意向新增（`git add -N`）也先清除索引记录。
- 重命名携带新旧两个路径；复制记录只操作目标路径，不能取消暂存或恢复源文件的独立更改。
- 首个失败停止，保留已有诊断，并重新读取状态；不把部分成功伪装成跨文件事务。
- Git 同时报告“暂存删除”和“保留的未跟踪磁盘副本”时，窗口只保留同标识的已跟踪记录，防止把应恢复的删除当作新增文件。已经展开的未跟踪目录使用子项，而不是同时保留整目录删除项。
- 回滚步骤由 Core 按 Git 原始状态生成，确认后先按字面路径复核所选记录。
- Worktree 的更改页复用相同流程，但使用固定在对应工作树根的仓库，不改变主工作区的暂存区。

正确示例：提交面板勾选 A、B，打开回滚窗口后取消 B，确认只恢复 A 的暂存与磁盘内容。
不要在回滚窗口内调用暂存服务来实现勾选，也不要把当前高亮文件作为最终范围覆盖用户的确认草稿。

## 考虑过的备选方案

- 增加一个“批量回滚”按钮：不采用。现有回滚入口就应该正确处理勾选集合，重复按钮会增加歧义。
- 把提交勾选改成纯界面选择：不采用。会破坏既有真实暂存区语义、外部 Git 同步及部分暂存。
- 保留只列路径的普通确认框：不采用。用户无法在最终确认前排除文件，也不符合上游纳入集合的交互。
- 直接对所有目标调用丢弃操作：不采用。新增路径可能不存在于上次提交，且不能表达默认保留新增文件。
- 新增一套平台 Git 命令执行器：不采用。已有共享 Core 操作和执行生命周期足够，保持原有认证、命令记录、取消和有界进程控制。
- 全量状态读取期间一直禁用回滚：不采用。多仓库扫描或历史读取会让已勾选文件长时间不能操作；沿用写入互斥和过期读取保护即可，纯查询不当作写操作。

## 后果

用户可以一次恢复多个已暂存或部分暂存的文件，并在最后一步重新审核范围。
默认不删除新增文件，避免因为它没有历史版本而永久丢失内容；选择删除后仍是不可撤销操作。
多个 Git 写入不是原子事务：中途失败或取消可能已经完成前面的文件。
确认会复核模型和 Git 的路径状态，但不提供跨外部 Git 客户端的文件内容锁；不要宣称可以阻止外部同时改写。
草稿只在当前窗口和工作区会话中存在，不新增下载、缓存或安装目录写入。
