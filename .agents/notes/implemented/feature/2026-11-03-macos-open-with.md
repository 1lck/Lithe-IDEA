# Agent 笔记：项目树的“打开方式”选择应用

状态：已实现

## 先说结论

项目树中的本地文件可以通过“打开方式”直接交给电脑上的应用，无需先打开 Finder。Viva 桌面端通过平台的应用选择器选择应用，再由 Viva 工具包的打开调用交给系统打开该文件。这里只选择本次打开使用的应用，不修改系统默认关联；文件只作为已保存的磁盘路径交给应用，不读取内容，也不自动保存编辑器草稿。

## 问题

IDE 无法直接展示的格式仍需要外部编辑器或查看器。只提供“在 Finder 中显示”会增加一次窗口切换，而让用户逐个查找应用又不实际。

## 决策

- “打开方式”只作用于项目树中的单个本地文件，入口在文件菜单，编号见平台功能矩阵 `file-open-with`。
- 应用由用户在应用选择器中指定；Lithe 不维护扩展名与应用的名单，也不扫描固定的应用目录。
- 系统操作通过 Viva 工具包的打开调用执行，失败时显示实际的系统错误原因。选择器取消时不打开任何文件。
- 文件只作为磁盘路径交给应用，不读取内容、不自动保存编辑器草稿。未保存的编辑内容不会随之送给外部应用。
- 不修改系统默认关联，也不写入安装目录或发行包。

正确做法：项目树菜单调用共享的文件打开入口，由应用选择器取得应用路径后再调用打开。
不要这样做：在界面里写死 WPS 之类的应用列表，或在项目树中固定扫描 `/Applications`。

## 考虑过的备选方案

- 嵌入 Finder 自带的整个子菜单：没有公开的可嵌入接口，不调用私有 API。
- 维护扩展名与应用名单：会漏掉用户安装的应用和关联修改，不采用。
- 把系统应用列表放进右键菜单：需要为每个应用解析图标和名称，并和菜单的生命周期耦合，本次只做选择器。

## 后果

用户能直接选择实际安装的应用打开项目树中的文件，不需要切换到 Finder。
代价是每次都要经过选择器，没有“最近使用的应用”一类的快速入口。
Finder 的推荐和排序没有公开的一致性保证，不能声称与系统菜单完全相同。
应用选择和打开过程不产生新的缓存或下载，不改变代码签名或 Sparkle 增量更新的源字节。

## 验证

- `scripts/desktop/desktop-go.sh test ./internal/workbench/ -count=1`（在 `desktop/` 下运行）：项目树文件操作的回归（在 `desktop/` 下运行）。
- 真实产品需要验证中英文、深浅主题下的 DOCX、图片、未知扩展名、选择取消和打开失败的提示。未完成这些流程前，功能矩阵保持 pending。
