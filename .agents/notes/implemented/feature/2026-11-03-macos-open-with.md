# Agent 笔记：macOS 文件打开方式使用系统应用关联与原生菜单

状态：已实现

## 先说结论

项目树中的本地文件可以通过“打开方式”直接交给电脑上的应用，无需先打开 Finder。
可用应用、默认项和图标从 macOS 查询，整个文件右键菜单交给系统绘制，以满足用户对 Finder 菜单外观的要求。
这里只选择本次打开使用的应用，不修改系统默认关联；远程项目不开放本机应用入口。

## 问题

IDE 无法直接展示的格式仍需要外部编辑器或查看器。只提供“在 Finder 中显示”会增加一次窗口切换。
已有共享菜单采用产品样式，不能呈现系统材质、字体和菜单跟踪行为。

已核对 IDEA Community revision `c7f91397daa3a961b4e78bc634fe467a0a7d9ade` 的
`platform/platform-impl/src/com/intellij/ide/actions/OpenInAssociatedApplicationAction.java`：
它通过 `RevealFileAction.findLocalFile` 限定本地文件，再由 `NativeFileType.openAssociatedApplication`
调用系统关联。该动作没有提供 macOS 应用选择子菜单，因此本次复用公开 AppKit 能力补足选择，
不修改既有 IDEA 风格菜单的尺寸或绘制。

## 决策

使用 macOS 的应用关联服务（Launch Services，通过 `NSWorkspace` 公开接口访问）查找文件对应应用。
默认应用置顶，其余按系统本地化名称排序；只对相同应用 URL 去重，不按名称合并不同版本。
每次打开右键菜单重新查询，不维护第二份应用数据库或磁盘缓存。
图标只在内存生成菜单需要的 32×32 像素 PNG，再按 16pt 呈现；不能序列化应用图标的
全部 TIFF 表示。后者会解码高分辨率资源，实测本机一次查询约 30.9 秒，限定菜单尺寸后为 0.248 秒。

产品继续通过 `litheContextMenu` 和 `LitheContextMenuPresenter` 打开菜单。
项目文件菜单明确请求系统呈现，由唯一共享组件 `LitheSystemContextMenu` 创建完整 AppKit 菜单。
这样系统能拥有子菜单悬停、键盘、屏幕边缘、无障碍和关闭生命周期，不把系统子菜单混进自绘窗口。
这是用户要求的局部例外，不改变其他菜单的默认样式，也不开放业务自定义视觉配方。

系统操作仍通过 `PlatformUI` 注入；视图只提供动作和已解析图标。
“其他…”使用原生应用选择面板，选择后再次校验工作区身份，取消不打开任何文件。
文件只作为已保存的磁盘 URL 交给应用，不读取内容、不自动保存编辑器草稿。
打开失败显示实际系统错误；未知格式仍可以用“其他…”选择应用。
“App Store…”只按扩展名搜索，不传文件名、路径或内容。

正确做法：给共享呈现器传入系统查询结果，并用 `PlatformUI` 执行打开。
不要在 Project 行创建菜单窗口、扫描固定 `/Applications` 路径、写死 WPS 等应用列表，
也不要把 SSH 占位目录当作本机文件传给应用。

## 考虑过的备选方案

- 嵌入 Finder 自带的整个子菜单：没有公开的可嵌入接口，不调用私有 API。
- 用共享 SwiftUI 行模拟系统样式：难以随系统主题保持材质、字体和交互一致，不满足这次原生外观需求。
- 只把子菜单换成 AppKit：两套菜单跟踪和焦点生命周期容易冲突，因此整个文件右键菜单由一个系统菜单管理。
- 维护扩展名与应用名单：会漏掉用户安装的应用和关联修改，改为实时查询系统。

## 后果

用户能在项目树直接选择实际安装的应用，系统负责菜单行为，也不引入新的依赖。
代价是文件右键菜单采用系统外观，其余产品菜单继续使用 Lithe 外观；系统版本会影响真实呈现。
Finder 的私有筛选、推荐和同名应用排序没有公开一致性保证，不能声称逐像素或列表顺序完全相同。
Windows 未实现该入口，需要独立接入其系统选择器。

应用列表、图标和菜单只在内存存活，面板完成后释放；没有新增下载、解压或缓存目录。
系统打开的是用户明确选择的文件，Lithe 不写 app bundle 或安装目录，因此不改变代码签名或 Sparkle 增量更新基线。

## 适用范围

macOS 项目树的单个本地文件右键菜单、`PlatformUI` 外部文件动作和共享系统菜单呈现器。
不改变 IDE 的“打开”、双击、媒体路由、批量选择或系统默认应用关联。
