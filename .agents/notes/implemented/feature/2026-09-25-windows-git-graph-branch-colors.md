# Agent 笔记：Git 提交图布局与分支颜色

状态：已实现

## 先说结论

提交图的图头排序、永久布局、颜色身份和紧凑长边投影由 Rust Core 的 `git.graphProjection` 统一计算，规则以 Core 仓库的 `rust/fixtures/git/graph-projection-v1.json` 为准。桌面端只负责绘制、把颜色 ID 映射到明暗主题的 RGB，以及视口内的虚拟列表。布局和颜色规则应修改 Core；连线接缝、圆点中心及当前提交的圆环应修改桌面绘制层，不要在界面层重新分配泳道颜色或对颜色做取模。

## 问题

早期每个端各自维护泳道槽位算法。第一父提交会直接继承当前泳道颜色，本地分支新增的提交容易与父分支同色；泳道编号又随合并顺序和分页窗口变化，同一分支在不同窗口中颜色会跳变。两个端的算法不一致时，同一仓库展示的图也不同。

正确的投影仍可能被错误地画成分段线。Core 的每个打印元素是一条从提交中心到行边界的半边，相邻行的半边必须在同一个边界点相接；若用取整后的行中心再加减半个行高，缩放后端点会偏离行裁剪边界。圆点的直径和半径分别向下取整、圆角矩形绘制时再次取整边界，都会让圆点偏离连线中心。当前提交若仍绘制成普通实点则无法通过外圈识别。

端点相接还不足以保证颜色连续：线帽在行边界结束会产生抗锯齿缺口，直接让相邻行重叠则会把线条边缘混色两次，形成更亮、更粗的接缝。列表逐行绘制背景也会覆盖上一行越界的笔画，因此不能依赖跨行覆盖补洞。

同一条细线在行内也可能留下亮点。Viva 把描边矩形拆成两个三角形，如果每个三角形只按自己拥有的一条长边计算抗锯齿，会把靠近另一条长边的部分像素误算为完全着色。这个覆盖率由 Viva 渲染器按描边的两条边计算，桌面界面只负责提供正确的路径与裁剪范围。

## 决策

- **图头优先级统一。** 先按 `origin/main`、`origin/master`、其它远程分支、本地 `main`/`master`、其它本地分支、tag、HEAD 排序，同类引用使用自然名称排序。
- **永久布局。** 在有序图头上做非递归 DFS，生成与屏幕列无关的布局序号，再投影到当前页。已被更高优先级父分支占用的父提交保留父分支的片段；新增的本地图头从新片段开始。
- **颜色是身份，不是槽位。** 图头主片段的颜色由主引用名的完整 Java 风格 `String.hashCode` 决定，其它片段由布局序号决定。边的颜色取两端布局序号较大者所属片段的颜色。`colorIndex` 保存有符号颜色 ID，不能取模或取绝对值后传给绘制层。
- **紧凑长边。** 紧凑模式使用 30 行阈值，并保留两端各一行；展开模式使用 1,000 行阈值与 250 行端部。展开只改变长连线的展示方式，不折叠提交。
- **筛选不重建颜色。** 筛选在完整已加载历史的永久布局上计算可见节点，隐藏提交的祖先用虚线连接；直接父子关系仍为实线。清空筛选恢复原图。
- **明暗主题。** ID 0 使用正文色，其它 ID 按上游色相、饱和度和亮度生成颜色；主题切换只改变颜色，不重新计算布局。
- **半边在行边界连续相接。** 桌面绘制层直接按实际行边界确定上下端点，让相邻行共享同一个物理像素坐标；虚拟列表裁剪和非整数缩放都不能改变交点。不要从已取整的行中心反推边界，也不要通过改变 Core 泳道或父子关系来掩盖接缝。筛选虚线、紧凑长边及方向箭头仍使用 Core 返回的打印元素。
- **每行只绘制自己范围内的像素。** 图谱使用实际行边界裁剪，让相邻行共享同一个排他的像素边界。实线沿原方向延伸到裁剪范围之外，把线帽和抗锯齿端部留在不可见区域；延伸的纵向距离必须足以覆盖线宽，跨多泳道的斜线也不能只按路径长度延长。正确做法是延伸笔画、保持行裁剪不变；扩大行裁剪会重复混色。虚线相位、终止边和箭头位置保持原语义。
- **没有提交节点的贯穿竖线在行内也只画一笔。** 对 Core 在同一泳道连续给出的同色、实线上下半边，直接从行顶画到行底。两段各自使用圆头会在行中心重复混合抗锯齿边缘，形成每行一个亮点。只在提交圆点之间采样会漏掉其他泳道的亮点。
- **圆点与连线使用同一个中心。** 从同一个网格中心绘制线条和圆形路径，半径直接取直径的一半；不分别取整直径和半径，也不使用会再次取整边界的圆角矩形，否则奇数直径和非整数列表原点都会产生偏移。Git Log 与工作树提交历史共用这个绘制入口。
- **只有当前检出提交显示同心外圈。** 以 Core 行标签中的 `kind: head` 判断当前提交，外圈和内部实点保持同心，二者之间保留可见的背景间隔，连线不能穿过间隔。选中行、筛选首行和当前分支的可达祖先都不能代替 `head` 标签；切换选择、悬停或主题时仍须正确呈现当前行背景。

## 考虑过的备选方案

- **只修复第一父颜色继承。** 未采用。合并顺序、分页窗口和两端规则不一致的问题仍会存在。
- **按提交哈希取模。** 未采用。无关提交可能同色，也无法表达父子分支关系。
- **在每个界面各写一份算法。** 未采用。两份实现会随时间漂移，应只保留 Core 的一份规则。
- **仅加粗或让相邻行的笔画重叠。** 未采用。不能消除错误端点和圆点中心偏移，重叠还会重复混合抗锯齿边缘。正确做法是让相邻半边共享行边界、每个像素只由一行绘制，并统一节点几何。
- **按选中状态或分支高亮范围绘制外圈。** 未采用。选择可以落在任意历史提交，分支高亮包含祖先；它们都不代表当前检出提交，应直接消费 Core 的 `head` 标签。

## 后果

- 本地分支在父分支之上的新提交可以与父分支区分开。
- 两个端共用同一套布局规则，颜色身份不再因六色取模丢失。
- 图的像素级几何（HEAD 外圈、线宽、DPI 取整）仍由各端绘制层负责，单元测试不能代替真实窗口验收。
- 几何回归与无头绘制可以约束接缝、中心和外圈，但不同缩放、明暗主题及真实窗口的裁剪结果仍需目标平台截图证明，不能因共用绘制代码就把另一平台标为已验收。

## 验证

- Core 侧：`graph-projection-v1.json` 夹具（见 Core 仓库）。
- `scripts/desktop/desktop-go.sh test ./internal/core/ ./internal/workbench/ -count=1`：覆盖 `git.graphProjection` 的调用和图的绘制入口。
- `desktop/internal/workbench/gitgraph_test.go`：几何验收入口，检查 1×、1.25×、1.5×、2× 缩放下相邻半边共享行边界，圆点与连线同中心，外圈由 `head` 标签决定，并保留筛选虚线和箭头的几何约束。
- `desktop/internal/workbench/gitgraph_visual_test.go`：无头绘制验收入口，逐像素比较相同背景下跨行直线及其抗锯齿边缘的颜色，覆盖提交节点之间和贯穿其他泳道提交行的竖线，包含行中心及行边界。截图还检查分叉、当前提交的同心外圈和实点、普通提交及选择/悬停背景。只比较端点几何不能检出重复混色。
- 在包含交错分支和合并的真实仓库中验收：筛选后的虚线、直接父子实线、无关分支不误连，清空筛选后恢复原图。
- 在 Git Log 和工作树提交历史分别核对明暗主题与上述缩放：跨行无可见接缝，节点位于连线中心，当前检出提交始终显示外圈加实点，选择其他提交不转移外圈；记录实际平台、缩放和截图。取得目标平台的真实证据前，功能矩阵中的验证状态保持 `pending`。
