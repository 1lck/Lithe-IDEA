# Agent 笔记：未合并分支的强制删除必须二次确认

状态：已实现

## 先说结论

普通删除继续保护尚未合并的本地分支。用户先点击“强制删除…”查看警告，再点击独立弹窗中的“确认强制删除”才执行；取消、关闭和初始焦点下的 Enter 都保留分支。Rust Core 负责合并检查和提交身份校验，桌面端只呈现结构化结果与确认步骤。

## 问题

备份分支可能保留已改写的旧提交，普通删除会返回“尚未完全合并”，用户却没有可继续的入口。原有确认文案声称未合并分支也会删除，与 Core 的保护行为不符。

## 决策

- 普通删除失败后，只对 Core 明确报告尚未合并的分支提供强制入口，不匹配英文诊断。批量操作只把这些失败项带入二次确认，成功项与其他错误不重试。
- 混合批量结果保留原始选择的每项状态，失败分支名标红并可悬停查看原因。成功项不再重试，其他失败不进入强制确认；强制阶段的结果更新原列表，不能掩盖先前的远程失败。
- 独立确认弹窗展示目标列表与提交可能失去分支引用的警告，初始焦点为取消。“强制删除…”只打开弹窗，不发送写请求。
- 提交身份以完整对象 ID（Git 为提交计算的标识）固定。Core 在第一次拒绝时返回身份，强制请求必须携带该身份；分支变化后旧确认失效，用户重新开始删除。
- 强制仅跳过合并检查。当前分支和任何工作树中已检出的分支仍不能删除；实际删除继续使用带预期对象 ID 的原子引用操作，拒绝并发更新。
- 确认绑定原仓库。关闭或替换弹窗、切换仓库后，旧操作结果不得改变新弹窗。

正确示例：普通删除备份分支被拒绝后，查看警告并再次确认，按已审阅提交删除。不要在捕获任意 Git 失败后自动加 force 重试，这会跳过用户确认并误解释工作树占用等其他错误。

## 考虑过的备选方案

- 所有本地删除直接强制执行：放弃普通删除的合并保护，也无法体现本次明确要求的二次确认。
- 在失败通知里点击一次就强制删除：用户还未单独确认数据后果，因此未采用。
- 桌面端识别 `not fully merged` 文本：诊断可能翻译或变化，因此采用 Core 稳定错误码与结构化参数。

## 后果

用户能明确删除保留旧历史的备份分支，同时普通删除与工作树保护不变。操作多一步确认，Core 和宿主需同步升级；旧 Core 只返回通用失败时不提供强制入口。

## 验证

- Core 的真实 Git 回归覆盖普通拒绝、显式 force、缺少或非法预期身份、身份变化、当前分支、工作树占用与恢复目标。
- `desktop/internal/workbench/branch_delete_test.go` 覆盖二次确认前不删除、Enter 默认取消、确认成功、批量只重试未合并项、确认后目标变化、已删除项同名重建不受重试影响，以及远程失败与未合并混合的逐项结果。
- `desktop/internal/workbench/branch_delete_visual_test.go` 采集未合并提示和独立确认的中英文、明暗主题截图。
- 用 `scripts/desktop/desktop-go.sh` 链接本地 Core 执行上述定向测试；原生平台交互仍需独立验收。
