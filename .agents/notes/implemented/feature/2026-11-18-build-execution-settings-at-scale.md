# Agent 笔记：构建、执行、部署设置页在大量插件注入时的结构

状态：已实现

## 先说结论

「构建、执行、部署」原来一页装着作用域与保存、每个插件的工具卡片和调试器单步过滤，页面高度随插件数量线性增长。现在分组页是**目录**，宿主固定两个子页「工具链」「调试器」，插件声明的页面按种类排在后面，多了就折叠成文件夹。

这里是**聚合，不是搬家**：插件自己的设置位置不变，插件详情的「设置」标签照样列出该插件的全部设置（包括声明了 `page` 的那些）；「构建、执行、部署」只是把各插件里和构建相关的内容额外汇到一处。两处编辑的是同一份设置、同一份草稿，宿主不按插件名写分支。界面按原型 [`docs/design/build-execution-settings.html`](../../../../docs/design/build-execution-settings.html) 复刻，偏差见下文“与原型的差异”。还没做的契约缺口见[构建设置剩余的契约缺口](../../proposed/feature/2026-11-18-build-settings-remaining-contract-gaps.md)。

## 问题

- 一页装了三件事。按旧卡片高度，每个插件约增加 150 像素，几千个插件时页面高达几十万像素。
- 同一条路径在一张卡片里出现三次：生效行、下拉框、候选行。
- 插件 ID 原样显示，原因码 `versionUnsatisfied` 没有翻译。
- 每张卡片自带「保存」和「使用自动」，和窗口底部的「应用 / 好」是两套提交方式。
- 调试器单步过滤挤在工具链下面，以后其他调试设置没有地方放。

## 决策

### 页面结构

| 位置 | 内容 | 谁决定 |
| --- | --- | --- |
| 「构建、执行、部署」分组页 | 目录：最上面汇总需要处理的工具，下面是子页、两个作用域的状态和插件页种类 | 宿主 |
| 「工具链」固定子页 | 所有插件声明的工具（`toolDefinitions`，API-23） | 宿主固定页面，行来自插件声明 |
| 「调试器」固定子页 | 支持单步过滤的调试器（API-30） | 宿主固定页面，行来自插件声明 |
| 插件页 | 插件用 `settings[].page`（API-19）声明的构建工具页、编译器页 | 插件声明；折叠规则见[设置页分类](2026-10-15-macos-settings-hierarchy.md) |

插件页里的设置同时留在插件详情的「设置」标签：Core 的设置文档把全部设置放进详情的 `sections`，`page` 只额外生成一个聚合页（`pages`）。两处由同一个按插件 ID 的表单渲染，在一处改了、没应用就切到另一处，看到的是同一份草稿。

### 工具链页

- **作用域**（全局默认 / 当前项目 · 项目名）放在工具栏，两段说明收进 ⓘ。两个作用域的草稿分开保存，切换不丢草稿。
- **列表**一行一个工具，用 Viva 的按需渲染列表，只创建看得见的行。筛选、分组和计数由 Core 的设置投影算好（Lithe-core-rust#99：Core 按筛选条件给出行列表、组和计数），宿主不自己排序计数。
- **筛选**：文字筛选（名称、版本、路径、插件），加「全部 / 需要处理 / 已手动指定」。**分组**按类别（工具定义的 `category`）或按插件。
- **详情**：「当前生效」只显示实际在用的程序、版本和来源标签；「为什么是这个」按 Core 的决策链（`tool.Trace`）逐层列出。下面是单选的安装列表：第一项「自动（实际生效值）」，其后是发现的安装和手动目录，各带来源标签；末尾「添加安装目录…」。单个工具用「恢复自动」。
- 固定值是选中的那一项，不是一个来源：它的目录已经出现在其他来源里时，不再加「全局默认」之类的标签。
- **项目信任**只在「当前项目」作用域、确实有工具来自项目内环境时出现，通知条和详情里各有「信任此项目」。

### 调试器页

左侧列出声明了单步过滤的调试器、提供插件和「已自定义」标记，可筛选；右侧编辑。「不进入的代码」是逐条列表，可以添加、删除；跳过合成方法等开关只显示调试器声明支持的。插件没有给出名称时，图标用调试器名称的字母。

### 提交和搜索

- 提交统一走窗口底部的「应用 / 好」。只有在 Build 相关页面或有草稿时才显示「应用」；没有草稿时「好」直接关闭窗口。
- 侧栏搜索同时命中设置页、工具和调试器；只命中页面时不显示结果分组标题。

### 与原型的差异

- 宽度随窗口自适应，不用原型的固定像素宽度；侧栏行高 24、缩进按 Viva 侧栏调整。
- 字形图标换成 Viva 的图标；选中标签页的下划线画成一条线。
- 应用时「取消」禁用；没有 toast 提示。
- 角标按需计算；搜索命中的页面不截断到 8 条。
- 工具详情底部的工具 ID 一行不用等宽字体，因为等宽字体会把中文字隔开一格。

### 正确做法

- Gradle 插件声明 `toolDefinitions`（Gradle，`category` 为构建工具）。宿主在「工具链」的“构建工具”组里放一行 Gradle，插件不写页面。
- 八个插件各声明一个构建工具页：侧栏出现“构建工具”文件夹，展开列 6 个和“全部 8 个…”。

### 不要这样做

- 不要因为某个设置聚合到了「构建、执行、部署」，就把它从插件详情的「设置」标签里拿掉；聚合入口是额外的，不替代插件自己的位置。
- 不要在宿主里按插件名或构建工具名加专用页面、专用分组或专用折叠阈值。
- 不要在卡片或插件页里放自己的保存按钮。
- 不要把草稿值显示成当前生效值。

## 考虑过的备选方案

### 保留一页长列表，卡片改成可折叠

改动最小。但页面高度仍然随插件数量增长，问题工具只能靠用户自己往下找。不采用。

### 每个插件一个页面，工具放在各自插件页里

JDK 这类工具会被几个插件各自选一次，用户不知道哪个生效；侧栏也会有几千个入口。不采用。

### 宿主为常见构建工具写专用页面

违反“宿主不为具体语言或构建工具写专用页面”的规则，新构建工具也得等宿主发版。不采用。

## 后果

- 插件数量增加时，目录页和工具链页的高度只跟子页数量和可见行数有关。
- 宿主依赖 Core 的设置投影；Core 固定版本必须包含 Lithe-core-rust#99。
- 旧的「构建、执行、部署」长页消失，用户需要从目录页进入子页。
