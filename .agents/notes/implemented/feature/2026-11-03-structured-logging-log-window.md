# Agent 笔记：应用级日志窗口与诊断导出

状态：已实现

> Viva 迁移状态：当前桌面端已有日志存储、独立日志窗口、Core 查询和导出接线；语言服务器日志入口尚未接入，旧平台的事件目录与使用检查尚无完整等价门禁（[#1802](https://github.com/1lck/Lithe-IDEA/issues/1802)）。下文的 Swift 实现和旧平台验收不能直接当作 Viva 验收。历史源码与命令见[迁移前笔记](https://github.com/1lck/Lithe-IDEA/blob/5a54c41aa37a4e6e6b68918a4b05765b9dd07a36/.agents/notes/implemented/feature/2026-11-03-structured-logging-log-window.md)。

## 先说结论

macOS 的应用日志只在一个地方看：用 ⌘⇧L 打开的独立日志窗口，所有项目共用。语言服务状态里的“查看日志”打开编辑器区的“LSP 日志”标签页，读的是同一份脱敏记录，一次只显示一个服务器的通道，不会改动应用日志窗口的筛选。窗口读取磁盘上已经由 Core 脱敏的 v2 日志，以及写入器的实时广播。过滤语法、重复折叠、事件分布、调用链和复制格式都由 Rust Core 计算，SwiftUI 只负责读文件、订阅和画表格。导出对话框和窗口使用同一套 Core 查询，导出的永远是脱敏版。语言服务原来那份 100 条的内存日志和设置页里的日志时间线已经删除。Windows 仍然使用 v1 日志，没有迁移。

## 问题

改造前有三个问题：

1. 查看日志的入口有两个，证据来源也不同。设置页的时间线读磁盘，语言服务的日志标签页读一份 100 条的内存缓冲。用户无法回答“我导出的是不是我看到的”。
2. 用户看到错误提示后，找不到对应的那条日志。设置页时间线只是一个 180pt 高的文本框，不能跟随新日志，不能定位，也不能把同一次操作的记录串起来。
3. 如果在 Swift 里实现过滤和折叠，Windows 迁移时要用 TypeScript 再写一遍，两端的过滤结果会不一致。

## 决策

### 一个窗口，一个打开请求

日志窗口属于应用，不属于某个项目。所有入口都发出同一个 `LogWindowOpenRequest`（打开请求，可带通道前缀、过滤表达式和一条记录引用）：

- 工具栏齿轮菜单的“日志与诊断…”，紧跟在“插件…”下面，和“主题…”之间隔一条分隔线；
- 菜单栏的“日志”菜单项；
- 可改键的命令 `show-logs`，默认 ⌘⇧L；
- 应用内提示上的“查看日志”；
- 应用菜单的“导出诊断包…”：打开窗口后直接弹出导出对话框。

窗口已经打开时，请求只套用过滤条件并把窗口提到前面，不会再开一个窗口。

### 语言服务器日志在编辑器标签页里看

语言服务状态菜单里的“查看日志”不发 `LogWindowOpenRequest`，而是打开编辑器区的“LSP 日志”标签页（`EditorTabItem.languageLogs`）。
每个工作区窗口最多有一个这样的标签页；已经打开时，再次“查看日志”只切换服务器并聚焦这个标签页。

原因是两类用户目的不同。查语言服务器的人要一边看代码，一边连续阅读某个服务器的会话事件、stderr（标准错误输出）和服务器消息，
编辑器标签页正适合这种用法，也是用户原来查看 LSP 日志的位置。查应用问题的人在应用日志窗口里按通道、级别和时间筛选。
如果语言服务器日志借用应用日志窗口，点一次“查看日志”就会覆盖用户刚设好的通道筛选；如果单独开一个窗口，阅读日志时就离开了编辑区，用户要在窗口之间来回切换。

正确做法：

- `AppModel.showLanguageServerLogs(providerID:)` 调用 `LanguageServerLogsModel.open(providerID:)`，把 `.languageLogs` 放进混合标签顺序并聚焦它。状态菜单里某个服务器的“查看日志”传该服务器的 id；菜单底部的“查看日志”传列表中的第一个服务器。
- `LanguageServerLogsModel` 持有一个不折叠重复记录的 `LogWindowModel`。选中服务器后，先用 Core 的 `windowEngineChannel(providerID:)` 把 id 换成该服务器的通道，拿到通道后才开始查询。因此标签页不会显示未过滤的整个 `lsp` 前缀，也没有“全部语言服务器”选项。
- 标签页顶部从左到右是：服务器选择、“服务器日志”和 ⓘ 说明、最低级别（信息、警告、错误，默认信息）、“清空视图”。
- “清空视图”只隐藏当前服务器已经显示的记录，不删除磁盘上的日志。模型为每个服务器分别保存清空点（每个日志会话已显示到的 seq），切换服务器时换入该服务器自己的清空点。所以清空 Java 后切到 Go，Go 的记录照常显示；切回 Java，之前清空的记录仍然隐藏，只显示清空之后的新记录。
- 生命周期属于标签页。关闭标签页或重置工作区时调用 `stop()`，查询、订阅和清空点一起丢弃；切到别的标签页只是视图消失，查询继续，清空点保留。
- 输出文本由 `LanguageServerLogText` 按记录身份（与 `LogWindowModel.recordID` 相同的路径、seq、时间）逐条缓存。实时批次只在末尾追加、缓冲满 20000 条后从开头淘汰，所以每批只格式化新增记录，并按缓存的 UTF-8 长度从文本开头截掉被淘汰的行；状态、摘要、选中这类发布不改变记录，一条都不格式化。新查询、清空等其他变化整份重建一次。格式化和文本拼接只随批次大小增长；确认缓冲里的记录没变仍要逐条比较身份，但只是整数和共享字符串的比较。按 2026-11-04 在本机 release 构建测得的数字（20000 条、约 3.4 MB 文本）：原来每次发布全量格式化约 58–96 ms；整份重建约 93 ms，只在打开、切换服务器或级别、新查询、清空时发生一次；记录不变的发布约 2–4 ms，淘汰 100 条并追加 100 条约 2 ms。实时路径已经远低于一帧，因此没有移到后台线程；后台准备还要额外处理取消和过期结果。

数据来源仍是 `MacLogStore` 的磁盘 v2 记录和实时广播，所以标签页里看到的就是应用日志窗口和诊断导出里的同一份脱敏证据。

已知限制：通道只由服务器 id 决定，不区分工作区窗口，同一个服务器在其他窗口产生的记录也会出现在这里。Server Trace 和 RPC 消息捕获没有接入 v2 日志，ⓘ 说明里写明了这一点。

不要这样做：每次状态发布都对全部记录重新格式化并拼接全文（#1700 审查发现的问题）；为语言服务器另建内存缓冲或第二份日志文件；在 Swift 里用 providerID 拼通道名；为了打开这个标签页改写应用日志窗口的查询；在通道解析完成前就开始查询；用一个共享的清空点同时清空所有服务器。

### 设置里没有日志页

日志与诊断是独立界面，不和设置共用。原来的“设置 → 工具 → 日志与诊断”页已经删除，`SettingsCategory` 里没有日志分类。那一页独有的三项搬进了窗口：

- 开启详细诊断：侧栏底部的诊断卡片。未开启时显示“开启”按钮，开启后显示类别和自动关闭倒计时。
- 日志目录：工具栏“⋯”菜单显示当前生效目录，可以更改或恢复默认目录。目录是真实配置，只在用户确认后写回。
- 清理磁盘日志：同一菜单里的“清理日志…”，会显示占用大小，并要求确认。

导出只有窗口里这一个对话框。主窗口不再挂导出 sheet，所以不存在“从设置导出”和“从窗口导出”两种状态。

记录引用 `LogRecordReference` 由通道、事件名和可选的 op（操作 ID）组成，不用 seq（写入器分配的序号）。原因是显示提示时这条记录可能还在写入队列里，seq 还没分配。窗口按引用定位到匹配的最新一条记录。

正确做法：提示和日志在同一个处理边界产生，提示携带由生成事件类型给出的引用。`LogRecordReference` 定义在 `LitheModuleAPI/Logging`，由生成事件的 id、通道和 operationID 构造；`LogScope.emitReferenced` 和 span 的失败终态返回实际发出那条事件的引用。`AppModel.notificationFailure(_:operation:)` 和 `notificationRejection(operation:reason:)` 在决定显示失败提示的地方记录事件并返回引用，`operation` 是稳定的蛇形标识，日志里不复制本地化的提示正文。Git 生命周期适配器在实际发出事件时返回引用，经执行日志按 operationID 带回命令结果，最多缓存 256 个。同一条提示合并时保留最近的非空引用。

不要这样做：为某个插件写专门的打开方法；在提示里手写事件名或通道字符串；在提示里保存 seq。

### Core 计算，宿主只做 I/O

日志窗口和导出需要的通用逻辑全部在 `rust/lithe-core/src/diagnostics/`：

| 能力 | Core 入口 |
| --- | --- |
| 过滤表达式解析、错误位置、加词项 | `queryLogsV2` 的 `expression`、`diagnostics.parseLogFilter`、`diagnostics.composeLogFilter` |
| 重复记录折叠 | 每条记录的 `foldKey` 和响应里的 `foldMinimumRun` |
| 事件分布条 | `histogramBuckets` 与 `histogram` |
| 调用链 | 带 `op` 查询时的 `opSummary` 和每条记录的 `opOffsetMs` |
| 通道侧栏的计数 | 不受过滤影响的 `channels` |
| 复制为 JSON / Markdown | `diagnostics.formatLogRecords` |
| 导出范围和大小估计 | `planLogCollection` 的 `recentSessions`、`since`、`estimatedBytes`、`sessions` |
| 导出清单 | `diagnostics.buildManifest` 的 `redaction: "core-v2"` |

这样做的原因：Windows 迁移时可以直接复用；行为可以用共享 fixture 测试；正则表达式的长度和内存上限只需要在一处保证。

Swift 只负责读日志文件尾部、订阅 `MacLogStore` 的实时批次、调用 Core、按 `foldKey` 相等把相邻行分组，以及画界面。

不要这样做：在 Swift 里解析 `level>=warn`、拼 JSON 或判断两条记录是否重复。

### 过滤语法和日志内容不翻译

窗口的按钮、提示、占位符和无障碍标签走共享 i18n。级别名（DEBUG/INFO/WARN/ERROR）、日志消息、事件名、通道名、字段名和值、过滤语法、复制出来的 JSON 都不翻译。这些是证据和技术格式：翻译后会和磁盘文件、Issue 里贴的内容对不上，过滤语法也会因语言不同而失效。

### 浏览与实时跟随

表格是用 `NSViewRepresentable` 包装的 view-based `NSTableView`：固定行高、复用单元格，每行的显示内容在进入模型时算一次。窗口内存里最多保留 20000 行，超出丢弃最旧的。仓库里没有现成的 SwiftUI 表格封装，`NSTableView` 直接提供列宽调整、列隐藏和固定行高复用。

实时跟随消费写入器已经编码好的广播，每个批次只调用一次 Core 查询、只发布一次状态，不会因为滚动重新读取全部日志。用户向上滚动时自动暂停跟随，并显示新日志的条数。

“清空显示”只记住当前最后一条记录的 seq，之后只显示更新的记录，绝不删除磁盘文件。删除磁盘日志只在“⋯”菜单的“清理日志…”里做，而且必须先确认。

序号只在所属会话内递增，清空水位必须按会话保存。Core 返回每个已读取会话在过滤前的最大序号，并在历史查询和实时批次中使用同一份水位；不能把上一会话的高序号当成当前会话的门槛。水位只属于当前窗口生命周期，不写进偏好或书签。清空时同时废弃在途查询，避免旧结果恢复已清空的行。

时间框选对历史查询和实时批次都生效。导出“当前过滤结果”时，窗口时间范围与导出范围在 Core 按真实时间取交集；交集为空就导出空证据，不扩大范围。从当前应用的错误提示打开引用时，显式选择当前会话并清除旧过滤和水位，保证用户能够定位刚发生的失败。

实时查询或订阅失败后，窗口停止显示正在跟随，记录一次失败并提供显式“重试”；恢复跟随也会重新建立失败的订阅并读取遗漏的磁盘记录。不自动循环重连，旧订阅的迟到结果由独立订阅版本拒绝，关闭窗口仍取消全部任务。

### 隐私：只有脱敏版

磁盘上只存 Core 脱敏后的日志，所以窗口和导出都不可能显示原文，导出对话框也没有“包含原文”的选项。`manifest.json` 记录 `redaction: core-v2`，让读包的人知道用的是哪一版脱敏规则。

导出范围包含多个会话时，附带本应用在所选时间内的崩溃报告。崩溃报告不经过日志写入器，所以导出前逐份经过 Core `diagnostics.redactText` 脱敏，并限制份数和大小。导出只写到用户在保存面板里选的位置，从不自动上传。

导出对话框打开时冻结日志窗口当前的通道前缀、级别集合和过滤表达式；范围另外映射到 Core `planLogCollection` 的当前会话、最近三次会话或起始时间。所有文件在用户确认之前就完成收集和脱敏，确认后不再读取日志源，所以确认的内容就是写进压缩包的内容。

暂存目录是平台缓存目录下的 `Lithe/diagnostics-export/<UUID>/`：一次确认拥有一个目录，替换、取消或导出完成后删除；不跨工作树复用，不写发行包，不影响代码签名和 Sparkle delta。

崩溃报告由 macOS 原生适配器从 `~/Library/Logs/DiagnosticReports` 只读读取：文件名必须以当前进程名或 bundle ID 加 `_` 或 `-` 开头，按修改时间筛选，最多 5 份、每份最多 1 MiB，以 `O_NOFOLLOW` 打开，脱敏后写成 `crash/report-<n>` 这类不透明文件名，不泄露原文件名。目录不存在属于预期的缺失；读取失败和限额截断写进 `collection-status.txt`，读取失败另记一条 WARN。已知局限：崩溃时间用的是文件修改时间，不是 `.ips` 里的 captureTime；“最近三次会话”的时间下界用的是会话目录的创建时间，日志目录被复制或恢复后可能偏离。这两点要由 Core 契约提供明确的起始时间后再修。

### 快捷键选 ⌘⇧L

⌘L 已经是“跳到行”。原提案里的 ⌥⌘L 是 IntelliJ 系列默认的“格式化代码”，从 IDEA 迁移过来的用户会误触。命令可以在快捷键设置里改键。

### 警告和错误必须进日志

日志窗口只有在“出了问题就一定有记录”时才有用。所以显示给用户的警告和错误、功能降级、回退、自动恢复、重试耗尽和被丢弃的错误，都必须在处理边界记录一条目录事件。怎样设计一条合理的日志，写在 `develop-lithe` Skill 的日志参考页里。

`scripts/logging/verify-log-usage.mjs` 把其中能静态发现的部分变成门禁：丢弃结果的 `try?`、只退出不记录的 `catch`、生产代码里的 `print`、Rust 里丢弃结果的 `.ok();` 和 `let _ =`。门禁没有存量额度，任何违规都直接失败。确属例外时在同一行或上一行写 `// log-exempt: <类别>：<原因>`，类别只能是四类封闭例外之一（用户取消、预期的缺失、随输入实时重算的校验提示、同一次失败已经记录过）。`scripts/logging/log-usage-allowlist.json` 只接受绕过写入器的规则（例如写入器自身的 `NSLog` 兜底），计数必须与实际完全一致；丢弃错误的规则不能进入允许名单。允许名单当前为空。

门禁看不到两类问题，靠 Skill 规则和评审清单把关：只在界面显示、没有日志的警告；以及默认值为 `nil`、生产构造处从未传入的 `logSink` 参数。sink 只从依赖注入的入口取得（`MacServiceContainer` 的构造参数、`AppServices.logSink`、`ModuleContext.logSink`、SwiftUI 环境值 `applicationLogSink`、`RustCoreBridge.coreLogSink`），不使用全局单例；默认值 `nil` 只留给测试替身。写入器还没有注入前发生的失败进有界缓冲，注入后补记。

写入器自己的失败（打开、写入、关闭句柄失败）不能再写日志，否则会递归。`MacLogStore` 把这些失败计入计数器，导出时写进 `collection-status.txt` 的 `write_failures`。

### 存量迁移

切换到 v2 时，Rust Core 和 macOS Swift 里所有被门禁标出的旧写法都迁移完毕，基线文件随之删除。迁移遵守以下取舍：

- 只补诊断，不改用户流程。原来失败后静默继续的路径（历史快照写入、过期图片清理、凭据清理、远程主机元数据保存）现在会记录失败，但成功提示和后续流程不变。`LanguageWorkspaceEditService` 回滚写入失败会导致已写文件无法恢复，现在汇总记录这次失败，回滚策略本身不变。这些行为缺陷单独修复，不混在日志迁移里。
- 批量操作汇总记录。Rust 的 `StorageCleanup` 只累计失败次数和第一个 `io::ErrorKind`，结束时发一条 WARN，不逐个文件刷屏。临时文件尚未创建或已被删除时的 `NotFound` 属于预期的缺失。
- 事件进入有身份的通道。LSP 原生进程句柄不直接写全局事件，而是把至多一个原生错误交回拥有角色身份的 engine，由 engine 选择 `lsp`、`vcs` 或 `plugins.host` 下的目录事件。
- 只记稳定字段。Git 历史和远程 SSH 清理的错误只保留固定消息、稳定的 code/domain 和受控阶段，不复制 stderr、对端正文、路径或地址。
- 接收端已离开的发送失败视为取消。通道发送失败只会因为唯一接收端随游标关闭或连接取消而发生，按用户取消处理；已关闭游标后的 EOF 或读取失败通知没有消费者，不再重复记录。

### 窗口实现细节

- 日志窗口是独立的 `Window` 场景，由进程拥有的 `LogWindowCoordinator` 管理；系统菜单入口放在 `CommandGroup(after: .windowList)`。
- 旧的 `LanguageServerLogsView`、`LanguageServerLogsModel`、`.languageLogs` 标签页、`LanguageServerLogEntry` 和 100 条 `languageServerLogs` 缓冲已经删除。Java 失败处理改为记录 v2 目录事件，不再另写一份 v1 内存日志。
- 显示缓存和逐像素滚动锚点由 `NSTableView` 的 coordinator 持有；详情面板高度用共享分隔条；关闭窗口时取消查询、调用链和订阅。
- Core 的脱敏占位符是 `<redacted>`，窗口灰色显示、不可点击。

### 窗口尺寸、筛选与实时呈现

表格把窗口多出来的宽度分给事件、消息和字段列；窄窗口保留原来的可读列宽及横向滚动。
每列保存的是“基准宽度”：固定列直接显示基准宽度，三个扩展列按各自基准宽度的比例分掉视口剩余宽度。
自动分配只属于当前视口，不写用户偏好。只有表头拖动结束后才保存列宽，避免窗口放大、
隐藏列或延迟的原生列宽通知污染已保存配置。

拖动扩展列松手时，`LogTableView.adoptResizedWidths(previous:)` 把松手宽度反推成基准宽度：
设可分配宽度为 S、其他扩展列基准之和为 B，列显示为 b·S/(b+B)，反推得 b = r·B/(S−r)。
这样下一次适配视口、窗口缩窄再放大、重新打开窗口时，这一列都停在松手的位置；
缩窄到没有剩余宽度时显示基准宽度并横向滚动。反推结果低于最小列宽 40pt 时，基准取 40pt，
其余扩展列的基准按同一比例放大，松手宽度照样保持。只剩一个扩展列时它总是填满整行，
松手超过 S−B 时已经没有剩余宽度，这两种情况基准就是松手宽度。

不要这样做：把扩展列松手时的显示宽度直接存成基准宽度。下一次适配会在它上面再加一份剩余宽度，
松手后列又变宽，而且自动扩张的部分也被保存（#1700 审查发现的问题：约 483pt 的事件列拖到 493pt 后变成约 750pt）。

详情与调用链以视口宽度作为最小内容宽度，
从左上角展开，长内容继续横向滚动；右侧动作说明在自己的滚动区域内，不能覆盖底部状态栏。

筛选框复用共享搜索组件，ⓘ 说明表达式的 AND、排除、字段、前缀和正则语法，以及它与通道、
级别和时间条件的交集。通道列表通过共享列表的原生渲染入口承载 NSTableView（系统表格控件）的选择流程，⌘ 点击增减、Shift 点击
连续选择，“全部通道”清除限制；不要在 SwiftUI Button 的动作闭包里读取可能已变化的 currentEvent。
⌘F 由所属窗口的原生目标处理，工作台快捷键分发器先交给它，避免编辑器抢走日志窗口的 Find。
窗口关闭时目标取消事件监听；有 sheet 或输入法正在组字时保留输入所有权。

事件分布显示带秒数的时间刻度。时间范围弹层使用共享下拉承载系统日历与时分秒编辑器，
编辑草稿后点击应用才交给现有 Core 时间查询；界面使用本地时区，结束时间包含该秒的全部记录。
范围与实时批次、其他过滤条件取交集，清除后恢复不限时间。调用链的 ⓘ 明确条形和 +N ms
表示相对首条记录的偏移，不能把它解释成事件执行耗时。

实时批次只替换表格受影响的末尾行，选择、暂停或状态变化不整表重建；跟随时用短时原生滚动
衔接批次，并遵守系统减少动态效果设置。历史查询一次显示实际结果，真实突发仍保留原始时间
和顺序，不增加空闲定时器或延迟队列来制造稳定的事件发生速度。

## 考虑过的备选方案

- 保留旧 LSP 日志标签页的 100 条内存缓冲和设置页时间线两套浏览：来源和生命周期继续不同，无法回答“导出的是否就是看到的”。
- 设置里保留一个只放日志目录、保留与清理和详细诊断开关的“日志存储”页：日志功能又会分散在两个地方，用户要在设置和窗口之间来回找。窗口工具栏的“⋯”菜单已经能放下这几项。
- 在 Swift 里实现过滤、折叠和复制格式：开发更快，但 Windows 迁移要重写，两端行为会漂移。
- 提示里保存 seq 定位记录：显示提示时记录可能还没写盘，seq 未分配；改用通道、事件和 op 组成的引用。
- 导出提供“包含原文”选项：磁盘上根本没有原文。要支持就得另存一份未脱敏日志，扩大隐私面。
- 每个事件单独调用 Core、每次打开文件：实现简单，但跨语言调用和磁盘开销随日志量线性增长；选择按批查询和读取尾部。
- 两端一次迁移：扩大验证范围并阻塞 macOS；Windows 保留 v1 兼容，以后单独迁移。
- 语言服务器的“查看日志”继续打开应用日志窗口并切换通道（PR4 的做法）：入口少一个，但每次打开都会覆盖应用日志窗口的通道筛选，表格视图也不适合连续阅读服务器输出。
- 语言服务器日志单独开一个“语言服务器日志”窗口（#1700 的早期版本）：不再干扰应用日志窗口，但阅读日志时离开了编辑区，用户要在窗口之间切换，也不是用户原来查看 LSP 日志的位置。最终改回编辑器标签页，数据来源不变。
- 标签页提供“全部语言服务器”：多个服务器的输出交错在一起，连续阅读时分不清来源。需要对照多个服务器时，用应用日志窗口筛选 `lsp` 通道。

## 后果

收益：应用日志只有一个查看入口，LSP 日志标签页也读同一份数据，看到的、复制的和导出的是同一份脱敏证据；错误提示可以一键跳到对应记录；过滤和折叠在 Core 里，有 fixture 覆盖，Windows 可以复用。

代价：Core 的诊断 API 变大，每个新字段都要同步契约、fixture 和 Swift 桥接。实时跟随每个批次都要调用一次 Core 查询，事件分布也由 Core 对有界窗口重新计算；高吞吐下的成本还需要整机测量，如果不可接受，应扩展 Core 的增量摘要接口，而不是在 Swift 里复制统计规则。门禁零额度意味着每个新的 `try?`、空 `catch` 或丢弃结果都必须当场记录或写明例外类别。

## Viva Page 写法

日志窗口用 `ui.NewPage` 和 `func (w *window) view(c ui.C)` 声明，不再持有 `*ui.Frame`，没有窗口级的按键、滚动和指针分发。取舍如下：

- 记录表是 `ui.List`：只声明可见行，多选和键盘导航由列表给出，`RowWidth` 让窄窗口横向滚动，表头是单独一行并用 `ScrollWith` 跟随。列表按记录的稳定 key（`Model.keyBase` 加下标，永不复用）持有选中状态，Model 的 `selection`（按记录 id）仍是详情和复制读取的真源，两边用 `selectionRevision` 区分谁改了选择。
- 日志查询是页面的 `ui.Effect`，以 `Model.queryKey` 为 key：新的过滤条件取消上一次查询，清屏只让在途结果过期、不重新查询（所以 key 和 `generation` 分开）。实时订阅是推送流，不是一次一个结果的任务，仍走 Model 的邮箱（`post`、`drain`），在 `OnWake` 里应用；查询以外的后台任务（用量、导出暂存、目录选择）同样没有迁。
- 菜单、时间范围编辑器、确认框、命名框、导出面板分别用 `ui.Menu`、`ui.Popover`、`ui.Modal`；详情的上下分隔用 `ui.Splitter`（比例保持，不再限制最大高度）。直方图是 `ui.Control` 加 `Draw`，调用链是第二个 `ui.List`。
- 等宽文字：Viva 当前没有按格子断行的等宽文字（vivaui/viva#187），`mono()` 里非 ASCII 的补宽和 `wrapDetailWords` 保留，上游修复后删除。
- 被放弃的做法：把表头做成 `ListState.Header` 的第 0 行（记录下标整体错位，选择和 key 要处处减一）；把整个查询邮箱改成 Effect（实时流没有“一个 key 一个结果”的形状）。
