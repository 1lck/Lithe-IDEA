# Agent 笔记：提交文件菜单与插件 VCS 文件操作

状态：已实现

## 先说结论

提交面板和 Worktree 的文件右键菜单提供提交文件、回滚、差异、删除与添加到 VCS 等操作。右键目标取被点击行及其所在多选集合，不把行高亮等同于提交复选框。插件提供的版本控制系统（VCS，例如 SVN）必须处理自己的添加和已跟踪文件删除；删除先显示明确范围的确认，取消不改文件。Git 删除后要发布对应仓库的状态，已暂存的新文件还需清除残留的索引记录，不能只移走磁盘文件。

## 问题

- 菜单缺少常用操作时，用户必须逐个打开文件或切到外部工具。
- 把“添加到 VCS”当作 Git 暂存的别名会漏掉 SVN 等系统；把已跟踪文件的删除退回普通磁盘删除会绕过插件的版本记录。
- 删除目录还可能跨越嵌套仓库、删除编辑器中尚未保存的内容，或在工作区切换后继续执行旧请求。

## 决策

### 目标、能力与所有权

- 右键选中集合中的行时作用于该集合；右键集合之外的行时只作用于被点击文件。
- Git 的添加只暂存未跟踪目标。插件的添加只允许全部目标为未版本化状态，并要求 `fileOperations` 能力（见 `desktop/internal/core/vcs.go`）。
- 插件已跟踪文件的删除使用同一能力下的删除操作；未版本化文件使用系统废纸篓。Provider 拒绝或失败时不退回磁盘删除，缺少能力时菜单禁用。
- 发出请求前检查根、状态快照、路径和忙状态；异步的根归属检查返回后再次检查工作区代次与根集合。目录内部存在其他已识别或归属歧义的根时拒绝递归操作；根发现被截断时不假定未返回的区域安全。
- Git 删除在执行前重新发现实际仓库，阻止确认期间才出现的嵌套仓库或 linked worktree 被整目录移走。
- 废纸篓会移走整个目录，所以未版本化目录的删除在执行前在有界预算内重新发现 Provider 根。新结果与缓存不一致、被截断或失败时拒绝本次删除，提示用户刷新后重新选择；不在旧缓存上继续执行。这是已发现范围的保护，不是与外部客户端之间的原子文件系统锁。

### 删除确认与编辑器保护

- 确认对象是不可变的目标集合和单次请求身份；取消、被替换或已使用的请求不能重放。
- 目录目标先去重、合并子项，拒绝根目录本身和根外路径。叶子符号链接可移走，父目录解析后必须仍在确认根内。
- 先同步目标编辑器的待处理输入，再检查未保存修改、工作区生命周期和取消状态。存在脏文档或脏后代时拒绝删除，不代替用户保存或丢弃。
- 每次废纸篓操作前重新检查，首错停止；成功后只关闭相应的干净文档并刷新。
- 已跟踪的插件删除只派发一次确认批次，成功导致状态项消失不能反过来阻止清理干净文档。

### Git 索引与状态

Git 的废纸篓操作不会改索引。删除已暂存的新文件后，Git 仍会报告“暂存新增、磁盘已删除”，所以提交列表会继续显示它。删除完成后，只对本次确认中的新增目标重新读取状态；只有 Git 确认它仍是新增且磁盘已删除，才取消暂存。
即使废纸篓批次中途失败，也对已经消失的新增目标做这一处理；保留未删除目标、普通跟踪文件的删除记录和无关索引内容。
状态读取失败时保留现有行并提示需要刷新确认，不能直接从界面隐藏文件来伪装成功。

对应仓库的确认状态先更新提交面板、Worktree 和已打开的差异，再允许文件监听继续更新项目树。不能把其他仓库扫描、历史或 Stash 刷新放在文件状态发布之前。

正确示例：在 SVN 未版本化列表多选 A、B 后添加，宿主向 SVN Provider 发送一次排序去重的添加请求。
不要这样做：把 A、B 传给 Git 暂存，或在 SVN 删除失败后用磁盘删除强行移走文件。

## 考虑过的备选方案

- 删除后直接隐藏所选行：不采用。已跟踪文件的删除仍是需要提交的真实变更，隐藏会让视图与 Git 不一致。
- 删除整个批次后统一清空索引：不采用。会破坏普通文件的部分暂存以及未删除或无关文件的待提交内容。
- 统一用磁盘删除：破坏已跟踪文件的 VCS 语义，不采用；普通磁盘删除仅用于 Git 或未版本化文件的废纸篓流程。
- 自动保存全部脏文件再删除：会未经用户同意写入草稿，不采用；同步输入后仍有修改就要求用户先处理。

## 后果

用户得到完整可执行的菜单，插件仍是自己版本控制语义的唯一执行者。
代价是含嵌套或歧义工作副本的目录需要拆开选择，脏编辑器必须先由用户处理。
多文件删除没有跨文件事务；进行中的一次废纸篓调用不能被中途撤销，但取消后不再派发后续删除。
Provider 自身负责服务器与工作副本的原子性，宿主不保证其批次一定全成或全败。
这些动作只使用平台文件接口、现有插件协议和会话状态，不新增发行包写入、下载或共享缓存。
