# Agent 笔记：编辑器标签分屏与空状态提示

状态：已实现

> Viva 迁移状态：Viva 已有部分文本与终端分组展示，分组与布局规则由 Core 计算（见下文"Viva 宿主只画布局，规则在 Core"）。跨类型拖放、Diff 会话、焦点及生命周期仍需逐项核验，平台的像素对照与实机验收尚未完成。

## 先说结论

用户把标签拖到编辑区边缘后，工作台把该标签移入新的编辑分组；每组有自己的标签和选中内容。文档、媒体和终端仍由原功能对象维护，分屏不复制文件，也不重新创建会话。Git 的工作区、工作树、目录、分支、历史提交和保存更改的比较各自使用独立的普通 Diff 标签，不覆盖其他比较。空编辑区只展示已接入的搜索和查找操作及当前快捷键，不展示尚未实现的入口。

## 问题

旧标签只能重排，右键分屏会把两个文档塞进同一个编辑器，无法提供独立的标签组或底部分屏。空编辑区的文案面向外部 Diff，不能提示实际可用的操作。

## 决策

编辑分组是二叉布局树（每次把一组拆成两组）。标签位置、选中项和拖放规则由 Core 的 `lithe-editor-layout` 计算，宿主只做命中几何和绘制。

同一个文档在组间移动时复用原来的编辑器容器，不重建其编辑模型，保留撤销栈和视图状态。移动文件前要先同步未提交的输入，失败时保留原布局；较旧的待处理落点不能覆盖新请求。

文档容器只绑定自己的文档，旧挂载退出不能移除目标容器中的编辑器。后台光标事件及迟到的焦点事件不能切换活动组。异步挂载与正文更新共用同一套活动文档判断，并检查所属组的选中项。

右键分屏菜单与拖放共用同一个 `canDrop` 判断：当前组只有一个标签时禁用，文档与终端等混合多标签组仍可分屏。关闭或移走最后一个标签后合并空组；新标签进入当前聚焦的组。文件和会话生命周期不交给布局树。

分组是当前项目会话的状态，不增加重启恢复编辑分屏或跨窗口传输。分隔条使用共享的分隔容器，尺寸变化只在局部视图中更新，释放后再提交比例。

LSP 日志是普通编辑器标签。单个工作区只有一个 LSP 日志标签，再次查看另一个服务器时复用该标签并切换服务器；标签可以参与重排和分组。日志标签不拥有文件缓冲区：选中它要清除活动文件投影，关闭后恢复原来的内容，不能关闭未保存的文件。

数据库标签共享工作区和查询状态，统一保留在同一个编辑分组，只允许组内重排，不能直接跨组移动，否则两个分组会显示同一数据库上下文。

### Viva 宿主只画布局，规则在 Core

Viva 桌面端（Go 宿主）不自己决定标签能放到哪里、放下后分组怎么变。这些规则在 Core 的 `lithe-editor-layout` crate，宿主通过两条命令使用它：

- `editor.groupLayout.dropTargets`：拖动开始时问一次，Core 回答每个分组的标签栏能否插入（join）、正文边缘能否拆分（split）、正文中间能否追加（append），以及空编辑区能否接收。宿主只拿这份答案和上一帧画出的位置做命中测试，算出插入序号、拆分方向和预览区域。
- `editor.groupLayout.reduce`：打开标签、放下拖动的标签、移除空分组时调用。Core 同时改分组状态和布局树：拆分时插入新分组，最后一个标签离开后删掉空分组，兄弟分组占满空出的位置。过期的落点（标签已关闭、分组已消失）被拒绝，不会变成另一种移动。

宿主保留的只有 Core 不需要知道的东西：每个拆分节点的分隔条比例，按 Core 返回的节点编号复用原节点，因此其他分组变化时分隔条比例不丢。停靠在终端工具窗口里的分组作为 `docked` 传给 Core，只有终端标签（`dockable`）能拖进去，它永远不拆分，最后一个终端离开后保留。

正确做法：拖放、打开位置、空分组的规则改在 Core，桌面端只改命中几何和绘制。
不要这样做：在 `desktop/internal/workbench` 里重新写布局树算法，或按标签种类加"能不能放"的分支。

### 终端标签与工具窗口之间移动

终端标签拖动只在工具窗口与编辑区之间移动放置位置，不重建终端会话或进程。编辑器内的分屏预览与标签栏重排各自独立。

正确做法：把工具窗口的终端拖到编辑器底边得到上下分屏，再把同一标签拖回工具窗口，shell 提示符和滚动历史保持连续。
不要这样做：为拖拽重建终端会话。

### Git Diff 也属于普通编辑标签

所有仓库比较入口进入同一个编辑标签类型。同一个仓库、文件和版本组合再次打开时切回已有标签；不同文件、不同提交以及不同类型的比较可以并存。工作区文件身份不包含暂存状态，暂存或后台刷新不会额外产生标签。仓库路径参与身份，避免嵌套仓库里同名文件互相覆盖。

Commit 右键"在新标签页中显示差异"是明确例外：即使已存在同一文件的比较，也创建独立的标签和会话。普通"显示差异"和单击仍按比较身份复用。

插件提供的版本控制比较也使用同一编辑标签与分屏生命周期，但内容来自所属的插件后端，不能为其激活 Git 或把内容放入 Git 会话。标签先以加载中状态创建，异步读取基线后只填充原标签，不抢回用户已经切走的焦点。关闭标签或工作区时取消并移除对应的读取任务，迟到的成功或失败不能复活标签或发布旧错误。

每个比较标签由自己的会话持有比较内容、加载状态、文件列表、空白符选项和请求代次。异步读取只回写捕获的会话，关闭一个标签只使该会话失效，不取消其他标签，也不在结果到达时抢焦点。Git 的服务、监听和写入流程仍由共享的功能模型持有，不为每个标签复制整套功能模型。

状态刷新对已打开的比较遵守三条规则：第一，只有本次刷新真正读取过状态的仓库才能证明文件已干净；链接工作树的标签不在工作区快照里，它的缺席说明不了问题，应由该工作树自己的状态读取决定是否关闭。第二，内容没有变化就不触碰会话，避免丢掉滚动位置。第三，目录比较刷新时就地更新，保留已有行直到新行不同，不清空也不闪现加载态。

整文件和块级写入显式使用当前显示的更改对象，不能在非活动分组操作时误写全局选中的另一个文件。

正确做法：打开 A 文件的工作区比较，再打开 B 文件和 A 文件的历史提交比较，三个标签同时保留；把两个标签分屏后分别浏览。
不要这样做：只给标签分配 ID，却让它们都读写同一份全局的比较行。

## 考虑过的备选方案

- 继续使用旧的"次要文档"右键分栏：无法提供每组标签、底部分屏和组间移动，因此替换为分组模型。
- 直接引入 IDEA Swing 停靠容器：与当前技术栈不同，本次只参照其检测、预览和释放提交规则。
- 用普通位移移动整张标签：会受标签栏裁剪，并参与连续布局，因此使用浮动预览。
- 一个可复用的 Diff 预览标签：不能同时对照多个文件与版本，因此拆分比较会话，每个标签独立。
- 每个标签复制整个 Git 功能模型：会重复仓库监听、服务和写入状态，因此只拆分比较内容和加载生命周期。
- 插件比较另开一套覆盖层或借用 Git 的比较模型：会绕过普通标签清理，或引入错误的仓库事实；因此复用标签身份和内容宿主，只由插件返回比较数据。

## 后果

编辑区可以独立选择不同文件，并连续拆分或把标签移回另一组。代价是打开的比较会保留各自的内容，资源随打开的标签数增长，关闭即释放；活动文件与每组显示内容必须区分。当前不做跨窗口传输或重启恢复。

每个已访问且仍打开的文档可能保留一个编辑器实例，资源随文档数量增长；关闭文档后随之释放。大量标签时的资源预算若不足，后续应采用共享编辑器网格。
