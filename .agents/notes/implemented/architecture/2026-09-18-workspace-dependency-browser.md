# Agent 笔记：工作区依赖浏览器与语言插件 Provider 边界

状态：已实现

> Viva 迁移状态：Viva 尚未接入依赖侧栏、依赖快照或语言服务器依赖工作流，下文是 Viva 要实现的目标边界，不代表当前桌面端已有该能力。功能矩阵见 `shared/platform-feature-matrix/features/dependency-browser.json`。

## 先说结论

依赖侧栏只显示语言能力明确注册的依赖源，不把运行配置自动复制过来。语言插件从语言服务（LSP）或其上游项目模型取得工作区外的依赖根和虚拟文档，再交给统一的树模型。Java 同样走这条入口：JDT 项目准备好后读取其已解析的 classpath；Docker Compose、Node 脚本和 Java 启动项仍只在运行面板出现，仅有运行配置不会进入依赖树。

## 问题

运行配置表示怎么启动程序，不表示可浏览的外部依赖。一份项目可能生成许多 Docker、Node 和 Java 启动项，直接拿它们做依赖清单会出现重复的空服务。另一方面，用户仍需要手动加入特定源码或生成目录，并持久化排除某个目录及其子目录。

## 决策

- 依赖源只能由语言服务显式注册。宿主只在语言服务已激活、且其能力实现依赖快照协议时按语言 ID 注册；打开侧栏不会自动激活 LSP。语言服务停用时撤销注册。运行配置不参与清单、索引键或依赖路径推导。
- 依赖节点、依赖图与提供者协议属于 Core 契约（Core 仓库的 `shared/plugins/contract/v1/`）。通用的依赖提供者把插件路径和用户 JSON 配置分成"源码""构建输出""依赖""额外搜索路径"四组；侧栏只显示非空组，不自行递归发现缓存。
- 语言插件提交已解析的快照，包括源码根、二进制根、依赖根和虚拟 URI。自动文件根只接受工作区外路径；工作区内的 `vendor`、`node_modules`、`bin` 不由声明或运行配置自动注入。用户在 JSON 中明确配置的工作区内路径仍然显示。快照调用只读取已有结果，不能启动构建、LSP 或包扫描。上游变化由插件通知宿主比较并刷新。
- 依赖树的虚拟节点携带 URI，点击时按该语言 ID 路由到运行中的语言服务。没有语言 ID 的导航入口可依据插件声明的虚拟文档 scheme 寻找唯一归属；不唯一或服务休眠时明确失败，不把 URI 发给另一个语言服务器。
- 用户在语言行右侧补充源码、构建产物、依赖和额外搜索路径。目录逐层列出直接子项，勾选后一次加入草稿，点"保存"才写入配置。工作区内存相对路径，工作区外存绝对路径，已添加路径不能重复勾选。右键可排除目录，排除项按工作区相对路径保存到语言依赖源的 `excludedPaths`，匹配该目录本身及所有子路径。这里不枚举整棵目录树，也不替代语言服务提交的自动路径。
- 每个语言源的索引签名按固定键序编码语言源 ID、Provider ID、用户配置和该 Provider 负责的依赖管理文件摘要。索引另存插件提供的已解析快照：输入不变时复用完整的图。依赖管理文件的新增、修改或删除只使所属语言源失效，不递归扫描工作区。
- 文件监听只转发变化路径。依赖管理元数据不发送给语言服务，索引文件不触发工作区快照或项目服务重载。其他语言插件根据自己的管理文件变化更新上游解析结果并通知宿主，宿主不替插件猜测何时解析完成。
- 路径配置与索引分别保存在工作区的 `.lithe/dependencies/config.json` 与 `.lithe/dependencies/index.json`。构建工具窗口与依赖侧栏独立。

## 其他语言如何接入

1. 在语言支持声明的 `dependencies` 中列出实际管理文件名（例如 Rust 的 `Cargo.toml`、`Cargo.lock`），并让语言服务能力实现依赖快照协议。不要为了出现侧栏行去创建运行配置。
2. 从上游项目模型或语言服务已经解析的结果生成快照：外部源码放在 `sourceRoots`，外部构建目录放在 `binaryRoots`，包目录或归档放在 `dependencyRoots`，非文件 URI 放在 `virtualDocuments`。快照读取必须同步返回缓存，不得启动语言服务、调用包管理器、扫描主目录或递归目录。没有已解析结果时返回空，让已有的持久化索引先显示上次有效数据。
3. 上游模型在管理文件变化后重新解析、或语言服务报告项目配置就绪时，更新缓存并调用宿主注册的变化回调。宿主负责比较快照、按语言源失效索引并持久化；插件不直接写索引文件。工作区切换、插件卸载和会话终止时撤销回调与旧快照，不能把上一个项目的路径注入新项目。
4. 测试应覆盖：只有激活的语言能力才注册；管理文件变化只刷新所属语言；重复与工作区内路径被过滤，显式 JSON 路径仍可见；会话停止与工作区切换不泄漏快照；索引输入不变时复用。不能假设所有语言服务都有标准的"列依赖"方法，先核对服务器真实支持的只读项目模型接口。

## 考虑过的备选方案

- **侧栏直接扫描 Maven 本地仓库或包缓存**：无法证明包属于当前语言源，也会把机器环境绑定到某个语言上，因此否决。
- **把依赖树放进构建工具窗口**：会破坏构建窗口原有导航，并阻止非 Java 服务使用依赖树，因此否决。
- **每种语言复制一套侧栏和索引状态**：排除、缓存和监听行为会出现差异，因此采用语言无关的契约和提供者。
- **每次点击或打开工作区递归扫描**：大型仓库会产生不可预测的延迟，因此只使用插件已有快照、工作区文件清单和持久化索引。
- **把所有语言的包缓存地址写进宿主**：缓存地址可能由工具链或项目配置改变，宿主不能依据语言名称或机器环境猜测；插件应消费上游已解析的路径。
- **把全部运行配置当成依赖源**：Docker Compose 和 Node 脚本会产生大量无关或重复的空行，因此改为语言插件显式注册。

## 后果

依赖浏览器不依赖特定语言的构建工具，也不会被 Docker 或 Node 的运行项填满。配置与索引分离后，用户路径不会和构建工具配置互相覆盖，索引也能独立失效。代价是仅有语言服务启动配置的语言不会出现依赖树行；插件必须实现可选的快照协议并显式注册。
