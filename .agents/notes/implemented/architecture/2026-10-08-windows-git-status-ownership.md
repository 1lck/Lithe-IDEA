# Agent 笔记：Git 状态按仓库统一管理

状态：已实现

> Viva 迁移状态：Viva 当前只展示当前项目的 Git 状态，并在打开项目和部分 Git 操作后读取；尚无等价的多仓库状态表与全局 Git 元数据监听。同一项目内读取乱序的风险跟踪在 [#1809](https://github.com/1lck/Lithe-IDEA/issues/1809)，不能把下文的刷新保证当作已迁移。

## 先说结论

顶部、Commit 面板和项目文件树使用同一个工作区内的仓库状态表。外部 pull、checkout 或暂存后，全局监听刷新这张表；关闭 Commit 面板不会停止状态更新。各界面仍可以使用适合自己的文件路径，但不能独立保存或发布另一份分支和同步计数。

## 问题

顶部如果优先读取 Commit 面板留下的状态，全局监听却只更新工作区级状态，就会出现过期显示：旧分支落后三次提交，外部拉取并切到已同步的新分支后，工作区已读到零，顶部却仍显示旧的落后箭头。

简单让顶部改读工作区状态也不充分：Commit 支持多个仓库和用户选择的活动仓库，文件树则需要主目录所属仓库的原始相对路径。互相覆盖会丢失文件归属。

## 决策

- 仓库状态表是唯一真源：键为查询的仓库路径，值保留 Core 返回的分支、领先与落后计数和原始文件记录。
- 启动读取、Commit 读取和全局刷新都通过同一个发布入口与请求版本规则更新状态。较新结果已经发布后，旧读取不能恢复旧分支、计数或暂存状态。切仓库、清空工作区和重置时推进版本，防止旧会话的迟到结果写入。
- 操作状态（合并、变基、冲突）只由 Commit 的完整读取提供，使用独立的已发布水位线，只在操作状态真正发布时推进。全局的纯状态发布只推进文件状态水位线，因此不会淘汰更早开始、尚未返回的完整读取所带的操作状态；但比已发布操作状态更旧的结果仍被拒绝。
- 顶部直接读取所选仓库的原始记录。界面投影（`工作区` 与 `Commit` 使用的展示结果）从状态表一次性生成，不保留独立的写入动作。单仓库时两个投影可以共用同一对象；多仓库 Commit 聚合文件时保留仓库路径和仓库相对路径，文件树投影保留主目录的原始路径。
- 全局刷新宿主随主布局运行，监听所有已发现仓库的变化并合并读取。元数据监听由应用级控制器按存活的工作区实例维护，覆盖主根、附加根及已知仓库；切换活动项目不释放，移除根、关闭实例或窗口时才撤销对应注册。每个仓库拥有独立的注册标识，规范路径共享底层监听，防止同一窗口的多个仓库相互覆盖。
- 仓库查询按根独立收集结果，由共享的状态合并计划决定新快照、保留旧快照或标记未知。失败的根不能视为干净，也不能确认暂存操作；移除的根不得从旧状态复活，并提示结果可能过期。
- 读不到状态时保留已知行与未确认的勾选，并显示本地化错误，不把"查询失败"当作"仓库干净"。
- 相同的原始记录和投影复用对象，重复的相同快照不会反复重建文件列表。
- 不新增持久化目录、下载资源或运行时写入路径；状态和监听标识只属于工作区生命周期。

Git 事件分类由 Core 的纯函数统一完成：指针、规则文件、共享引用、当前工作树的 index、其他工作树的私有状态，以及对象、LFS 和临时提交目录的事件都在这里分类。子模块目录的事件在没有明确子模块根身份时保守地刷新，不能整体过滤。仅有当前工作树 index 写入的批次只刷新工作区 Git 状态，不额外重拉历史与工作树列表。分类失败时保守地重扫并重新检查监听根。远程源文件与 Git 元数据混在同一批次时，必须同时保留工作区路径与元数据刷新标志。桌面端只负责读取元数据（`desktop/internal/gitmetadata/`），分类结果来自 Core。

正确做法：外部 checkout 触发全局刷新，一次发布后顶部与 Commit 都看到新分支。
不要这样做：顶部比较两个缓存的更新时间，或在分支菜单里手动同步两个独立状态。

参考 IntelliJ Community 的 `GitRepositoryUpdater` 与 `GitWidgetApiImpl`：仓库服务统一更新，顶部与 Commit 通过同一模型读取分支，工作区观察回调刷新元数据。Lithe 参考其状态归属，顶部的同步箭头尚未实现。

## 考虑过的备选方案

- 顶部永远读旧工作区快照：只能修复单仓库场景，活动仓库切换及多仓库文件列表仍不一致。
- 根据时间戳选一份缓存：仍有两份真源，无法证明旧异步请求不会覆盖较新结果。
- 关闭面板时清空缓存：会丢失可复用的文件状态，重新打开前仍无法共享状态。
- 给每个界面分别增加监听：重复维护刷新规则，资源生命周期会依赖可见面板。
- 文件状态与操作状态共用一条版本水位线：纯状态刷新先发布后，较早开始的完整读取所带的操作状态会被丢弃，冲突横幅停在旧值。

## 后果

顶部、Commit 和文件树看到的分支及文件变化由同一次发布决定。多仓库的原始记录和展示投影仍占用各自的内存，但不会独立查询，也不会成为另一个可写真源。新增 Git 状态消费者应读取仓库状态表或已有投影，不能恢复独立的写入入口。
