# Agent 笔记：LSP 插件构建与语言服务器资源归属

状态：已实现

## 先说结论

带语言服务器（Language Server，通过 LSP 提供补全、诊断和跳转能力的进程）的插件，默认在构建阶段固定语言服务器的来源和校验值，下载并校验后放入插件包，插件包完成签名后再分发。运行时不能把下载物、解压物或插件状态写入应用安装目录，也不能写入跨工作树共享的缓存。插件卸载、重装和回滚时，必须能按声明管理自己的语言服务器。

下文的包内入口和随版本替换规则适用于默认的 bundled 模式。显式声明 `requires.managedRuntimes: 0`
及对应安装权限的插件可以采用[受管插件运行时](2026-11-18-managed-plugin-runtimes.md)：来源与校验值仍在插件清单中固定，
经审批后先检查已有安装，只为缺失项下载，并保存到该插件独立、跨版本的状态目录。
这个受控模式没有恢复宿主自行识别语言、选择版本或维护跨插件共享工具目录的旧路径。

语言服务器的声明位于插件的 `plugin.json` 的 `languageServers` 中；Lithe 负责插件包验证、启停、运行时发现、进程生命周期和现有 LSP 会话编排。插件包是声明式的，不含宿主加载的代码，见 [声明式语言插件](2026-10-12-declarative-language-plugins.md)。

## 问题

语言服务器通常包含可执行入口、第三方归档、许可证和平台相关资源。把这些文件直接放进应用，或让应用在运行时自行下载，会带来几个问题：不使用该语言的用户承担下载和索引成本；插件签名边界不完整；语言服务器可能写入安装目录，破坏发行包的基线；插件卸载后还可能留下脱离插件的运行时。

## 决策

### 1. 插件清单是构建输入

每个带 LSP 的插件在自己的源码目录提供 `language-server.json`。清单至少固定：服务器版本、HTTPS 下载地址、SHA-256、归档格式、归档根目录、启动脚本相对路径和许可证路径。清单只描述构建所需的上游输入，不保存机器路径、用户目录或运行时缓存路径。

如果新的语言服务器使用 zip、单文件可执行程序或不同的启动方式，应扩展构建脚本支持的格式，并保持"固定来源、固定校验、构建后签名"的原则；不能跳过校验直接把网络下载物复制进插件。

### 2. 构建阶段完成下载、解压和组装

构建脚本负责：读取插件的 `plugin.json` 和 `language-server.json`；调用插件专属的准备步骤下载并校验语言服务器归档；把启动器、上游运行文件、许可证和语言服务器清单放入包内 `language-server/`，路径与 `plugin.json` 中的启动路径一致；需要发布者签名的包对完整包签名，签名后不得再修改包内容。

插件包不编译、不链接任何本地代码，因此与宿主的架构和构建无关。语言服务器的组装逻辑放在插件自己的目录里，后续插件可以复用相同的构建阶段和校验结构，但不能把某个语言的路径、版本或下载地址硬编码到宿主应用中。

打包语言服务器前必须确认上游许可证允许再分发。不允许时只能声明 `systemCommand`，由用户自行安装，例如 PHP 的 Intelephense 最终即采用这种方式。

### 3. 插件包是发布和安装单位

需要独立安装的插件使用与宿主兼容的签名构建，作为单独的发布资产。插件管理下载或导入包后，按以下顺序处理：

1. 由 Core 校验声明（插件 API 版本、权限、激活事件、模板），再按宿主信任策略校验包签名。
2. 确认声明的打包启动器是包内的普通可执行文件，不是符号链接。
3. 把整个插件版本放到用户级插件版本目录。
4. 在重启边界完成启用、替换或卸载，再让语言服务控制中心显示可用状态。

语言服务器必须位于该插件版本目录内，由插件版本目录拥有。不能另建一个由宿主长期管理的通用语言工具副本。

### 4. 运行时只发现已安装插件提供的入口

语言服务控制中心和工具发现沿用现有 Core 的 LSP 会话。插件声明的打包启动器按命令名传给平台运行时；插件未安装、被禁用、隔离或等待重启时，不得重新启用宿主内置的旧路径或通用安装器。

打包的语言服务器只能从本插件已安装的版本目录启动：它是唯一候选，不按文件名在 PATH 或其他插件中查找，升级前保存的自定义路径也不能顶替它。`systemCommand` 形式的服务器走普通工具发现。

语言符号、诊断、补全和类型分析继续由上游语言服务器负责。Lithe 只拥有会话生命周期、取消、超时、旧结果保护、资源预算和稳定的跨平台适配契约，不在各平台各自实现第二套语言语义。

### 5. 运行时资源必须离开安装目录

构建脚本可以写入待签名的包；已安装的应用包和 Windows 安装目录在运行时视为只读。下载临时文件、解压目录、插件状态、日志、锁和语言服务器工作区状态，必须通过平台存储适配器放到应用支持目录、缓存目录、临时目录或用户工作区。

正确做法：构建阶段把校验后的语言服务器放进待签名的插件包，安装后整体复制到用户级插件目录，运行时只读取启动器。

错误做法：启动时从应用包内解压语言服务器、在插件包里创建索引，或卸载插件时只删除清单而保留语言服务器目录。

### 6. 跨平台实现保持相同边界

各平台使用自己的插件包格式、签名和缓存适配器，但接入共享契约 `shared/plugins/contract/v1/`（位于 Core 仓库）时复用同一份声明语义。平台之间不照搬构建脚本。两端都必须满足：插件自有资源、构建时校验、运行时只读安装目录、禁用和卸载可清理自有资源。

## 考虑过的备选方案

1. 把所有语言服务器随应用打包：启动简单，但增加应用体积和每个用户的维护成本，也无法实现按需安装。
2. 只在宿主中记录可执行文件名，交给用户自行安装：减少构建工作，但插件无法保证版本、校验值和安装后的生命周期，重装与卸载也无法清理自己的资源。
3. 运行时由宿主直接下载到共享语言工具目录：可以快速接入，却会形成宿主与插件的双重所有权，容易留下跨插件污染和不可验证的缓存。
4. 为每种语言重新实现 LSP 进程和语义分析：已有 Core 会话和上游语言服务器已经提供这些能力，重复实现会产生协议、项目状态和资源清理的第二个真源。

## 后果

用户只为安装的语言承担下载和索引成本，插件包可以独立发布、验证、重装和卸载。代价是构建过程需要访问固定的上游归档，发布环境必须准备对应架构和签名身份；Node.js 等外部运行时仍由平台能力检查，插件不会偷偷写入安装目录。

插件包、解压结果、语言服务器下载缓存和运行时语言工具没有可靠的跨工作树身份标记，不跨工作树复制。

## 验证

- 构建与校验：各插件仓库的 CI 负责组装、签名和包内容校验；本仓库不再保存官方插件的组装脚本（#1495）。
- 运行时不变量：`scripts/desktop/verify/verify-runtime-bundle-immutability.sh` 确认典型启动和插件工作流不会改写已安装的发行包。
- 新增插件还必须验证下载失败、校验失败、取消、等待重启、重装、回滚、禁用和卸载后的进程与文件清理。
