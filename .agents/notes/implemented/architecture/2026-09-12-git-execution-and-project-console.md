# Agent 笔记：Git 执行与项目控制台

状态：已实现

> Viva 迁移状态：Viva 的 Git 工具窗口已有“控制台”页，命令、输出、退出码和查询开关都接入了 Core 事件（`desktop/internal/core/gitconsole.go`、`desktop/internal/workbench/gitconsole.go`）；认证交互和双平台原生验收仍未完成，不能据此宣称已经迁移。

## 先说结论

用户从更改、分支、工作树或远程入口执行 Git 时，项目控制台保留实际命令、完整工作目录和连续输出。记录由 Core 的共享执行入口产生，界面只负责展示；内部查询默认不记录（与 IntelliJ IDEA 一致），用户可以在设置里按类别打开，启动前失败保留原因，不能伪造已经执行的命令。参数策略、事件解码和展示规则在 Core，原生进程与认证生命周期由平台适配器负责。

## 问题

只在操作结束后显示结果，会丢失传输进度、认证等待和部分成功的信息。如果各个功能自己记录命令，同一次操作可能重复显示，关闭 Git 面板还可能丢失发布等入口的历史。请求也可能在启动 Git 前失败，因此计划命令、实际子进程和请求结果必须分开记录。

行为参考 IntelliJ Community 的 `GitHandler`、`GitLineHandler` 与 `GitVcsConsoleWriter`：实际进程事件接到控制台，内部读命令默认静默，输出逐块接收并识别跨块换行与进度。Lithe 的退出码和耗时显示是额外设计，不归因于 IDEA。

## 决策

### 实际执行由共享入口记录

Core 的 Git 参数策略、事件解码、脱敏和结果模型位于 Core 仓库的 `rust/crates/git-host/` 及相关 Git 模块；原生子进程、管道、临时输入文件和限时清理也由 Core 的 Git 宿主适配器完成。平台只接收事件并展示。

带事件的调用把请求注册、实际启动、输出、子进程完成和请求完成按序送到同一接收者，并在返回前释放它。一次请求可以有多个子进程，也可以一个都未启动。正确做法是收到启动事件后再添加实际命令；不要根据工具栏按钮预先造一条执行记录，否则校验失败也会显示成 Git 已经运行。

认证回复在事件回调内同步完成时，外层观察者要临时移开、嵌套请求结束后恢复，防止回复覆盖外层事件 ID。取消状态和绝对截止时间也必须按调用层级恢复，同名操作的每个调用持有自己的取消注册，退出时只释放自己的。

原生 rebase 执行后的会话读取仍属于原请求：请求未取消或超时时，继续使用剩余的绝对截止时间和原取消标识。只有进入读取前请求已经结束，才使用独立的两秒清理期限确认 Git 留下的暂停或完成状态。不要给每次读取重新套两秒期限，否则负载较高时会把已成功的 edit 误报为中断。

stdout 与 stderr 分别持续读取，输入由私有临时文件持有，避免管道互相等待。清理和排空管道都有截止时间，失败必须报告。输出在完整行解码后才脱敏；过长行整行省略并标记；解析所用的原始输出超限时显式失败，不能把截断内容当作完整结果解析。

纯展示操作（如控制台刷新）不产生执行事件，避免控制台刷新反过来增加自身历史。

### 配置按来源解释，只在明确保存时持久化

可执行文件解析、能力探测和临时策略集中在共享执行入口。临时配置固定解析所需的颜色、路径转义和语言行为，但配置检查命令不套用这些显示覆盖，以免把临时策略误报成用户配置。替换可执行文件后，版本探测缓存失效。

Fetch 选项依次采用单次选择、仓库 `lithe.fetch.*` 覆盖、应用默认值；远程目标不保存为应用默认值。继承选项不生成覆盖参数，让 Git 自己处理系统、全局、仓库和远程配置。含有自定义脚本或凭据的配置值不能直接打印到日志。

只有明确的保存或清除才写选定作用域。保存前比较先前读取的值并获取仓库写入许可，发现外部修改要求重新加载。这是乐观检查，不承诺与外部 Git 写入形成原子比较交换。清除只删除所选文件的覆盖，不删除被包含文件的值。

远程地址展示在正文、悬浮提示和浏览器入口中去掉用户信息、查询参数和片段；无法解析或不支持的协议不回退显示原文。Git 的真实远程配置保持不变。

### 认证由原生会话持有

凭据助手默认启用，让系统既有凭据先回答。交互操作安装临时 AskPass 会话，HTTP 与 SSH 都经应用的早期认证入口处理，不能初始化第二个窗口或触发单实例转发。

会话通过带随机令牌校验的本机回环连接传递有限长度消息。事件只带提示和不透明请求标识，答案不进入控制台，也不由 Lithe 持久化。连接、回答、并发请求和重复挑战都有上限，取消或执行结束即清理监听器和未完成回答。确认认证失败后，用户可以明确重试；重试仅为本次操作绕过助手，最多三次，每次保留独立命令和退出结果。用户取消或放过凭据询问（询问过期未答）视为已经拒绝，Core 直接返回认证失败，不再询问是否重试。没有事件接收者时不能等待不可见的交互提示。

### Fetch 保留各远程的真实结果

命令预览和执行共用远程解析及参数构造，尊重跳过远程的配置，并按稳定顺序执行。某个远程失败不能覆盖其他远程的成功；每个结果绑定实际子进程标识，保留更新、删除和显式截断信息。引用检查失败不能解释为零变化，也不把无关远程的进度合成总百分比。

跳过远程的布尔配置交给 Git 自己解析，不能用把空字符串视为未配置的文本查询：`skipFetchAll` 不带值表示真，`skipFetchAll =` 表示假，非零数字也表示真。非法配置必须报告错误，不能悄悄启用远程。用户明确选择单个远程时仍可 Fetch，跳过设置只约束 Fetch 全部远程。

设置页显示的标签行为由 Core 的 `git.executionInspect` 从同一份 Git 配置和实际 Fetch 选项计算，平台只翻译结果与来源。`fetch.pruneTags` 或远程的完整标签 refspec 会让 Git 即使收到 `--no-tags` 也获取标签。部分或排除型标签 refspec 显示为自定义，不猜测完整结果。无可用远程或 Git 拒绝的布尔配置显示不可确定，原始配置仍可编辑。

### 单分支抓取规则下的上游信息

只抓取 `preview` 的仓库仍可能保留其他远端引用以及本地分支的上游配置。Git 的 `for-each-ref %(upstream)` 依赖 fetch 映射，此时可能返回空；不能据此断言用户没有配置上游。

Core 的引用读取保留正常 Git 查询结果；对缺失的上游元数据，用本次读取专用的 `-c remote.<name>.fetch=...` 常规映射再交给 Git 解析，复用 Git 本身的配置读取、引用映射和领先/落后计算，不另写配置解析器。已有上游（包括自定义映射）不被覆盖，没有跟踪配置的同名分支也不被猜测关联。

这个配置只存在于子进程参数，不写 `.git/config`，也不执行 Fetch。

### 项目控制台保留原文与取消能力

历史属于项目窗口，切换仓库或工作树不会隐藏之前的操作。内部状态、引用和配置查询不生成占位行，也不挤掉可见历史；显式命令继续显示。远程发现使用静默的 `git.remoteUrl` 查询，缺少 origin 返回空结果。

真正的启动前失败保留所属目录和原因，状态为未确认，不能伪造参数或退出码。Git 功能包裹的配置保存和仓库初始化同样要接收原始请求目录与失败事件，即使上层只返回 `Void` 或 `Bool`。工作流内后续请求若在启动前失败，应单独记录，不能附到先前成功的命令。

清空历史会抑制旧请求的迟到输出，包括仍处于预检查阶段的请求，但继续保留取消句柄直到请求结束。耗时使用单调时钟，时间戳只用于显示。

连续的 `-c key=value` 在原位置折叠，连续进度以最后一行原文作为提示；普通长输出、长提交消息和文件列表不压缩为统计或摘要，重复操作也不合组。失败上下文默认展开，stderr 单独着色，成功或失败由退出码和操作结果决定。

运行中无输出、成功无输出和确认无引用变化分别显示本地化状态提示，且与 stdout/stderr 分开，复制原始输出时不混入提示。没有完整变化计数时，只能说执行成功且无输出，不能推断 Fetch 没有变化。

按稳定标识保留手动展开状态，丢弃过期展示回复。复制使用完整保留内容；真正因内存上限丢弃的内容标为截断，不能假装可以展开恢复。控制台历史只存在于有界内存，不定义磁盘保存和长期保留策略。字段和容量的正式契约见 Core 仓库的 `rust/contracts/rust-core-api.md`。

### 记录哪些查询由用户设置决定，在记录前过滤

内部查询指 Lithe 为了显示状态、日志、差异等自己发起的读命令。它们默认不进控制台，和 IntelliJ IDEA 一致；用户排查问题时，可以在“设置 → 版本控制”的“Git 控制台：省略的查询”里按类别关掉省略。九个类别是：后台分支读取、操作后的自动重新加载、保存后的差异刷新、差异读取、日志浏览、日志路径筛选、注解与行历史、列表与面板、操作前检查。开关写成“省略……”，初始全部打开。

过滤发生在 Core 记录之前。桌面端把要记录的类别放进 `gitExecution.consoleQueries` 交给 Core，没选的类别成功时 Core 直接不报，因此不占控制台保留的记录。类别默认由 Core 按命令判断，例如 `git.diff` 归差异读取，`git.history*` 归日志浏览，没有归入其他类的 `git.*` 查询归操作前检查。同一条命令在不同场景下需要不同开关时，宿主才在请求上用 `queryCategory` 显式标注；目前标注的是后台分支读取、操作后重新加载（获取、分支操作，以及提交、暂存、贮藏、搁置、变基、历史改写等操作之后和手动刷新更改列表时读取的状态，入口是桌面端的 `reloadGit`）、保存后差异刷新和日志路径筛选。后台请求没有标注就永远不记，所以随仓库变化自动刷新的状态、行号区标记、行尾 Blame 不会把控制台刷满。

Core 只接受它列出的类别名，写错一个名字整条 Git 请求都会被拒绝。所以桌面端的类别是 `core.GitQueryCategory` 类型常量，测试拿它和 Core fixture `git/console-queries-v1.json` 的 `queryCategories` 逐项对照，名字或顺序不一致就失败。

用户执行的命令、失败的 Git 请求、意外的退出码和未确认的命令不受这些开关影响，始终记录。没开类别的查询在用户发起的请求里失败时，Core 也会补报它的命令行、stderr 和退出码，按查询的样子显示；后台请求里的查询失败了也不报。

Core 在已报告查询的 `started` 事件里带上 `queryCategory`。用户打开某个“省略”开关时，控制台把已记录的、该类别的成功查询一并移除，释放它们占的记录和输出预算；失败的查询、可见命令和仍在运行的请求里的查询保留，后者的后续事件还要写进原记录。

“Git 控制台：显示”里的四个开关（折叠 10 行以内的查询输出、省略无输出提示、完全隐藏临时 `-c` 配置、省略仓库名）只改变已记录内容的画法。它们作为 `git.consolePresentation` 的 `display` 参数在 Core 里生效；切换后，控制台用新参数重新请求展示。新结果回来之前，旧参数下的折叠和片段照常绘制，避免长输出闪开一帧，但搜索命中、匹配计数和提示只用当前参数下的结果。复制全部内容仍用完整原文，带仓库名和临时配置。显示参数只存在设置里，控制台日志本身只保存要记录的类别。

成功查询的输出超过 10 行才整段折叠，10 行以内照常显示；打开“折叠 10 行以内的查询输出”后短输出也折叠。删除类命令一律不折叠：它的 `-c` 配置、进度和输出都完整显示，让用户看清删掉了什么。删除类的判定在 Core 的 `console/deletion.rs`，包括 `rm`、`clean`（含试运行），带 `-d`/`-D`/`--delete` 的 `branch`、`tag`、`update-ref`、`symbolic-ref`，带删除选项或空源 refspec 的 `push`，带修剪选项的 `fetch`/`pull`，`remote remove`/`prune` 和带修剪的 `remote update`，删除配置的 `config`，`stash drop`/`clear`/`pop`，以及 `worktree remove`/`prune`。只看 `--` 之前的选项。`reset`、`checkout --` 这类回退不算删除。“完全隐藏临时 `-c` 配置”对删除类命令仍然生效，因为那是用户明确选的省略，不是折叠。

正确做法：新增一种需要单独开关的读取，而它和已有命令同名时，在调用处用 `core.WithQueryCategory` 标注类别，并在 Core 的类别表和 fixture 的 `queryCategories` 登记。不要这样做：桌面端拿到记录后再按命令名隐藏，被藏起来的查询仍占记录名额，会把用户真正执行的命令挤出去。

## 考虑过的备选方案

- 由每个功能界面记录计划命令：实现直接，但会重复或漏记其他入口，而且无法区分启动前失败，因此记录放在执行边界。
- 每个平台分别实现输出折叠和搜索：界面实现方便，但配置参数位置、进度范围和无输出提示容易不同，因此共享纯 Core 展示计划，平台只负责交互。
- 自动汇总长输出和重复命令：可以缩短文本，但会改变诊断语义并掩盖独立操作，因此只折叠连续配置和进度，始终保留可复制原文。
- 默认禁用凭据助手或由 Lithe 保存答案：会绕开用户已有凭据配置并增加凭据存储责任，因此默认保留助手，仅在明确重试时临时绕过。
- 为远程另建更细粒度的并发队列：Lithe 已有共享仓库与工作树写入许可，本次保留既有互斥边界，不在执行层改写并发策略。
- 把控制台做成持久历史库：需要另外定义存储、清理和隐私契约，本能力只保留内存诊断历史。
- 所有 mutation 后的读取都使用独立清理期限：会截短正常请求的剩余预算并屏蔽其取消，因此只为已经结束的请求使用。
- 只在显示时隐藏查询（原控制台工具栏的“隐藏读取命令”开关）：实现简单，但被隐藏的查询照样占用记录名额，频繁的后台读取会挤掉用户执行的命令，因此改为记录前过滤，工具栏开关换成打开 Git 设置页的按钮。
- 每条命令一个开关：最精细，但 Core 的 `git.*` 查询有上百个，用户无法判断该关哪个，因此按用户能感知的九个场景分类。
- 由桌面端逐条决定是否记录：归类规则会留在平台层，将来换界面实现时要重写，因此归类在 Core，平台只为场景不同的请求标注类别。

## 后果

用户可以跨功能和工作树查到真实执行过程，取消、认证和部分失败也有一致的归属。代价是必须维护请求与子进程两层生命周期，并同时验证 Core 与平台展示。共享展示减少两端规则偏差，但异步回复仍要求界面正确配对快照并丢弃过期结果。内存上限保证长时间使用可控，也意味着控制台不能承担完整审计存档。查询在记录前过滤，打开开关之前发生的查询找不回来；用户要先打开对应开关再重现问题。省略一个类别会移除它已记录的成功查询，重新打开也找不回来。

## 验证

- 共享 fixture 覆盖命令、事件、生命周期、Fetch、远程查询和完整展示结果；Core 的真实 Git 测试对照标签 refspec、无效布尔值与实际 Fetch。
- 认证和重试回归需要包含：本机 HTTP 认证测试服务器直接绑定数字回环地址，不做反向 DNS 查询；认证、重试与取消场景保留 15 秒预算。
- Viva 侧验证：`scripts/desktop/desktop-go.sh test ./internal/core/...` 覆盖事件桥；`scripts/desktop/desktop-go.sh test ./internal/core ./internal/workbench -run 'TestGitConsole|TestConsole' -count=1` 覆盖查询类别的记录、类别与 Core fixture 一致、省略类别时移除已记录的成功查询、偏好到类别与显示参数的映射，以及显示开关切换后的重绘。
- 进程清理和管道排空必须在真实 Windows 与 macOS 产品中验收；静态检查不能替代运行时清理证据。
- `./scripts/agent-notes/verify-agent-notes.sh`
