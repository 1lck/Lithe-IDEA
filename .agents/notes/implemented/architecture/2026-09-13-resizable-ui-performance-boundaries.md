# Agent 笔记：可调整 UI 的交互与性能边界

状态：已实现

## 先说结论

涉及分隔条、可调整面板、连续拖动或其他高频 UI 交互时，优先复用项目已有的布局组件，不要在业务页面里重新拼一套拖动逻辑。拖动过程中界面要保持稳定，面板不能缩成不可用的尺寸，也不能因为鼠标移动就重建整个页面。各平台的实现技术可以不同，但用户看到的交互行为和基本约束必须一致。分隔条在悬停和按住拖动时都不增亮，只靠调整光标识别可拖动边界。

## 问题

可调整面板会在很短时间内收到大量鼠标或指针事件。如果每个事件都直接改动业务页面状态，就容易出现拖动跳动、界面卡顿、面板变成负尺寸，以及拖动时整页反复重建。

这类问题通常只在连续拖动、窗口缩放、隐藏面板后恢复，或较复杂的页面中出现，因此需要在实现方式上提前设边界。

## 决策

### 开发者应该怎么做

- 优先复用项目已有的分隔容器。确实不能复用时，必须在变更说明中写明原因，并保持相同的尺寸限制和交互行为。
- 拖动使用稳定的坐标空间。连续拖动优先使用全局坐标，避免分隔条移动后坐标原点也跟着移动，导致指针和分隔条跳动。分隔条的当前位置不能决定下一次拖动的坐标原点。
- 高频事件必须节流、合并或经过死区过滤。尺寸状态尽量放在局部布局容器中，避免每次拖动都重新计算整个功能页面。
- 已有容器宽高足以确定面板边界时，直接分配确定的矩形，不反复询问子面板的最小、理想和最大尺寸。只有容器尚无确定宽高时才读取内容的理想尺寸。
- 每个面板先包装成单个布局容器再参与分配。内容的条件分支和列表展开后可能产生零到多个子视图，不能靠调用方逐处补包装，也不能因子视图数不是预期数量就跳过布局、任由内容重叠。空的加载状态同样要保留面板边界。
- 尺寸读取只处理可见宽高。全文测量、折叠计算、数据分组等数据计算放在闭包外，数据变化时更新；长文本使用固定宽度的文本容器，只绘制可见区域，不用普通容器一次布置整份文件。
- 为面板设置最小尺寸、最大尺寸和可用空间约束。窗口缩放、面板隐藏和恢复后，都不能产生负尺寸或布局溢出。
- 拖动过程中不写持久化存储。尺寸需要在重启后保留时，只在拖动结束时保存最终尺寸。保存的比例允许完整的 0 到 1 范围，实际最小尺寸由分隔容器按当前可用空间约束，不能在保存时再截断，否则合法的窄面板会在保存和重启时变大。
- 同一平台内，分隔条交互保持一致：无高亮的间隙、`ew-resize` / `ns-resize` 光标、帮助文本、无障碍标签、尺寸限制和拖动结束后持久化都要保留。
- 新增可调整 UI 之前，先查找现有布局组件，不要在当前页面快速写一套局部逻辑。

### Diff 双栏的收起边界

Diff 允许完全隐藏一侧，是这条规则的例外：先裁剪代码，再裁剪该侧行号，最后隐藏连接带。边缘必须保留完整的拖动命中范围，才能把隐藏的编辑器重新拉出来；窄窗口下各部分尺寸都不得为负。普通工具窗口仍使用各自的最小尺寸，不把 Diff 的零宽行为扩散到其他面板。

两侧文字使用原生文本控件，同一布局身份持续复用已准备的文字和固定文字容器，鼠标移动只改变外围裁剪范围。透明定位层不能截获文字选择事件；不要在拖动回调中逐行创建文字控件，也不要把连接带画成覆盖整份长文件的画布。

Diff 的纵向同步以视口三分之一处为映射锚点，通过已规划的增删改边界把当前侧位置映射到另一侧：匹配区保留偏移，单侧新增或删除区夹住较短的一侧。不能把整段区间按比例拉伸，也不能让两侧共用一个固定偏移，否则连接带无法随滚动变平。同步只更新视口偏移、滑块和连接带，不向业务模型发布高频状态。

### 设置等窗口只观察相关变化

设置窗口不能整体订阅应用的全部状态。主窗口里编辑代码、索引或刷新 Git 状态时，整个设置页如果随之重新计算，工程越忙设置页越卡。正确做法是设置页只订阅和设置相关的变化通道；高频的功能转发不进入设置窗口。需要实时状态的页面，自己订阅对应功能模型，或在小的叶子视图里订阅。

### 正确做法

```text
分隔条拖动
  → 局部布局容器接收事件
  → 按最小/最大尺寸限制结果
  → 必要时合并高频事件
  → 拖动结束后保存最终尺寸
```

### 不要这样做

- 在业务父视图中直接堆叠多个拖动手势，并在每个事件里同时修改多个状态。
- 让分隔条的当前位置决定下一次拖动的坐标原点。
- 拖动还没有结束就不断写入用户设置或其他持久化存储。
- 只在一个平台实现明显不同的交互，而不检查另一个平台的对应体验。

## 考虑过的备选方案

### 每个页面自己实现拖动

页面可以快速开始，但每个页面会逐渐产生不同的坐标计算、尺寸限制和性能问题，后续修复也无法让所有页面一起变好，因此不采用。

### 只依靠人工体验判断流畅度

人工体验能发现明显卡顿，但很难稳定发现高频重建、窗口边界和布局恢复问题。人工体验可以作为补充，不能代替边界检查和相关验证。

### 强制两端使用同一种分隔条高亮

2026-10-12 用户明确要求分隔条悬停和按住拖动时都不变亮，因此不采用高亮。依靠调整光标识别拖动边界，不放宽生命周期、性能或可访问性约束。

### 直接重写分支树或缓存详情高度

IDEA 的分支树复用树组件、一个行渲染器和树级悬停与右键监听。Lithe 仍有行布局的成本，本次先暂停拖动时无用的交互装饰，复用已有行和菜单动作。若工作区仍卡顿，再把分支呈现迁到已有的原生滚动树模式；不能把暂停装饰视为与 IDEA 原生树等价。

## 后果

- 收益：拖动行为更稳定，面板不容易出现负尺寸或溢出，页面重建范围更小。
- 代价：新增可调整 UI 时需要先理解现有布局组件，不能只在当前页面快速写一套局部逻辑。
- 需要重新评估的情况：现有布局组件无法支持新的交互，或实际性能数据证明局部布局容器仍然不够用。

## 验证

- 代码审查时确认拖动不会导致高频整页重绘。
- `git diff --check` 与对应平台的产品构建。
- 拖动延迟需要在目标工作区中用真实的连续拖动检查，组件计时只作为诊断，不能代替整机帧延迟验收。
- Diff 收起与恢复要通过窗口发送真实的按下、拖动、松开事件验证，直接调用内部方法不能证明事件没有被外层分隔条抢走。
