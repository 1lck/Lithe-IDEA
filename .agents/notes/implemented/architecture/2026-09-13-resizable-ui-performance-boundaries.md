# Agent 笔记：可调整 UI 的交互与性能边界

状态：已实现

## 先说结论

涉及分隔条、可调整面板、连续拖动或其他高频 UI 交互时，优先复用项目已有
的布局组件，不要在业务页面里重新拼一套拖动逻辑。拖动过程中要保证界面
稳定、面板不会缩成不可用的尺寸，也不能因为鼠标移动就重建整个页面。
macOS 和 Windows 可以用不同的 UI 技术实现，但用户看到的交互行为和基本
约束必须一致。

## 问题

可调整面板会在很短时间内收到大量鼠标或指针事件。如果每个事件都直接改动
业务页面状态，容易出现拖动跳动、界面卡顿、面板变成负尺寸，以及拖动时
整页反复重建等问题。

这类问题通常不是一次点击就能发现。它们往往只在连续拖动、窗口缩放、隐藏
面板后恢复，或较复杂的页面中出现，因此需要在实现方式上提前设边界。

## 决策

### 开发者应该怎么做

- macOS 可调整面板优先使用 `LitheSplitPaneView` 和 `SplitHandleView`。
  如果确实不能复用，必须在变更说明中写明原因，并保持相同的尺寸限制和
  交互行为。
- 拖动使用稳定的坐标空间。连续拖动优先使用全局坐标，避免分隔条移动后
  坐标原点也跟着移动，导致指针和分隔条跳动。
- 高频事件必须节流、合并或经过死区过滤。尺寸状态尽量放在局部布局容器
  中，避免每次拖动都重新计算整个功能页面。
- 共享分隔容器只在拖动开始、结束时通过 `isLithePaneResizing` 环境值
  通知后代暂停交互装饰。嵌套分隔器必须保留祖先的拖动状态；尺寸每次变化
  不再发布另一份状态。共享右键菜单在拖动时移除原生命中覆盖层，行悬停
  不写状态，工具提示清除已悬停项。暂停只改变覆盖层，不替换行内容，结束后
  恢复菜单及提示；容器消失时清理本地拖动状态。
- 工具提示的几何锚点（用于把提示定位到来源控件的边界）只属于正在悬停的
  来源。不要给所有空闲分支行登记锚点，再在每次布局中合并全树的字典。
  这个修复在共享提示组件中完成，其他使用它的工具窗口同样受益。
- 已有容器宽高足以确定面板边界时，共享分隔容器通过 SwiftUI `Layout`
  直接分配三块确定的矩形（两个面板与分隔条），不使用 `HStack/VStack`
  反复询问子面板的最小、理想和最大尺寸。仅容器尚无确定宽高时读取内容
  的理想尺寸。这个边界对应 IDEA `ThreeComponentsSplitter` 对现有组件
  设置 bounds 的做法；达到尺寸限制后的相同结果不再写入拖动状态。
- 尺寸读取器的闭包仅处理可见宽高。全文测量、Diff 折叠与双栏规划、Git
  文件树构建等数据计算放在闭包外，数据变化时更新；长 Diff 的代码文本使用固定宽度的原生文本容器，行号与连接带按
  可见区域绘制；折叠和导航定位仍用 `LazyVStack`，不能用普通 `VStack` 布置整份文件。否则保持父视图不重建
  仍可能因每次高度变化而重复扫描全部数据。Git Log 中间列表复用原生可见区域
  绘制，保留滚动、选择和导航，不在连续拖动时生成每条提交的控件。
- 为面板设置最小尺寸、最大尺寸和可用空间约束。窗口缩放、面板隐藏和
  面板恢复后，都不能产生负尺寸或布局溢出。
- 交互应与现有 Git、编辑器和工具窗口保持一致，包括悬停/拖动高亮、
  平台习惯的调整光标、帮助文本和无障碍标签。
- 如果尺寸需要在重启后保留，只在拖动结束时通过现有布局持久化机制保存
  最终尺寸，不要在拖动过程中持续写入持久化存储。
- Windows 编辑器标签栏的滚轮处理和活动标签可见性判断必须使用内层可滚动
  列表，不能使用包含导航按钮的外层工具栏。滚动直接更新 DOM，不写入应用
  状态；手动处理滚轮时使用可取消的原生事件监听，避免浏览器再次应用水平
  位移；跳过不可取消或已被子元素消费的事件，并在禁用、拖动或卸载时移除
  监听。新配置默认开启滚轮横向滚动，
  保留用户已保存的关闭设置。

### Diff 双栏的收起边界

`DiffSplitPaneView` 继续复用 `SplitHandleView` 的稳定坐标和事件合并。Diff 是
用户明确要求可完全隐藏一侧的例外：先裁剪代码，再裁剪该侧行号，最后隐藏连接带。
保留边缘的拖动命中范围，才能将隐藏的编辑器重新拉出来；窄窗口各部分尺寸都不得为负。
普通工具窗口仍使用各自最小尺寸，不把 Diff 的零宽行为扩散到其他面板。
边缘保留的是完整原生命中区域，不只是 5pt 布局占位：10pt 命中面必须整个留在
Diff 正文内，避免与左右工具窗口的分隔条重叠。验证要在嵌套工作区中经窗口发送
按下、拖动、松开事件，再次从两端拉回；直接调用内层 handle 方法不能证明事件
没有被外层分隔条抢走。横向滚轮被 Diff 消费后不再交给原生父滚动区重复处理。

两侧文字复用 AppKit（macOS 原生界面库）的 `NSTextView`（原生文本控件）。
正确做法是：同一个布局身份继续使用已准备的文字和固定文字容器，鼠标移动只改变
外围裁剪范围；透明定位层不能截获文字选择事件。不要在拖动回调中逐行创建文字控件，
或将连接带画成覆盖整份长文件的画布。`DiffNativeCodeColumn.swift` 只负责显示、
原生选择和可见区域绘制，不接管比较结果或业务动作。

Diff 的纵向同步依据 Community `SyncScrollSupport.ScrollHelper` 和
`BaseSyncScrollable`（`c7f91397daa3a961b4e78bc634fe467a0a7d9ade`）：以视口三分之一处
为映射锚点，通过已规划的增删改边界将当前侧位置映射到另一侧。匹配区保留偏移，
单侧新增/删除区夹住较短的一侧；不能把整个区间做比例拉伸，也不能让两边共用
一个固定偏移，否则连接带无法随滚动变平。像素边界已包含现有折叠/提示行高度，
不重新比较文件。`DiffScrollSynchronization` 只观察本视图两个 clip view，直接更新
原生偏移、滑块和连接带；不向业务模型或父级 SwiftUI 发布高频状态。卸载探针时
移除通知，观察闭包不强持有同步器。连接带使用两个视口偏移绘制可见区域。

验证使用真实原生分隔条事件，检查两侧收起/恢复、连续选区、文字准备次数和排版
有效范围。记录的组件布局与截图耗时只是本地诊断数据，不能替代整机连续拖动的
帧延迟，也不能把 `split.drag` 手势持续时间当成帧性能。

### 正确做法

```text
分隔条拖动
  → 局部布局容器接收事件
  → 根据最小/最大尺寸限制结果
  → 必要时合并高频事件
  → 拖动结束后保存最终尺寸
```

### 不要这样做

- 在业务父视图中直接堆叠多个 `DragGesture`，并在每个事件里同时修改
  多个 `@State`。
- 让分隔条的当前位置决定下一次拖动的坐标原点。
- 拖动还没有结束就不断写入用户设置或其他持久化存储。
- 只在 macOS 实现一套行为明显不同的交互，而不检查 Windows 的对应体验。

## 考虑过的备选方案

### 每个页面自己实现拖动

页面可以快速开始，但每个页面会逐渐产生不同的坐标计算、尺寸限制和性能
问题。后续修复时也无法保证所有页面一起变好，因此不采用。

### 只依靠人工体验判断流畅度

人工体验能发现明显卡顿，但很难稳定发现高频重建、窗口边界和恢复布局问题。
因此人工体验可以作为补充，不能代替边界检查和相关验证。

### 本次直接重写原生分支树或缓存详情高度

IDEA 的 [BranchesTreeComponent](https://github.com/JetBrains/intellij-community/blob/c7f91397daa3a961b4e78bc634fe467a0a7d9ade/plugins/git4idea/backend/src/ui/branch/dashboard/BranchesTree.kt)
复用 Swing 树、一个行渲染器以及树级
悬停和右键监听。Lithe 仍有 SwiftUI 行布局的成本，本次先暂停拖动时无用的
交互装饰，复用已有行和菜单动作。若目标工作区仍卡顿，再把分支呈现迁到
已有原生滚动树模式；不能把这次暂停装饰视为与 IDEA 原生树等价。

右侧详情的默认高度需要随容器高度变化，保持默认详情区域的大小。仅计算
高度减法不是新增内容扫描；把同一个高度写进状态会增加更新，因此没有
采用这项建议。后端、数据读取、分支筛选与操作语义均不参与本次调整。

### 让标签栏外框统一处理滚动

外框还包含固定操作按钮，其宽度不等于标签列表可视宽度。读取外框的滚动
范围会漏掉内层溢出；因此保留外框用于拖动命中判断，滚动使用独立的内层引用。

## 后果

- 收益：拖动行为更稳定，面板不会轻易出现负尺寸或溢出，页面重建范围更小。
- 代价：新增可调整 UI 时需要先理解现有布局组件，不能只在当前页面快速
  写一套局部逻辑。
- 需要重新评估的情况：现有布局组件无法支持新的交互，或实际性能数据
  证明局部布局容器仍然不够用。

### 编辑器标签的浮动拖动预览

普通文件、媒体和 Repository Diff 的拖动预览在原生非激活 `NSPanel` 中显示，
从现有标签捕获一次真实图标/字型；鼠标移动只移动窗口，不重复截图或每帧写入
整个编辑区域的 SwiftUI 位移。原标签保留空白圆角占位，目标变化才调整临时
显示顺序，松开时写入实际顺序。预览不能受标签栏 ScrollView 裁剪或单行 Y 轴
钳制；单行与多行共享这条路径。栏外松开恢复原顺序，不隐式创建编辑器窗口。

依据 Community `c7f91397daa3a961b4e78bc634fe467a0a7d9ade` 的
`DragHelper` / `DockManagerImpl.MyDragSession` / `DragImageDialog` / `TabLabel.paint`：
拖出预览与标签重排独立，浮动预览 90% 不透明，落点用占位块而非蓝色插入线。
占位颜色取 `DragAndDrop.areaBackground`，Islands 深色 `#FFFFFF10`，浅色父主题
`#3D7DCC33`。源卡片保持原尺寸与资源，不新增另一套图标或字体。

预览忽略鼠标且不抢焦点；松开、Esc、来源关闭、布局切换或编辑区卸载均清理
子窗口和键盘监视器。Esc 后同一按住过程不能重新开始拖动。终端跨容器传输
仍由原生拖放所有者负责。`EditorTabOrderFeatureModelTests` 用真实窗口事件
覆盖文件/Diff、单/多行、离栏再返回重排，以及预览窗口取消与焦点保持。
这不代表实现了 IDEA 的拖出独立编辑窗口或跨编辑器拆分功能。

标签拖动的开始、占位换位、松开与取消均不使用动画。标签栏清除继承的动画
transaction，并禁止后代重新启用动画；浮动 NSPanel 的 animationBehavior 为
none，防止系统淡出与标签从透明恢复时的弹簧/渐变。窗口事件回归必须走生产
样式，不在测试宿主额外关闭动画，以免掩盖这一回归。

标签栏现在使用固定的命名坐标空间记录标签矩形与鼠标位置。占位槽可以换位，但
坐标空间挂在整条标签栏上，不随来源标签移动；边界和目标行判断直接使用鼠标
位置，不能用标签中心加位移代替，否则从靠下位置抓取后在顶部松开会被误判为
栏外。浮动预览仍使用位移。事件回归覆盖偏离中心抓取、顶部松开及离栏再返回。

`GitLogReferenceResizeTests` 用真实临时 Git 仓库加载 1,000 个分支，通过外层
原生分隔条事件调整 Git Log 高度，验证离屏行不挂载原生交互控件并记录布局耗时。
它用于检查界面结构是否退化，不用机器耗时作为易波动的测试断言，也不等价于
真实项目的整帧流畅度。原生表格承载相同 SwiftUI 行的试验未显示稳定收益，
因此保留现有分支树；不能仅因为 IDEA 使用 JTree 就引入另一套无收益的容器。

最新正式预览已在此工作树中打开全部引用，完成多次 Git Log 上边缘上下拖动并
确认布局恢复。采样同时包含 SwiftUI 布局、工作区外部刷新和 Java 准备工作，
不能据此把用户报告的卡顿归为单一根因。用户随后在本机明确确认“现在不卡顿了”，
本次报告的高度拖动卡顿据此完成用户实机验收；这不等同于所有复杂工作区场景的
帧延迟保证，组件计时仍只作为诊断。
