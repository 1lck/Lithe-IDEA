# Agent 笔记：可调整 UI 的交互与性能边界

状态：已实现

## 先说结论

涉及分隔条、可调整面板、连续拖动或其他高频 UI 交互时，优先复用项目已有
的布局组件，不要在业务页面里重新拼一套拖动逻辑。拖动过程中要保证界面
稳定、面板不会缩成不可用的尺寸，也不能因为鼠标移动就重建整个页面。
macOS 和 Windows 可以用不同的 UI 技术实现，但用户看到的交互行为和基本
约束必须一致。

## 问题

可调整面板会在很短时间内收到大量鼠标或指针事件。如果每个事件都直接改动
业务页面状态，容易出现拖动跳动、界面卡顿、面板变成负尺寸，以及拖动时
整页反复重建等问题。

这类问题通常不是一次点击就能发现。它们往往只在连续拖动、窗口缩放、隐藏
面板后恢复，或较复杂的页面中出现，因此需要在实现方式上提前设边界。

## 决策

### 开发者应该怎么做

- macOS 可调整面板优先使用 `LitheSplitPaneView` 和 `SplitHandleView`。
  如果确实不能复用，必须在变更说明中写明原因，并保持相同的尺寸限制和
  交互行为。
- 拖动使用稳定的坐标空间。连续拖动优先使用全局坐标，避免分隔条移动后
  坐标原点也跟着移动，导致指针和分隔条跳动。
- 高频事件必须节流、合并或经过死区过滤。尺寸状态尽量放在局部布局容器
  中，避免每次拖动都重新计算整个功能页面。
- 为面板设置最小尺寸、最大尺寸和可用空间约束。窗口缩放、面板隐藏和
  面板恢复后，都不能产生负尺寸或布局溢出。
- 交互应与现有 Git、编辑器和工具窗口保持一致，包括悬停/拖动高亮、
  平台习惯的调整光标、帮助文本和无障碍标签。
- 如果尺寸需要在重启后保留，只在拖动结束时通过现有布局持久化机制保存
  最终尺寸，不要在拖动过程中持续写入持久化存储。

### 正确做法

```text
分隔条拖动
  → 局部布局容器接收事件
  → 根据最小/最大尺寸限制结果
  → 必要时合并高频事件
  → 拖动结束后保存最终尺寸
```

### 不要这样做

- 在业务父视图中直接堆叠多个 `DragGesture`，并在每个事件里同时修改
  多个 `@State`。
- 让分隔条的当前位置决定下一次拖动的坐标原点。
- 拖动还没有结束就不断写入用户设置或其他持久化存储。
- 只在 macOS 实现一套行为明显不同的交互，而不检查 Windows 的对应体验。

## 考虑过的备选方案

### 每个页面自己实现拖动

页面可以快速开始，但每个页面会逐渐产生不同的坐标计算、尺寸限制和性能
问题。后续修复时也无法保证所有页面一起变好，因此不采用。

### 只依靠人工体验判断流畅度

人工体验能发现明显卡顿，但很难稳定发现高频重建、窗口边界和恢复布局问题。
因此人工体验可以作为补充，不能代替边界检查和相关验证。

## 后果

- 收益：拖动行为更稳定，面板不会轻易出现负尺寸或溢出，页面重建范围更小。
- 代价：新增可调整 UI 时需要先理解现有布局组件，不能只在当前页面快速
  写一套局部逻辑。
- 需要重新评估的情况：现有布局组件无法支持新的交互，或实际性能数据
  证明局部布局容器仍然不够用。
