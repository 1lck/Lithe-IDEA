# Agent 笔记：声明式语言插件与进程外执行

状态：已实现

## 先说结论

语言插件是声明式插件包：包里只有 `plugin.json` 和它声明的资源（例如随包提供的语言服务器）。Core 读取声明、校验并展开运行与测试命令，宿主自己启动语言服务器和运行进程。插件不在宿主进程内执行任何代码，因此插件包不依赖宿主二进制，应用每次发版也不必重新编译插件，插件可以独立维护和发布。

对日常开发的直接影响：新增语言插件时写 `plugin.json`，不要写原生代码入口。声明格式和语义以 Core 仓库的 `shared/plugins/contract/v1/` 为准，校验与命令模板展开只在 Core 实现一次。

## 问题

早期的原生插件需要与宿主构建的模块接口严格对应，插件一旦脱离宿主构建，就可能找不到符号甚至崩溃；插件在宿主进程内运行，崩溃会带垮应用；插件拆到独立仓库后，还必须跟着每个版本重新编译和发布。

另外，语言插件实际只做四件事：声明语言和文件扩展名、启动语言服务器、生成运行命令、生成测试命令。这些都是数据，宿主已经有通用的语言服务器和执行模块，不需要插件代码。

## 决策

### 1. 契约放在 shared，执行放在 Core

- Core 仓库的 `shared/plugins/contract/v1/` 定义 `plugin.json` 的字段、权限、激活事件、命令模板变量、错误码和状态语义，并提供合法样例、非法样例（附期望错误码）和命令展开的标准答案。
- 兼容性只看插件 API 版本，不以宿主版本号代替。能力版本按能力分别升级，见 [插件契约从统一基线 0 开始](2026-11-11-plugin-contract-single-baseline.md)。
- 校验和模板展开是两端共享的确定性逻辑，放在 Core 实现，通过 `plugins.declarative.validate`、`runPlan`、`discoverTests`、`testPlan` 四个命令暴露。命令是纯函数：宿主每次把清单和请求传进去，Core 不读包、不读工作区。清单内容问题以 `{status: "rejected", error: {code}}` 返回稳定的 `plugin.*` 错误码；只有请求格式错误才是 Core 失败。

### 2. 宿主的加载流程

1. 读取 `plugin.json`，把它交给 Core 的 `validate` 得到规范化声明。旧的原生包格式直接拒绝，绝不加载其代码。
2. 信任检查：宿主内置的官方插件目录固定官方 ID 的签名要求，防止包自行降级；发布者包必须通过整包的 Ed25519 签名验证；与宿主同团队的包只认放在应用内部的包。社区包（`signatureRequirement: "none"`）可以由市场或磁盘确认流程安装，但不能冒用官方 ID。
3. 每个 `packaged` 语言服务器入口必须是包内的普通可执行文件，不能是符号链接。
4. 启用状态只决定能否激活，不需要重启。启动后才安装的包才需要重启才能进入模块图。
5. 语言服务器固定为本插件已安装版本目录中的完整路径，它是唯一候选，不按文件名在 PATH 或其他插件中查找。`systemCommand`（如 gopls）走普通工具发现。
6. 运行时依赖（如 `node`、`go`）由宿主发现，导出为 `LITHE_<TOOL>_PATH` 并放到语言服务器 PATH 的最前面。宿主只使用自己选中的运行时，不使用项目目录里的同名程序；语言服务器会在打开文件时自动启动，不能执行仓库自带的程序。
7. 带 `validationArguments` 的服务器只有探测通过的候选才会被使用。插件在启动后才启用时，宿主先探测再启动，而不是先报"找不到"再靠重试恢复。

### 3. 磁盘安装沿用声明与审批边界

磁盘安装的输入同样交给 Core 的 `plugins.marketplace.installReview` 生成权限和完整程序清单，宿主不另写一套审查语义。本地磁盘的社区包每次首次安装、升级或同版本替换都要确认全部权限和完整程序列表，即使没有新程序也不能免确认。审查与持久化必须保留程序的全部字段（参数、模板、验证探测、初始化选项及构建声明），不能只按命令名批准。

磁盘来源与市场来源分开保存，不声称经过远端仓库或发布者认证。安装暂存、扫描和回滚时都要复验内容。磁盘安装先复制到平台临时目录的私有快照再审查，安装时重验暂存内容，不能审查原目录后再从原目录安装。运行时不写发行包或安装目录。

### 4. 去掉进程内加载与进程级隔离标记

声明式插件不在进程内运行代码，因此不需要进程级加载标记。旧版本留下的标记在启动时直接清除，不隔离任何模块。模块激活的 pending 标记保护保留不变。

### 5. 语言插件的运行与跳转

运行和测试计划由 Core 展开，进程由宿主持有并随插件禁用一并停止。语言服务器跳转到工作区外的源码（如标准库或依赖源码）时，只允许只读打开，并且同时满足：

- 目标按打开时的路径和解析符号链接后的真实路径分别判断，两者都在工作区内才算工作区文件；其余一律按外部规则处理，工作区内指向外部的符号链接，以及外部指向工作区文件的符号链接，都不能绕过只读限制。
- 目标文件及其真实路径都必须是发起跳转的语言的源码文件（例如从 Go 跳只能打开 `.go`）。不能放宽成任意已知语言，因为 `json`、`yaml`、`sh` 等格式也可能存放密钥。
- 历史回放不保存来源语言，而是把文件当作它自己语言的源码重新校验。
- 外部文件始终只读，保存被拒绝。普通打开（项目树、搜索、外部 URL）仍然拒绝工作区外路径。

### 6. 无后缀文件按首行识别

名称和扩展名先交给编辑器原有的路径关联。只有无后缀且未命中关联的文本文件才使用已安装 TextMate 语法文件中的首行规则。Core 验证语法时一并提取规则。宿主在打开文档的后台任务中从已解码的缓冲区取完整首行，交给 Core 按启用插件的注册顺序匹配。启动时恢复的无后缀标签等待首份语言注册表，再决定语言。高亮、行注释和语言服务使用选中的语言。关闭后重新打开文件时重新识别。

例如，插件可以用一条首行规则覆盖用户环境里的解释器路径和常见的 `env` 写法。把解释器名称写进宿主，或执行首行来猜测文件类型，都会破坏插件声明与文件内容之间的边界。匹配只消耗有界文本，沿用打开文档已读取的内容。规则在启动语言服务器之前可用。

提供自有语法的插件可以在语法文件内带首行规则。沿用宿主语法的插件使用独立首行元数据，由 Core 解码后只注册匹配规则。包装宿主语法会触发旧版编辑器替换内置 token 分类规则，导致已有文件的配色变化。独立文件随插件包签名，宿主运行时按包内只读资源读取，旧版忽略该文件。

### 正确与错误示例

正确：为新语言写 `plugin.json`，声明 `languageServers` 和执行提供者，在契约 fixture 中补一个命令展开样例，并在 Core 测试中验证。

错误：在插件包里放入可执行的原生代码；在宿主里按语言 ID 写分支生成命令；在宿主里写死某个插件的工具路径或 ID 来查找语言服务器。

## 考虑过的备选方案

1. 保留原生插件并开启库演进模式：能缓解二进制兼容，但要冻结大量接口，插件仍在宿主进程内运行，崩溃会带垮应用。
2. 先拆仓库再改形态：每次发版都要同步重编插件，发布链路更脆弱，没有解决根因。
3. 在宿主里实现模板展开、只把 fixture 放进契约目录：改动更小，但两端共用的确定性逻辑应放在 Core，否则第二个平台接入时会出现第二份实现。
4. 引入完整的第三方插件进程协议（Worker 或扩展宿主）：当前只需要语言声明和命令模板，已有通用模块足够；将来需要插件自定义逻辑时再单独设计。
5. 让磁盘安装绕过 Core 审查，或复用市场来源：会产生第二套权限语义，并把本地字节误当作有仓库校验来源，因此改为共用审查、保存独立来源。

## 后果

插件与宿主二进制解耦，可以独立发布和拆仓库；同一份声明可供各平台使用；启用、禁用不再需要重启；崩溃后不再误隔离插件。宿主侧的语言特判改为由声明驱动。

代价：声明只能表达契约里定义的能力，需要新能力（新模板变量、新运行时依赖、新权限）时必须升级对应的契约版本，并同步更新 Core 实现、schema、fixture 和桌面端；本机的真实 PHPUnit 集成依赖 PHP 与 Composer，未安装时只能运行语言服务器那一半。

## 验证

- Core：`cargo test` 覆盖合法样例、非法样例错误码、命令展开标准答案，以及仓库内官方 `plugin.json`。
- 桌面端：`scripts/desktop/desktop-go.sh test ./internal/pluginhost/... ./internal/pluginbackend/... ./internal/plugintrust/... ./internal/plugininstall/...` 覆盖包校验、信任策略、安装审查与进程清理。
- `scripts/desktop/verify/verify-runtime-bundle-immutability.sh` 检查插件安装不写入发行目录。
- 新增插件还要验证下载失败、签名失败、取消、等待重启、重装、回滚、禁用和卸载后的进程与文件清理。
- 首行识别：`scripts/desktop/desktop-go.sh test ./internal/workbench -run TestOpenFileUsesPluginFirstLineLanguage`。
- `./scripts/agent-notes/verify-agent-notes.sh`
