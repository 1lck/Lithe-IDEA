# Agent 笔记：项目环境和执行能力的统一 API 与本地 MCP

状态：已实现

## 先说结论

Lithe 对外开放项目环境、Maven、运行配置和执行输出，复用界面已经使用的操作。模型上下文协议（MCP，用于 AI 客户端发现并调用工具）和插件使用同一能力清单、参数校验和项目授权；文件编辑不属于本次开放范围。开发者新增能力时，应先补共享契约，再接入现有工作流，不能在 MCP 辅助程序里重建项目模型或拼另一套启动命令。

## 问题

外部 Agent 能改文件，但不知道当前 IDE 真正采用的工具链、构建 Profile、项目准备状态和运行会话。只公开 Core 命令会绕开应用持有的状态；只复制按钮行为则会让平台、插件和 MCP 各自维护不同的执行链。

## 决策

- 本机通信适配器（Core 仓库的 `lithe-ide-host`，桌面端对应 `desktop/internal/core/ide_host.go`）统一工具清单、参数验证、授权检查、连接文件、请求队列和输出游标。它不负责语言或构建工具的语义、项目事实或进程启动。
- MCP 辅助程序（Core 仓库的 `lithe-mcp`，桌面端对应 `desktop/internal/core/ide_host_helper.go`）使用官方 Rust SDK 实现协议协商、标准输入输出传输和结果格式。它只转发到用户明确授权的本地 IDE 项目。
- 桌面端的 IDE 能力由 `desktop/internal/workbench/ide_api_dispatch.go` 分派到已有的运行、构建与设置工作流。运行前的准备、保存、语言服务同步和原生进程生命周期仍由原有功能负责。
- 插件复用公开能力，而不是访问整个应用对象。插件声明 IDE 权限后，才能通过已绑定的授权连接调用对应接口。声明不能扩大项目授权，也不改变本地语言包只贡献运行计划的限制。
- 用户在设置中的独立"MCP 配置"入口开启连接，不隐藏在 JDK 或构建环境设置内。未打开项目时显示提示，不创建授权。读取、配置和执行权限按项目处理，配置与执行默认关闭。项目关闭、窗口销毁和应用退出都会关闭连接。禁用 MCP 后，已接受的执行仍归 IDE 管理，不能因为一个客户端断线而误杀用户正在看的服务。
- 授权代际：打开连接前登记授权代际，撤销后迟到的连接必须关闭，旧通知只能影响自身连接。项目关闭会等待正在打开的连接完成清理。
- 输出 ID 标识一次执行。旧 ID 不能停止占用同一输出槽的新进程。输出游标在 Core 中按 UTF-8 字节分页，前缀发生变化时显式返回 reset，避免截断后漏读。
- 请求调度：Core 接收请求后通过窗口定向通知推送请求身份，应用恢复后先领取未过期、未取消且未领取的请求。领取响应携带剩余有效期；执行前拒绝超时请求。通知失败不撤销授权，但不自动重放已领取的操作，超时后用户需要先检查操作状态。
- 工具清单与平台接线：共享清单只列出各平台实际接通的工具，声明随授权连接写入私有连接文件。请求入队前执行相同校验，因此直接调用已删除工具会明确失败，而不会触发模块初始化或旧业务路径。
- 构建任务与 Agent：Agent 先查询插件检测到的构建实例、声明和模型 ID，再通过公共构建入口执行。参数保持数组形式，选择器必须与当前模型核对，模型过期时不能执行旧的项目、目标或模型任务。目标语义、参数解释与进程由构建插件负责，宿主不拼接命令。
- 输出快照只保存在内存中：构建输出槽保存最近一次操作的 ID、状态、退出码和输出，任务结束后仍可读取。新任务替换或同路径重开会撤销旧 ID；停止只取消仍匹配的运行身份。
- 环境工具只编辑 JDK 和构建工具的工具链，不激活执行模块，也不为配置 JDK 加载项目模型。设置页存在未保存草稿或正在保存时返回忙碌，不重置草稿，也不代替用户提交其他编辑。
- 连接信息存入平台应用数据目录，锁文件按项目排他持有。关闭连接时删除凭据文件，崩溃后的陈旧文件在重新授权时覆盖。辅助程序随安装包发布且运行时只读，不改变代码签名或增量更新的源字节。连接目录、锁和构建输出不可跨工作树复制。

正确示例：Agent 查询某个构建声明的目标后，把 `["clean", "verify"]` 作为参数数组交给构建 Provider，界面与 Agent 使用同一份生效配置。不要在辅助程序里自行执行构建工具，也不要用旧操作 ID 停止一个已经替换的运行。

## 考虑过的备选方案

1. **只公开磁盘操作**：不能观察 IDE 实际生效的设置和运行会话，收益有限。
2. **辅助程序自己启动构建或 Java 进程**：会绕开已有工作流、模块资源和项目准备，两端出现两套项目状态，因此不采用。
3. **直接公开 Core 调度器**：内部命令不是授权边界，还包含文件与凭据等不属于首期的能力，因此只允许共享能力清单里的命名操作。
4. **将 MCP 协议写两遍**：增加版本兼容和测试成本，因此使用官方 SDK，平台只负责动作接线。
5. **只延长心跳或无限重试**：只能掩盖界面暂停，不能阻止恢复后执行旧操作。原生通知加执行前领取，同时保留请求上限、超时和显式撤销。
6. **共享清单直接等同于每个平台的发现清单**：会向客户端宣称尚未接通的能力。改为由平台宿主选择已接通的工具，但不允许平台另写一套 schema，以免参数类型和权限规则逐渐分叉。

## 后果

用户复制一次客户端配置后，就能通过 AI 使用 IDE 的环境、构建和运行操作。插件获得同一套能力入口。代价是各平台仍须接入自己的应用状态，不能假设类型化的 Core 命令可以直接替代当前窗口或工作区的状态所有权。

连接只面向本机，内部桥接不是公开的 MCP HTTP 服务。默认读取可能包含项目日志中的敏感信息，授权界面需要明确说明。原生进程内插件并没有因此获得新的沙盒隔离。

## 验证

- Core 侧：`lithe-ide-host` 的单元测试覆盖授权、路径、模块参数、输出游标、连接互斥与请求路由。
- 桌面侧：`scripts/desktop/desktop-go.sh test ./internal/core/...` 覆盖 `ide_host_test.go`，`scripts/desktop/desktop-go.sh test ./internal/workbench/...` 覆盖 `ide_api_dispatch_test.go` 与 `ide_api_operation_test.go`。
- 真实 stdio 会话：辅助程序的握手、工具发现、结构化结果和工具错误需要在构建后的程序上验证，Windows 与 macOS 原生验收不能由 Linux 测试代替。
- `scripts/desktop/verify/verify-runtime-bundle-immutability.sh` 确认辅助程序和连接数据不写入发行目录。
- `./scripts/agent-notes/verify-agent-notes.sh`
