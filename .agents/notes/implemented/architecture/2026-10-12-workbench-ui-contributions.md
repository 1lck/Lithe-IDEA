# Agent 笔记：宿主管理的工作台 UI 贡献

状态：已实现

## 先说结论

本轮是第一阶段 UI Contribution 基础设施，静态文本和打开自身窗口的命令只是 API level 2 的当前子集，不是最终公共插件接口。工具窗口和命令使用稳定 ID 注册，由宿主决定怎样显示和保存布局。数据库使用 `database.workspace`，声明式插件也走同一个动作与渲染注册表，新增插件不需要修改工作台的视图分支。插件包只声明数据，公共控件、主题、显隐、顺序和模块生命周期归宿主所有。

## 问题

工作台原有动作和渲染器注册表，但只组装内置模块。工具窗口状态使用封闭枚举，插件新增工具视图就必须修改宿主；布局只保存尺寸，也无法保存某个稳定工具窗口的位置和入口顺序。

## 决策

复用 `WorkbenchModuleUIRegistry`（按贡献 ID 查找动作和内容的宿主注册表）、`ModuleRuntime`（模块生命周期管理器）以及已有共享控件。内置模块仍在组合根组装原生内容；API level 2 声明式插件由同一个通用适配器注册，宿主不读取插件 Swift、脚本或 HTML。

`WorkbenchFeatureModel.ToolWindow` 改成稳定字符串 ID。保留现有静态名称供业务调用，数据库、终端等会话仍归原功能模块所有。宿主保存按贡献 ID 索引的位置、顺序和入口隐藏状态；默认声明只决定首次显示位置。窗口位置、分组和显隐使用已有 `ToolWindowState`，菜单移动与鼠标拖动写入同一份状态，注册偏好仅补充入口隐藏和非窗口命令顺序。旧枚举名称的停靠记录读取时映射为贡献 ID；插件同样可以放入次分组，并与主分组独立打开、关闭和恢复。布局尺寸提交必须合并已有 UI 偏好，不能覆盖它们。禁用或缺失模块时关闭其内容和入口，保留位置与顺序偏好。正常退出或关闭项目先解绑布局存储，再清理窗口；用户主动隐藏才改写保存的展开状态，资源清理不能伪装成用户布局编辑；结束布局会话后，晚到的 SwiftUI 尺寸提交也不能保存清理后的窗口状态。

项目、提交和搜索侧栏也通过模块目录声明动作和内容，不再由工作台枚举分支显示。原生内容仍由宿主组合根组装，保留现有字体、树、提交表单和搜索状态。Pull Requests 入口复用原有能力开关，注册入口不表示该功能已经可用。左侧、右侧和底部按稳定 ID 独立保存，标题收起操作关闭自己的 ID；否则侧栏移动后会误关原先的左栏。

旧工作区会话中的 `project`、`changes`、`search`、`pullRequests` 名称由兼容适配映射到贡献 ID；插件左栏直接保存贡献 ID。旧会话里的插件已卸载或模块已禁用时回退项目入口，不能把无效 ID 打开成空白底栏。旧尺寸配置没有左栏字段时保留原会话选择，新配置明确记录左栏选择和展开状态。恢复所有内置或声明式窗口时按贡献归属激活所属模块，原生窗口通过注册的激活回调复用能力缓存和观察绑定，不能用文本字段或可见标志判断模块已经准备好；例如 Services 即使已恢复为可见也要完成数据库按需激活。Show 入口共用这个 open-only 路径。恢复声明式插件左栏时必须激活其所属模块，并使用只打开语义，不能把已选中的窗口误当成用户切换关闭；等待激活时用户关闭窗口或选择另一窗口，也不能在激活结束后重新抢回左栏。左侧入口列表复用现有滚动控件，插件增加入口后不挤掉设置按钮。几何提交、模块释放与正常退出均不能覆盖用户最后保存的左栏状态。项目树行高与提交背景状态参与渲染身份，既能跟随现有设置，又不会在分隔条每帧更新时重复构造内容。

命令面板复用已有 `LitheActionRegistry`，内置命令以及主工具栏 Run/Debug/Stop 也从宿主动作注册表执行；工具栏读取注册贡献。现有入口右键提供显示、隐藏入口、移至左侧/底部/右侧和调整顺序。按产品要求，主工具栏不再显示 Workbench Actions 省略号菜单，也不另增替代入口；注册目录、已有入口右键动作及偏好存储保留。显示入口与显示内容是不同动作：业务流程显式打开窗口时恢复其入口，隐藏入口不停止模块拥有的进程。

Run、Debug 和 Stop 的主工具栏入口也使用宿主贡献 ID，与插件按钮共用显隐、顺序和工作区偏好。具体按钮保留既有原生呈现，动作由注册表决定运行、重跑或停止目标；禁用所属执行或调试模块时入口不可执行。命令面板中的内置命令与插件命令都从贡献目录读取，保留原分组、快捷键和业务动作，宿主可保存每个入口的隐藏状态和顺序；快捷键也从同一注册表执行，隐藏入口不禁止仍有效的快捷键。原生窗口的命令别名委托已有窗口注册动作，命令面板勾选状态跟随同一个窗口 ID；尤其打开 Run 输出窗口必须走按需激活动作，不能只修改显示布尔值。命令面板和快捷键复用同一模块所有权判断。找回工具栏或菜单入口只恢复可见性，不执行命令；只有显示工具窗口才按需激活。移除顶部管理菜单后，不再宣称提供“菜单命令”和“命令面板入口”的统一恢复子菜单。插件可以声明左侧、右侧或底部为首次停靠区域，保存布局仍优先。

宿主动作注册提供统一的可见、可用、勾选和激活中状态。工具窗口入口、工具栏、菜单及命令面板读取同一个状态；内置命令复用已有快捷键可用性判断，不另建条件表达式。声明式命令在所属窗口激活期间禁用，窗口入口仍允许取消本次显示请求。菜单和命令可以持有旧引用，但每次执行都必须重新检查当前完整贡献与状态；不能只比 ID，也不能只依靠按钮变灰。暂不在活动栏显示的 Services 仍可通过“显示”按需激活，其内容渲染条件不能当成禁用动作条件。

多个窗口属于同一模块时，运行时合并在途构造。取消一个 UI 请求只撤回这个窗口的显示意图，另一个窗口仍可等待同一次模块激活。禁用和关闭先阻止新激活，再取消并等待已有激活清理，完成后才释放资源；晚到的激活不能重新发布能力和贡献。宿主发出 `module.activation-joined` 事件使这种等待可观察，正常取消不显示错误通知。这是宿主生命周期行为，不允许插件在清单里运行状态脚本。

声明式 UI 目前只支持宿主渲染的静态文本窗口和打开本插件窗口的命令。窗口和命令可以声明宿主图标的稳定语义 ID，或包内 SVG/PNG 及可选亮暗变体。宿主统一图标槽位、着色和交互状态；命令面板选中行的模板图标使用宿主选中文字颜色，键盘移动选择时品牌图标仍保持对应亮暗资产的原色；品牌模式只保留资产原色，不改变外层按钮规范；宿主图标声明 original 模式时同样使用原生资源原色，缺少打包资源的调试运行仍使用宿主占位图标。工作台中的窗口与工具栏管理子菜单也复用已注册图标，通过共享下拉组件呈现，不单独定义菜单样式。内部旧 `icon` 字符串仍属于原生模块元数据，声明式字段通过有类型的 `uiIcon` 接入，不能把它解释成 SF Symbol 或任意资源路径。这个阶段范围保证第一条接入路径可以完整验证。API v2 的窗口必填文本、命令必关联窗口，以及无语言/无 UI 的拒绝规则继续保持兼容；这些规则不应复制到下一版公共接口。后续版本化原生组件、独立动作和领域 Provider 的设计见[公共扩展契约与原生 Provider 接入方向](../../proposed/architecture/2026-10-13-public-extension-contract-and-provider-api.md)，当前尚未实现。

Agent 的配置入口由同一个目录补齐，移动到任何已有停靠区域后仍可找到；禁用 Agent 只停止模块资源，保留宿主配置说明。Services 的显示动作复用数据库按需激活入口，激活成功后只展开 Services，不额外打开数据库侧栏。动作可用性与内容可渲染性分别判断：未激活的 Services 仍能请求 Show，实际停靠内容必须同时满足 renderer 的可见/选中条件和动作可用性；旧布局中的 Maven 在非 Maven 项目不占据停靠区域。

共享 Rust 校验要求 `ui.contribute` 权限、`onView`/`onCommand` 事件、插件命名空间内的唯一 ID 和有效引用。插件激活等待上一会话的关闭完成，随后再次检查可用性、取消与工作区身份；关闭会话取消宿主拥有的激活任务。启动时在每个候选包上检查全局动作和渲染器冲突，拒绝的包只留在插件管理诊断里；工作台失败时回退到内置注册，不因第三方元数据终止应用。Windows 仅共享校验，UI adapter 尚未实现，矩阵保留待验证状态；共享市场解析在 Windows/Linux 上不把 API level 2 标为可安装。社区索引 Lithe Store 与 Lua 示例模板沿用既有 schema-2 数据包，语言插件保持 API level 1，新增 UI 才升到 level 2，签名、SHA-256 和社区安装确认流程不变。

图标资源由 macOS 平台适配器在安装、扫描和启动时校验，只接受包内普通文件，逐级拒绝符号链接并限制文件大小和图片尺寸。SVG 使用系统 XMLParser 校验静态子集，再交给原生图像解码；不接受脚本、实体或外部引用。资源内容受插件包签名或社区摘要保护，宿主只在当前目录生命周期内持有不可变字节和解码图像，不生成磁盘缓存；包内资源和 app bundle 均只读，不影响代码签名或 Sparkle delta。插件图标沿用安装版本的更新、回滚和卸载所有权，不能跨工作树复用。

正确做法：数据库注册 `database.workspace` 和其 renderer，宿主根据保存的位置显示。新数据插件声明工具窗口和打开命令，通用适配器完成注册。

不要这样做：按插件名称在 `WorkbenchView` 增加分支；从插件包加载第三方 UI 代码；把终端会话或数据库连接放到显示位置的状态里；运行时写入 app bundle 或插件安装目录。

首次打开、Show 和布局恢复都按停靠组记录临时显示请求。激活完成只提交仍属于该组最新请求的窗口；同组 A 等待期间选中 B 后，A 不能抢回选择。不同组互不取消。用户显隐、移动和布局重置使相应请求失效，这些 token 不写入持久布局。工具窗口贡献排序与实际入口都读取 `ToolWindowState.order`，前移/后移据此寻找相邻项；非窗口命令继续读取贡献偏好或声明顺序。

## 考虑过的备选方案

- 重新引入原生 Bundle UI 插件：会重新绑定宿主二进制，违背已经落地的声明式插件方向。
- 每个插件扩展工具窗口枚举和视图分支：只能实现内置特例，插件无法独立接入。
- 一次性实现全部声明式组件与拖动停靠：扩大协议和资源边界；复用已有六个停靠分组和原生拖动提交路径，复杂插件组件协议另行扩展。

## 后果

内置窗口与声明式窗口可以使用相同稳定 ID、动作查找、布局偏好和禁用清理。宿主不因工具窗口移动而重新创建模块资源；插件安装资源只读，偏好仍通过已有平台设置存储保存，不影响签名或 Sparkle delta。

代价是静态文本和打开窗口命令还不能表达任意插件业务表单；当前复用左侧、底部与右侧各两个停靠分组，每组同时显示一个窗口。内置业务内容仍通过宿主原生 renderer 注册；这条路径不等于任意第三方 Swift Bundle 加载。`database.services` 和组合根的 Maven/按语言 Debug 装配继续作为当前实现保留，后续通用 Services 与类型化 Provider Registry 独立迁移。
