# Agent 笔记：宿主管理的工作台 UI 贡献

状态：已实现

## 先说结论

插件只能声明数据，例如工具窗口、命令和静态文本；显示位置、公共控件、主题、显隐、顺序和模块生命周期都归宿主所有。工具窗口与命令使用稳定 ID 注册，宿主决定怎样显示和保存布局。插件新增工具视图不需要修改工作台的分支，插件包也不能携带第三方界面代码。

## 问题

工作台原本只组装内置模块。工具窗口状态使用封闭枚举，插件新增工具视图就必须修改宿主；布局只保存尺寸，也无法保存某个稳定工具窗口的位置和入口顺序。

## 决策

内置模块仍在宿主中组装原生内容。声明式插件通过同一个通用适配器注册动作与内容，宿主不读取插件中的脚本或 HTML。

工具窗口使用稳定的字符串 ID。宿主保存按贡献 ID 索引的位置、顺序和入口隐藏状态；插件的默认声明只决定首次显示位置，已保存的用户布局优先。旧的枚举名称在读取时映射为对应的贡献 ID。插件也可以放入次分组，与主分组独立打开、关闭和恢复。布局尺寸的保存必须合并已有的界面偏好，不能覆盖它们。

命令和工具窗口可以声明宿主提供的图标语义 ID，或包内的图标资源（可选亮暗变体）。宿主统一图标槽位、着色和交互状态；插件图标只接受包内普通文件，逐级拒绝符号链接，并限制文件大小和尺寸，不接受脚本或外部引用。

命令的可见、可用、勾选和激活中状态由宿主动作注册表统一提供，菜单、工具栏、命令面板与快捷键读取同一份状态。每次执行都必须重新检查当前的完整贡献与状态，不能只依靠按钮变灰，也不能只比较 ID。

API level 2 的声明式 UI 只包括宿主渲染的静态文本窗口和打开本插件窗口的命令。更丰富的组件（树、列表、面板工具栏和右键菜单）与后续版本化的原生组件属于另外的契约，范围见 Core 仓库的插件契约。

插件 UI 的共享校验要求 `ui.contribute` 权限、`onView`/`onCommand` 激活事件、插件命名空间内的唯一 ID 和有效引用。启动时在每个候选包上检查动作和渲染器冲突，被拒绝的包只出现在插件管理的诊断中，宿主不因第三方元数据而终止。

## 考虑过的备选方案

- 重新引入原生 UI 插件包：会重新绑定宿主二进制，违背声明式插件的方向。
- 每个插件扩展工具窗口枚举和视图分支：只能实现内置特例，插件无法独立接入。
- 一次性实现全部声明式组件与拖动停靠：扩大协议和资源边界。当前复用已有的六个停靠分组和原生拖动提交路径，复杂组件协议另行扩展。

## 后果

内置窗口与声明式窗口使用相同的稳定 ID、动作查找、布局偏好和禁用清理。宿主不会因为工具窗口移动而重新创建模块资源。代价是静态文本和打开窗口的命令还不能表达任意插件业务表单。

## 验证

- Core：`cargo test` 覆盖声明式插件的契约校验，包括 UI 权限、激活事件和 ID 唯一性。
- 桌面端：`scripts/desktop/desktop-go.sh test ./internal/workbench/...` 覆盖注册、布局偏好和禁用清理。
- 插件图标和资源只读：`scripts/desktop/verify/verify-runtime-bundle-immutability.sh`
- `./scripts/agent-notes/verify-agent-notes.sh`
