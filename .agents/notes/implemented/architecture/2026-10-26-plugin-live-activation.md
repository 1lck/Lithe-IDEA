# Agent 笔记：插件热激活——后端准备好的插件装完即用，其余仍然重启

状态：已实现

## 先说结论

安装、更新、回退、卸载、启用、停用一个插件时，只有“它的每一项贡献在宿主里都有运行期实现”的插件才免重启生效。判断由宿主后端决定，写在 `PluginDescriptor.canActivateWithoutRestart`，不是 `plugin.json` 里的字段，所以插件契约没有变化，不需要改 Core 仓库的 `shared/plugins/contract/v1/`。这条规则目前落地了四类：第一阶段的“纯调试适配器插件”（只贡献 `debugAdapters`，以及它声明的语言和设置，没有后端、没有其他模块），第二阶段的“纯语法高亮插件”（只贡献带 `grammar` 或编辑配置的语言，见 [独立插件编辑器 API](2026-10-31-plugin-editor-extension-apis.md)），以及“纯项目生成器插件”和“纯工具定义插件”（见[插件注入的新建项目向导](../feature/2026-10-23-plugin-project-generators.md)的工具字段一节）。这几类也可以出现在同一个插件里。

开发者的直接影响：新增一种可以热激活的贡献，必须先给它写运行期的“登记、撤回、查找”三件事，再把它加进 `canActivateWithoutRestart`；不要因为“某个插件看起来简单”就按名字放行，也不要在清单里加一个“免重启”字段。

## 问题

原来每次安装或更新插件，都要重启 Lithe 才生效。原因是插件的贡献在启动时被一次性装进模块图，运行期没有“再登记一个模块”或“撤回一个模块”的路径。对 lldb 这类只给宿主多提供一个调试器的插件来说，重启显得多余：用户装完插件，马上想断点调试。

如果直接把所有插件都改成免重启，会出两个问题：

1. 语言服务器、构建系统、VCS、界面贡献等，在运行期还没有对应的登记和撤回代码。强行放行会得到“装上了但没有任何效果”或者“卸载后进程和界面还在”。
2. 模块图的生命周期和已打开的项目窗口绑定，每个项目窗口各有一套模块图。往模块图里热插一个模块，要同时改所有窗口的图。

## 决策

### 1. 由后端能力决定，不是清单字段

- 正确做法：新增一种贡献（例如语言服务器）的热激活时，先实现它的运行期登记和撤回，再在这个谓词里放行。
- 错误做法：在 `plugin.json` 里加 `restartRequired: false` 让插件作者声明。作者不了解宿主哪些贡献有运行期实现；声明错了，用户看到的是“装上了但没生效”。
- 错误做法：在宿主里写 `if pluginID == "..."`。这违反“插件专属逻辑不进宿主通用代码”。

## 考虑过的备选方案

1. **所有插件默认热激活，插件显式声明才重启**：被否。语言服务器、构建系统、界面贡献等在运行期没有登记和撤回实现，放行等于让用户看到“装上了但没效果”。这个方案要等每类贡献都有运行期实现之后才成立，所以改成逐类放行。
2. **在 `plugin.json` 里加免重启字段**：被否，理由见决策 1。字段会进入公开契约，要在 Core 仓库的 `shared/plugins/contract/v1/` 里新增并登记协议更新记录，且作者无法判断宿主后端是否支持。
3. **把热插件登记进模块图**：被否。模块图和项目窗口的生命周期绑定，每个窗口一套，运行期没有撤回路径；先做模块图的动态登记才能支持语言服务器等贡献，那是后续阶段的工作，不应该让第一类热插件等它。
4. **启动时清理或改写安装资源来省去扫描**：被否。已发布的 app bundle 是只读基线，写入会破坏 Sparkle 增量更新校验。

## 后果

- 收益：只有“后端能力已具备”的插件免重启，其余插件行为不变，没有因为热激活引入半生效状态。
- 生命周期：热激活的登记只在内存中，不持久化；插件包的所有权不变，安装、卸载、回退仍只经过插件包存储。
- 可写位置：不新增可写目录，不写安装目录或安装资源，不影响代码签名和 Sparkle 增量更新基线。
- 代价：插件包被替换或停用时，正在运行的相关调试会话会被停止；其他项目窗口的插件管理列表要等下一次刷新。
- 仍需重启的贡献：语言服务器、运行/测试、编辑器动作后端（依赖 `backend`）、构建系统、VCS、界面贡献、网页窗口。后续按“先有运行期登记和撤回，再放进谓词”的顺序逐类加入，每类单独验证。
