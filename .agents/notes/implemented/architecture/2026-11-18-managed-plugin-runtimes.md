# Agent 笔记：插件声明的运行时按依赖身份安装并跨插件版本复用

状态：已实现

## 先说结论

插件可以显式声明安装自己所需的运行时，用户批准该插件的程序与下载权限后，宿主先让插件检查已有安装，只下载缺失项。完成校验的依赖放在该插件的跨版本状态目录，因此普通插件升级不必重复下载大型运行时。Core 决定声明是否合法、当前平台选哪个归档以及回复是否完整；插件判断实际安装是否合用，宿主负责下载、文件安全和进程生命周期。默认随插件打包资源的方式仍然有效，不声明新能力的插件保留原有流程。

## 问题

把大型运行时随每个插件版本打包，更新少量插件代码也要重新传输依赖；完全依赖用户安装，又容易因工具缺失、版本或目录不兼容而启动失败。简单地在语言服务器启动时下载也有问题：包已显示安装成功，实际依赖却可能尚未可用；下载中断和插件更新重叠时，旧进程还可能读到正在覆盖的文件。

已有插件状态目录可以提供写入位置，但目录本身不回答依赖版本、平台、来源、校验值和兼容性问题。需要把这些内容纳入正式清单和审批，同时保持应用安装包只读，且不能把某种语言的下载规则搬回宿主。

## 决策

### 1. 新能力必须显式声明并进入程序审批

`managedRuntimes` 是版本为 0 的可选能力，同时要求 `runtimes.install` 权限。插件清单固定每个依赖的版本、平台归档、HTTPS 来源、SHA-256 和相对目录布局，并声明一个检查函数。这些内容进入既有程序审批摘要，插件改变下载来源或可执行文件布局时必须重新走审批。

检查函数由插件自带的后端运行；这个后端必须能够独立启动，不能先依赖尚待准备的工具。宿主在审批后、插件版本提交前运行检查，因此检查失败或下载失败不会替换已安装的可用版本。检查进程不加入正常插件函数转发，不获得工作区和其他宿主服务授权；宿主仍可直接调用它，并接收能力查询和日志。

### 2. Core、插件与宿主分别回答不同问题

Core 校验清单、按平台选择唯一归档、计算稳定缓存键，并校验检查结果覆盖全部依赖且没有未知或重复项。插件检查显式配置、宿主提供的候选目录和外部工具事实，决定哪些目录合用、哪些依赖缺失；无效的显式选择应报告错误，不能悄悄换成下载。宿主只执行通过 Core 校验的计划，不推断语言版本，也不维护特定工具的下载地址。

安装检查使用全局设置；启动前修复使用随后启动所用的有效设置快照，避免忽略项目覆盖。选中的运行时目录只读传给该次语言服务器启动；声明绑定的工具也只覆盖这一次启动，不写全局工具目录、项目配置或用户选择。

全局选择模式不抹除已打开项目的路径边界。工作区上下文按真实 Open、Close、CloseAll 生命周期登记根目录，跨窗口和标签页按引用计数维护；一次准备捕获同一份根快照，供原生探针执行前检查和 Core 工具路径分类使用。检查函数返回的工具目录仍以固定 Home 走 Core 校验，确认实际可执行文件是同一文件后，向后续启动传递已验证的规范路径与 Home，避免重新使用项目内可变的符号链接。这个过程只读，不写工具目录或信任授权。

上下文由界面在打开项目时同步建立。后台激活、语言服务启动和共享构建服务只消费捕获的 ContextRef，不代替已关闭项目重新 Open；关闭后即使重新打开同一路径，旧身份也不能借用新项目。准备结束及原生启动边界再次核对身份，失效时沿用取消与销毁流程。这使共享根引用严格对应仍打开的项目，迟到后台任务不会留下永久根记录。

正确做法：插件检查函数确认一个外部安装完整可用后返回该目录；若另一个声明依赖缺失，宿主只下载后者。
不要这样做：宿主通过插件名称猜测所需工具版本，或者发现项目工具不合适时直接修改项目默认工具。

### 3. 按依赖身份保留完整文件，不按插件版本覆盖

受管文件位于 `<plugin-root>/.state/<plugin-id>/runtimes/<cache-key>/`。缓存键包含选定依赖的版本、平台、下载内容身份和布局，不包含插件版本；同一依赖跨插件升级可直接复用。不同插件不共享这个目录，外部安装也不转为宿主拥有的文件。

下载归档经过 SHA-256 校验后保存。解压先写私有目录，核对路径、链接、数量和字节预算，再调用插件检查；检查通过且输入文件没有被改写，才原子发布完成记录。每次发布使用新的完整目录，不原地替换旧进程正在读取的文件。归档损坏时重新下载；展开文件损坏而归档仍有效时可离线重建。旧的完整目录保留到插件状态被删除，为仍运行的进程和旧插件版本提供稳定路径。

安装与升级完整核对缓存文件哈希；正常启动先核对文件清单和元数据，再由插件作有界兼容性检查。启动发现缺失或损坏时复用同一准备流程。缓存布局、限制与清理规则见 [CI 构建与资源归属](../../../../docs/ci-builds.md)，它不是可以跨工作树复制的构建缓存。

### 4. 取消、禁用和卸载必须等待准备工作结束

宿主跟踪准备任务及其检查进程。取消后清理未发布文件；禁用、替换或卸载先阻止新任务，取消并等待已有任务和语言服务器退出，再进行后续操作。停止失败保留包和状态供重试，避免后台任务在删除后重新创建目录。外部安装不在删除范围内；禁用也不删除已下载完成的依赖。

应用包、插件包和受管完成目录都是只读输入。索引、日志和进程的可写配置仍使用各自状态目录；这沿用[运行时保持发布程序包不变](../bug-fix/2026-09-25-runtime-bundle-immutability-and-update-delta.md)的边界。默认打包资源的规则见 [LSP 插件构建与分发](2026-09-30-lsp-plugin-build-and-distribution.md)。

### 5. 准备进度使用共享词条和原有生成器

检查、下载、解压、验证、修复和取消都显示当前准备阶段；失败说明保留旧插件版本与已校验下载物，用户可以重试。宿主新增文案仍由共享 i18n 生成，具体插件的诊断由插件自己翻译。

这组声明和双语译文放在 `shared/i18n/features/plugin-managed-runtimes.json`。既有注册表已经超过提交接口的单次内容上限，而旧下载与权限文案的语义不适用于运行依赖，因此采用构建时的小文件输入，不重排大词库，也不换用含义不同的提示。原生成器合并后继续执行同一套声明、平台、别名、参数和完整翻译校验；片段不能重复或覆盖别处的词条。运行时只读取既有生成字典，没有额外加载路径。格式与操作见[共享翻译](../../../../shared/i18n/README.md)。

## 考虑过的备选方案

- 每个插件版本都内含完整运行时：适合需要完全离线分发的插件，也继续受支持，但会重复传输不变的大文件。
- 宿主按语言名称管理共享工具目录：目录少，但兼容规则、下载地址和清理责任会重新落回宿主，多个插件还可能互相影响版本。
- 只在第一次语言服务器启动时补装：接入简单，却无法在安装提交前发现问题，用户看到安装成功后仍要等待或排查失败。
- 插件更新时覆盖同一路径：节省旧目录空间，但无法保证旧进程继续读取完整文件，Windows 上运行中的可执行文件也可能无法替换。

## 后果

插件更新可以复用未变化的依赖，已具备合用外部安装的用户不必重复下载；缺失和损坏都经过相同的检查、校验与错误通道。新增语言的规则留在插件仓库，宿主和 Core 只新增一次通用能力。

代价是首次安装可能需要较大下载，插件必须提供独立可运行的检查后端并维护固定校验值。保留归档和旧的完整目录会占用更多磁盘；当前按整个插件状态清理，不在升级时猜测哪些旧进程已经不再使用目录。没有匹配平台归档、无法联网且没有合用缓存、或显式配置无效时，准备会明确失败，不提交半完成的插件版本。
