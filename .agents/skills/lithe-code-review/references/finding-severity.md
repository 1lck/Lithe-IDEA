# Finding 严重程度与证据规则

## 两个维度

严重度描述问题本身的影响，归属描述它和本次改动的关系。两条都要标，缺一不可。

**严重度**

- **P0**：安全事故、数据破坏、凭据泄露、发布系统全面失效或无法安全回滚。
- **P1**：明确导致核心功能错误、严重回归、数据丢失、跨平台契约破坏或关键资源无法清理。
- **P2**：能够复现但影响有限的问题，或缺少重要边界处理、测试或错误路径。
- **P3**：有明确维护收益的非阻塞问题。

**归属**

- **本次引入 / 本次加剧**：由这次改动造成或明显恶化。
- **存量（#issue）**：改动之前就存在，已经建单，不在本次修复范围。
- **存量未建单**：改动之前就存在且还没有 Issue。不要求改代码，只要求当次建单，
  合并前补齐；补上编号后即视为已处理。

阻塞合并的只有三种：P0、P1，以及归属为“存量未建单”的条目。P2/P3 只能作为建议修改，
不能包装成阻塞问题。同样是 P2，标“本次引入”和“存量（#123）”的区别在于要不要在这个
PR 里修，而不是问题轻重不同。

存量问题不因为严重就借本次 PR 扩大范围：严重度照常标，但它走建单和排期，不在本次修。

## 示例（格式示意，不对应真实代码）

无法复核的写法，不要这样报告：

> 建议重构这块，职责不够清晰。

可复核的写法：

> **[P2 / 本次引入] 后退失败时不回滚历史快照，后退会停在失效位置**
> `macos/Sources/Lithe/Application/Features/NavigationHistoryFeatureModel.swift:71`
> - 实际影响：目标文件已被外部删除时，一次失败的后退仍消耗一条历史记录
> - 触发条件：`navigateBack` 找不到目标，`onFailure` 未恢复 `historySnapshot`
> - 复现步骤：打开 A、B → 后退到 A → 在 Finder 删除 A → 再后退一次
> - 修复方向：失败分支恢复快照，或在恢复前校验目标仍存在

该报却没报的写法（归属为“存量未建单”）：

> 发现两端各写一份历史快照逻辑，但 PR 里写“后续再沉入 Core”——没有 Issue 编号，
> 按存量未建单报告，合并前补齐。

## 存量条目的去向

- 存量且已建单 → 写进输出的 `Observations`，本 PR 不修。
- 存量且未建单 → 作为阻塞项报告，当次建单后解除；不要求改代码。
- 本次引入或加剧 → 写进 `Findings`，本 PR 修。

## 证据要求

只报告高信号问题。内部估计置信度低于 80/100 时不要报告；不要为了填充输出
而降低标准。

每条 Finding 必须包含：

- 当前 head 中可定位的仓库相对路径和行号。
- 触发条件。
- 实际影响。
- 可复现步骤，或足以构造复现的输入和调用路径。
- 为什么是本次变更引入或加剧。
- 对应的具体修复方向。

默认将位置指向当前 PR 修改或新增的行。如果问题发生在未修改调用方，
必须同时指出修改的接口或行为，以及它如何导致该调用方出错。

不要报告以下内容：

- 仅有格式、命名偏好或更 idiomatic 的写法。
- 没有实际回归的推测性未来风险。
- 变更前就存在、未被本次改动恶化、并且已经建单的问题：只写进 `Observations`，
  不放进 `Findings`；尚未建单的按“存量未建单”作为阻塞项报告。
- 只有“可以更优雅”但没有明确影响的结构意见。
- 无法稳定复现、无法定位或证据不足的问题。
