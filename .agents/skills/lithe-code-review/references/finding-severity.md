# Finding 严重程度与证据规则

## 严重程度

- **P0**：安全事故、数据破坏、凭据泄露、发布系统全面失效或无法安全回滚。
- **P1**：明确导致核心功能错误、严重回归、数据丢失、跨平台契约破坏或
  关键资源无法清理。
- **P2**：能够复现但影响有限的问题，或本次变更缺少重要边界处理、测试或
  错误路径。
- **P3**：由本次变更引入且有明确维护收益的非阻塞问题。

P0/P1 才能阻塞合并。P2/P3 只能作为建议修改，不能包装成阻塞问题。

## 流程阻塞项

不属于 P0–P3 的一类阻塞项：不要求本次改动修改代码，只要求补齐流程证据，合并前
必须完成。目前只有一条：

- 存量债（本次改动之前就存在、未被本次改动恶化）没有对应的 Issue 编号和链接。
  发现即建单；PR 说明或审查输出里出现没有 Issue 的“以后处理”“后续 PR 跟进”
  “记录在此”同样计入。补上 Issue 后该项即解除，不需要修改代码。

## 证据要求

只报告高信号问题。内部估计置信度低于 80/100 时不要报告；不要为了填充输出
而降低标准。

每条 Finding 必须包含：

- 当前 head 中可定位的仓库相对路径和行号。
- 触发条件。
- 实际影响。
- 可复现步骤，或足以构造复现的输入和调用路径。
- 为什么是本次变更引入或加剧。
- 对应的具体修复方向。

默认将位置指向当前 PR 修改或新增的行。如果问题发生在未修改调用方，
必须同时指出修改的接口或行为，以及它如何导致该调用方出错。

不要报告以下内容：

- 仅有格式、命名偏好或更 idiomatic 的写法。
- 没有实际回归的推测性未来风险。
- 变更前就存在且未被本次改动恶化的问题（存量债按上面的流程阻塞项处理：不要求
  修，但必须已建单）。
- 只有“可以更优雅”但没有明确影响的结构意见。
- 无法稳定复现、无法定位或证据不足的问题。
