# 统一代码审查政策

请严格结合需求、目标分支和实际改动进行判断。

## 核心检查

1. 先确认变更是否满足关联 Issue 或明确需求。没有关联 Issue 时跳过
   Issue 完成度判断；只实现部分内容时，明确已完成和未完成范围。
2. 判断问题是否由本次变更引入或明显加剧。非本次变更引入、且未被本次
   改动实质恶化的问题，不要求当前变更修复。
3. 检查是否符合现有架构、命名、风格、错误处理和模块边界。
4. 检查日志是否覆盖关键流程、异常分支和失败场景，是否有可关联且脱敏的
   上下文；不得输出密码、令牌、隐私、完整机器路径或环境内容。
5. 检查错误处理、边界条件、并发安全、取消、资源清理、兼容性和可测试性。
6. 评估职责是否清晰，是否新增隐式耦合、重复实现、难以测试的结构或整体
   重写风险。
7. 避免过度抽象和无必要依赖。新增抽象必须服务于明确复用、跨平台一致性
   或职责边界。
8. 检查新增文件的命名、目录归属和职责，避免单个文件职责过多或放置位置
   与同类文件明显不一致。
9. 只检查本次新增或显著扩大的文件、目录规模问题。拆分建议必须基于明确
   职责边界、依赖关系和维护收益，不得为了降低行数机械拆分。
10. 按 `develop-lithe` 第三节“逻辑归属”检查本次新增或修改的逻辑：不属于
    上游工具事实、不属于工具专属知识、也不需要调用操作系统或界面框架 API 的
    逻辑，必须在 Core 仓库的 `rust/crates/core` 实现。以下情况作为本次引入的问题报告：
    新功能把这类逻辑写在 `desktop/` 的 Go 代码中；修改了平台层已有的这类逻辑，
    既没有迁入 Core，也没有在 PR 说明中写明理由并关联 `refactor` Issue。
    本次未触及的历史平台层逻辑不要求当前变更迁移，按第 16 条列为观察项并必须已建单。
    判定必须落到可核对的证据，不能只凭“看起来像业务逻辑”：
    - 为本次新增和修改的每个逻辑块写一行归属；判为 Core 的行必须给出兼容命令名
      （例如 `workspace.filterChanges`）与对应 fixture 路径，给不出来按“本次引入”
      报告，不允许以“后续再沉入”带过。
    - 判为平台层的行必须指出它实际调用的原生 API 或平台类型；“和界面相关”“属于
      平台层”不是依据。
    - 同一行为在两端各有一份实现时，逐项对照两端文件与符号，确认差异属于平台差异
      而不是重复实现；确认不了按重复实现报告。
    - 对账结果写进输出模板的“架构归属对账”，本次仍未迁移的存量项写进“未沉入清单”。
11. 检查新增行为、失败场景、边界条件和跨平台契约是否有必要的测试、共享
    契约、文档和验证。不要为了形式完整增加与本次变更无关的内容。
12. 问题必须有明确触发条件、实际影响和合理复现路径。无法稳定复现或只是
    主观偏好时，不得列为阻塞问题。
13. 所有结构、质量和可维护性问题，都必须先确认由本次变更引入或加剧。
14. 检查本次变更是否改变了架构边界、共享契约、状态机、测试策略或发布流程。
    如果改变，必须确认相关 Agent Note 是否需要同步更新；如果新增或修改的
    `docs/` 文档包含长期决策、取舍或约束，应建议将决策正文迁入
    `.agents/notes/implemented/`，`docs/` 只保留操作说明、正式 schema、
    发布说明或验收材料。
15. 按 `develop-lithe` 第四节检查性能与内存。以下情况作为本次引入的问题报告：
    在用户尚未使用时预先启动的功能、插件后端、语言服务器、WebView 或子进程；
    空闲时持续运行的轮询或定时器；没有上限的缓存、队列或输出缓冲；关闭项目、
    窗口、面板或标签后未释放的独占资源；未设置内存上限的子进程；主线程上的
    文件读写、目录遍历或进程启动；跨 C ABI 或 web view 消息边界传输
    全量数据；未虚拟化的长列表。改动涉及启动、打开项目、输入、滚动、大文件、
    长输出或搜索时，检查 PR 是否给出改动前后的性能基线数据；上调预算、删减
    场景或缩小 fixture 按绕过检查报告。
16. 本次改动导致变成无用的代码却没有删除时，作为本次引入的问题报告。本次变更
    之前就已存在的无用代码、可重构之处或未沉入 Core 的逻辑不在当前 PR 中修复，
    但必须已经提交 `refactor` Issue。输出里每条存量债都要带 Issue 编号和链接，并写明
    代码位置与判定依据；没有编号的条目按归属“存量未建单”作为阻塞项报告，合并前补齐。
    发现即建单、修复另排是两件事：不要求当前变更修，但要求当前就建单。
    什么算“没有建单”、建不了单时怎么写，以 `develop-lithe` 第九节的执行步骤为准；
    这里不另立一份写法清单，避免两处漂移。
    审查默认只读、不代提 Issue；用户明确要求代提时按 `submit-lithe-issue` Skill
    执行（查重、模板、脱敏），不得跳过查重或伪造表单来源。
17. 缺陷修复按 `develop-lithe` 第八节检查：是否有修复前失败、修复后通过的
    回归测试（无法自动化时是否写明手动验证步骤）；被修改的函数、类型和契约
    字段的全部调用方（包括另一平台、插件、SDK、脚本和动态分发）在新行为下
    是否仍然正确；是否在症状位置加特判掩盖根因。
18. 按 `develop-lithe` 第三节“插件归属与宿主零依赖”检查本次改动有没有把插件专属内容带进
    宿主，或让宿主依赖具体插件。具体检查项和严重程度见下方“插件归属与宿主零依赖”。

## 取证手段

每条“检查是否……”都必须落到一个能复核的动作。按问题类型取用：

| 问题类型 | 取证动作 |
| --- | --- |
| 影响面与调用方 | `find_references`、`blast_radius`；跨平台、插件、脚本、SDK 另用 `rg` 搜符号名和命令名 |
| 行为何时被引入 | `git log -S '<符号或字符串>'`、`git blame <路径>` |
| 共享契约或字段变更 | 先对 fixture，再搜另一平台、插件 SDK、脚本三处消费者；缺一处即为 Finding |
| 分层与归属 | `develop-lithe` 第十一节验证表中对应的行；表中写明已移除、尚未恢复的边界检查，按“门禁未完成”写进 Verification，不得记为通过 |
| 插件归属 | `develop-lithe` 第三节“插件归属与宿主零依赖”的自查命令；再对本次新增或修改的测试逐个确认它的输入只有合成插件、Core 契约 fixture 或插件市场索引快照 |
| 性能与内存 | 改动前后各跑一次对应平台基线，报告里给出 `ready_rss_kib`、`stable_rss_kib` 之类实测值 |
| 用户可见文案 | `node scripts/i18n/verify-app-language-localization.mjs`、`generate-i18n.mjs --check` |
| 发行目录与资源 | `./scripts/desktop/verify/verify-runtime-bundle-immutability.sh` |

拿不到证据时写“信息不足”并说明缺什么；不得用推测补全结论，也不得把“看起来”写成“确认”。

## 成熟能力复用审查

插件 API 和迁移审查同时检查 `develop-lithe` 的“插件能力”规则：领域模型统一不等于所有插件必须
经 LSP/Build/Debug。独立高亮、文档和编辑器动作有自己的小型契约，复用基础设施但不继承无关
领域语义；真正的构建模型等也不能借私有函数绕过领域校验。用第二个不同工具检查通用性，
重点查宿主新增的工具/运行时/格式枚举、固定任务 ID、名字猜测、配置解析器及无退出条件的迁移回退。

触发：新增或扩大语言智能、项目导入、构建模型、依赖解析、编译、格式化、重构、测试发现、
运行/调试计划或 LSP/DAP 行为。判定标准以 `develop-lithe` 第三节“复用成熟上游”为准，
本节只规定审查侧的取证要求，不复述判定规则：

1. 必须指出已打包上游的版本、现有能力和官方扩展点，以及“升级或完整启用它仍不够”的具体
   证据。只写“接入麻烦”“更可控”“以后可能需要”不成立。
2. 新实现必须只拥有 Lithe 的编排、资源预算、取消、过期结果保护和稳定契约；符号、源码根、
   模块归属、依赖图、classpath、编译状态和调试目标仍以上游为准，不得出现第二份领域真源。
3. 用第二个语义不同的工具检验通用性：接入它需要改宿主或 Core，就说明扩展点泄漏了第一个
   工具的语义。宿主新增按工具名或格式的分支、固定任务 ID、名字推断同样属于泄漏。
4. 部分复用必须覆盖完整用户链路（例如保存 → 项目状态同步 → 构建 → 解析运行路径 → 启动），
   不能只验证单个命令、参数或 mock 返回值。
5. 确需自研时，相关 Agent Note 是否记录了上游版本与能力、许可与分发限制、已证实的能力缺口、
   被否方案和退出条件。

新增并行实现但缺少上述证据：按架构所有权与双重真源问题报告，默认 **P2**；只有在有明确
可复现的正确性、兼容性或资源回归时才按 **P1**。

## Lithe 特别边界

目录归属、Core 与平台层职责划分以 `develop-lithe` 第三节“目录归属”和“逻辑归属”为准，
本节不重复列举。审查时特别注意：

- 架构取舍、所有权边界和高风险约束以相关 `.agents/notes/implemented/` 为准，
  不以本次改动的自述为依据。
- 测试问题结合稳定性规则判断：有界等待、确定性时间、取消与清理，以及是否真正接入 CI。
- 只有当行为或契约确实改变时，才要求更新 Agent Note、共享契约或流程文档。
- 相关 Note 的适用范围、路径、验证命令或决策已经失效时，建议更新原 Note；新决策取代旧决策
  时迁移到 `archived/`，不要让过时 Note 继续作为当前实现依据。

## 插件归属与宿主零依赖

宿主仓库和 Core 仓库对具体插件零依赖；插件的代码、测试、功能矩阵、翻译和构建资源说明只在
插件仓库。定义和规则以 `develop-lithe` 第三节“插件归属与宿主零依赖”为准，本节只规定审查动作
和严重程度。每次审查都执行，不只在改动“看起来和插件有关”时执行：插件内容最常通过测试、
功能矩阵、i18n 词条和资源登记进入宿主。

逐项检查本次新增或修改的内容：

1. **测试。** 测试是否读取具体插件的插件包、仓库检出、构建产物或清单（包括通过环境变量、
   固定路径、下载或 Git 子模块获取）；是否使用真实插件 ID；是否断言某个具体插件的行为；
   是否用“缺少插件时跳过”保留这类测试。宿主的测试只能使用合成插件、Core 契约 fixture 和
   插件市场索引快照；对快照的断言只能针对所有条目共同适用的规则。
2. **代码与 CI。** 宿主代码、脚本和 CI 工作流是否按插件 ID、插件名或工具名增加分支，是否
   下载、构建或检出具体插件。
3. **功能矩阵。** 是否为具体插件提供的能力新建或更新 `shared/platform-feature-matrix/` 条目；
   宿主条目的证据路径和验证动作是否引用具体插件的测试、插件包或插件仓库。
4. **界面文案。** 是否把插件的文案（清单标题和说明、插件界面、插件后端消息）写进
   `shared/i18n/`，或在宿主代码里为某个插件补译文。
5. **资源与文档。** `scripts/resources/worktree-resources.json`、`docs/ci-builds.md`、Agent Note 和
   Skill 是否写入具体插件的构建步骤、资源路径、补丁、测试命令或验证结果，并把它们当作宿主
   规则或宿主验证证据。链接插件仓库作为示例不算问题。

严重程度：以上任一项由本次改动引入时，按 **P1 / 本次引入** 报告，属于阻塞项，合并前必须把内容
迁到插件仓库、改用合成插件或删除。它让宿主测试结果随插件版本和本机检出变化，并让插件内容
在两个仓库各有一份。不得以“测试默认跳过”“只在本机运行”“插件仓库还没有对应测试”作为降级
理由；插件仓库缺少对应测试时，修复方向是在插件仓库补测试，不是保留宿主里的副本。

修复方向的写法：指出内容应迁往的插件仓库，或应改用的合成插件、契约 fixture；需要删除宿主
矩阵条目时，同时指出受影响的宿主条目证据要改成哪些宿主测试。

## 界面文案与 i18n

只要变更新增或修改了用户可见文字，就必须逐项核对：

- 文案是否都经统一接口生成：视图字面量有 `shared/i18n` 词条，视图之外使用 `L10n.string`；
  出现直接 `String(localized:)`、`NSLocalizedString`、只传 `locale:`、`errorDescription` / `NSAlert` /
  `NSLocalizedDescriptionKey` / 通知 / 字符串参数里的裸英文，都按硬编码处理。
- 同一次改动是否补齐 `shared/i18n` 的 `messages.json`、`en-US.json`、`zh-CN.json` 并提交生成结果；
  参数个数、类型与顺序是否一致，句子是否被拆成会在中文里语序错误的片段。
- 是否修改了 `scripts/i18n/verify-app-language-localization.mjs`、扩大豁免名单、改用 `Text(verbatim:)` 或把文案放进
  变量来躲过检查；这类绕过本身就是问题，不能当作“检查已通过”。
- 是否把上游诊断、用户内容或 Agent 返回内容错当界面文案去翻译或改写。
- 是否把插件文案当作宿主文案写进 `shared/i18n`。这一项按“插件归属与宿主零依赖”报告。
- 审查时运行（或要求作者提供结果）`node scripts/i18n/verify-app-language-localization.mjs` 与
  `node scripts/i18n/generate-i18n.mjs --check`。

严重程度：硬编码或绕过 i18n 的用户可见文案默认按 **P2** 报告并要求修复后再提交 PR；
能说明在系统语言与应用语言不一致时会显示错误语言，或检查脚本被放宽、跳过时，按 **P1** 报告。

## 界面说明与生效值

变更新增或修改设置项、对话框选项或有标题的功能区时，按 `develop-lithe` 第五节检查：

- 满足“用 ⓘ 解释”任一触发条件的项是否提供了 ⓘ，内容是否说明这一项做什么、对用户有什么
  影响，而不是重复标签文字；是否改用了控件下方的常驻说明文字。
- 用户可修改的配置处于自动、默认或继承状态时，是否显示为“自动（实际生效值）”；括号中的值
  是否来自 Core 返回的同一个解析结果，而不是界面另写的推测逻辑；是否用带参数的 i18n 词条。

严重程度：缺少 ⓘ 按 **P3** 报告；只显示“自动”“默认”“继承”，或括号中的值由界面另行推测，
按 **P2** 报告。

## 需求与范围判断

- 多个 Issue 时逐个判断，并说明各自完成度。
- 没有可访问的 Issue 时写明“未找到可验证的关联 Issue”，不得虚构需求。
- PR 描述不能替代实际证据；以变更、调用链、测试和已有验证结果为依据。
- 按 `finding-severity` 的两个维度标注严重度和归属。只有“本次引入”“本次加剧”可以进入
  Findings；已建单的存量写进 Observations，未建单的按阻塞项报告。
- 如果 base/head、变更清单、关键调用链或验证信息不完整，结论写“信息不足”，
  不要用猜测补全。
