# 统一代码审查政策

请严格结合需求、目标分支和实际改动进行判断。

## 核心检查

1. 先确认变更是否满足关联 Issue 或明确需求。没有关联 Issue 时跳过
   Issue 完成度判断；只实现部分内容时，明确已完成和未完成范围。
2. 判断问题是否由本次变更引入或明显加剧。非本次变更引入、且未被本次
   改动实质恶化的问题，不要求当前变更修复。
3. 检查是否符合现有架构、命名、风格、错误处理和模块边界。
4. 检查日志是否覆盖关键流程、异常分支和失败场景，是否有可关联且脱敏的
   上下文；不得输出密码、令牌、隐私、完整机器路径或环境内容。
5. 检查错误处理、边界条件、并发安全、取消、资源清理、兼容性和可测试性。
6. 评估职责是否清晰，是否新增隐式耦合、重复实现、难以测试的结构或整体
   重写风险。
7. 避免过度抽象和无必要依赖。新增抽象必须服务于明确复用、跨平台一致性
   或职责边界。
8. 检查新增文件的命名、目录归属和职责，避免单个文件职责过多或放置位置
   与同类文件明显不一致。
9. 只检查本次新增或显著扩大的文件、目录规模问题。拆分建议必须基于明确
   职责边界、依赖关系和维护收益，不得为了降低行数机械拆分。
10. 确定性、可复用、跨平台的能力优先沉淀到 `rust/lithe-core`，再由平台
    适配层接入；平台特有能力留在对应平台。只有确实共享语义时才提出下沉，
    不得借 Review 要求无关的历史重构。
11. 检查新增行为、失败场景、边界条件和跨平台契约是否有必要的测试、共享
    契约、文档和验证。不要为了形式完整增加与本次变更无关的内容。
12. 问题必须有明确触发条件、实际影响和合理复现路径。无法稳定复现或只是
    主观偏好时，不得列为阻塞问题。
13. 所有结构、质量和可维护性问题，都必须先确认由本次变更引入或加剧。
14. 检查本次变更是否改变了架构边界、共享契约、状态机、测试策略或发布流程。
    如果改变，必须确认相关 Agent Note 是否需要同步更新；如果新增或修改的
    `docs/` 文档包含长期决策、取舍或约束，应建议将决策正文迁入
    `.agents/notes/implemented/`，`docs/` 只保留操作说明、正式 schema、
    发布说明或验收材料。

## Lithe 特别边界

- `rust/lithe-core` 承载确定性共享行为、模型、验证和跨平台语义。
- `shared/` 承载跨平台契约和 fixture，不承载编译实现。
- macOS 平台能力留在 `macos/Sources/Lithe/Platform/MacOS/`。
- Windows 前端通过 `@/platform/tauri-core` 和统一 dispatcher 接入共享能力。
- 架构取舍、所有权边界和高风险约束以相关 `.agents/notes/implemented/`
  为准。
- 测试问题必须结合稳定性规则判断，重点关注有界等待、确定性时间、取消和
  清理，以及是否真正接入 CI。
- 只有当行为或契约确实改变时，才要求更新 Agent Note、共享契约或流程文档。
- 如果相关 Note 的适用范围、路径、验证命令或决策内容已经失效，必须建议
  更新原 Note，或在新决策取代旧决策时迁移到 `archived/`；不要让过时 Note
  继续作为当前实现依据。

## 需求与范围判断

- 多个 Issue 时逐个判断，并说明各自完成度。
- 没有可访问的 Issue 时写明“未找到可验证的关联 Issue”，不得虚构需求。
- PR 描述不能替代实际证据；以变更、调用链、测试和已有验证结果为依据。
- 将每个问题标记为“本次引入”“本次加剧”“历史问题”或“未确认”。
  只有前两类可以进入 Findings。
- 如果 base/head、变更清单、关键调用链或验证信息不完整，结论写“信息不足”，
  不要用猜测补全。
