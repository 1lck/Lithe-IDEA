# 本地代码审查输出格式

始终使用简体中文。

```markdown
## Lithe Review

**结论：** ✅ 未发现明确问题 / ⚠️ 建议修改 / ⛔ 存在阻塞问题 / ❓ 信息不足
**范围：** `目标分支 ← 当前分支` · `commit range 或工作区状态`

### Findings

1. **[P1 / 本次引入] 简短且可执行的问题标题**
   `仓库相对路径:行号`

   - 实际影响：
   - 触发条件：
   - 复现步骤：
   - 修复方向：

   严重度与归属分开标：P0–P3 描述影响，归属取“本次引入”或“本次加剧”。存量条目
   不进 Findings，按下方 `Observations` 和“存量未建单”处理。

### Scope Check

- 关联 Issue 或需求是否完成：
- 已完成范围：
- 未完成范围：
- 是否复用了已有上游能力，或对自研边界给出充分证据：
- 每个 Finding 是否由本次变更引入或加剧：
- 是否属于本次变更职责范围：

#### 架构归属对账

| 逻辑块（`仓库相对路径:符号`） | 归属 | 依据 |
| --- | --- | --- |
|  | 上游工具事实 / 工具专属知识 / 平台 API / `rust/crates/core` | 判为 Core：兼容命令名 + fixture 路径；判为平台：实际调用的原生 API 或平台类型 |

- 未沉入清单：本次改动触及、但仍需迁入 Core 的存量项、当前实现位置和
  **已提交的 Issue 编号与链接**；本次未触及的历史平台层逻辑不列入，没有时写“无”。
- 本次改动不含可归属的逻辑块（纯呈现、文案、样式或配置调整）时，表格写“无”并写明理由。

### Checked and cleared

检查过并判定没有问题的项，每项一句依据。它证明确实看过，也让下一次审查不必重复劳动：

- 两端是否各写一份：`另一平台路径:符号` 调的是同一个实现，或确属平台差异
- 是否该复用上游能力：`上游名称` 已覆盖，依据是版本、官方扩展点或实测
- 门禁与阈值：`脚本:行` 判的是聚合值，本次改动后仍在阈值内
- 行为是否改变：`路径:符号` 的签名、可见性和调用方都没有变

### Suggestions

1. 与 Finding 1 一一对应的具体修改建议。

### Observations

- 本次变更之前就已存在的无用代码、可重构之处或未沉入 Core 的逻辑：`仓库相对路径`
  与符号名、判定依据、**已提交的 `refactor` Issue 编号与链接**。没有 Issue 编号的
  条目按归属“存量未建单”作为阻塞项报告；没有此类问题时省略本节。

### Summary

简要评价正确性、架构一致性、可维护性、测试充分性和后续扩展成本。

### Verification

- 实际检查的文件、提交和调用链：
- 已提供的测试或 CI 结果：
- 本次未运行的测试：
- 仍存在的非阻塞风险或平台验证缺口：
```

没有实质性问题时必须明确写：

> 未发现需要阻塞合并的问题。

此时省略空的 `Findings` 与 `Suggestions`，`Scope Check` 合并为三行即可：

- 关联需求与完成范围：
- 架构归属对账：表格照填，它证明看过逻辑归属，无 Finding 也要填
- 未沉入清单：无，或已建单 `#编号`

其余检查项用一行说明整组为什么不适用，例如“其余项不适用：本次为纯呈现改动”。
`Checked and cleared`、`Verification` 和非阻塞风险照常保留。
