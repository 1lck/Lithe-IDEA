# 日志接入

新增、迁移或审查日志事件、写入器、诊断采集、界面警告，以及任何丢弃错误的代码时遵守本页。通用规则见
[Lithe 开发规范](../SKILL.md)；路径均相对于仓库根目录。

事件声明、字段编码、限额、生成器和门禁扫描范围以 `shared/logging/README.md` 为唯一规则来源。本页规定什么必须记录、怎样设计一条日志，以及接入、豁免和审查动作，不另列一套会漂移的语法或参数表。

## 一、必须记录的情形

下表中的情形必须在处理边界记录一条目录事件。处理边界是决定重试、降级、回退、放弃或告知用户的那一层，不是抛出错误的最底层。

| 情形 | 级别 | 要求 |
| --- | --- | --- |
| 操作最终失败，用户的请求没有完成 | ERROR | 在拥有处理决定的边界记录一次；成对操作由 span 的 fail 记录。 |
| 显示给用户的错误：横幅、弹窗、通知、行内错误、状态栏错误 | ERROR 或 WARN（按处理结果） | 与提示出自同一边界、同一 op；提示文案走 i18n，事件消息是英文事实，两者分开维护。 |
| 显示给用户的警告 | WARN | 同上。只有界面提示、没有日志的警告不得合入。 |
| 功能降级、回退到备用路径、使用缓存或默认值代替失败的读取 | WARN | 记录降级原因的结构化分类和降级后的状态。 |
| 失败后自动恢复，或重试后成功 | WARN | 记录尝试次数和最终结果；不要逐次记录每一次重试。 |
| 重试耗尽后放弃 | 用户受影响时 ERROR，否则 WARN | 一条终态，带尝试次数和最后一次错误。 |
| 丢弃错误的写法（`try?`、只有 `return`/`break`/`continue` 的 `catch`、`.ok();`、`let _ =`） | 按上面各行判断 | 记录事件，或者属于第二节的例外并写豁免标记。 |
| 上游组件报告的警告和错误（LSP `window/logMessage`、插件宿主消息、子进程 stderr） | 按上游严重度映射 | 进入该组件已有的通道，不另建自由文本通道。 |
| 生命周期里程碑和有排障价值的操作终态 | INFO | 只记里程碑和终态，不记每个内部步骤。 |

“用户受影响”按处理后的结果判断：内部重试后成功记 WARN，最终没有完成用户请求记 ERROR。不得把上游的 ERROR 标签机械地升级成产品 ERROR，也不得用 INFO 掩盖真正的失败。

## 二、不记录的例外

只有以下四类可以不记录。例外是封闭清单，不得自行扩充；需要新类别时先修改本页并说明理由。

1. **用户取消。** `CancellationError`、`CocoaError(.userCancelled)` 等由用户或调用方主动取消的结果不是失败。取消之后的清理如果失败，清理失败仍然必须记录。
2. **预期的缺失。** 探测可选的文件、配置、缓存或功能时目标不存在，调用方按“没有”处理，并且这正是正常路径。权限不足、格式损坏、读到一半失败都不属于缺失。
3. **随输入实时重算的校验提示。** 表单里随键入即时更新、不阻断已经发生的操作、不反映系统状态的提示（例如“名称不能为空”）。提交后真正失败的操作仍然必须记录。
4. **同一次失败已经记录过。** 下层处理边界或同一操作的 span fail 已经记录了这次失败。不得再记录一次，见第五节。

门禁会标记的写法属于以上例外时，在同一行或紧邻的上一行写豁免标记，原因必须指明是哪一类例外以及具体原因：

```swift
// log-exempt: 预期的缺失：可选的项目级 .editorconfig 不存在时使用默认值
let override = try? fileStorage.read(projectRoot.appending(path: ".editorconfig"))
```

`// log-exempt:` 后面必须有原因；“不重要”“忽略”“暂时”不是原因。豁免标记只用于丢弃错误的规则，不能豁免 NSLog、stderr、`print` 等绕过统一入口的写法，那类永久例外写进 allowlist（第八节）。

## 三、如何设计一条日志

按以下顺序设计，每一步的答案都要能写进事件声明或代码审查说明。

1. **先写下读者的问题。** 维护者拿到用户附在 Issue 里的诊断包时，要靠这条日志回答什么问题？例如“Git fetch 为什么失败、失败在哪个远程、用了多久”。回答不了具体问题的日志不要加。
2. **确定事实和终态。** 一条事件描述一个已经发生的事实，事件 ID 的结果词用过去时（`fetch_failed`、`index_degraded`）。成对操作用 span，只产生一条带耗时的终态。
3. **确定 owner 和通道。** owner 是拥有这次操作结果的模块；通道由目录模板和已校验的身份决定（`lsp/{server}`、`vcs/{provider}`、`plugins/{plugin}/host`），不按显示名称、路径或用户输入分通道。
4. **按处理后的影响选级别。** 用第一节的表，不按“看起来严重”选级别。
5. **选最窄的字段类型。** 计数、耗时、体积用数值；阶段和结果用受控 token；失败用 `error` 保留稳定 code 和 domain。不把结构化信息拼进消息（第六节）。
6. **用 op 串起同一操作。** 有实际操作上下文时传 `operationID`。用户在日志窗口里选中一行，能看到同一 op 的全部记录及相对耗时；每层重新生成编号会切断这条链。
7. **控制频率。** 循环、逐按键、逐帧路径不用 INFO 逐项记录；需要时用 DEBUG 或在发送侧有界汇总，并按目录声明 rate。
8. **在日志窗口里验证。** 触发一次真实场景，在日志窗口（⌘⇧L）中按通道和事件过滤能找到这条记录，字段齐全、没有敏感内容，同一 op 的调用链完整。界面提示带“查看日志”时，点击能定位到这条记录。

反例与正例：

| 反例 | 问题 | 正例 |
| --- | --- | --- |
| `catch { return nil }` | 失败被吞掉，诊断包里没有任何痕迹 | 在处理边界记录 `*.load_failed`（WARN，带 `error`），再返回降级值 |
| 横幅显示“同步失败”，没有日志 | 用户报告问题时无从排查 | 同一边界记录 `vcs.fetch.failed`，横幅的“查看日志”指向它 |
| 消息 `"fetch origin failed: \(error)"` | 结构化信息拼进消息，未经字段脱敏 | 消息模板 `Fetch failed`，字段 `remote`（token）、`error`（error）、`duration` |
| 适配器、服务和视图各记录一次同一个失败 | 一次失败出现三次，计数失真 | 适配器返回结构化错误，服务决定降级时记录一次 |
| 重试循环里每次失败都记 WARN | 噪声淹没真正的终态 | 一条终态带 `attempts` 和最后一次 `error` |

## 四、只使用目录生成的事件

1. 先调查真实调用和消费者，确定 owner、通道身份与需要保留的事实；没有实际来源不预造事件。
2. 新增事件先修改 `shared/logging/events/<root>.json`，按共享 README 声明稳定 ID、通道模板、英文消息、级别和字段含义。字段说明必须解释本事件中的来源、语义和单位，不能用按类型的通用短语凑说明。
3. 运行 `node scripts/logging/generate-log-events.mjs`，审查生成的 Swift 类型和 Rust 静态目录。不得手改 `LogEvents.generated.swift` 或 `catalog_generated.rs`。
4. 调用生成的事件类型与 span，把类型化输入交给宿主统一日志入口；Rust 使用生成目录和共享边界。不得手写事件 ID、自由消息或字段字典来规避目录声明，不得自行实现序列化或脱敏。

生成事件是尚未脱敏的内存输入。落盘必须经过 Core 的目录字段校验、共享脱敏和编码；只通过类型检查或通用编码器不能证明隐私安全。日志路径由平台可写存储适配器提供，不从 bundle、插件安装目录或 Windows 安装目录推导。

macOS 从服务构造器、`AppServices.logSink` 或模块激活时的 `ModuleContext.logSink` 获取组合根注入的同一个 sink；不得新增全局可变日志单例。`LogScope` 携带同一操作的 op 和可信身份，目录决定通道。路径传 URL，错误传 Error，不先拼成字符串。启动早期的适配器只能有界缓存类型化事实并等待注入，不能另建自由字符串通道。

macOS 的日志窗口和诊断包只读取 v2 会话文件；v1 文件只进入保留清单，按 30 天自然过期。Rust 的 v1 API 和旧命令继续供 Windows 使用，不得改变其输出。

## 五、一个操作、一条终态、一个错误处理边界

- 成对操作使用生成的 span，由一个调用方拥有。成功调用一次 finish，失败调用一次 fail，生成一条带耗时的终态；不要再手工补“结束”记录。begin 总会产生一条 DEBUG 级别的 started，是否落盘由写入端按级别和详细诊断通道过滤。
- 不复制 span 来产生多份生命周期，不用墙钟差值计算耗时。跨异步边界保留同一个操作所有者和单调计时上下文。
- 有实际操作上下文时传 `operationID`，持久化层用 `op` 关联跨模块证据。不得把 op 重新声明为普通字段，不得用用户内容作为操作编号。
- 错误只在处理它的边界记录一次。下层把错误和稳定分类返回；上层决定恢复、降级或告知用户时记录。不得“记录后再抛出”；span 的 fail 已经记录该操作失败时，不再额外写相同错误。

例如 Git 命令由拥有该命令生命周期的调用方 begin，再按真实结果 finish 或 fail；底层进程适配器只返回退出码和结构化错误。

## 六、字段选择与隐私

选择能表达事实的最窄类型，不把结构化信息拼进 message 或自由文本：

| 信息 | 选择原则 |
| --- | --- |
| 计数、开关、耗时、体积 | 使用 int、bool、duration、bytes，单位与编码依共享 README。 |
| 身份、阶段、版本 | 身份用 id；受控短词用 token；版本用 version。id 必须来自已验证的真实身份，字符合法不等于来源可信。 |
| 文件位置 | 使用 path，由共享边界脱敏，不自己拼用户绝对路径。 |
| 失败 | 使用 error，保留稳定 code/domain 等结构化类别，不传未清理的整段错误转储。 |
| 无法结构化的上游诊断 | 仅在必须保留 stderr 行、LSP logMessage 等上游原文时使用 text，并在声明中写 reason 说明结构化字段为什么不能代替；“方便调试”不是理由。 |

不得记录源码、编辑缓冲区、环境变量值、命令输出、凭据、终端历史或协议正文，也不得把它们塞进 text、error、token、路径或消息模板绕过。命令只记录受控名称、阶段、退出码与耗时，不记录完整命令行。

每个动态通道段必须能追溯到已校验的插件、provider、server 或内部连接 ID，不得使用主机名、显示名称、项目路径和任意用户输入。

## 七、界面提示与日志的对应

- 每个显示给用户的警告和错误都对应第一节的一条事件。提示和事件在同一个处理边界产生，共用同一个 op。
- 提示需要“查看日志”时，携带日志记录引用（通道、事件，有 op 时带 op），打开日志窗口并定位到这条记录。打开日志窗口只走统一的打开请求，不为某个插件或 provider 写专门分支。
- 插件发给宿主的消息和警告由宿主记入 `plugins/{plugin}/host` 通道，再按插件声明显示；插件不能绕过宿主写日志文件。
- 日志消息、事件名、通道、字段、级别名和过滤语法不翻译；提示文案、按钮和日志窗口自身的界面文字走共享 i18n。

## 八、门禁、豁免与基线

`node scripts/logging/verify-log-usage.mjs` 扫描生产代码，具体写法和排除范围以共享 README 为准。规则分两类：

| 类别 | 规则 | 合法的例外方式 |
| --- | --- | --- |
| 绕过统一入口 | Swift 的 `NSLog`、stderr 写入、`os_log`/`Logger`、字符串 `record(level:)`、`print`/`debugPrint`；Rust 的 `eprintln!`、`println!`、`dbg!` | 只能写进 `log-usage-allowlist.json`，必须给出具体的协议或架构理由和精确计数 |
| 丢弃错误 | Swift 语句级 `try?`、只有 `return`/`break`/`continue` 的 `catch`；Rust 语句级 `.ok();`、`let _ =` | 记录事件；属于第二节例外时写 `// log-exempt: <原因>` |

不得利用别名、包装函数或动态调用逃避门禁。门禁无法静态识别“界面提示没有对应日志”，这一条由第七节和审查清单保证。

`scripts/logging/log-usage-baseline.json` 按文件和规则记录引入门禁时的存量，计数只减不增：

- 修改一个函数时，必须一并处理该函数里被门禁标记的存量（记录事件或写豁免标记），再用 `--update-baseline` 把计数写成当前值。
- 不得给新违规加基线、增大计数、在文件之间移动旧违规，或留下虚高的计数当额度；计数低于基线时门禁同样失败，必须更新基线。
- 永久例外不进基线，按上表写进 allowlist 或豁免标记。
- 迁移机器读取的性能标记等协议输出时，同步修改它的消费者，不得直接删除协议输出。

## 九、验证

```sh
node scripts/logging/generate-log-events.mjs --check
node scripts/logging/verify-log-usage.mjs
```

修改目录、生成器或门禁本身时，再运行 `node --test --test-timeout=60000 scripts/logging/test-log-events.mjs`（目录、生成器和门禁共用这一个测试脚本），以及直接受影响的 Core 或宿主测试。只读核验只用 `--check`，不执行会写生成物的命令。

新增或修改用户可见的警告和错误时，按第三节第 8 步在真实应用的日志窗口里确认记录存在、字段正确、“查看日志”能定位；无法在本机验证时在 PR 说明中写明。

## 十、审查清单

- 第一节的每种情形都有事件：界面警告和错误、降级、回退、自动恢复、重试耗尽、丢弃的错误。没有只出现在界面上的警告。
- 豁免标记属于第二节的四类之一，原因具体；绕过统一入口的例外只在 allowlist 里。
- 事件有真实来源和 owner，级别按处理后的用户影响选择；高频路径没有 INFO 逐项输出。
- 声明先于调用，使用生成类型；没有手写 ID、消息、字段字典、第二套 writer 或直接打印。
- 同一操作只有一个 span 所有者和一条终态；错误只在处理边界记录一次，op 贯穿调用链。
- 动态段来源可信并经过校验；字段类型最窄，description 具体，text 的 reason 说明不可替代性；没有禁止记录的内容。
- 生成物检查和用法检查通过，基线只减少。
- 写入、查询、保留和导出保持有界，文件位于平台可写存储。
