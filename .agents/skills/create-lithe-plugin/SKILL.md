# 创建 Lithe 插件

插件契约、SDK、API 等级和示例插件都在持续演进。本 Skill 只规定流程、长期不变的原则和验收要求，不复制任何字段、接口名、版本号或命令；这些内容一律以第一节“参考地址”中的当前版本为准。

插件开发只在插件自己的仓库进行。任务需要同时修改宿主（本仓库）或 Core 仓库时，那部分改动还必须遵守 `.agents/skills/develop-lithe/SKILL.md` 的全部规则，其中第三节“插件归属与宿主零依赖”规定了宿主一侧不得收录哪些插件内容。

## 用词约定

| 用词 | 含义 |
| --- | --- |
| 必须、不得 | 没有例外。无法满足时停下来告知用户，不得自行放宽。 |
| 默认 | 除非满足该条写明的例外条件，否则照做。采用例外时在交付说明中写明理由。 |

| 不适用 | 某一项的对象在这个插件里不存在。例如纯语法插件没有进程，就没有 SDK、上游程序、取消入口、高频操作和降级路径。标记不适用时，在交付说明中写明对象为什么不存在。对象存在的项不得标记不适用；对象存在但无法验证的项，列为未验证。 |
| 插件仓库 | 插件自己的 Git 仓库。插件的全部内容只在这里维护。 |
| 宿主仓库 | 本仓库（Lithe 桌面端）。 |
| Core 仓库 | [Lithe-IDEA/Lithe-core-rust](https://github.com/Lithe-IDEA/Lithe-core-rust)。 |
| 插件资料目录 | Core 仓库的 [`shared/plugins/`](https://github.com/Lithe-IDEA/Lithe-core-rust/tree/main/shared/plugins)：插件契约、开发指南、参考和官方后端 SDK 的唯一来源。 |

## 二、核心要求

1. **日志接线是交付条件。** 第四节中对象存在的每一项都必须完成，并按第五节验收。缺任何一项，插件都按未完成处理，不得以“功能已经可用”为由跳过或推迟。对象不存在的项按“不适用”处理。
2. **插件是声明式包。** 插件代码不进入 Lithe 进程；宿主读取插件清单，再启动其中声明的进程。插件不得要求宿主或 Core 按插件名、工具名增加分支。
3. **选能满足需求的最低 API 等级**，只声明实际用到的能力和权限。
4. **运行时不下载任何东西。** 插件用到的外部程序、运行时入口和 SDK 都在构建时获取，按锁定的哈希或 commit 校验后放进插件包。安装后的插件必须能离线运行。
5. **已安装的插件包只读。** 插件只写宿主通过启动模板提供的可写目录，不得从插件包路径推导任何可写路径。
6. **插件进程只在需要时启动。** 每个提供者由自己的激活事件启动，不得设计成应用启动或项目打开时就常驻。
7. **契约缺能力时不得绕过。** 插件需要的能力契约中没有时，不得用私有字段、借 stderr 传数据或要求宿主特判来实现，必须停下来告知用户，按 `develop-lithe` 第三节“插件能力”提出公共 API 变更。
8. **插件的全部内容只在插件仓库。** 插件的源码、清单、构建脚本和锁文件，插件的全部测试（包括端到端测试），插件的功能矩阵，插件文案的翻译，以及构建资源的说明，都只在插件仓库维护。不得把这些内容提交到宿主仓库或 Core 仓库，也不得要求宿主或 Core 的测试、CI、功能矩阵或 i18n 词条为插件兜底。

## 三、流程

1. **建立插件仓库。** 每个插件使用独立的仓库和自己的命名空间。插件 ID 的命名规则以插件资料目录 `README.md` 为准；进入插件市场的仓库命名和收录方式以 Lithe Store 发布指南为准。
2. **确定形态。** 按插件资料目录的 API 等级说明选最低等级。默认先用纯声明式实现，只有声明式无法表达时才增加后端。从插件资料目录“示例插件”中最接近的一个开始。
3. **编写清单。** 按契约编写，并按插件资料目录的说明在编辑器中关联 Schema。用户可调整的选项通过插件设置声明；难以理解的设置必须写说明，宿主会显示为 ⓘ。插件界面默认使用宿主渲染的原生内容，只有原生内容无法表达时才使用网页内容。
4. **准备构建期资源。** 构建脚本负责获取、校验和组装插件包，每个外部输入都在锁文件中记录来源和哈希。上游许可证不允许随包分发时，改为使用用户已安装的程序。资源的来源、校验方式、缓存位置和多个工作树之间能否复用，写在插件仓库的文档中。
5. **编写后端。** 默认使用官方 SDK 的当前版本，SDK 负责协议、取消、进程清理、错误处理和日志协商。所用语言没有官方 SDK 时，可以按契约自行实现协议，但必须用契约 fixture 测试全部用例。
6. **翻译插件文案。** 插件的用户可见文字至少提供中文和英文。契约能翻译的文案（例如清单中的标题和说明）使用插件包的翻译文件，文件格式、覆盖范围和回退顺序以契约 `README.md` 的 Translations 一节为准。插件自己的网页界面和插件后端返回给用户的文字，由插件按宿主提供的界面语言自行翻译。契约无法翻译的插件文字，按第二节第 7 条提出契约变更，不得请宿主为插件补词条。
7. **完成日志接线。** 按第四节。
8. **编写测试。** 按第五节第 2 项，测试和测试数据都放在插件仓库。
9. **维护功能矩阵。** 在插件仓库维护插件自己的功能矩阵：每项用户可观察的能力占一条，写明各平台的状态、证据（插件仓库中的实现和测试路径）和最近一次验证。格式由插件仓库决定，可以参照宿主 `shared/platform-feature-matrix/` 的字段。插件能力不得写进宿主的功能矩阵。
10. **安装试用。** 按插件资料目录的入门步骤从磁盘安装；发布前再从插件仓库的发布物走一遍用户的真实安装流程。
11. **验证。** 按第五节。
12. **发布。** 版本号必须按 `.agents/skills/release-lithe/SKILL.md` 的“Choose the version number”确定，发布按 Lithe Store 发布指南进行。依赖尚未随稳定版宿主发布的能力时，只能发预发布版本，不进入插件市场。已发布版本的包不得修改，任何改动都发新版本。

## 四、日志接线（必须）

本节规定接入逻辑和级别判定。协议名称、SDK 接口、字段和通道的具体写法会随版本变化，一律按第一节的地址读取当前版本；本节的分工、判定顺序和禁止事项不随版本变化。

### 接入逻辑：两个入口，一个出口

插件不直接写日志。插件的操作结果只从两个入口进入 Lithe 的日志 Core，之后走同一条路径：

1. **SDK 上报。** 用 SDK 编写的插件进程，通过 SDK 与宿主协商的日志协议上报自己的操作结果。
2. **宿主观察。** 插件只声明、不带 SDK 进程的贡献（例如声明式的语言服务器、调试适配器、命令式构建），由宿主在每次尝试的开始和结束边界观察结果，交给 Core 记录。声明式插件没有能上报的进程，但它的结果同样进入日志 Core，不存在“声明式插件不接入日志”的情况。

两个入口之后的路径相同：Core 校验输入，补上已安装插件的身份，确定级别和失败类别 → 目录事件 → 该插件的通道 → 唯一的写入器 → 日志窗口。两个入口写进同一个插件通道，使用同一组事件。插件不得在这条路径之外另开出口：自建文件、自由文本 stderr、包装脚本里的日志、私有通道都不允许。

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 宿主（Core 与平台层） | 日志协议的校验；观察声明式贡献每次尝试的结果；插件身份、目录事件、通道、级别和失败类别的映射；脱敏、限流、唯一的写入器、日志窗口 | 插件的业务判断 |
| 官方 SDK | 与宿主协商日志协议；在每次请求的结果边界自动上报成功或失败终态；把插件的降级、恢复上报转换成协议消息 | 决定某个分支算不算降级 |
| 插件的代码和声明 | 返回真实的结果；让声明的程序如实反映成败；在真实发生降级或恢复的分支上报一次；声明哪些高频操作不记录成功；配置上游程序的日志 | 级别名、通道、消息正文、写文件 |

### 按来源接入

先列出插件的全部贡献和进程，再逐个对照下表接入。各进程角色对应的通道，以及宿主当前替哪些声明式贡献记录结果，以 Core 仓库 `rust/logging/README.md` 和 `rust/logging/events/` 的当前内容为准。

| 来源 | 宿主怎么记录 | 插件必须做的 |
| --- | --- | --- |
| 用 SDK 编写的进程（插件后端，以及用 SDK 实现的构建、VCS 等提供者） | SDK 自动上报每次请求的成败终态；插件上报降级和恢复；未分类 stderr 记为 DEBUG | 返回真实结果；在降级、恢复分支上报；为高频操作关闭成功记录 |
| 声明式贡献（插件声明、由宿主启动的语言服务器、调试适配器、命令式构建等） | 宿主观察每次尝试，Core 记录一次成功或失败终态；失败类别由 Core 按失败阶段决定，例如找不到程序、启动失败、握手失败、超时、提前退出、输出无效；取消不记录 | 声明的程序必须如实反映结果：失败时以非零状态退出；不得用包装脚本吞掉错误、把失败改成成功退出，或在内部重试到超时；输出只包含协议约定的内容；不得为这些尝试自行补写日志 |
| 上游程序自身的输出（语言服务器、构建工具、调试适配器等） | 按进程角色进入对应通道：未分类 stderr 记为 DEBUG；标准日志消息保留上游声明的严重度；进程或协议的真实失败由宿主记为 ERROR；调试适配器的原始输出只进调试控制台 | 上游日志级别默认 warning 或等价级别，详细日志只能由用户在插件设置中开启；上游只能写文件时，只写宿主提供的日志目录，并配置大小上限和轮转 |
| 不启动进程的声明内容（语法、主题、快捷键、设置、界面等） | 宿主记录安装、校验、激活和加载失败 | 声明必须能通过校验。这类内容没有进程，也没有取消入口、高频操作和降级路径，日志验收只覆盖宿主记录的那几项（见第五节第 3 项） |

以下情况必须停下来告知用户，不得退回自由文本日志、自建日志或在插件里补写日志：

- 所用 SDK 版本不支持宿主当前的日志协议；
- 插件用到的某种声明式贡献，宿主当前还不记录它的尝试结果。这是宿主的缺口，按第二节第 7 条提出宿主变更。

使用宿主日志目录前，必须在目标宿主上确认它提供该目录。

### 级别判定

对每一个结果，按下表**从上到下**逐条判断，第一条命中的就是它的级别，不再往下看。级别只按处理后的结果决定，不按“看起来严不严重”，也不按输出来自 stdout、stderr 还是上游的 error 标签。

| 顺序 | 判断 | 结果 |
| --- | --- | --- |
| 1 | 用户或调用方主动取消了吗？ | 不是失败，不记录 ERROR 或 WARN。取消后的清理作为另一个结果，从第 2 条起判断。 |
| 2 | 是预期的缺失吗？可选的文件、配置、缓存不存在，或收尾时对象已经不在（进程已退出、连接已关闭）。 | 不记录。权限不足、格式损坏、读到一半失败、超时后对象仍在，都不是缺失，继续往下判断。 |
| 3 | 用户这次请求最终没有完成吗？包括重试耗尽后放弃。 | **ERROR**。在决定放弃的边界记录一次。 |
| 4 | 请求完成了，但这是因为某个失败或能力损失才走了降级路径吗？降级路径指：失败后改走备用路径、用缓存或默认值代替失败的读取、结果被截断、部分功能因失败被关闭。或者后台工作失败、重试耗尽，但用户的请求没有受影响吗？ | **WARN**（降级）。每个原因在一次请求中只记录一次。没有发生失败的正常缓存命中、按设计使用默认值或用户主动关闭的功能，不是降级，继续往下判断。 |
| 5 | 之前失败过，现在自动恢复了，或重试后成功了吗？ | **WARN**（恢复）。只记最终结果，不逐次记录每次重试。 |
| 6 | 清理、关闭、终止失败，留下了残留（文件、仍在运行的进程、未释放的远端资源）吗？ | **WARN**。 |
| 7 | 是关键用户操作的成功终态，或进程生命周期的里程碑吗？ | **INFO**。读取、预览、统计、轮询、补全、悬停这类高频操作除外：它们的成功不记录，失败仍按第 3 条记录。 |
| 8 | 以上都不是：内部步骤、性能数据、排障细节。 | **DEBUG**。不得升级成 INFO 或 WARN。 |

同一个结果只有一个级别、只记录一次：SDK 已经自动记录的成功或失败，插件代码不得再记录；底层已经记录过的失败，上层不得再记录。

下表是常见的错误定级，验收时逐条排除：

| 错误做法 | 正确做法 |
| --- | --- |
| 重试过程中每次失败都记 WARN | 只记最终结果：成功按第 5 条，放弃按第 3 条 |
| 用户取消记成 ERROR | 按第 1 条，不记录 |
| 可选配置文件不存在记 WARN | 按第 2 条，不记录 |
| 回退成功后只记 INFO，降级被掩盖 | 按第 4 条记 WARN |
| 正常命中缓存、使用默认配置也记 WARN | 没有发生失败，不是降级；按第 7、8 条判断，高频读取的成功不记录 |
| 轮询、补全每次成功都记 INFO | 按第 7 条关闭成功记录 |
| 往 stderr 打印 “ERROR: …”，以为宿主会记成 ERROR | stderr 一律是 DEBUG；失败必须通过返回失败表达 |
| 上游打印了 error 级别日志，就把用户操作当成失败 | 只有用户请求没有完成才按第 3 条记 ERROR |
| 进程正常关闭也记 WARN | 正常关闭是生命周期状态，按第 7 条或不记录 |
| 声明的命令或包装脚本出错后仍以 0 退出 | 失败必须以非零状态退出，宿主才能按失败记录 |
| 捕获异常后直接返回默认值，什么都不报 | 按第 4 条上报一次降级 |

### 内容与输出规则

1. **只带受控内容。** 日志只带稳定的类别标识和计数。类别标识描述原因的种类（例如“工具缺失”“连接不可用”），同一种原因始终用同一个标识，不包含任何运行时数据。不得包含源码、凭据、SQL、HTTP 头和正文、终端历史、协议载荷、命令输出、路径和用户输入。返回给用户的错误信息同样不得包含路径和堆栈。
2. **stdout 和 stderr 各守其职。** stdout 只用于协议帧。stderr 只写不含上一条受限内容的简短诊断，宿主把它当作 DEBUG 证据。
3. **不自建日志设施。** 插件不得自建日志文件、日志目录、写入线程、轮转或脱敏，不得把日志写进状态目录或插件包。状态、缓存和索引也不得写进宿主日志目录。
4. **宿主侧改动走目录事件。** 插件不能新增目录事件。插件需要的记录种类当前协议没有时，按第二节第 7 条处理。只有本次任务确实需要修改 Core 或宿主时，才按 `develop-lithe` 的日志接入规则修改，并运行其中要求的生成和门禁检查。宿主新增一种声明式贡献时，必须在同一次改动里让 Core 记录它每次尝试的结果：平台层只上报观察到的阶段和耗时，级别和失败类别只由 Core 决定。

### 接入步骤

没有对应对象的步骤按“不适用”处理，例如没有进程就没有 SDK 和上游程序。

1. 列出插件的全部贡献、进程和角色，从 Core 仓库 `rust/logging/README.md` 和 `rust/logging/events/` 查到每个进程当前对应的通道，以及宿主替哪些声明式贡献记录结果。
2. 从所用 SDK 的 README 确认该版本支持宿主当前的日志协议，并读懂它自动上报什么、插件需要调用什么。
3. 为插件的每个操作写出级别表：成功记 INFO 还是关闭成功记录；可能的失败及其类别标识（ERROR）；每条降级路径及其类别标识（WARN）；每条恢复路径（WARN）。级别按上面的判定顺序确定。
4. 按级别表实现：失败就返回失败；降级、恢复分支各上报一次；为高频操作关闭成功记录；检查每个捕获异常的分支都属于判定表中的某一条；检查每个声明的程序和包装脚本在失败时以非零状态退出。
5. 配置上游程序的日志级别和日志文件位置。
6. 按第五节第 3 项验收，并把级别表写进交付说明。

## 五、验证

以下各项都必须执行，并在交付说明中写明结果。

1. **清单。** 插件在 Lithe 的安装审查中通过校验，审查显示的程序、权限和来源与设计一致。
2. **插件自身测试。** 插件的单元测试、集成测试和端到端测试，以及它们用到的测试工程、fixture 和替身，都放在插件仓库，由插件仓库的 CI 运行。端到端测试针对一个明确的宿主或 Core 版本运行（例如已发布的 Lithe 版本，或 Core 的固定 commit），版本写在插件仓库中。测试必须有界、结果确定：超时、时间、进程清理的要求与 `.agents/skills/write-stable-tests/SKILL.md` 相同。不得把插件测试放进宿主仓库或 Core 仓库，也不得要求宿主的测试读取插件包或插件仓库检出来覆盖插件行为。
3. **日志验收。** 在真实宿主中执行插件的工作流，按插件实际包含的来源，在下表中逐行触发。每一行里对象不存在的触发项按“不适用”处理，对象存在但在本地无法制造的触发项（例如制造不出的失败）列为未验证。

   | 来源 | 必须触发 |
   | --- | --- |
   | 用 SDK 编写的进程 | 一次关键操作成功；一次真实失败；每一条降级或恢复路径；一次高频操作 |
   | 声明式贡献（宿主启动的程序） | 每个贡献的一次成功；能在本地制造的失败（例如程序缺失、提前退出）；该贡献有可取消的尝试时，一次取消 |
   | 不启动进程的声明内容 | 一次正常的安装和激活，其间不得出现 WARN 或 ERROR；能在本地制造的校验或加载失败（例如清单无法通过校验、语法文件无法加载）。宿主当前对这类内容记录哪些结果，以 Core 仓库 `rust/logging/README.md` 和 `rust/logging/events/` 为准，不要求成功有终态记录 |

   在日志窗口中逐项确认：
   - 每条记录出现在插件对应的通道，级别符合第四节“级别判定”和交付说明中的级别表，同一结果只出现一次，并关联到触发它的操作；
   - 高频操作的成功没有产生 INFO；
   - 声明式贡献每次尝试在插件通道中恰好有一条终态，失败类别与制造的失败一致，取消没有记录；
   - 记录中没有第四节“内容与输出规则”第 1 条列出的内容；
   - 第四节“级别判定”的错误定级表中的情况一条都没有出现；
   - 用户看到的错误提示与接入日志前一致；
   - 使用原生日志文件时，文件只出现在宿主提供的日志目录。

   只看到日志窗口“有输出”不算验收。
4. **翻译。** 分别把宿主界面语言切换为中文和英文，确认插件的清单文案、设置、插件界面和插件返回给用户的文字都显示为对应语言；翻译文件通过契约 schema 校验，缺少某条译文时按契约的回退顺序显示。
5. **功能矩阵。** 插件仓库的功能矩阵覆盖本次新增或修改的每项能力，状态与实际验证结果一致：没有实际执行过的平台不得标为已验证。
6. **只读。** 比较一次完整工作流前后已安装插件包的文件清单或哈希，结果必须一致。
7. **平台。** 各平台的日志存储进度以 Core 仓库 `rust/logging/README.md` 的当前说明为准。没有在某个平台上实际执行过工作流，就不得声称该平台已验证。
8. **清理。** 验证结束后关闭本次启动的 Lithe 和全部插件进程，并确认没有残留。

## 六、交付说明

交付说明（或 PR 描述）必须包含：

1. 插件仓库、API 等级、声明的能力和权限，以及每项权限的用途。
2. 所依据的参考资料版本：契约的 commit，SDK 的版本或 commit，端到端测试针对的宿主或 Core 版本。
3. 日志接线表：每个进程及其角色和通道；每个操作的级别表（第四节“接入步骤”第 3 步）及全部类别标识；关闭了成功记录的操作；由宿主记录结果的声明式贡献；是否使用原生日志文件，以及上游的级别、大小上限和轮转设置。
4. 插件仓库中测试、功能矩阵、翻译文件和构建资源说明的位置，以及本次更新了哪些条目。
5. 实际执行的验证及结果。没有验证的平台和工作流必须如实列出；标记为不适用的项及其原因也必须列出。
6. 本次是否需要修改宿主或 Core。需要时列出对应 PR，并说明那部分改动只涉及通用扩展点，没有把插件内容放进宿主或 Core。
7. 发现参考资料过时或互相矛盾时，列出具体位置。
