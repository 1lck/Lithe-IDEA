# IDE capability API v1

Lithe exposes the current project's environment, plugin Build and Run workflows to
plugins and MCP clients. File editing and arbitrary shell execution are outside
this contract. Both platforms reuse their existing application actions, including
project preparation, saved toolchain selection and native execution ownership.

## Ownership and connections

`rust/lithe-ide-host/src/catalog.rs` owns the tool names, schemas, validation,
permission classification and UTF-8 output paging. `lithe-ide-host` owns the
local broker and private connection descriptor; the `lithe-mcp` binary uses the
official `rmcp` SDK for stdio MCP. HTTP here is an internal authenticated loopback
bridge, not a public Streamable HTTP MCP endpoint.

The user enables one opened project in Settings > MCP Configuration. Read access
includes logs, which can contain sensitive project information. Configure and
execute permissions are independent, disabled by default, and fixed until the
connection is disabled. No tool argument grants permission. Closing the project,
window, or IDE revokes the connection. Already accepted native executions remain
owned by the normal IDE Run/Build workflow; disabling MCP does not kill work the
user may still be observing in the IDE. A closed project uses its existing
execution cleanup. Re-enable access after reopening; copied configuration keeps
the same project descriptor path. A second window cannot replace an enabled
connection for the same project.

Connection files and locks belong in platform app data, never the installation,
repository or shared worktree caches. macOS uses a private directory and mode
0600 files; Windows uses the current user's local application data directory.
The copied client configuration contains a helper path and descriptor path,
not bearer credentials. The helper reads the current descriptor on every call,
uses only `127.0.0.1`, disables proxying and redirects, and writes protocol output
only to stdout. The broker rejects browser Origin headers and missing/wrong
tokens, bounds request bodies to 64 KiB and pending requests to 16, and times out
delivery after 120 seconds. Inspect operations before retrying a timed-out mutation.

Native-only `ideHost.control` is not exported as an MCP tool. Its actions are
`open`, `close`, `closeOwner`, `poll`, `claim`, `respond`, `catalog`, `validate` and `output`.
The native window binds `open.arguments.ownerId` (strict camelCase decoding);
`closeOwner.arguments.ownerID` retains its existing spelling. Callers must not
rename both actions together. The owner is supplied by the native adapter, not
trusted from a client request.
Windows attaches an owner-checked native request event sink before returning `open`.
The broker emits `lithe-ide-request` with `{hostID, requestID}` to the owning WebView when work arrives;
WebView timers and visibility do not maintain its authorization. The receiver
calls `claim` with those IDs immediately before the application action. It returns
`{request: {requestID, name, arguments, remainingMilliseconds}}` at most once, or `{request: null}` for
expired, cancelled or already claimed work. A delayed event after suspend cannot
execute an expired mutation. The Windows receiver also measures elapsed time from
before `claim` IPC using Windows WebView's monotonic `performance.now()` clock,
which includes suspension and is unaffected by system clock adjustments. It rejects
an expired reply before executing,
because the claim response itself may be delayed while the WebView is suspended.
`respond` reports `{delivered: boolean}`; a false
result is not permission to replay an operation. Notifications or replies that
fail never reopen a revoked host or replay work; later requests can use the same
authorization. Native window destruction still revokes the connection and releases
the retained event sink. The frontend registers its window-scoped listener before
opening the host and disposes it on failed open, late open after revocation, and
close. Independent events do not wait for missing Channel sequence numbers; a
lost notification expires without blocking later requests or replaying work.
Application actions retain their existing workspace checks.

The macOS polling adapter remains compatible: it polls only while enabled and
rejects external work after 15 seconds without a heartbeat. That heartbeat check
applies only to polling hosts, not native event subscribers. Both delivery modes
retain the 16-request bound and 120-second deadline. UI reports authorization and
the last request outcome separately. Product-owned failure messages use shared
i18n at render time; original tool diagnostics remain in the MCP response.
Successful tool discovery is not proof that
the project dispatcher answered a tool call.

MCP `tools/list` includes `ttlMs: 0` and `cacheScope: "private"`, including for
`2026-07-28` discovery. Protocol negotiation and envelopes remain SDK-owned;
legacy and modern clients are verified in separate stdio sessions using
`shared/fixtures/ide-api/mcp-protocol.json`.

## Capabilities

Every call carries `name` and an object `arguments`. Unknown keys, missing required
arguments, invalid types and unsupported selection fields are rejected before dispatch. See the executable schemas and
`shared/fixtures/ide-api/calls.json`. Requests do not accept a workspace root:
the connection already owns its workspace. Native toolchain paths are local
configuration values, never portable workspace identifiers.

| Tool | Arguments | Permission | Result |
| --- | --- | --- | --- |
| `lithe_project_inspect` | none | read | workspace identity, name, permissions and available readiness state |
| `lithe_environment_inspect` | none | read | project-local `settings`, `discovered`, and `effective` toolchains |
| `lithe_environment_configure` | optional `javaHomePath`, `mavenExecutablePath`, `mavenJavaHomePath`, `settingsPath`, `localRepositoryPath` | configure | persisted/effective settings or explicit failure; omitted settings are preserved |
| `lithe_maven_inspect` | none | read | project/modules, profiles, skip-tests and reload/error state |
| `lithe_maven_configure` | optional `profiles`, `skipTests` | configure | saved profiles and reload state |
| `lithe_maven_reload` | none | execute | outcome of existing project/Java synchronization |
| `lithe_build_inspect` | none | read | detected plugin instances, declarations and current model identities |
| `lithe_build_reload` | `instanceID` | execute | model reload requested; inspect until model state is ready |
| `lithe_build_configure` | `instanceID`, `optionID`, `value` (string, boolean, string list or null) | configure | checked persisted option and reload state; null resets the declared option |
| `lithe_build_execute` | `instanceID`, `taskID`, optional `projectID`, `targetID`, `modelTaskID`, `userArguments` | execute | `operationID` for the same Build execution shown by the IDE |
| `lithe_maven_execute` | `goals`, optional `modulePath` | execute | Windows current Maven execution; unavailable on macOS |
| `lithe_run_list` | none | read | project configurations with IDs, names, providers and readiness |
| `lithe_run_start` | `configurationID` | execute | `operationID` after launch; failure if launch was refused |
| `lithe_run_restart` | `operationID` | execute | replacement execution's `operationID` |
| `lithe_operations_list` | none | read | retained Build/Run operations and status, without log bodies |
| `lithe_operation_output` | `operationID`, optional opaque `cursor` | read | state, nullable exitCode, bounded output and cursor |
| `lithe_operation_stop` | `operationID` | execute | stop request for that exact execution |

Empty configuration paths restore automatic selection. Maven-only paths require
a loaded Maven project. Configuration writes use the existing platform stores;
they are not a transaction across multiple settings documents. An error can follow
a partial save, so inspect settings before retrying. Credentials, full launch
environment values and command arguments are not included in run configuration
listing. Toolchain discovery uses existing installed tools; it does not install
or download a JDK or Maven. Maven execution may download dependencies or execute
plugins, and is therefore an execute capability.

On macOS, build execution uses the enabled plugin's detected instance and task
identities. Read them with `lithe_build_inspect`; model project, target and task
selectors require a loaded, current model and are resolved again for each call.
A model task also requires its declaring template and project. Arguments remain
an array of tokens all the way to the Provider; the host does not reinterpret
Maven goals, construct a command string or use the old Maven execution service.
`lithe_build_inspect` also returns each option's ID, kind, effective value, source,
choices and allowCustom, plus native-configuration availability. `lithe_build_configure`
validates one value with the same current instance/model used by the native option
editor, rejects invalid/dropped values before persistence, and reads it back.
Unknown options cannot create preferences. Empty multi-select uses the existing
instance marker, null removes the override, and sibling-only selections survive.
This edits invocation options; it does not mutate native XML. Native configuration
has a separate explicit source/draft/save/read-back workflow. Option changes cancel
stale Provider work and invalidate native drafts, models and language import.

The same effective Build options, configured tool resolver and workspace Provider
serve UI and Agent calls. An active Build execution returns `BUSY`.

Windows does not yet host Build Providers. It returns `NOT_AVAILABLE` for the
plugin Build tools and retains its existing Maven execution tool until its
current consumer migrates. This is a platform capability boundary, not a macOS
fallback. Maven inspect/configure/reload still use their existing paths in this
increment; the full Maven configuration and project migration remains pending.

Run operates on saved project configurations, not the currently focused editor
file. Existing Java build decisions are still shown in the IDE; the API never
silently answers them. Output is retained only as long as its existing IDE output
slot: replacing a run, removing its tab, or closing the workspace may expire an
operation. Callers receive `OPERATION_EXPIRED`, never another run's output.

## Output and errors

Operation IDs identify executions, not reusable UI slots. Copying/updating a run
snapshot preserves identity; restarting changes it. Build retains its latest execution identity, final state and exit code after
the task exits. Model/dependency logs in the shared UI console are not added to
that execution snapshot. Replacement or workspace reopen expires the old ID; an
old stop request cannot cancel the new task. Clearing output preserves the ID
and resets its buffer, allowing the existing cursor to report the discontinuity. Both the primary application output panel and service
output tabs are included. Operations expose `running`, `preparing`, `stopping`,
`completed`, `failed` or `cancelled` as applicable and a nullable `exitCode`.

Output pages contain at most 32,768 UTF-8 bytes, never split a Unicode scalar,
and include `nextCursor`, `hasMore` and `reset`. A cursor fingerprints the consumed
prefix. If a UI clear or buffer trim invalidates it, `reset: true` reports the
discontinuity explicitly. Pass the cursor only with its original operation ID.

Failures contain `error: {code, message}`; callers must check `error` rather than
infer success from a transport response. Shared errors include `INVALID_ARGUMENTS`,
`NOT_SUPPORTED`, `PERMISSION_DENIED`, `BUSY`, `DISCONNECTED`, `DISPATCHER_UNAVAILABLE`, and `TIMEOUT`.
Application failures include `NOT_READY`, `NOT_FOUND`, `NOT_AVAILABLE`,
`WORKSPACE_CLOSED`, `OPERATION_EXPIRED`, `LAUNCH_FAILED`, and `OPERATION_FAILED`.
MCP returns these as visible tool errors (`isError: true`) with structured content.

## Plugin entry points

macOS native plugins resolve `.ideCapabilities` from `PluginHostContext`, cast to
`IDECapabilitiesProviding`, enumerate authorized workspace IDs and call JSON
capabilities. The registry holds weak workspace references. Windows integration
Worker plugins declare `permissions: {"ide": true}` and use
`api.ide.authorizedWorkspaceIDs()` / `api.ide.call(workspaceID, name, args)`.
The data-only SDK is `Plugins/win/SDK/ide-capabilities.ts`; the host routes through
`callAuthorizedIdeCapability` in the host-api connection module. The manifest
permission cannot enable a project or increase its configure/execute grants.
Both use the same granted project and validators as MCP. This adds a capability
surface; it does not introduce a new plugin marketplace, sandbox or UI extension SDK.

## Verification

- `cargo test --manifest-path rust/Cargo.toml -p lithe-ide-host`
- `cargo build --manifest-path rust/Cargo.toml -p lithe-ide-host --features mcp --bin lithe-mcp`
- `node --test scripts/test-ide-mcp.mjs`
- Windows: the host-api, Maven, run and project-environment frontend tests, plus a
  native packaged run using the generated client configuration.
- macOS: `IdeCapabilitiesTests`, followed by a packaged native run.
- Both platforms: configure JDK/Maven, reload, execute Maven, start a configuration,
  read incremental output, restart, reject the old ID, stop, revoke, and close the
  project. Confirm installed resource manifests/hashes remain unchanged.
